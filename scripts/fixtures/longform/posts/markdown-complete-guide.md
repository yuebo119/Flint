Markdown 之所以能成为技术写作的事实标准，靠的是两条设计原则：一是**可读性优先**——即使不渲染，源文件也应当好读；二是**可扩展性**——核心语法保持极简，其余能力交给扩展。本文系统梳理常用语法与工程实践。

## 基础语法速查

### 标题与段落

标题用 `#` 到 `######` 表示一至六级；段落之间用空行分隔。正文中可以用 **粗体**、*斜体*、***粗斜体***，以及`行内代码`。删除线用双波浪线：~~这是要删掉的话~~。

### 列表的三种形态

无序列表用短横线：

- 第一项
- 第二项
  - 嵌套子项
  - 另一个子项

有序列表用数字加点，渲染器会自动纠正序号：

1. 先解析 front matter
2. 再装配页面树
3. 最后渲染模板

任务列表适合记录待办：

- [x] 完成大纲
- [x] 补充示例
- [ ] 二次校对

## 代码块的工程用法

代码块建议始终标注语言，既获得高亮，也方便工具识别：

```python
def fib(n: int) -> int:
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a
```

```javascript
const debounce = (fn, ms) => {
  let t;
  return (...args) => {
    clearTimeout(t);
    t = setTimeout(() => fn(...args), ms);
  };
};
```

## 表格与引用

表格用竖线与分隔行描述：

| 特性 | 语法 | 备注 |
|------|------|------|
| 链接 | `[文本](地址)` | 外链建议显式协议 |
| 图片 | `![描述](地址)` | 描述即替代文本 |
| 脚注 | `[^1]` | 放文末统一编号 |

引用块支持嵌套与多段：

> 好的文档让读者三分钟上手。
>
> —— 更好的文档让读者不需要文档。

## 链接与图片

相对链接指向站内页面（如 [关于页](/about/)），外链写全协议。图片语法在链接前加感叹号，替代文本会在图片加载失败时显示，也是无障碍访问的关键。

## 工程实践建议

第一，一行一个段落，diff 里改动粒度才细。第二，标题层级不要跳级，一级标题留给文章题目。第三，代码块内不要用 Tab，统一空格。第四，长文加目录锚点，方便跳转。第五，图片描述认真写——它同时服务于搜索引擎与读屏软件。

Markdown 的简洁是它的超能力：语法记住了，注意力就能回到内容本身。

## 转义与特殊字符

Markdown 里的星号、下划线、反斜杠都有语法含义，想原样输出需要转义。最常见的坑是文件名里的下划线：`snake_case_name` 在某些渲染器里会被解读成斜体，写成 `snake\_case\_name` 才稳妥。反斜杠可以转义所有 ASCII 标点，但日常只需要记住五个：星号、下划线、反引号、方括号、反斜杠。

嵌套结构也有讲究。列表项里放代码块，缩进必须对齐列表标记之后的第一个字符；引用里放列表，每一行都要带引用前缀。这些细节各渲染器实现略有差异，跨平台发布的内容建议用"最保守写法"，保证在任何渲染器下效果一致。

## 与工程链路的结合

Markdown 在工程链路里的角色远不止写文档。README 是项目的门面；变更日志（CHANGELOG）是版本发布的凭证；设计文档与决策记录沉淀在仓库里，随代码一起评审。很多团队还把 Markdown 用于静态检查——术语表校验、链接有效性检查、图片替代文本检查，都能在持续集成里自动完成。

工具链的另一个方向是**渲染器的统一**。同一份 Markdown 在不同渲染器下可能有细微差异：表格对齐、任务列表、脚注编号。团队内统一渲染器与扩展集合，能避免"我这里好好的"式争论。如果内容要发布到多个平台，建议锁定一份渲染器配置作为唯一事实。

## 内容的组织策略

当文档多起来之后，组织策略比写作技巧更重要。常见的三种组织法：按时间（博客）、按主题（知识库）、按任务（操作手册）。博客天然按日期归档，知识库按主题树形组织，操作手册则以任务为线索、每篇解决一个具体问题。

三种组织法可以共存，但要约定每一篇的归属。判断的标准是读者与更新频率：给外部读者看的、持续更新的进博客；给团队看的、偶尔修订的进知识库；跟着版本走的进代码仓库。归属清晰了，查找路径才短。

最后是一条写给所有写作者的话：工具与语法都是手段，把想法准确交付给读者才是目的。语法书可以查，但"为谁写、写什么、写到什么程度"这三个问题，只能自己回答。
