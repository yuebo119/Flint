订单中心上线第三年，运营看板的一条统计查询稳定地慢：八秒。开发同学最初的方案是加缓存，命中时快，未命中时运营照样等，后台定时刷新还会把数据库打满。这篇文章记录这次优化的完整过程：三处改动，每轮只动一个变量，最终把查询压到四十毫秒。

## 现场：一条慢查询和它的执行计划

出问题的 SQL 长这样：

```sql
-- 运营看板：最近三十天，待发货状态的订单明细，按创建时间倒序
SELECT o.order_id, o.user_id, o.amount, o.status, o.created_at
FROM orders o
WHERE o.created_at >= '2026-03-01 00:00:00' AND o.status = 1
ORDER BY o.created_at DESC
LIMIT 50;
```

orders 表八千万行，日均新增两百万。先看执行计划：在同一条查询前面加上 `EXPLAIN` 再执行，关键字段读出来是这样的：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| type | ALL | 全表扫描，没走任何索引 |
| rows | 78000000 | 预估扫描行数，接近全表 |
| key | NULL | 实际没用到索引 |
| Extra | Using filesort | 结果需要额外排序 |

全表扫描加文件排序，八秒完全说得通。表上没有 `status` 索引，`created_at` 上倒有一个单列索引，但优化器没选，原因是 `created_at >= ...` 是范围条件，预估命中的行占了全表相当一部分，走索引再回表的代价比全表扫描还高。

补充两个背景数字。这条查询在运营看板上的调用频次是每次页面加载一次，高峰期每分钟两百次，八秒的延迟意味着大量请求堆积在数据库连接池里。表也没有做分区，八千万行挤在一个表空间里。这两点决定了它的优先级：这条查询不只是慢，还在高峰期挤占连接池，影响同库的其他业务，所以它排在了当周优化的第一个。

## 读懂执行计划的四个字段

优化前先补齐基本功。日常排障盯住四个字段就够了：

- `type`：访问方式，从好到差依次是 system、const、eq_ref、ref、range、index、ALL，出现 ALL 就必须给出解释
- `rows`：预估扫描行数，与真实值偏差大说明统计信息过期，用 `ANALYZE TABLE` 刷新
- `key`：实际使用的索引，NULL 即未走索引，要结合 `possible_keys` 看是没建还是没选
- `Extra`：Using filesort 意味着排序没走索引，Using temporary 意味着用到了临时表，两者都是重写信号

> 执行计划是优化器给的估算，不是承诺。`rows` 与真实行数差一个数量级时，先修统计信息，再谈索引。

## 三处改动，逐一验证

遵循一次只改一个变量的原则，分三轮进行，每轮改完重跑执行计划并记录耗时。

### 第一轮：消除隐式类型转换

翻代码时发现，`created_at` 字段是 `datetime` 类型，而查询参数由 Java 层拼成了带时区后缀的字符串。MySQL 在字段与条件类型不一致时会在字段侧套转换函数，索引直接失效。把参数格式统一成 `yyyy-MM-dd HH:mm:ss` 后，`created_at` 索引终于出现在 `key` 字段里，耗时降到两秒一。

问题也随之暴露：范围查询仍然扫掉几百万行，再逐行回表取数据，IO 压力全在回镇上。

### 第二轮：联合索引替代单列索引

`status = 1` 是等值条件，`created_at >= ...` 是范围条件。按等值在前、范围在后的原则建联合索引：

```sql
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);
```

索引建好后执行计划变成 `type = range`，`rows` 从七千八百万降到一百二十万，耗时降到九百毫秒。等值条件把定位范围收窄到具体状态，范围条件在这小块数据里再切时间窗，扫描量只剩原来的千分之二。

### 第三轮：覆盖索引消除回表

`rows` 还有一百二十万，说明时间窗内的订单量本身不小，每行回表是主要开销。查询列表是固定的五个字段，把 `user_id` 和 `amount` 也放进索引，让扫描在索引内闭环，DDL 是在原索引上直接扩展：`ALTER TABLE orders DROP INDEX idx_status_created, ADD INDEX idx_status_created (status, created_at, user_id, amount);`。

执行计划 `Extra` 里的 Using filesort 也消失了，因为索引本身按 `(status, created_at)` 有序，`ORDER BY created_at DESC` 反向扫索引即可。最终耗时四十毫秒，回表次数为零。

## 优化器为什么不听你的

建了索引不等于用上索引。这一节解释第一轮改动前的怪事：`created_at` 上有单列索引，执行计划却走了全表扫描。

MySQL 的优化器基于成本模型做选择，估算每种访问路径的 IO 与 CPU 开销，挑便宜的那个。`created_at >= '2026-03-01'` 这个条件预估命中八千万行里的三千万行，走索引意味着三千万次回表，全表扫描只需要顺序读一遍，成本模型算出来后者更划算，索引就被主动放弃了。优化器不是不认识这个索引，是经过计算后放弃的。

这也给了一条经验：区分度低的查询条件，索引帮不上忙。想让优化器改变主意，路有三条：把范围收窄，比如加上 `status` 等值条件；让索引覆盖查询列，消掉回表成本；或者用 `FORCE INDEX` 强制指定。最后一条要谨慎，它绕过成本模型，数据分布变化之后可能从优化变成负优化，上线前必须在影子表上验证过。

## 另一个受害者：深分页查询

排查看板问题时顺带发现，订单后台的分页也有隐患。两条查询放在一起看，差别只在一个条件：

```sql
-- 深分页：偏移量与页码成正比，越翻越慢
SELECT * FROM orders WHERE user_id = 10086 ORDER BY id DESC LIMIT 100000, 20;
-- 游标翻页：以上一页最后一条 ID 为起点，恒定为常量定位
SELECT * FROM orders WHERE user_id = 10086 AND id < 982341 ORDER BY id DESC LIMIT 20;
```

普通用户的订单量不大，第一条查询一直很快。运营账号的订单量过万之后，偏移十万行意味着要先扫过十万行再丢掉，延迟随页码线性增长，翻到第一百页时要两秒以上。这里的误区是把慢归因于索引缺失，实际上 `(user_id, id)` 索引一直存在，问题出在 LIMIT 的语义本身：它不提供起点，只提供跳过的行数。

第二条就是改法：以上一页最后一条记录的 ID 作为下一页的起点，每次查询都是常量定位，与翻到第几页无关。接口入参从 `page` 改成 `last_id`，前端多传一个参数，收益是任何页码的耗时都是同一个数量级。这个改法在分库分表之后同样成立，而 LIMIT 大偏移量在跨片场景下要先聚合再排序再切页，代价还要再翻几倍。

## 验证工具：除了 EXPLAIN 还有什么

EXPLAIN 是入口，不是全部。排障时另外三个工具用得也很多：

- `SHOW PROFILE`：给出语句在各阶段的耗时分解，等待 IO、发送数据、排序各占多少一目了然
- `optimizer_trace`：打开后能看到优化器的完整决策过程，包括每个索引的成本估算值，索引被放弃时在这里找原因
- `performance_schema`：按语句指纹聚合统计全库的慢查询，用来发现下一个目标，而不是只盯着已知的这一条

日常习惯是每周看一次 `performance_schema` 的全景，按总耗时排序找 Top 十条。很多慢查询不是有人报障才发现的，是这么捞出来的。

## 验证与回归

优化不是改完就算数，做了四件事收尾：

- [x] 用生产影子表重放三天的查询，确认耗时分布稳定
- [x] 检查新索引对写入的影响：日均两百万插入，写放大在可接受范围
- [x] 与运营确认看板各维度数据与旧版一致，无静默错误
- [ ] 把这次的排查过程整理成组内分享，每周五下午茶时间过一遍

## 经验清单

回头看，这次优化没有用到任何高深手段，全是基本功的叠加：

1. 先看执行计划再谈优化，脱离执行计划的优化都是猜，`type`、`rows`、`key`、`Extra` 四个字段定位瓶颈
2. 隐式类型转换是索引失效的头号隐形杀手，字段与条件的类型必须严格对齐
3. 联合索引遵循等值在前、范围在后，查询列表尽量被索引覆盖，列顺序定错会让等值条件被范围条件挡住
4. 每轮只改一个变量，改完立刻重跑执行计划，归因才清晰
5. 优化后验证写入代价，索引是拿写入换读取的生意，读多写少可以激进，写入密集要克制
6. 优化器按成本模型选路，索引被忽略时先看条件的选择性，再考虑强制索引
7. 深分页改游标翻页，LIMIT 大偏移量与索引结构无关，任何索引都救不了
8. 每周用 `performance_schema` 捞一次全库慢查询 Top 十条，别只处理报障的那几条
