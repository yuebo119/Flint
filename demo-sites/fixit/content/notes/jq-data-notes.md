调接口取数是日常里最频繁的临时任务：看一眼返回结构、抽两个字段、数一下条目。以前的开法是写个 Python 脚本，现在我的默认姿势是 `curl` 加 `jq`，一条管道出结果，脚本都懒得建。这篇笔记收拢 jq 的三板斧和联用片段，全是验证过无数次、闭眼能写的模式。

## jq 的心智模型

jq 的世界只有两个核心动作：选择，从 JSON 里取出你要的部分；转换，把取出的部分变成新形状。所有程序都是管道：上一个过滤器的输出，是下一个过滤器的输入。忘掉循环、变量、下标越界这些概念，多数数据处理用管道就能说完，这是它和通用脚本语言最大的区别。

刚上手时最大的思维转换是：`.` 不是"当前对象"这种模糊概念，就是"输入本身"。`'.'` 是原样输出，`'.a'` 是取字段，`'.a.b'` 是嵌套取字段。想清楚"这一点的数据长什么样"，过滤器自然写得出来。还有一条心法：写过滤器时先在脑子里跑一遍数据流，说得出"这里进来的是一篇文章，出去的是一串标题"，管道就不会乱。说不出数据形状的地方，就是 bug 的藏身处。示例数据统一用这个虚构接口，可以直接替换成自己的：

```bash
curl -s https://example.com/api/posts
```

返回是一页文章列表，字段有 `id`、`title`、`views`、`author`、`tags`、`published`。后面所有片段都基于它。

## 三板斧

### 选择：拿到你要的那部分

选择、转换、聚合三板斧覆盖日常九成场景，分工也很清晰：选择决定看哪些数据，转换决定数据长什么样，聚合决定最后留下什么结论。写复杂查询时按这个顺序拆，一层一层来，每层只关心一件事。

```bash
# 第一条的标题
jq '.posts[0].title' posts.json

# 全部标题，一行一个
jq '.posts[].title' posts.json

# 只看已发布的
jq '.posts[] | select(.published == true)' posts.json

# 取数组切片，前五条
jq '.posts[0:5]' posts.json
```

`select` 是过滤器界的 if，把不满足条件的元素直接滤掉，留下的是原对象，后面还能继续接管道。判断写法很自由：`.views > 1000`、`.tags | index("go")`、`.title | test("正则")`，字符串还能直接上正则，这是很多人不知道的隐藏能力。

### 转换：把数据变成新形状

```bash
# 只保留两个字段，数组自动映射
jq '.posts | map({id, title})' posts.json

# 标签全部大写
jq '.posts[] | .tags |= map(ascii_upcase)' posts.json

# 构造带计算值的新对象
jq '.posts[] | {title, hot: (.views > 5000)}' posts.json
```

`map` 对数组每个元素应用同一个过滤器，是转换的主力。对象构造 `{title, hot: ...}` 支持简写和计算混排，拼装 API 请求体、生成报表行都靠它。注意 `|=` 是原地更新管道，`.tags |= map(...)` 只改 tags 不动其他字段，比整体重建对象省事。

### 聚合：从集合算出标量

```bash
# 平均阅读量
jq '[.posts[].views] | add / length' posts.json

# 按作者分组计数
jq 'group_by(.author) | map({author: .[0].author, count: length})' posts.json

# 阅读量前三条
jq '[.posts[]] | sort_by(-.views) | .[0:3] | map(.title)' posts.json
```

聚合的标准套路是先 `[...]` 把流收成数组，再 `add`、`length`、`max` 一路算下去。`group_by` 加 `map` 的组合等于 SQL 的 group by，写两次就形成肌肉记忆。`sort_by` 传负数实现倒序，不用再套 `reverse`，这个小技巧能省一层管道。聚合数字时还要留意除零和空数组：`add / length` 遇到空数组会得到 null，生产查询先判断 `.posts | length > 0` 再算平均值。健壮性和便捷性在管道里同样重要，临时脚本翻车一次就够记一辈子。

## 常用过滤器对照表

| 目标 | jq 写法 | Python 一行 |
|------|---------|------------|
| 取嵌套字段 | `.a.b.c` | `d["a"]["b"]["c"]` |
| 列表过滤 | `map(select(.x > 1))` | `[i for i in l if i["x"] > 1]` |
| 改字段 | `.x |= . + 1` | `d["x"] += 1` |
| 分组计数 | `group_by(.k) \| map({k: .[0].k, n: length})` | `collections.Counter(i["k"] for i in l)` |
| 排序取前 N | `sort_by(-.v) \| .[0:N]` | `sorted(l, key=lambda x: -x["v"])[:N]` |
| 摊平嵌套 | `flatten` | `[x for sub in l for x in sub]` |

对照着看很直观：jq 的表达力大致等于 Python 列表推导加标准库，但不用 import、不用声明变量，一行出结果。代价是复杂逻辑写起来费劲，超过五层管道就该考虑换脚本语言，工具各有边界。

## 进阶：reduce 与自定义函数

三板斧之上，有两个进阶功能日常频率不高，但用上了就回不去。

`reduce` 是聚合的通用形态，前面那些 `add`、`max` 背后都是它，复杂累积逻辑直接写它：

```bash
# 按标签统计文章数，一行 reduce 搞定
jq 'reduce .posts[] as $p ({};
    reduce $p.tags[] as $t .;
    .[$t] += 1)' posts.json
```

自定义函数用 `def` 定义，把重复的过滤逻辑收成名字，长管道立刻可读：

```bash
jq 'def is_hot: .views > 5000 and .published;
    .posts | map(select(is_hot)) | length' posts.json
```

经验是自定义函数别急着写，同一段过滤器在一条命令里出现第二次，再抽不迟。过早抽象的 jq 程序比 Python 还难懂，那就本末倒置了。

## 常见报错与调试

jq 的报错风格是"短促加准确"，常见错误就那几类，认出来就能秒修：

| 报错关键词 | 含义 | 常见原因 |
|------------|------|----------|
| `Cannot index array with "x"` | 把数组当对象取了 | 少了 `[]` 遍历那一步 |
| `Cannot iterate over null` | 对空值做遍历 | 字段名拼错或层级不对 |
| `null (null) has no keys` | 链式中途断了 | 中间结果意外为空 |
| `Invalid numeric literal` | 输入不是合法 JSON | 接口返回了 HTML 错误页 |

调试三板斧按顺序上：先 `jq '.'` 确认输入是合法 JSON，再用 `jq 'paths'` 打印全部路径对照层级，最后把长管道从后往前逐段砍，找到第一个输出异常的位置。这套流程对九成的报错都够用，剩下的通常是引擎版本差异，`jq --version` 看一眼就能排除。

## 与 curl 的联用套路

管道组合是 jq 的主场，日常取数基本是这个形状：

```bash
# 取数、筛选、只留关键字段，一次到位
curl -s https://example.com/api/posts \
  | jq '.posts[] | select(.views > 1000) | {title, views}' \
  | head -20
```

嵌套列表记一下组合顺序，调试时按层拆：

- 取原始响应
  - `curl -s` 静默拿数据
  - 先 `jq '.'` 看结构，别急着写过滤器
- 定位数据层
  - `.posts` 或 `.data.items`，看实际包装
  - `keys` 看一眼有哪些字段
- 逐层加条件
  - `select` 过滤
  - `map` 转换
  - `group_by` 聚合
- 收尾
  - `-c` 紧凑输出配其他命令
  - `head` 防刷屏

这套顺序的核心是"先看结构再写逻辑"，和写 SQL 之前先 EXPLAIN 一个道理。跳过结构直接写过滤器的后果，多半是对着 null 输出发半天呆，最后发现层级少看了一层。

`jq -c` 输出单行紧凑 JSON，是喂给其他工具的标准格式；`jq -r` 去掉字符串引号，输出纯文本，配合 `read` 循环处理特别顺。调试复杂过滤器时用 `jq 'paths'` 或 `jq 'leaf_paths'` 把结构路径全打出来，比盯着缩进猜快得多。

## 真实场景：一次接口巡检

把前面所有模式串起来，跑一次完整的接口巡检，这条命令我每周都在用：

```bash
# 一次输出：总量、平均阅读、最热三篇、按作者分布
curl -s https://example.com/api/posts | jq '
  .posts as $p
  | {
      总量: ($p | length),
      平均阅读: (($p | map(.views) | add) / ($p | length) | round),
      最热: ($p | sort_by(-.views) | .[0:3] | map(.title)),
      作者分布: ($p | group_by(.author) | map({author: .[0].author, 篇数: length}))
     }'
```

这个例子值得拆开讲三处。`as $p` 把数据存进变量，后面四处复用，不用反复写 `.posts`，长查询里这是保持可读的关键。中间用 `|` 连接的每一步都在变换数据形状，从原始响应到最终报表只有一层嵌套。最后的对象构造把四个指标并列输出，人读起来像一份小报表，而不是一堆零散数字。

巡检之外，同一套套路稍改就是周报生成器：把 `最热` 换成 `新增`，把 `作者分布` 换成 `标签分布`，一条命令定期跑，结果直接贴进周报。工具用顺之后，临时取数这件事从"开个编辑器写脚本"降级成"敲一行命令"，省下的不只是时间，还有上下文的来回切换。
