很多团队第一次接大模型，都是同一个死法：把资料往对话框里一贴，能用；等资料变成几百份 PDF、几千篇工单，对话框塞不下了，开始瞎答。检索增强生成（RAG）就是来解决这件事的——把"问模型"改成"先检索相关资料，再让模型基于资料回答"。维基百科的[检索增强生成条目](https://zh.wikipedia.org/wiki/检索增强生成)对这个思路有完整梳理，原始论文见 [arXiv:2005.11401](https://arxiv.org/abs/2005.11401)。这篇文章按工程顺序把整条流水线走一遍，每个阶段都给出"为什么"和"怎么做"。

## 整体流水线：五步一条线

一个最小可用的 RAG 系统由五步组成，离线两步、在线三步：

1. **离线**：解析文档，切成块（chunk）；
2. **离线**：用嵌入模型把每个块转成向量，写入向量数据库；
3. **在线**：把用户问题同样转向量，检索最相关的若干块；
4. **在线**：对检索结果重排、截断，拼进提示词；
5. **在线**：模型基于拼好的上下文生成答案，附上引用来源。

![RAG 流水线的离线入库与在线检索两个阶段](/images/demo-2.svg)

这条链上每个环节都会漏水，而最终答案的质量上限由最弱的环节决定。见过太多团队把全部精力花在第 5 步的提示词打磨上，对前两步的切分策略和嵌入选型敷衍了事，结果自然是"模型挺聪明，答非所问"。

## 第一步：文档解析与切分

真实世界的文档不是干净文本：PDF 有页眉页脚和多栏排版，Word 里有嵌套表格，网页要先去广告和导航。解析阶段的错误会被后续所有步骤继承，而且极难定位——答案错了，你以为是检索问题，其实是表格在解析时被拍扁成了乱码。

### 结构优先，保留重叠

切分的核心矛盾是：块太大，向量被"平均"掉，检索不精准；块太小，上下文不完整，模型看到半句话没法推理。常见做法是按文档结构切（标题、段落、列表项各自成块），相邻块之间保留 10% 到 20% 的重叠，避免一句话正好被拦腰截断。元数据一定要跟着块走：来源文件、页码、章节标题，这是后面做引用的依据。

解析环节还有一个专门值得一提的对象：表格。表格拍平成文字后，行列关系尽失，检索到也读不懂。务实的做法是把每个表格整体作为一个块，前面拼上表格标题和说明文字，让"这句话是哪张表的哪一行"可追溯；跨页的长表格按行组分块，表头在每一块开头重复。这类细节不影响演示，但直接决定真实文档上的检索质量。

```python
def split_by_heading(text: str, max_len: int = 500, overlap: int = 50) -> list[dict]:
    """按 Markdown 标题层级切分，超长块再按段落细分，相邻块保留重叠。"""
    import re
    blocks = re.split(r"(?m)^(?=#{1,3} )", text)
    chunks = []
    for block in blocks:
        if len(block) <= max_len:
            chunks.append({"text": block.strip(), "heading": block.splitlines()[0][:40]})
            continue
        # 超长块退化为按段落累积切分
        buf = ""
        for para in block.split("\n\n"):
            if len(buf) + len(para) > max_len and buf:
                chunks.append({"text": buf.strip(), "heading": block.splitlines()[0][:40]})
                buf = buf[-overlap:]  # 保留尾部作为下一块的开头重叠
            buf += "\n\n" + para
        if buf.strip():
            chunks.append({"text": buf.strip(), "heading": block.splitlines()[0][:40]})
    return chunks
```

这段代码演示了两个关键决策：优先尊重文档自身的结构（标题是天然的语义边界），以及用重叠换取跨块语义完整。块的大小没有银幕数字，几百字的中文块是常见起点，但要拿自己的问答集去调。

## 第二步：向量化与入库

嵌入模型把文本变成定长向量，语义相近的文本向量距离近。选型上有个常被忽略的点：**检索用的嵌入模型和生成用的模型最好是两套**，各管一段。向量库的选型则要看数据量和延迟要求：

| 方案 | 适用规模 | 特点 | 典型用法 |
|------|----------|------|----------|
| pgvector | 百万级以内 | 复用现有 PostgreSQL，事务和权限一起解决 | 已有关系库的团队首选 |
| FAISS | 亿级以内 | Meta 出品，本地库，无服务端 | 研究与单机服务 |
| Milvus | 亿级以上 | 分布式，支持标量过滤 | 云上海量检索 |
|  Elasticsearch 8+ | 百万到千万级 | 向量与全文混排，一套集群 | 已有 ES 技术栈的团队 |

每个块入库时都要带元数据，这是检索阶段做过滤的抓手：

```json
{
  "id": "chunk_0031",
  "text": "退款政策：签收后七天内可无理由退货，定制类商品除外。",
  "embedding": [0.012, -0.304, "… 共 1536 维 …"],
  "metadata": {
    "source": "售后政策-v3.pdf",
    "page": 4,
    "section": "退换货规则",
    "updated_at": "2026-03-01"
  }
}
```

注意 `metadata.section` 这个字段。上线后你会发现，相当比例的"检索不准"不是向量不像，而是该按部门、按时间过滤的没过滤——把三年前的旧政策检索出来当答案，模型再聪明也救不了。

## 第三步：检索与重排

向量检索解决"意思相近"，但会漏掉另一类查询：精确编号、型号、错误码。用户搜 "ERR-4092" 时，语义嵌入未必比传统关键词匹配更好用。成熟的方案是混合检索：向量分数与 BM25 关键词分数加权融合，各取所长。

粗排取回 top 50 之后，交给重排模型（cross-encoder）精细打分，取 top 5 进上下文。重排模型慢但准，只处理少量候选，这笔账划算。

> 检索质量是 RAG 的天花板。如果正确答案压根没进 top 5，后面再精巧的提示词也只是让模型把无关材料说得更流畅而已。定位问题时先看检索日志：相关块在第几名？

## 第四步：生成与引用

上下文的拼法直接决定答案的可信度。一个经过验证的提示词骨架是：先声明角色与任务，再给出资料块并逐块编号，明确要求"仅依据给定资料回答，资料中没有就说不知道，并在句末标注引用编号"。

```yaml
# 流水线配置示例：把上面几个阶段串成可复现的作业
pipeline:
  name: after-sale-rag
  stages:
    - name: retrieve
      type: hybrid
      top_k: 50
      weights: { vector: 0.6, bm25: 0.4 }
      filters: ["metadata.department == '售后'"]
    - name: rerank
      type: cross_encoder
      model: bge-reranker-base
      top_n: 5
    - name: generate
      model: internal-llm-70b
      temperature: 0.2
      max_tokens: 800
      require_citation: true
  evaluation:
    dataset: qa-set-2026-06
    metrics: [recall_at_5, faithfulness, answer_relevance]
```

引用不是锦上添花，而是排障入口：用户指出答案不对时，顺着引用能定位到是检索错了还是生成错了，两者修法完全不同。

## 第五步：评估

没有评估集的 RAG 系统等于盲人摸象。最小评估集是一两百条覆盖真实场景的问答，每条标注答案应出自哪个文档，然后盯三个指标：

### 三个指标，按顺序修

- **检索召回率（recall@5）**：正确答案是否进了前 5 个候选块，这是最先要修的；
- **忠实度（faithfulness）**：生成的每句话是否都能在给定资料里找到依据，治幻觉；
- **答案相关性**：答没答到点上，治跑题。

上线前的检查清单，建议逐项打钩再发布：

- [ ] 评估集覆盖高频问题与边界问题，不是清一色简单题
- [ ] 无答案场景已测试：资料里没有时，系统回答"不知道"而不是硬编
- [ ] 检索日志记录了每个问题的 top 候选，可回放
- [ ] 引用编号与来源文档可点击，用户能自己核验
- [ ] 文档更新流程已打通：新文档入库到可检索的时延有明确预期

## 文档更新与增量索引

生产 RAG 不是一次性导入。政策改了、工单模板换了，索引里的旧块不更新，模型就会拿着过期资料自信作答。增量索引要回答三个问题：怎么发现变更（文件监听、定时扫描、上游发布事件），怎么处理失效块（删除后重建该文档的全部块，避免新旧块混在候选里打架），怎么验证生效（导入后立刻用该文档的两三个已知问题验证检索）。这三个问题都有明确答案之后，文档更新才是分钟级的常规操作，而不是每次都心惊胆战的全量重建。把"资料已更新"的时延写进服务承诺，用户问起来你答得出来。

---

最后提醒一个反复出现的坑：RAG 不是"接个向量库就完事"的一次性工程，文档在变、问题在变、嵌入模型在升级，检索日志和评估集要跟着持续运营。把它当成一条需要维护的生产流水线，而不是一个演示脚本，这套系统才真正立得住。
