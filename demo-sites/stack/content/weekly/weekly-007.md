选开源协议这件事，多数团队在创建仓库时随手一勾，三年后接到律师函才想起当初选的是什么。这周做一期入门：用三个问题给主流协议分类、讲清 Apache-2.0 那个容易被忽略的专利条款、划出 GPL 的传染边界，最后给一份能抄的选择建议。四个条目都不构成法律意见，但足够让你在填表时知道自己在签什么。

## 条目一：协议三问，先分类再细节

面对一份陌生协议，先别读全文，问三个问题：能不能商用？修改后能不能闭源发布？改了要不要公开源码？三个问题的答案把主流协议切成两大阵营。permissive 阵营（MIT、Apache-2.0、BSD）对三个问题基本都点头，只要求保留版权声明；copyleft 阵营（GPL 家族）对第二个问题摇头：你修改后分发，就得把修改部分的源码一起给出。一进一退之间，是两种截然不同的软件观。

```toml
# Cargo.toml 里的协议声明，SPDX 表达式支持双协议
[package]
name = "widget-core"
version = "0.3.1"
license = "MIT OR Apache-2.0"   # 使用者二选一，是 Rust 生态的常见做法
```

### 分发才是触发点

对使用方来说，协议真正影响的场景只有一个：分发。内部使用、自建服务不触发分发义务，这是最常被误解的一点。把 GPL 组件放在内部工具里跑，和把它打进售出的二进制里，法律含义完全不同。协议的底层是版权法：代码写出来那一刻，版权默认归作者，别人无权使用、复制、修改。协议做的事就是作者主动让渡一部分权利，把"保留所有权利"改成"在遵守这些条件的前提下授予你权利"。由此推出两个实用结论：没有协议的仓库等于保留所有权利，别人拿去商用是侵权，别被"放在 GitHub 上"误导；协议授予的是许可而不是所有权，别指望签了协议就能管别人怎么用。

> 协议的问题从来不是"能不能用"，而是出问题时谁能说清责任。这句话在选型时想一遍，能省掉事后的大部分扯皮。

先想清楚自己的使用场景落在哪一侧，再看协议条款，顺序反了就会自己吓自己。

## 条目二：permissive 家族，和那张专利牌

MIT、Apache-2.0、BSD 三家的核心条款惊人地一致：保留版权声明和许可文本，其他随意。差别在细节：MIT 最短最友好；BSD 有两条款三条款之分，多出来的是不得用作者名义做衍生推广；Apache-2.0 最长，因为它多了一张牌：明确的专利授权条款。使用者获得贡献者专利的明示许可，同时条款规定：如果你拿这个软件去告它侵犯你的专利，授权自动终止。

```json
{
  "name": "oss-inventory",
  "version": "2.0.0",
  "license": "Apache-2.0",
  "notice": "保留 NOTICE 文件中的署名与专利声明",
  "dependencies": {
    "left-pad": "1.3.0"
  }
}
```

这张专利牌对企业采用是实实在在的定心丸：法务审 Apache-2.0 项目时，通过率明显高于裸 MIT项目，因为授权范围写得清楚。代价是 Apache-2.0 要求分发时带上 NOTICE 文件的内容，合规检查时容易漏。小工具随便选，打算给大企业用的库，Apache-2.0 通常是更稳的默认。

BSD 家族内部也有段历史值得知道：原始的 BSD 带一个广告条款，要求所有宣传材料提及伯克利，条款一多就没人愿意用，删掉广告条款之后才是今天的三条款版。这段历史是协议设计的一课：合规成本每增加一条，采用率就掉一截，MIT 的极简能赢下半壁江山，靠的就是把义务压缩到"保留版权声明"一句话。MIT 和 Apache-2.0 之间还隔着一层兼容性：Apache-2.0 与 GPLv3 兼容，与 GPLv2 不兼容，这个细节在协议混用的项目里会变成真问题。双授权（MIT OR Apache-2.0）流行的原因就是把选择权交给使用者，Rust 生态把这招用成了惯例。

参考：[Apache-2.0 专利条款解读](https://example.com/apache2-patent-clause)

## 条目三：GPL 家族的传染边界

GPL 的传染性是它最出名的特征，也是最容易被夸大的特征。准确的说法是：当你分发基于 GPL 代码的衍生作品时，整个衍生作品要以 GPL 提供源码。注意两个限定：分发，和衍生作品。内部使用不触发；仅仅是进程间通信、命令行调用，通常不构成衍生。真正需要小心的是静态链接进同一个二进制，以及把 GPL 代码复制进自己的源码树。

| 协议 | 商用 | 修改后闭源分发 | 网络服务需公开源码 | 严格程度 |
| --- | --- | --- | --- | --- |
| MIT | 可以 | 可以 | 不要求 | 最松 |
| Apache-2.0 | 可以 | 可以 | 不要求 | 松，带专利牌 |
| LGPL | 可以 | 库本身不行 | 不要求 | 中 |
| GPL | 可以 | 不行 | 不要求 | 严 |
| AGPL | 可以 | 不行 | 要求 | 最严 |

LGPL 松一档：动态链接使用 LGPL 库，自己的代码可以闭源；AGPL 紧一档：它堵上了"SaaS  loophole"，通过网络提供服务也算分发，修改必须公开。选型口诀一句话：做闭源商业产品，远离 GPL 和 AGPL 的直接依赖；做工具库给全世界用，GPL 会挡住一半潜在用户。这两条不是法律结论，是无数团队用脚投出来的票。

GPL 的传染边界里最有争议的是链接：FSF 主张动态链接 GPL 库也构成衍生作品，业界的通行实践更宽松，认为进程间通信不算。两边分歧至今没有司法定论，企业合规的稳妥做法是避开争议区，宁可换实现。另外 GPLv3 加了反数字版权管理的安装信息条款，嵌入式产品选型时要多看一遍；AGPL 则把"通过网络提供服务"也纳入分发，堵上了当年 Google 式的用法。协议文本每年都有小修订，重大决策前以官方文本和法务意见为准。

参考：[GPL 传染边界详解](https://example.com/gpl-boundaries)

## 条目四：依赖地雷与选择建议

协议风险大多不在你的代码，在依赖的依赖。一个 MIT 的框架拖进来一个 GPL 的组件，传染性沿着链路传导，而你的合规清单上只有第一层。工程上的解法是 SBOM（软件物料清单）：把依赖树和协议清单化，CI 里跑自动扫描，新依赖进门前先过一遍。这件事的成本是一次性的配置，收益是半夜被法务叫醒时的那份底气。

- [ ] 新依赖进门前查协议，白名单外要评审
- [ ] CI 里有依赖协议的自动扫描，报警而不是记录
- [ ] 每个仓库根目录有 LICENSE，和声明的协议一致
- [ ] 贡献指南里写清了对外补丁的协议要求

如果现在让你为新仓库选协议，默认答案是这样：库类项目选 MIT 或 Apache-2.0，追求最大传播度；应用类项目选什么都行，但记得写清楚，免得用户来问；有强烈 reciprocity 诉求的选 GPL，并接受传播受限。把选择写进 README 的第一段，让使用者零成本确认，这是礼貌，也是自我保护。

工程化的合规抓手是 SBOM：用 SPDX 或 CycloneDX 格式把依赖树和协议清单化，CI 里跑扫描，新依赖进门先过白名单。工具链已经成熟，一条命令就能出报告，成本比想象中低。真正的难点从来不是技术，是让"查协议"成为依赖进门的固定动作，而不是发布前的突击人工核对。习惯一旦错过发布时间，就会被无限期推迟。
