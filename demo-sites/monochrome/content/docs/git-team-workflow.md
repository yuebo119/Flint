Git 本身只是一套分布式版本控制工具，它不规定你怎么用。两个人各写各的代码时，任何用法都能跑通；五个人以上同时改动同一批文件时，没有约定的仓库很快就会变成一团乱麻：提交信息写着"修复 bug"却不知道修的是什么，分支从三个月前建出来合并时冲突上百处，线上出问题想回滚却找不到对应提交。这篇指南给出一套经过多数团队验证的协作约定，覆盖分支、提交、评审、冲突与事故恢复五个环节。

## 为什么需要约定

版本控制的价值不在"保存历史"，而在"历史可读、变更可追溯、事故可回滚"。约定要解决三个具体问题：任何一个提交都能回答"改了什么、为什么改"；任何一次发布都能找到对应的代码区间；任何一个新人看着提交记录就能理解项目演进。做不到这三点，Git 就退化成了网盘。

还有一点常被忽略：约定必须尽量由工具兜底，而不是靠人记。提交格式用 CI 校验，分支保护用仓库设置锁定，格式问题交给 pre-commit，把"要求"变成"做不到就合不进去"，约定才算真正落地。纯文档形式的约定，三个月后通常就没人记得了。

## 分支策略：三种常见模式

没有放之四海而皆准的分支模型，按团队规模和发布频率选：

| 模式 | 适用场景 | 分支结构 | 主要代价 |
|------|----------|----------|----------|
| GitHub Flow | 持续部署的互联网产品 | main + 短期功能分支 | 需要强自动化测试兜底 |
| Git Flow | 有固定版本周期的软件 | main + develop + feature + release + hotfix | 分支多，流程重 |
| 主干开发 | 成熟工程团队 | 仅 main，用特性开关控制上线 | 对代码质量与 CI 要求高 |

对大多数五到二十人的团队，推荐主干开发加短期特性分支：功能分支存活不超过三天，合并即部署，配合特性开关控制功能可见性。版本周期固定的客户端软件可以选 Git Flow，但要把 release 分支的生命周期写进文档，否则很容易出现修复同时进两个分支、漏合一个的情况。

整合分支时有两条路，团队必须统一选一条，混用会让历史极难读：

| 方式 | 做法 | 历史形态 | 风险 |
|------|------|----------|------|
| Merge | `git merge main` 生成合并提交 | 保留真实并行轨迹 | 提交图交错，`git log` 噪声多 |
| Rebase | `git rebase main` 把提交挪到最新主干之后 | 线性历史 | 改写已推送的提交会坑到队友 |

记住一条铁律：只对自己还没推送的分支做 rebase，对任何已共享的分支只用 merge。判断标准很简单——这个分支上有没有别人的提交。

## 提交信息规范

提交信息是给未来的读者看的，包括三个月后的你自己。推荐采用约定式提交（Conventional Commits），格式为 `类型(范围): 描述`：

| 类型 | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(api): 增加分页参数` |
| `fix` | 缺陷修复 | `fix(parser): 修复空文件崩溃` |
| `docs` | 文档变更 | `docs: 更新部署说明` |
| `refactor` | 重构，不改变行为 | `refactor: 抽取配置加载逻辑` |
| `test` | 测试调整 | `test: 补充边界用例` |
| `chore` | 构建、依赖、杂项 | `chore: 升级构建工具链` |

```markdown
fix(cache): 修复键大小写不一致导致的缓存未命中

缓存键在写入时转换为小写，读取时未做同样处理，
导致带有大写字符的键永远读不到缓存。

关联 issue #128。
```

三条硬规则：标题一行说清结论，不超过五十个字符；正文解释"为什么"而不是重复"改了什么"；一个提交只做一件事，重构与功能改进分开提交。这样出问题时 `git log` 就是一份可检索的诊断记录，`git revert` 也能干净地撤销单个变更。

> 判断提交信息是否合格，有个简单的测试：只读提交列表，能否说清这个项目最近在做什么。如果满屏都是"修改""更新""修复"，说明历史已经失去可读性。

## 提交的粒度

一个提交只做一件事，这条规矩的收益比任何格式约定都大。混合提交是代码评审和缺陷定位的头号敌人：一个提交里既有功能又有全仓库格式化，评审者就没法专注看逻辑，出问题时也没法单独回滚。实践中可以用 `git add -p` 把改动按块拆分，把格式化、重命名、逻辑修改分成不同提交；提交前用 `git diff --cached` 把暂存区完整过一遍，确认这次提交确实只包含预期内容。如果一次改动实在拆不开，至少保证提交本身能通过编译和测试，别把半成品留在历史里。

## 日常协作流程

以主干开发为例，一个功能的完整生命周期：

1. 从 main 拉取最新代码，创建特性分支：`git switch -c feat/login-rate-limit`。
2. 在分支上小步提交，每次提交保持可编译、测试可通过。
3. 推送分支，发起 Pull Request，在描述中写清背景、方案与验证方式。
4. 至少一名同事评审通过，CI 全绿后合并，推荐 squash 合并保持主干历史线性。
5. 删除已合并分支，观察线上指标，确认无异常后关闭关联 issue。

分支命名同样值得约定：`feat/`、`fix/`、`docs/`、`chore/` 前缀加简短描述，一眼就能看出意图。分支存在越久，合并越痛，超过一周的分支要么拆分，要么先合并再继续。

## Pull Request 的写法

PR 描述是评审的上下文，写得好能省掉来回追问。模板可以直接放进仓库的 `.github/pull_request_template.md`：

```markdown
## 背景
为什么需要这次改动？关联哪个 issue？

## 方案
采用了什么方案，为什么放弃其他选项？

## 影响范围
涉及哪些模块，是否需要配置变更或数据迁移？

## 验证
- [ ] 本地构建通过
- [ ] 新增/修改的用例已覆盖
- [ ] 已在测试环境验证
```

PR 体积直接影响评审质量。一个四百行的 PR 和四个一百行的 PR，后者的缺陷发现率通常高得多。拆不开的巨大改动，至少要在描述里给出阅读顺序。

## 评审与被评审

协作流程里最容易被低估的是评审环节，它同时消耗两个人的时间，值得立几条简单的规矩：

- **作者侧**：推送前自己先读一遍 diff；PR 描述写清验证方式，别让评审者猜；收到评论二十四小时内回应，哪怕是"已收到，排期处理"。
- **评审者侧**：首次响应不超过一个工作日；评论分级表达，把"必须改"和"建议改"区分开；指出问题时给出理由和替代方案，而不是只留下"这里不行"。
- **有分歧时**：技术争论超过三轮就约个短会当面聊，评论区的长篇辩论对第三方读者没有价值，对结论也没有帮助。

## 冲突处理

冲突不可怕，可怕的是看不懂为什么冲突。

### 标准处理流程

```bash
# 合并前先更新主干，把冲突暴露在本地
git fetch origin
git rebase origin/main        # 或 git merge origin/main，二选一勿混用

# 查看冲突文件，搜索 <<<<<<< 标记逐处解决
git status

# 解决后标记为已解决并继续
git add <已解决的文件>
git rebase --continue         # merge 场景用 git commit

# 任何一步想放弃重来
git rebase --abort            # merge 场景用 git merge --abort
```

### 解决原则

解决冲突时先理解双方意图，不要机械地"两边都留下"。拿不准就找冲突另一方的作者当面确认，这部分时间花得值。合并策略上，团队要统一用 rebase 还是 merge：rebase 历史线性但对共享分支有风险，merge 保留真实轨迹但历史图复杂，混用会让 `git log` 极难读。冲突解决完成后必须重新构建并跑一遍测试，冲突解错是静默错误的高发区，肉眼审查很难发现。

## 危险操作与事故恢复

下面几条命令能救命，但前提是理解它们在做什么：

- **改错了但没提交**：`git restore <文件>` 丢弃工作区改动，执行前用 `git diff` 确认。
- **提交错了但没推送**：`git commit --amend` 修补最近一条提交；`git reset --soft HEAD~1` 撤销提交保留改动。
- **推送错了**：`git revert <提交>` 生成一条反向提交，历史可追溯，适合公共分支；不要对共享分支用 `git reset` 后强推。
- **分支被删了**：`git reflog` 能找到本地的HEAD移动记录，绝大多数"丢失"的提交都能找回来。
- **误操作后先备份**：`git bundle create backup.bundle --all` 把仓库打成文件，恢复操作前先留后路。

**fatal: refusing to merge unrelated histories**：两个仓库没有共同历史。确认远端地址无误后，用 `git pull origin main --allow-unrelated-histories` 显式允许合并。

**hint: Updates were rejected because the remote contains work that you do not have locally**：远端领先于本地。先 `git pull --rebase` 再推送，不要直接强推。

**CONFLICT (content): Merge conflict in xxx**：按上面的流程解决，解决后必须重新构建并跑测试，冲突解错是静默错误的高发区。

**error: pathspec 'xxx' did not match any file(s) known to git**：通常是分支名或路径拼错，`git branch -a` 与 `git status` 确认后再操作。

## 团队落地检查清单

- [ ] 确定并文档化分支策略，所有人按同一套流程走
- [ ] 提交信息统一为约定式提交，CI 中校验格式
- [ ] PR 模板入库，描述不写"修复若干问题"这类空话
- [ ] 合并前 CI 必须全绿，不允许"先合并再修"
- [ ] main 分支开启保护，禁止强推与直接提交
- [ ] 每季度回顾一次提交记录，看约定是否被真正执行

## 小结

Git 约定的本质是把个人习惯变成团队契约。落地时分三步：先统一提交信息与分支命名，成本最低收益最快；再固化 PR 流程与 CI 门禁；最后才是分支策略这种结构性调整。约定不在多，在于每条都有人执行、有工具兜底。参考材料可以读 <https://zh.wikipedia.org/wiki/Git> 与 <https://www.conventionalcommits.org/zh-hans/v1.0.0/>，但真正适合你们团队的规则，一定是在协作中磨合出来的。
