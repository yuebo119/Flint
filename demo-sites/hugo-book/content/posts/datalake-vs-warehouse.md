"我们到底该建数据湖还是数据仓库？"这个问题被问了十几年，答案也从没变成一句干脆话。更准确的描述是：两者从不同的假设出发，各自长成了一套体系，然后在湖仓一体的浪潮里重新握手。这篇文章把分歧的根源、各自的取舍、以及今天怎么选讲清楚。

## 定义之争：两套假设

数据仓库诞生于关系数据库时代，核心假设是**数据进来前就要想清楚怎么用**：建模、分层、指标口径先定义，数据清洗转换后按规范入库，这叫 schema-on-write。它的黄金搭档是 SQL 分析师，一条查询能拼出跨部门的经营报表。

数据湖诞生于大数据时代，核心假设反过来：**先把数据原样存下来，用的时候再解释**，这叫 schema-on-read[^1]。原始日志、图片、JSON、半结构化事件，不管有没有想清楚用途，低成本存着。代价是查询时要现场解析，没有仓库里那些打磨好的语义层。

一个管" Pipeline 终点"，一个管" Pipeline 起点"，这才是错位的根源——它们本来就不是竞争关系，是分工关系。维基百科的[数据仓库条目](https://zh.wikipedia.org/wiki/数据仓库)对传统数仓的定位有经典描述。

## 一张对比表

### 七个维度看差异

| 维度 | 数据仓库 | 数据湖 |
|------|----------|--------|
| 数据形态 | 结构化、清洗后 | 原始、结构化与非结构化混杂 |
| Schema 时机 | 写入时约束 | 读取时解析 |
| 主要用户 | 分析师、BI 报表 | 数据工程师、算法、探索分析 |
| 典型存储 | 专有列式格式 | 对象存储上的 Parquet 等开放格式 |
| 查询延迟 | 毫秒到秒 | 秒到分钟（未经优化时） |
| 治理重点 | 口径一致、权限行级管控 | 数据发现、血缘、湖内权限 |
| 单位成本 | 高 | 低一个量级 |

注意最后一行。数仓按计算和存储打包计价，冷数据也占着昂贵资源；湖用廉价对象存储，PB 级日志存一年的成本和数仓存一个月相当。成本结构不同，决定了它们各自擅长的问题不同。

## 存储格式：Parquet 为什么赢了

湖上能跑起分析查询，列式存储格式是幕后功臣。Parquet 把数据按列组织存，分析查询通常只碰几列，按列读能跳过九成无关数据；列内再做字典编码和压缩，重复度高的文本列能压到十分之一体积。读 Parquet 只需要一个计算引擎，不需要数仓那套专有存储引擎。

```sql
-- 通过外部表直接查询湖上的 Parquet 文件，无需导入
SELECT
    dt,
    event_type,
    COUNT(*) AS pv,
    COUNT(DISTINCT user_id) AS uv
FROM read_parquet('s3://datalake/events/dt=2026-03-08/*.parquet')
WHERE dt BETWEEN DATE '2026-03-01' AND DATE '2026-03-08'
GROUP BY dt, event_type
ORDER BY dt, pv DESC;
```

### 引擎补上另一半

这段 SQL 点出了湖的另一半拼图——查询引擎。Hive、Spark、Trino 这类引擎让湖上的开放格式也能跑分布式 SQL，湖和仓在"能跑 SQL"这件事上逐渐趋同。

## 从湖仓分立到湖仓一体

纯粹的数据湖有个著名绰号：数据沼泽。没有治理的湖里，同名不同义的表、无人认领的临时目录、权限黑洞，新人不认三个老员工都不敢下钻。业界于是把仓库的能力往湖上搬，长出三条技术路线：

- **Iceberg / Delta Lake / Hudi**：给湖上的文件加事务表格式，支持 ACID 更新、时间旅行、Schema 演进；
- **湖仓一体（Lakehouse）**：开放格式加事务语义，一份存储同时服务 BI 报表和机器学习；
- **仓的开放化**：新一代数仓支持直接查询湖上数据，甚至支持存算分离。

### 方向：存储开放，语义事务

方向很清楚：**存储用湖的开放格式，语义用仓的事务和治理**。两边的优点都想拿，代价是运维复杂度上了一个台阶——事务表格式的元数据服务、compaction 任务，都是新的运维面。

## ETL 还是 ELT

数仓时代是 ETL：进入仓库前，数据在独立的 ETL 服务器上洗好。湖时代流行 ELT：原始数据先落湖，用湖上的算力边查边转，转换逻辑本身就是 SQL。ELT 的好处是转换步骤可重放、可版本管理，出了问题能从原始数据重新洗一遍，而不是面对一份来路不明的中间表。

## 数据目录：湖的导航系统

湖里最缺的不是存储，是"知道有什么"。数据目录（Data Catalog）就是湖的搜索引擎：自动扫描元数据、解析表结构和字段含义、记录数据血缘，让分析师搜"用户近三十天活跃"时，能搜到那张靠谱的表，而不是三张同名表里挑一张赌运气。主流工具能力大同小异，真正难的是运营：字段描述要有人维护，表要有负责人，废弃表要及时归档。工具只解决"能被找到"，运营才解决"敢被使用"——没有后者的目录，三个月后就是一潭死水里的又一层沉积物。

## 一个务实的迁移路径

从零搭湖仓一体，别想一步到位。一条被反复验证的路径是：先把报表和指标搬进仓（或仓的开放形态），让 BI 有稳定口径；同时把原始日志和明细全量落湖，作为可回溯的唯一事实来源；机器学习和探索分析直接消费湖上的数据；最后用同步管道把湖上的清洗结果喂回仓，让仓里的集市报表能追溯到湖上的原始行。这个结构里，湖和仓各干各擅长的事，中间靠数据契约衔接。任何宣称"一个系统取代另一个"的方案，都值得先问一句：谁来保证跨表的口径一致？

## 治理：没有治理的湖是沼泽

技术路线之争之外，真正决定成败的是治理。几条血泪经验：

1. **分层规范要早定**：原始层、清洗层、汇总层从第一天就分开，目录命名、负责人、更新频率全部落文档；
2. **血缘要能查**：一张报表数字不对，要能顺藤摸瓜到上游每张表和每个作业，靠口口相传的团队撑不过两次人员流动；
3. **权限要跟人走**：离职人员的访问权限回收、敏感字段的列级脱敏，出事之后再补就是事故复盘的一部分了；
4. **成本要能归因**：按团队和作业分摊查询成本，否则总有人用全表扫描把月度账单刷出天际。

治理的投入要跟数据资产的价值匹配。一个只服务三个人的部门数据集，全套血缘加强权限是过度设计；反过来，支撑全公司报表的汇总层，治理缺任何一项都是定时炸弹。务实的做法是分而治之：核心资产重治理，边缘目录轻管理，目录标签让分析师一眼看出哪层碰不得、哪层可以随便试。

> 一个反直觉的观察：大部分团队失败在治理缺位，而不是技术选型。同样的 Iceberg，治理完善的团队用成了资产，治理缺位的团队用成了沼泽，工具不背这个锅。

## 今天怎么选

给一个务实的决策框架。数据以报表和 BI 为主、团队偏分析出身，数仓或湖仓一体是主线；数据以日志和机器学习为主、探索性查询多，湖打底、在湖上建语义层；混合需求是常态，主流做法是湖存全量、仓建集市，中间用同步管道打通，集市的数据可追溯到湖上的原始层。

![数据湖与数据仓库的分层架构与数据流向](/images/demo-8.svg)

最后一句话总结这场十年之争：**湖和仓争的从来不是存储位置，而是"什么时候理解数据"**。写入时理解，换来一致性和低延迟；读取时理解，换来灵活性和低成本。成熟的团队两个都要，并且清楚每一份数据在哪一层被理解。

[^1]: schema-on-read 并不等于"没有 schema"。原始层确实无约束，但读取时数据必须被解析进某个结构，只是这个结构推迟到使用时才确定，且同一份数据可以按不同结构反复解读。
