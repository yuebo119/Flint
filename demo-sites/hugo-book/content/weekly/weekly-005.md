## 条目一：管道哲学为什么还没过时

1970 年代的管道设计到今天依然能打，靠的是把"一个工具只做一件事，用文本流连接所有事"做到了极致。grep、sed、awk、sort、uniq 这一排老工具，单个看都简陋，组合起来能完成数据分析、日志排查、代码重构前导。更现实的优势是可预期：它们的输入输出都是字节流，行为写在 man 页里，不会因为升级就变脸。你的管道脚本放三年还能跑，这种稳定性在工具圈是稀缺品。

```bash
# 一条管道：找出近半年提交最多、且单文件最长的源文件
git log --since="6 months ago" --name-only --pretty=format: \
  | sort | uniq -c | sort -rn | head -10 \
  | awk '{print $2}' \
  | xargs wc -l | sort -rn | head -5
```

管道思维真正值钱的地方是可分合：上面这条命令，每一步的输出都能单独看一眼，中间加一个 `tee` 就能落盘，发现不对随时拆开重来。换成大而全的工具，一步出错只能整个重跑。当然管道也有死穴：处理结构化数据时，逗号分隔的文本会反过来咬人，这种场景就该请出 jq，硬用 awk 解转义是自虐。

管道玩家的基本功里还有一条：排序和比较先设 `LC_ALL=C`。本地化语言环境会让 sort 慢一个量级，还会让字符类匹配的行为变得难以预测。脚本里固定用 C locale，交互终端里保留本地化，这条分界线写进团队规范都不为过。

管道组合还有个隐性收益：每一步都可观测、可中断、可复用。长命令拆成短管道，中间结果随时能看，错了能从半截重来；一次性写成巨型单行命令，调试时只能整条重跑，出了错连现场都没了。写管道时多几个换行和缩进，贴进 README 或 issue 也好看，这个习惯几乎零成本，却能省下最多的人在深夜里对着一行天书发呆。

## 条目二：现代替代品，该换的换，不该换的别跟风

近十年终端工具来了一波换血：ripgrep 替 grep、fd 替 find、bat 替 cat、fzf 替历史命令搜索。我的态度是分开评价：ripgrep 和 fd 无条件推荐，快一个数量级且默认忽略 gitignore，没有任何迁移成本；fzf 强烈推荐，它改变的是交互方式而不是单个命令；bat 看口味，语法着色舒服但脚本里千万别用，它的分页器会把管道卡住。

| 场景 | 经典选择 | 现代选择 | 建议 |
| --- | --- | --- | --- |
| 搜代码 | grep | ripgrep | 换，无痛 |
| 找文件 | find | fd | 换，无痛 |
| 看文件 | cat / less | bat / less | 交互换，脚本不换 |
| 选历史 | Ctrl-R 翻 | fzf | 换，改变交互 |
| 改文本 | sed | sed | 不换，够用 |

跟风换工具的真实成本不在学习，在团队一致性：你的脚本依赖 fd 的某种默认行为，同事的机器上没装，CI 里直接红。所以换工具的红线是：交互层随便换，脚本和 CI 里只用出厂自带的那批。

脚本里换工具的安全姿势是探测加降级：`command -v fd >/dev/null && FD=fd || FD=find`，有就用快的，没有退回标准的。这条写法不优雅，但它让脚本在同事的机器和 CI 镜像上都能跑。工具链的现代化应该发生在你的手指上，不应该成为别人运行你代码的前提，这是交互层和脚本层的根本分界。团队推广新工具时，最好的姿势也不是发通告，而是在评审里自然用出来：你用 ripgrep 三秒定位到问题，同事用 grep 等了二十秒，下一次他会自己来问怎么装。新机器想一步到位，可以照这份清单装：

## 条目三：tmux 会话，断线不丢现场

远程工作的经典悲剧：SSH 上跑着编译，网络抖了一下，连接断了，编译跟着陪葬。tmux 这类终端复用器解决的就是这件事：会话跑在服务器上，你的客户端只是附着上去的一扇窗，窗关了，会话还在。更深一层的价值是工作区：窗口分屏、会话命名、布局保持，让你在任何机器上 SSH 上去都能恢复到熟悉的现场，换电脑、换网络、换城市，现场原样。

- 会话管理
  - `tmux new -s work` 起会话，`tmux attach -t work` 接回去
  - 断线自动重连靠的是会话常驻，与网络无关
- 窗口与分屏
  - 一个窗口一个任务：编辑、跑测试、看日志各占一屏
  - 分屏布局可以保存，重启后一键恢复
- 与编辑器的分工
  - 编辑器处理单文件深度，tmux 处理多任务的广度
  - 两者叠用，中间只需要一个快捷键的距离

### 先学三个快捷键就够

新手最常见的阻力是快捷键，跨平台的机器上尤其劝退。我的建议是先只学三个：新建窗口、切窗口、脱离会话，够用之后再慢慢加。工具是给自己省事的，不是用来考试的。

网络差的场景值得多说一句 mosh：它基于 UDP 做预测回显，弱网下的输入响应比 SSH 顺滑得多，断线重连也更快。但它替代不了 tmux：mosh 解决的是"路上"的体验，tmux 解决的是"现场"的保存，两者叠用才是完整的远程工作流。只装其中一个，都会在某个具体场景里怀念另一个。

> 工具的价值在手指上，不在配置里。装得最多的工具往往是用得最少的，顺手的配置胜过齐全的清单。

参考：[tmux 入门与工作区实践](https://example.com/tmux-workspace)

## 条目四：交互用 zsh，脚本写 sh

一个反复被人讲错的分工：交互 shell 和脚本 shell 应该是两个东西。交互追求响应快、提示信息丰富、补全聪明，zsh 配一套插件是甜点；脚本追求可移植和可预期，写 POSIX sh，在任何 Linux、任何 CI 镜像里都能跑。把 zsh 的语法写进脚本，等于给脚本加了一台服务器没装依赖的风险，而这种风险只在你最不想它出现的时候出现。

```toml
# starship 提示符配置：跨 shell 通用，交互层专属
format = "$directory$git_branch$character"
[directory]
truncation_length = 3
[git_branch]
format = "[$symbol$branch]($style) "
```

配置文件管理只有一条路：进 git。dotfiles 用裸仓库加符号链接，或者chezmoi 这类工具，新机器一条命令还原全套环境。这件事的回报不是"酷"，是重建环境时省下的半天，以及某个凌晨排查时确认"配置和三个月前一致"的安心。配置漂移是隐形故障源，而版本控制是唯一可靠的锚。

配置激进的 zsh 会拖慢每次开终端的速度，插件超过十个就该警惕。自检方法很直接：`time zsh -i -c exit`，超过两百毫秒就值得裁剪。提示符和补全的收益是每次交互都享受到，启动变慢的代价也是每次交互都付一次，后者攒起来比想象中贵。starship 这类外部二进制把逻辑移出 shell 脚本，是目前的性价比解。

参考：[Shell 分工与 dotfiles 管理](https://example.com/shell-dotfiles)
