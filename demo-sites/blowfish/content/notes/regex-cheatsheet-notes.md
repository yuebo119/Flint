正则是一门"每次用都像第一次学"的语言：语法就那么多，但组合出来的写法千变万化，隔三个月不碰就忘光。这篇笔记把常用元素收拢成表，配上两个日常真会写的实战片段，用时直接翻，不用从头推导。全篇按"查表到实战"的顺序组织：先认积木，再看组合，最后是完整片段。每一节都可以单独查，不必从头读到尾。

## 字符与量词

最基础的积木，速查表一张：

| 类别 | 写法 | 含义 |
|------|------|------|
| 通配 | `.` | 任意字符（默认不含换行） |
| 数字 | `\d` `\D` | 数字 / 非数字 |
| 单词 | `\w` `\W` | 字母数字下划线 / 除此之外 |
| 空白 | `\s` `\S` | 空白字符 / 非空白 |
| 字符类 | `[abc]` `[^abc]` `[a-z0-9]` | 枚举 / 排除 / 区间 |
| 量词 | `*` `+` `?` | 零到多 / 一到多 / 零或一 |
| 区间量词 | `{3}` `{2,}` `{1,5}` | 精确 / 至少 / 区间 |
| 选择 | `a\|b` | 匹配左边或右边 |
| 转义 | `\.` `\\` | 匹配字面量 |

量词默认是贪婪的：`<.+>` 配 `<a><b>` 会一口吞成整串，想停在最近处用惰性写法 `<.+?>`。贪婪和惰性是正则最常用的一对开关，拿不准匹配范围时，先问自己"要最近还是要最远"。这张表建议截图存手机，忘了就翻。真正难的不是记住语法，是记住每个元素在边界情况下的行为。

## 分组、锚点与环视

### 命名分组

圆括号把多个字符合成一个整体，也决定捕获内容。现代引擎推荐命名分组，可读性比编号高一截：

```text
(?P<year>\d{4})-(?P<month>\d{2})-(?P<day>\d{2})
```

提取日志字段时，命名分组配 `match.groupdict()` 之类的接口，代码自解释，后人不用数括号猜第几组是什么。非捕获分组 `(?:...)` 只分组不捕获，需要分组但不想占用编号时用它。分组的第二个知识点是编号规则：从左到右按左括号出现顺序编号，命名分组也占编号。混用命名和编号时，非捕获分组能帮你省下被搅乱的编号，它在长正则里的价值比看上去大。

### 环视：只看不吃的断言

环视是正则里最被低估的特性：它在某个位置检查左右文本，但不消耗字符。四种写法各管一段：

```text
(?=...)    正向先行：右边必须跟着
(?!...)    负向先行：右边不能跟着
(?<=...)   正向后行：左边必须是
(?<!...)   负向后行：左边不能是
```

典型用途是"替换掉 X 但保留 Y"：给数字加千分位分隔符，规则是"在数字前插入逗号，条件是左边还有数字"，一行环视搞定，比循环切分干净得多。环视的代价是部分引擎对变长后行支持有限，用之前确认目标引擎的口径。环视写起来最常犯的错是位置感错位：先行断言写在字符后面，检查的是"这个字符之后"，不是"这个字符之前"。第一次用建议拿 `a(?=b)` 这种最小例子试，确认匹配的是 a 而 b 不被消耗，再上复杂规则。

## 实战片段

### 从访问日志提取 IP 与状态码

```bash
# 提取全部出现过的 IP，去重排序
grep -oP '\b(?:\d{1,3}\.){3}\d{1,3}\b' access.log | sort -u

# 统计各状态码出现次数
awk '{print $9}' access.log | sort | uniq -c | sort -rn | head
```

`\b` 是单词边界，防止把 `192.168.1.1000` 这种错值切一段出来。日志格式五花六门，写之前先 `head -1` 看一眼真实字段，别照抄别处的正则，那是正则事故的主要来源。

### 清洗表单输入

```javascript
function normalizePhone(raw) {
  const digits = raw.replace(/\D/g, "");
  if (!/^1[3-9]\d{9}$/.test(digits)) return null;
  return digits;
}
```

先清洗再校验，是表单处理的老顺序：`replace` 去掉所有非数字，`test` 一次性验完整格式。反过来先校验后清洗，边界情况会多一倍。注意校验正则两头的 `^` 和 `$`，少了它们 `1xx...x` 后面跟着垃圾字符也能通过。

表单之外，另一个高频场景是批量重命名和日志脱敏。脱敏的思路固定：先定位敏感模式，再原地替换成掩码，替换时保留长度特征，方便下游按原格式定位问题。写脱敏正则时把测试数据里的边界情况备齐：空串、纯符号、超长串、嵌套引号，这四类不过关，上线就是数据事故。

## 引擎差异：同一套语法，不同的脾气

正则的语法手册基本通用，但引擎实现各有取舍，同一个写法换环境可能变脸。最常踩的几个点：JavaScript 的 `\d` 只认 ASCII，配 `u` 标志也不全认，匹配 Unicode 数字要显式写 `\p{N}` 加 `u`；Python 的 `re` 默认贪婪，部分高级特性要换 `regex` 库；Go 的 `regexp` 用 RE2 语法，干脆不支持回溯，也就没有环视，别问为什么 `(?=...)` 报错；GNU grep 加 `-P` 才是 PCRE，不加就是 POSIX 基本正则，`\d` 直接失效。

结论很直接：写跨环境共用的正则前，先确认目标引擎的脾气。最省事的做法是把正则和目标引擎写进同一条注释，后人换环境时第一眼能看到约束。

## 什么时候该扔掉正则

正则的天花板来得很突然：嵌套结构、需要计数的配对、多行上下文关联，写出来的东西会从工具退化成符文。判断标准也简单：如果一条正则超过一屏，或者需要三番五次试错才匹配对，就该换解析器了。HTML 用 DOM，JSON 用序列化，日志用结构化解析，配置用现成格式库。正则的定位是单行文本的模式匹配，超出这个定位就是用螺丝刀钉钉子，能钉进去，但钉子会弯。

真实的教训来自一次日志清洗：用一条两百字符的正则解析带引号转义的字段，修了六个边界 bug 之后放弃，换成按分隔符逐段扫描的状态机，二十行解决，还能顺手处理转义。有些复杂度不是用来克服的，是用来绕开的。

## 调试与习惯

正则最怕"看起来对，跑起来错"。我的调试流程：先拿最小样本试，再上真实数据。编辑器里按 <kbd>Ctrl</kbd>+<kbd>F</kbd> 打开查找面板，开启正则模式，边写边高亮，比写完再跑脚本快一个量级；需要环视和命名分组时，VS Code 的替换面板还支持 `$1` 引用分组。

几个值得养成的习惯：

- [ ] 复杂正则先拆成命名分组，再拼装，不要一行写到底
- [ ] 贪婪改惰性之前，先想清楚要的是"最近"还是"最远"
- [ ] 给生产代码里的正则配三组测试：正常、边界、恶意输入
- [ ] 复盘一条曾经灾难性回溯的正则，记录嵌套量词的教训

还有一条关于性能：写性能敏感的正则先在小样本上计时。量级差一百倍的两条写法，在大文件上是秒级和毫秒级的差别，值得花十分钟选一条更快的。定稿之后用真实数据跑一遍，比任何基准测试都直接。

嵌套量词是性能深渊：`(a+)+` 这类结构遇到不匹配的长串会指数级回溯，把进程卡死。写到嵌套量词时停下来，改用更精确的字符类，或者拆成两步匹配。维基百科的正则条目有完整语法谱系，地址在 <https://zh.wikipedia.org/wiki/正则表达式>。

## 片段收藏

最后收几条我反复用的小模式，都是改过几版才定型的：

- 去首尾空白：`^\s+|\s+$`，替换为空
- 匹配中英文混合词：`[\u4e00-\u9fa5a-zA-Z0-9]+`
- 邮箱粗校验：`^[^\s@]+@[^\s@]+\.[^\s@]+$`
- URL 取协议：`^(https?)://`

粗校验的意思很明确：挡掉明显乱填的，别指望它替代服务端验证。正则的定位是"快速筛掉大半错误"，不是"保证输入合法"，这个边界想清楚，代码里就少很多过度的复杂度。最后提醒一个维护问题：正则没有类型检查，写错只在运行时暴露。凡是进了代码库的正则，旁边就该有注释说明匹配什么、为什么这么写。三个月后回看，你会感谢当时多打的那几行字。
