## 一、问题定义

幂等性指的是同一个操作执行一次与执行多次，系统状态相同。在理想网络里它无关紧要，
在真实网络里它是刚需，因为重复请求的来源比想象中多：

- **客户端超时重试**：请求已到达服务器并执行成功，但响应在回程丢失，客户端只能重试。
- **消息队列 at-least-once 投递**：主流消息系统保证至少投递一次，重复消费是常态[^1]。
- **定时任务重投**：任务执行时间超过调度间隔，同一任务被多次触发。
- **用户双击与刷新**：提交按钮连点、支付页刷新重放，都会带来等价重复请求。

按操作语义可以把接口分三类：查询类天然幂等；删除与设置类（`DELETE /x`、
`SET k = v`）天然幂等；新增与扣减类（创建订单、扣余额、转账）不幂等，
必须显式设计。出问题的永远是第三类。

## 二、方案枚举

| 方案 | 核心机制 | 一致性保证 | 代价 |
| --- | --- | --- | --- |
| 唯一索引 | 业务唯一键上建数据库唯一约束 | 硬保证，重复插入直接失败 | 只挡得住"落库"这一步 |
| 幂等 token | 先申请 token，提交时携带，服务端去重 | 覆盖"执行前"的并发窗口 | 两阶段交互，客户端改造成本 |
| 状态机 | 只允许合法状态流转，重复流转返回当前态 | 语义级幂等 | 需要把业务流程建模成状态机 |
| 乐观锁 | `UPDATE ... WHERE version = ?`，版本不匹配即拒绝 | 防并发覆盖 | 失败重试由调用方处理 |
| 去重表 | 独立表记录已处理的消息主键 | 通用，跨队列复用 | 额外存储与查询开销 |

## 三、深入分析

### 3.1 唯一索引：最后一道防线

所有幂等方案的终点都是数据库约束，因为它是唯一能在并发下给出硬保证的机制。
先建幂等记录表：

```sql
-- 幂等表：token 上的主键约束是重复请求的最后一道防线
CREATE TABLE idempotency_record (
    token        VARCHAR(64) NOT NULL,
    status       VARCHAR(16) NOT NULL,
    request_hash CHAR(64)    NOT NULL,  -- 防止同一 token 携带不同参数重复提交
    response     JSONB,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (token)
);
```

`request_hash` 常被忽略但没有它，幂等表会允许"同一 token 换了请求体"这种
张冠李戴的攻击面：先故意用错误参数提交占位，再用正确参数提交时被误判为重复。
生产实现里建议 token 与请求内容一起哈希落库。

### 3.2 幂等 token：两段式的工程形态

token 方案把去重前移到业务执行之前，适合创建订单这类副作用重的操作。
一个自洽的服务端骨架：

```java
public class IdempotencyService {
    private final IdempotencyRecordRepository repo; // 落库，唯一索引兜底

    public Order submit(String token, SubmitCommand cmd) {
        // 1. 已处理过：直接返回上次的结果，不再执行业务
        var existing = repo.findByToken(token);
        if (existing.isPresent()) {
            return existing.get().toOrder();
        }
        // 2. 未处理：插入占位记录，唯一索引保证并发下只有一个请求能成功
        try {
            repo.insert(new IdempotencyRecord(token, Status.PROCESSING, hash(cmd)));
        } catch (DuplicateKeyException e) {
            // 3. 抢锁失败说明另一请求正在处理：返回处理中，让客户端轮询结果
            throw new ConcurrentProcessException(token);
        }
        // 4. 执行业务并回填结果，失败时把记录置为失败态允许重试
        Order order = placeOrder(cmd);
        repo.complete(token, order);
        return order;
    }
}
```

这里有两个容易写错的点。其一，占位记录必须先于业务执行插入，否则两个并发请求
都查不到记录、都执行业务，数据库里有两条订单，唯一索引也只能干着急。
其二，业务执行失败后要把记录置为失败态或删除，否则该 token 被永久标记为
"已处理"，用户永远无法用同一 token 重试。

### 3.3 状态机与消息消费

对订单流转这类天然有状态的操作，状态机是最优雅的幂等形式：定义合法迁移表，
任何不在表内的迁移直接拒绝。重复的"支付回调"落到已支付订单上时，
状态机检查发现当前态不接受该事件，返回当前状态即幂等[^2]。

消息消费的幂等分两层。第一层是框架层：给每条消息分配全局唯一 messageId，
消费前查去重表。第二层是业务层：用业务主键（如订单号加操作类型）判重。
两层都要有：框架层挡重复投递，业务层挡"同一业务动作被不同消息触发"。
去重表要配 TTL 或归档策略，按消息最大重试窗口设保留期即可，不必永久保留。

### 3.4 幂等不是设计出来的，是测出来的

幂等方案写在文档里不算数，要用攻击性的测试证明它成立，三类用例必备：

- **并发重放**：同一请求同一时刻打 N 次，验证副作用只有一次。注意用并发而不是
  循环，串行重试会被"第一次已处理"的分支轻松挡住，根本测不到竞态。
- **乱序与延迟**：模拟响应丢失后的延迟重试，间隔从毫秒到分钟多档，
  覆盖占位记录与业务执行之间的所有窗口。
- **故障注入**：业务执行到一半抛异常，验证幂等记录回到可重试态，
  而不是把 token 永久钉死在"处理中"。

压测环境里开着并发重放打写接口，同时观察唯一索引冲突率与重复业务单的比例，
是验收幂等方案最直接的方式。指标定义要提前约定：
"副作用只有一次"对订单是订单表行数，对扣款是流水表金额合计，
写成可查询的断言，而不是"看起来只有一单"。

配套监控同样不能少：DuplicateKey 冲突率、幂等表行数增速、
"同一 token 二次提交返回缓存结果"的命中率。第三个指标尤其有用，
它直接量化客户端重试的规模，重试率持续上升说明网络或客户端库有系统性问题，
该修根因，而不是让幂等层一直兜底。还有一类容易漏测的场景是跨服务：
A 调 B 时 B 的幂等 token 由 A 生成，A 重试是否复用同一 token，
要在联调用例里显式验证，跨服务边界上的 token 传递断裂
是分布式幂等最常见的漏洞。

把这三类用例并进日常回归，成本是一次性的，收益是每次改动幂等逻辑都有安全网。
幂等代码的特点是"平时无感、出事致命"，没有回归用例兜底，
重构时的侥幸心理会把它悄悄改坏。存量接口补幂等时同样先补用例再改实现，
否则"修复"本身可能引入新的重复路径。

> 判断一个接口要不要做幂等，只需问一句：这个请求因为任何原因重来一次，
> 业务能接受吗？不能，就设计幂等；能，就把"为什么不用"写进文档，
> 免得后人反复追问。

## 四、选型建议

1. **查询接口**
   1. 无需任何处理，天然幂等。
   2. 注意分页参数与时区参数固定，避免同一请求两次结果集不同。
2. **下单、支付类写接口**
   1. 上幂等 token，客户端在进入页面时申请，提交时携带。
   2. 服务端幂等表 + 唯一索引兜底，业务失败要允许 token 重新提交。
   3. 对账任务定期比对支付流水与订单状态，作为兜底巡检。
3. **消息消费**
   1. 框架层 messageId 去重，业务层业务主键去重，两层都要。
   2. 消费逻辑先判状态再执行，执行与状态更新在同一事务。
4. **定时任务**
   1. 执行前抢分布式锁，同一实例同一时刻只跑一份。
   2. 任务本身设计成可重入：幂等键用业务日期而非执行次数。

上线前的检查清单：

- [ ] 每个写接口的文档里明确写出幂等键是什么、重复请求返回什么
- [ ] 压测脚本包含"同一请求并发 N 次"场景，验证副作用只有一次
- [ ] 唯一索引的冲突路径有监控：DuplicateKey 突增说明重复请求在变多
- [ ] 幂等表有容量与清理策略，不会无限增长
