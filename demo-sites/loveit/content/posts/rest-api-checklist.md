这份清单来自我们团队三年的 API 评审沉淀，最初是评审时重复说的十句话，后来整理成 checklist，每次新接口评审逐个过。文章按十个分组组织，共五十项，不需要全中，但每一项不过都要能说出理由。使用方法：设计阶段过一遍，评审阶段让另一个人独立过一遍，上线前再过一遍与安全相关的分组。

先说清单的边界：它管的是接口的形状，不管业务对错。业务对不对要靠领域模型和用例评审，形状标不标准直接决定接入方骂不骂人。我们的经验是，形状规范的接口，接入方的提问量会少一半，剩下的问题才真正值得讨论。

![API 评审清单](/images/demo-5.svg)

> 接口是团队对外的承诺。形状不规范的接口，每一次调用都在消耗接入方的信任，而信任的重建比接口重写还慢。

## URL 与资源

REST 风格的核心主张是"用 URL 定位资源，用 HTTP 方法表达动作"，概念背景可以参考 https://zh.wikipedia.org/wiki/表现层状态转换 。我们团队对 REST 的采纳是务实派：核心资源遵循风格，边缘动作允许必要的例外，但不允许"一半 REST 一半 RPC"的混搭，那是最难接入的形态。

- [ ] URL 只使用名词复数，不出现动词：`/orders` 而不是 `/getOrders`
- [ ] 层级表达归属关系，不超过三层：`/orders/{id}/items`
- [ ] 大小写统一用短横线分隔：`/order-items` 而不是 `/orderItems`
- [ ] 查询参数用于过滤和排序，不承载资源身份
- [ ] 批量操作使用子资源：`POST /orders/batch-cancel`

动词进 URL 是新手最常犯的错误，代价是接口语义只能靠文档约定。动作无法用名词表达时（比如审批通过），优先建模为状态转移资源，例如 `POST /orders/{id}/approval`。还有一类隐蔽的违规是把过滤条件拼成路径，比如 `/users/by-phone/138xxxx`，查无此人的 404 和号码格式错误的 400 会缠在一起，放进查询参数就没有这个歧义。

## HTTP 方法语义

- [ ] GET 只读，不产生副作用，可被缓存和重试
- [ ] POST 创建非幂等，重试可能产生重复资源
- [ ] PUT 整体替换且幂等，重复执行结果相同
- [ ] PATCH 局部更新，只提交变化的字段
- [ ] DELETE 幂等，重复删除返回相同状态码
- [ ] 不在 GET 上做写操作，包括"点击计数"这类看似无害的副作用

幂等性值得单独强调：网络超时后客户端一定会重试，非幂等接口每次重试都是一次新副作用。所有支付和下单接口，要么用幂等键，要么用 PUT 语义，没有第三条路。PATCH 和 PUT 的区别在实战里经常被问：判断标准就一句，这次提交的是完整表示还是部分字段。完整表示用 PUT，客户端可以先 GET 再改再 PUT；部分字段用 PATCH，但要注意"把字段显式改成 null"和"不提交这个字段"是两种语义，JSON Merge Patch 和 JSON Patch 对 null 的解释正好相反，接入前先说清楚。

## 状态码

| 场景 | 状态码 | 常见错误 |
| --- | --- | --- |
| 查询成功 | 200 | 全部返回 200，错误也包在 body 里 |
| 创建成功 | 201 | 用 200 且不返回 Location 头 |
| 无 body 的成功 | 204 | 用 200 返回空对象 |
| 参数错误 | 400 | 用 500 掩盖客户端错误 |
| 未认证 | 401 | 和 403 混用 |
| 已认证但无权限 | 403 | 用 401 导致前端反复跳登录 |
| 资源不存在 | 404 | 用 400 或不存在的资源返回 200 加 null |
| 状态冲突 | 409 | 用 400 表达"订单已支付不能取消" |
| 限流 | 429 | 不限流或限流不返回 Retry-After |

状态码里争议最大的是 409 和 422 的分工，我们的约定是：409 表示"资源当前状态不允许这个操作"（订单已支付），422 表示"语义正确但业务校验不过"（优惠券已过期）。两者都表达拒绝，但前者客户端要刷新状态，后者只需要提示用户。另一个常见错误是用 200 加 body 里的错误码表达一切，短期省事，长期所有监控、网关、重试策略全部失效，因为它们都只认状态码。

## 错误格式

- [ ] 错误响应体结构统一，至少包含机器可读的 code 和人类可读的 message
- [ ] 字段级错误指明字段路径：`errors[0].field = "amount"`
- [ ] 不把堆栈、SQL、内部 IP 返回给客户端
- [ ] 错误 code 稳定，不随文案变化

```json
{
  "code": "ORDER_ALREADY_PAID",
  "message": "订单已支付，不能重复支付",
  "trace_id": "3c9a1f0e2d8b47c5",
  "errors": [
    { "field": "payment.no", "message": "支付单号已存在" }
  ]
}
```

错误格式里 trace_id 是最被低估的字段。用户截图投诉时，靠 trace_id 能把一次请求在网关、服务、数据库三层的日志串起来，定位时间从半小时缩到五分钟。约定俗成的做法是响应体返回 trace_id，同时写进响应头，网关侧也记录，三处对齐，任何一方都能发起排查。

## 性能与传输

- [ ] 响应体启用压缩，文本接口 gzip 或 br
- [ ] 支持字段过滤，客户端按需取数：`?fields=id,name,amount`
- [ ] 大列表接口支持批量查询，避免客户端循环调用单条接口
- [ ] 图片等二进制资源走对象存储加 CDN，不进应用服务
- [ ] 长连接场景提供 WebSocket 或 SSE，不用轮询

字段过滤这一项听起来是优化，实际是接口卫生。我们有个详情接口响应体三 KB，移动端只用到两百字节，加了字段过滤之后下行流量降了九成，移动端耗电和用户流量投诉一起解决。

## 版本与兼容

- [ ] 破坏性变更必须发新版本：`/v2/orders`
- [ ] 同一版本内只做增量：加字段可以，删字段不行
- [ ] 废弃字段先标记 deprecated，至少观察两个迭代再移除
- [ ] 响应新增字段不影响老客户端（未知字段忽略）

### 版本兼容的正反例

反例是直接把 `GET /v1/users` 的 `name` 字段拆成 `first_name` 和 `last_name`，老客户端解析直接崩溃；正例是新版响应同时返回 `name`、`first_name`、`last_name` 三个字段，老客户端读 `name`，新客户端读拆分字段，等接入方全部切换后再标记 `name` 废弃。兼容的核心原则只有一个：**任何变更都不允许让老客户端的正常解析失败**，做不到这一点，就必须发新版本。

## 分页与集合

- [ ] 列表接口默认分页，不允许无 limit 的全量返回
- [ ] 页码超界时返回空列表，不返回 404
- [ ] 大数据集使用游标分页：`?cursor=xxx&limit=50`
- [ ] 响应中返回总数或 has_more，让客户端能判断翻页

深翻页是分页方案的隐形炸弹：页码模式在第五十页时要扫描并丢弃前四十九页数据，越往后越慢。我们的对账导出翻到两千页时数据库 CPU 打满，换成游标分页（上一页最后一条的排序值作为下一页起点）之后，任何深度的翻页都是常数时间。另外，导出类需求不要走分页接口循环拉取，提供一个独立的异步导出接口，生成文件后通知下载，对双方都轻松。

## 幂等与重试

- [ ] 所有写接口支持幂等键：`Idempotency-Key` 请求头
- [ ] 相同幂等键的重复请求返回首次结果，不重复执行
- [ ] 幂等键有存储期限，至少覆盖客户端重试窗口

幂等键的实现有个细节：存储介质用 Redis 就够，但 key 的过期时间要大于客户端可能的最长重试窗口，我们取二十四小时。重复请求到达时，如果键已存在且对应请求还在处理中，应该返回"处理中"而不是报错，让客户端继续等。见过太多实现把"重复提交"当错误返回，客户端反而更加疯狂重试，把一次幂等设计做成了放大镜。

## 安全

- [ ] 全链路 HTTPS，HTTP 请求直接重定向或拒绝
- [ ] 认证使用标准方案（OAuth 2.0 / JWT），不自定义 token 格式
- [ ] 授权在服务端逐资源校验，不信任客户端传入的角色字段

### 水平越权与垂直越权

两类越权的测法完全不同，都要有专门用例：

- 水平越权：确认资源归属当前用户
  - `GET /orders/{id}` 要校验订单属于调用者，换别人的 ID 必须返回 404
  - 列表接口默认按调用者过滤，不允许通过参数越出范围
- 垂直越权：管理接口单独授权
  - 管理端点单独路由前缀，中间件里强制校验角色
  - 低权限 token 访问管理端点返回 403，并记录审计日志
- [ ] 响应脱敏：手机号、身份证、邮箱按角色部分掩码
- [ ] 限流按调用方维度，返回 429 和 Retry-After
- [ ] 敏感操作记录审计日志，不含明文凭据
- [ ] 审计日志不可从应用层删除，只追加

安全分组里越权是最容易漏测的一类。功能测试覆盖的是"正常用户能做的事"，越权测的是"用户 A 能不能碰用户 B 的数据"，要靠专门的用例集：同一个 ID 换不同 token 访问、低权限角色访问管理接口、过期 token 访问。我们在 CI 里跑了一组越权用例，每次上线自动执行，拦下过三次回归引入的漏洞。没有自动化用例的团队，至少在上线前手工跑一遍核心接口的四个组合。

## 文档与可观测

- [ ] 提供 OpenAPI 描述文件，随代码同仓库维护
- [ ] 每个接口有可执行的示例请求和响应
- [ ] 结构化日志带 trace_id，串联一次请求的所有环节
- [ ] 核心接口有延迟和错误率的监控看板

## 最后一句话

清单的意义不在于全中，而在于每次不过都能指出是哪一项、为什么不过。评审时最常见的争论是"这个项目很小，要不要全套"，我的答案是：安全和幂等两组不过，其余按量级裁剪。小项目可以没有 OpenAPI，但不能有一个能被遍历的订单接口。
