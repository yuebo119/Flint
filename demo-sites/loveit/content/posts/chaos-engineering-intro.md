2010 年，Netflix 把 Chaos Monkey 开源，随机杀死生产环境的实例，逼着工程师写出真正容错的服务。十几年过去，混沌工程早已不是"随机关服务"的莽勇，而是一门有方法论、有工具链的工程实践，也是 DevOps 体系中专注韧性的一环，背景见[维基百科 DevOps 条目](https://zh.wikipedia.org/wiki/DevOps)。这篇文章讲清楚它的原则、流程和落地方式，并带你完成第一个实验。

> 混沌工程的出发点只有一句话：先假设系统会以某种方式失败，再用实验去验证它是否真的那样失败。没验证过的韧性，只是愿望。

## 混沌工程不是什么

先划清边界，混沌工程不是：

- **不是故障演练的随机化**：实验必须有假设、有观测、有停止条件，不是挑个服务乱搞；
- **不是破坏欲的出口**：不经审批在生产注入故障，是事故，不是实验；
- **不是一次性的活动**：它是持续实践，系统在演进，弱点也在演进。

用一句话概括：**混沌工程是通过受控实验，验证系统在恶劣条件下的行为是否符合预期的方法论**。

## 四条基本原则

1. **稳定状态假设**：先定义"系统正常"长什么样，通常是一组业务指标，比如订单创建成功率不低于 99.9%。没有正常基线，故障下的观测就没有参照。基线的建立本身就有价值：很多团队第一次认真讨论"我们的系统到底怎样算正常"时，才发现彼此的标准并不一致。
2. **真实世界事件**：注入的故障要模仿真实会发生的事：节点宕机、网络分区、依赖超时、磁盘打满，而不是臆想出来的极端场景。先问自己"过去一年真实发生过哪些故障"，从那些开始，别从想象开始。
3. **生产环境优先**：预生产和生产的差异（数据规模、流量模式、依赖行为）足以让结论失效。当然要循序渐进，从预发开始，成熟后再进生产。
4. **最小化爆炸半径**：实验范围可控，随时能停。影响一个可用区的一个服务，而不是半个集群。

## 第一个实验：删除一个 Pod

以最常见的"实例被杀"为例，完整走一遍实验流程。

### 步骤一：定义稳定状态

选定观测指标，明确"多好算好"：

| 指标 | 正常基线 | 实验期间底线 |
| --- | --- | --- |
| 接口成功率 | 99.95% | 不低于 99.5% |
| P99 延迟 | 120 ms | 不超过 400 ms |
| 错误日志速率 | 每分钟 5 条 | 不超过每分钟 50 条 |

### 步骤二：注入故障

用 Chaos Mesh 的 PodChaos 定义实验，指定每隔一段时间杀死一个目标 Pod：

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-failure-web
  namespace: chaos-testing
spec:
  action: pod-failure
  mode: one
  duration: 60s
  selector:
    namespaces:
      - web
    labelSelectors:
      app: web
  scheduler:
    cron: "@every 5m"
```

关键字段：`duration` 控制故障持续时长，`selector` 限定爆炸半径只覆盖 web 命名空间的 app=web，`mode: one` 表示每次只影响一个 Pod。**把作用域写小，是实验安全的第一个保障**。

### 步骤三：观察与回滚

实验期间盯住仪表盘，同时准备好随时中止：

```bash
# 观察 Deployment 的副本状态变化
kubectl -n web get deploy web -w

# 发现指标跌破底线时，立即删除实验对象，故障即停止
kubectl -n chaos-testing delete podchaos pod-failure-web
```

实验结束后务必清理，别让一个 cron 调度的实验在你下班后继续跑。真要中止时正在跑的任务，也可以先暂停再删除，Chaos Mesh 的资源被删掉，注入行为就随之消失。

实验报告的模板可以很简单，四行就够：假设是什么、注入了什么、观测到了什么、结论和行动是什么。把它存档在团队wiki里，半年后回头看，这些记录就是系统的韧性成长曲线，比任何架构文档都更有说服力。

## 常见故障类型目录

实验设计从选故障类型开始。下面这张目录按真实发生频率排列，新手从前往后练：

| 故障类型 | 模拟场景 | 常见工具能力 |
| --- | --- | --- |
| Pod / 实例失败 | 节点重启、进程崩溃 | pod-kill、pod-failure |
| 网络延迟 | 跨境调用、网络拥塞 | 固定或抖动延迟注入 |
| 网络丢包 | 弱网环境、链路故障 | 按比例丢包 |
| 依赖不可用 | 下游超时、返回错误 | 中断指定端点的连接 |
| 时钟偏移 | NTP 故障 | 容器内时间偏移 |
| 资源压力 | CPU 打满、内存耗尽、磁盘写满 | stress 类负载注入 |
| DNS 故障 | 解析失败、解析到错误地址 | 篡改解析结果 |

顺序有讲究：前四类是高频真实故障，工具成熟，结论直接；后三类更极端，但对金融和 IoT 系统是必修课。**不要一上来就玩最花的故障**， Pod 删除都还没验证明白，直接上网络分区，实验基本会以"不知道哪里坏了"收场。

## 游戏日：从单次实验到团队演练

单个工程师跑实验是技术验证，整个团队参与才形成能力。成熟的混沌实践有一种形式叫游戏日（Game Day）：定一个下午，相关团队坐在一起，预设一个故障场景，轮流值班响应，事后一起复盘。游戏日的价值有三层：验证技术假设、锻炼响应流程、把稳定性变成团队共同语言。操作上注意：提前通知范围，准备好随时中止的开关，事后 48 小时内产出书面复盘。把游戏日开成突然袭击，除了制造对立情绪，不会有任何额外收益。中止流程要提前演练成肌肉记忆：facilitator 全程守着终端，任何参与者喊停，第一时间按 <kbd>Ctrl</kbd>+<kbd>C</kbd> 停掉本地循环，紧接着删除实验资源，两步之间不要插入任何"先看看情况"的犹豫。

## 实验设计的常见错误

- **没有假设就注入**：不知道预期行为是什么，实验只会产出一堆图表，产不出结论。
- **一次注入多个故障**：网络延迟加磁盘故障加节点宕机一起上，结果无法归因，违反一次只改一个变量的纪律。
- **忽略下游连锁反应**：杀死服务 A 的 Pod，压力可能转移到服务 B，把 B 也纳入观测，否则你只看到一半现场。
- **只测恢复，不测降级**：服务挂了能自愈值得庆贺，但更应该验证"挂着的时候"用户体验降级是否平滑，比如兜底缓存有没有生效。
- **实验做完不留痕**：不写实验报告的混沌实验，等于没做。报告不需要长，但必须包含假设、观测数据、结论和后续行动四项，否则三个月后没人记得验证过什么。

## 组织落地：从"小白鼠服务"开始

引入混沌工程的现实路径：

1. **选一个非核心、有冗余设计的服务**作为第一个实验对象，团队对它的故障有一定容忍度。
2. **预发环境常态化**：每周自动跑一轮 PodChaos，把结果贴到稳定性看板上，先建立"故障是常态"的文化。
3. **生产实验走评审**：实验方案、回滚预案、观测指标三件套写清楚，值班负责人审批后才执行。
4. **从发现到修复闭环**：实验暴露的每个弱点都进 backlog，有 owner、有期限。只炸不修，团队很快会抵制这件事。更隐蔽的失败模式是"修复了但没人验证"：实验发现的重启恢复慢的问题，改完之后要再跑一次同样的实验确认，否则谁也不知道修复是否真的生效。混沌实验因此天然适合循环：同一实验定期重跑，直到它从"暴露问题"变成"证明韧性"。

## 小结

混沌工程的价值可以用一个类比收尾：消防演习不是盼着火灾，而是确认警报会响、通道能走、人会疏散。**混沌实验就是分布式系统的消防演习**：杀掉一个 Pod，确认控制面会重建、流量会绕开、监控会告警。第一次实验多半会暴露问题，那正是它的目的。建立信心的过程，就是把"我们以为它能容错"变成"我们验证过它真的能容错"。

如果这篇文章只留一条行动建议，那就是这个周末选一个最不关键的服务，写下它的稳定状态假设，删掉它的一个副本，盯着仪表盘看完整个过程。一个小时的实验，比读十篇架构文章更能改变你对自家系统的认知。

最后提醒一句心态：混沌工程不是证明系统完美的方式，而是**系统地发现系统不完美之处的纪律**。实验失败是成功，实验成功也是成功，唯一的失败是从来不实验。带着这个心态开始，第一个实验就不会因为"好像也没出什么问题"而显得白做，它至少证明了一件事：你的系统在这件事上，确实和你想的一样。
