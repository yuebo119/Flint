性能优化的第一原则是**先测量后优化**。没有性能预算与测量基线的优化，多半是自我安慰。本文按加载链路把常见的优化手段串成一本可操作的手册。

## 一、测量：建立性能基线

浏览器提供的三大指标值得每个团队监控：LCP（最大内容绘制）反映加载体验，INP（交互到下一次绘制）反映响应体验，CLS（累积布局偏移）反映视觉稳定性。建议在 CI 里接入实验室测量，在线上接入真实用户监控，两条数据互补。

测量的关键是**分位数**而非平均值：P75 的 LCP 比平均值更能代表用户的真实体验，平均值会被极端样本拖偏。

## 二、网络层：少请求、小请求、早请求

加载速度的上限由网络决定，优化按三个方向展开。

**少请求**：合并小文件、内联关键 CSS、删除未使用依赖。一个常见误区是"按需加载一切"——过度拆包反而让请求瀑布变长。

**小请求**：压缩（gzip/brotli）、图片转 WebP/AVIF、字体子集化。现代构建器可以自动完成大半：

```text
原始 CSS   115 KB
gzip 后     18 KB
brotli 后   14 KB
```

**早请求**：`preconnect` 提前建连第三方域名，`preload` 提前加载关键资源，`prefetch` 空闲时预取下一页。用对提示，白屏时间能明显缩短。

## 三、渲染层：别阻塞主线程

JavaScript 的解析与执行都在主线程，长任务会阻塞交互。三个立竿见影的做法：

1. 脚本加 `defer` 或 `async`，避免阻塞 HTML 解析
2. 长列表虚拟滚动，DOM 节点数量与可见区域挂钩
3. 动画只用 `transform` 与 `opacity`，它们走合成器不触发重排

## 四、缓存层：指纹与协商

静态资源用**内容指纹**命名（如 `style.a1b2c3.css`），配合一年期强缓存——内容变了指纹就变，缓存天然失效。HTML 则用协商缓存，保证入口永远新鲜。这对组合是静态站点性能好的一半原因，另一半是 CDN 边缘节点把字节放到了离用户更近的地方。

## 五、清单

把上述内容压缩成一张检查单：

- [ ] LCP 元素提前（preload 首图、内联关键 CSS）
- [ ] 脚本 defer/async
- [ ] 图片懒加载 + 现代格式
- [ ] 静态资源指纹 + 长缓存
- [ ] CI 接入性能预算

性能优化不是一次性工程，而是预算与监控支撑下的持续过程。预算定了，谁提交让指标劣化谁负责——把性能变成团队的共同语言，才是真正的"优化完成"。

## 六、图片：性能问题的第一大户

多数页面的性能问题是图片撑出来的。优化的次序值得背下来：第一，能不用图就不用图——界面装饰交给 CSS，图标交给字体或内联 SVG；第二，必须用图时选对格式——照片用 WebP 或 AVIF，图形简单时 SVG 的体积与清晰度都完胜位图；第三，尺寸对齐显示区域，一张两百像素宽的缩略图不应该加载两千像素的原图。

懒加载是图片优化的标配，但有两个反直觉的细节。其一，首屏大图**不要**懒加载——它是 LCP 元素，懒加载反而让最大内容绘制变慢，应该用预加载提前。其二，懒加载要预留占位空间，否则图片加载完成后页面布局一跳，CLS 指标立刻劣化。

## 七、字体：被低估的加载大户

自定义字体动辄数百 KB，且会阻塞文本渲染。优化路径有三条：子集化，中文字体尤其重要——全量中文字体动辄几 MB，子集化到常用字加站点专用字后通常能压到十分之一；预加载，字体文件在 CSS 里才被引用，浏览器发现它时往往已经晚了一轮往返；回退策略，用 `font-display: swap` 让系统字体先行、自定义字体加载完再换，代价是一次轻微的样式切换。

## 八、第三方脚本：请保持怀疑

统计、广告、客服、A/B 实验——第三方脚本是页面变慢的头号外部因素，而且它们的性能问题不在你的控制范围。引入任何第三方脚本前先问三个问题：它阻塞主线程吗？它的加载失败会拖垮页面吗（记得加异步与容错）？它的收益真的值这点性能吗？

实践上建议给第三方脚本建一张台账：脚本名、用途、体积、主线程耗时、责任人。每季度审计一次，下线没人认领的脚本——经验表明，总有那么几个是当年"先接上再说"的遗物。

## 九、把性能变成文化

工具与清单都给了，最后回到组织。性能预算要写进需求评审——新功能预期能否在预算内达成，评审时就要有答案；指标看板要对全员可见——看不见的指标等于不存在的指标；性能劣化的回滚机制要演练——知道指标劣化了、能定位到提交、能快速回退，三件事缺一不可。

性能不是发布前的突击作业，而是架构、编码、发布每个环节的日常约束。当团队里人人都能对"这个改动会不会让页面变慢"给出有数据支撑的回答时，性能优化才算真正完成了闭环。
