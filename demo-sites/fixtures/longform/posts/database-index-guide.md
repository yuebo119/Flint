索引是数据库性能的第一杠杆，也是最容易被误用的特性。本文从数据结构讲到实践守则，帮助建立一张完整的索引决策地图。

## 一、原理：为什么是 B+ 树

关系型数据库的主流索引结构是 B+ 树：树高通常只有三到四层，一次查询只需三到四次页读取。相比哈希索引，B+ 树额外支持范围扫描与排序——`WHERE created_at > ?` 与 `ORDER BY` 都能走索引；相比二叉树，它矮胖的形态让每个节点能装下数百个键，磁盘读取次数被压到最低。

叶子节点之间有双向链表串联，这让"扫一个区间"变成顺序读——顺序读在机械盘与固态盘上的差距，远小于随机读。

## 二、复合索引与最左前缀

复合索引的列顺序不是随便排的。索引 `(city, age)` 可以服务：

- `WHERE city = ?`（最左列命中）
- `WHERE city = ? AND age > ?`（两列都命中）
- `WHERE age = ?`（**命中不了**——缺最左列）

这就是最左前缀原则。设计时的经验公式：**等值列放前面，范围列放后面**。因为范围条件之后的列无法继续走索引，把高选择性的等值列提前，索引的过滤效率最高。

## 三、覆盖索引：让查询不回表

如果查询的列全部包含在索引里，数据库可以"只读索引不读表"，即覆盖索引：

```sql
CREATE INDEX idx_city_age_name ON users (city, age, name);

SELECT city, age FROM users WHERE city = '上海';
-- 两列都在索引里 → 覆盖索引，Extra 显示 Using index
```

覆盖索引的收益在大表上非常可观：回表是随机读，覆盖索引把随机读变成顺序读。

## 四、代价：写放大与维护成本

索引不是免费的。每个索引都是一棵需要随写入维护的 B+ 树——写一张五索引的表，等于写六棵树。此外索引占存储，优化器还要为它们付出统计与选择的成本。

实践中常见的误区有两个：一是"给每一列都建索引"，写放大拖垮写入；二是建了索引从不检查使用率——长期零使用的索引应当下线。

## 五、实践守则

把以上内容压缩成五条守则：

1. 按查询设计索引，不是按列设计索引
2. 等值在前、范围在后、覆盖查询的列收尾
3. 上线前用 `EXPLAIN` 验证执行计划
4. 定期审计索引使用率，下线僵尸索引
5. 大表加索引用在线 DDL，避开业务高峰

索引的本质是**用空间和写放大换读性能**。想清楚这个交换是否划算，索引的每一次增删就都有了依据。

## 六、执行计划：看懂数据库在做什么

`EXPLAIN` 是索引调优的起点。执行计划里有几个关键字段值得逐一看懂：访问方式（全表扫描还是索引查找）、扫描行数估算、是否使用覆盖索引、排序是否落在索引上。估算行数与实际行数偏差过大时，通常是统计信息过期——重新收集统计往往比加索引更见效。

读执行计划要警惕两个信号：一是"索引查找"实际扫了大量行——索引选择性差，等于变相全表扫描；二是"使用了索引"但查询依然慢——很可能是回表次数太多，需要检查覆盖性。

## 七、排序与分组的索引利用

`ORDER BY` 与 `GROUP BY` 也能走索引：索引本身有序，若排序键与索引列序一致，数据库可以跳过排序步骤。分页深的场景尤其受益——`ORDER BY id LIMIT 20 OFFSET 100000` 用索引扫到偏移处再取二十行，远快于全表排序后截取。

更优雅的深分页方案是**游标分页**：记住上一页最后一条的排序键，下一页改用 `WHERE id > last_id LIMIT 20`。它不随页码深入而劣化，也是无限滚动的天然实现。

## 八、特殊场景：前缀与表达式

长文本列建索引可以用前缀索引，只取前 N 个字符参与排序——选择足够区分的前缀长度是关键，太短选择率差，太长浪费空间。表达式索引则允许对函数结果建索引，例如对"转小写后的邮箱"建索引，让大小写不敏感的查询走索引。

不过表达式索引要注意维护成本：表达式变了索引就失效，查询写法必须与索引表达式严格一致。这类索引适合"查询模式固定且高频"的场景，不适合泛化使用。

## 九、容量与生命周期管理

索引的存储成本常被低估——一个复合索引的大小可能与主表相当。定期审计的方法并不复杂：从系统视图拉出全部索引的使用计数，对照查询日志逐个确认。零使用的索引先下线观察一个迭代，确认无影响再删除；删除是可逆的，索引定义留着随时能建回来。

最后提醒一句：索引调优没有一劳永逸。查询模式会随业务演化，数据分布会随时间漂移，统计信息需要定期刷新。把执行计划的检查纳入日常发布流程，索引才始终是性能的杠杆而不是负担。
