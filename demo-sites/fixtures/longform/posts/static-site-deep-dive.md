静态站点生成器（Static Site Generator，SSG）是近年来内容型网站的主流选择。它把"内容的编写"与"页面的渲染"分离：作者使用 Markdown 写作，构建器在部署时把内容编译成纯 HTML。本文从架构、管线、模板与性能四个角度，把 SSG 的内部机制讲透。

## 一、整体架构

一个完整的 SSG 由五个子系统组成：配置系统、内容系统、模板系统、资源系统与输出系统。配置系统负责读取站点级的设置——站点标题、基础 URL、菜单、分页尺寸等；内容系统扫描内容目录，把 Markdown 文件连同 front matter 解析成结构化的页面对象；模板系统把页面对象套进布局；资源系统处理 CSS、JavaScript 与图片等静态资产；最后由输出系统把渲染结果写进目标目录，并生成 sitemap 与 RSS 等附属文件。

这五个子系统的边界必须清晰。以内容系统为例，它只负责"内容变成页面对象"，不应该知道模板的存在；模板系统只负责"对象变成 HTML"，不应该回头去读文件。边界一旦模糊，增量构建与缓存就无从谈起。

## 二、构建管线

一次构建的执行顺序大致如下：

1. 加载配置，解析主题与参数的合并关系
2. 扫描内容目录，解析 front matter 与正文
3. 装配页面树：首页、段落列表、单页、分类页、标签页
4. 执行分页切分，生成列表页的第 N 页
5. 渲染每个页面对应的模板
6. 处理静态资源（压缩、指纹、复制）
7. 写出产物，生成 sitemap、RSS、robots.txt

其中第 3 步最容易被低估。页面树决定了"哪些 URL 存在"，而 URL 的存在性直接影响模板里的导航、面包屑与归档逻辑。一个成熟的生成器必须处理大量边界：没有 `_index.md` 的目录要不要生成列表页？分类页的父级是谁？分页后的第 N 页属于哪棵子树？

## 三、模板引擎的取舍

模板引擎是 SSG 的灵魂。Go 的 `text/template` 语法极简但表达力有限；Liquid 语义清晰；Scriban 性能出众且错误信息友好。选择模板引擎时，真正需要权衡的是三点：沙箱安全性、渲染性能与生态兼容。

Scriban 的亮点是"成员访问的空安全"——`page?.params?.title` 这样的链式访问在任意一环为空时安静地返回空值，这恰好契合模板"缺字段就降级渲染"的习性。此外它的解析器把模板编译成抽象语法树，重复渲染同一模板时几乎没有解析开销。

## 四、性能的两条铁律

第一，**解析一次，渲染多次**。模板解析的成本远高于渲染，缓存解析结果是显见的优化。第二，**输出缓冲必须隔离**。渲染子模板时如果不隔离输出缓冲，子模板的产物会污染调用者的缓冲区——这类 bug 的表现是"页面某一段凭空消失"，极难排查。

## 五、小结

静态站点生成器本质上是一个"领域特定的编译器"：源是 Markdown 与配置，目标是 HTML。理解了这一点，很多设计决策就变得自然——为什么要缓存解析树、为什么要做增量构建、为什么要对产物做指纹。工具会过时，但编译思维不会。

## 六、增量的艺术

全量重建在小站点上毫无压力，但当下规模增长到数千页面时，构建时间就会成为迭代速度的瓶颈。增量构建的核心问题是"哪些页面需要重渲染"，它的判断依据是一个依赖闭包：内容文件变了，重渲染该内容对应的页面；主题模板变了，重渲染所有引用该模板的页面；配置变了，几乎一切都要重来。

缓存键的设计因此成了增量构建的关键。一个可靠的缓存键至少要包含三个部分：内容的哈希、模板的哈希、以及渲染所依赖的配置片段的哈希。漏掉任何一环，用户就会遇到"页面明明改了，线上却没变"的灵异现象。反过来，缓存键过于敏感——比如把构建时间戳也算进去——会让缓存完全失效，增量构建退化成全量重建。

另一个容易被忽略的点是**写出的原子性**。构建进程在写文件的过程中被中断，会留下半截的 HTML；如果部署系统恰好在这时同步产物，半截文件就会上线。解决方案是先写到临时目录，全部成功后再原子地替换正式目录——两分钟的成本，换来的却是发布过程的崩溃安全。

## 七、错误处理的哲学

生成器面对内容错误有两种态度：硬失败与软降级。硬失败（构建直接退出）适合语法错误——模板写错了必须修；软降级（跳过该页并记录诊断）适合内容缺字段——某篇文章少了日期，不应该让整站无法构建。

关键在于两种态度的边界要清晰，而且诊断信息要**带位置**：文件名、行号、列号，一个都不能少。"渲染失败"四个字不带位置信息，对作者是纯粹的折磨。

## 八、结语与延伸

把静态站点生成器当作一个编译器来理解，很多问题就有了框架：前端是内容解析，中端是页面装配与依赖分析，后端是渲染与写出。编译器领域的经典方案——缓存、增量、依赖图、原子写出——在这里全部适用。读懂了这条主线，再去比较具体的生成器产品，就能一眼看出各自在哪些环节做了取舍。
