## 一、问题定义

缓存是读多写少系统里最常用的加速手段：一次热点查询的耗时从数据库的十几毫秒压到缓存的零点儿毫秒，
代价是同一份数据在系统里有了两个副本。缓存一致性讨论的就是这两个副本在有限时间内不一致时，
系统行为是否可接受、以谁为准。

这里要把三个常被混为一谈的问题分开：

- **缓存穿透**：查询根本不存在的数据，缓存永不命中，请求每次都打到数据库。
- **缓存击穿**：某个热点 key 在过期瞬间失效，并发请求同时回源数据库。
- **缓存雪崩**：大批 key 同时过期或缓存服务整体故障，数据库压力陡增。

穿透、击穿、雪崩本质是可用性问题，可以用空值缓存、互斥锁、随机过期时间与熔断降级来解决。
本文讨论的是更棘手的**一致性问题**：写操作之后，缓存与数据库何时一致、以谁为准、
并发写入下会不会出现旧值覆盖新值并无限期残留。

一致性的第一刀切在更新策略上。写库之后有两种善后方式：**删除缓存**还是**更新缓存**。
删除是懒加载语义，下次读自然回源，实现简单；更新是 eager 语义，写多读少时省一次回源，
但多个并发写之间的覆盖顺序需要额外处理。第二刀切在时序上：先写库还是先动缓存，
两步操作之间存在一个无法彻底消除的竞态窗口，单机锁关不掉它，只能靠取舍缩短。

## 二、方案枚举

| 方案 | 读路径 | 写路径 | 一致性强度 | 适用场景 |
| --- | --- | --- | --- | --- |
| Cache Aside | 先读缓存，未命中回源并回填 | 先更新数据库，再删缓存 | 最终一致，毫秒级窗口 | 绝大多数读多写少业务 |
| Read-Through | 缓存自行回源，对应用户透明 | 同 Cache Aside | 与 Cache Aside 等价 | 缓存客户端封装完善的场景 |
| Write-Through | 直接读缓存 | 同步写缓存，由缓存同步写库 | 强一致，写入延迟翻倍 | 读远多于写、容忍写变慢 |
| Write-Behind | 直接读缓存 | 先写缓存，异步批量刷库 | 弱一致，丢失风险以秒计 | 计数、日志类可容忍丢失的写 |
| 延迟双删 | 同 Cache Aside | 更新前后各删一次，间隔数百毫秒 | 最终一致，窗口更短 | 对旧值敏感的核心链路 |
| binlog 订阅 | 同 Cache Aside | 解析数据库 binlog 异步删缓存 | 最终一致，与业务代码解耦 | 多缓存副本、多业务方共享数据 |

## 三、深入分析

### 3.1 Cache Aside 的竞态窗口

最经典的组合是"先更新数据库，再删除缓存"。它在单线程下完全正确，但在并发读写下有一个
明确的污染窗口：读线程未命中缓存、从数据库读到旧值之后、写线程的删除动作执行之前，
读线程把旧值回填进了缓存；随后写线程的删除落在一个已经被重新写入旧值的 key 上，
而后续所有读都会命中这个旧值，直到 TTL 到期。

按时间顺序拆开这个坏情况：

1. 读线程 `GET user:42`，缓存未命中，准备回源数据库。
2. 读线程 `SELECT` 到旧值（写事务尚未提交或尚未执行）。
3. 写线程 `UPDATE users SET name = 新值 WHERE id = 42`，数据库变为新值。
4. 写线程 `DEL user:42` 执行，但此刻缓存里根本没有这个 key，删除是空操作。
5. 读线程 `SET user:42 旧值 TTL 600`，旧值从此无限期残留。

用一段伪代码对照这个时序：

```python
def write_aside(user_id, new_name):
    db.execute("UPDATE users SET name = ? WHERE id = ?", new_name, user_id)
    # 步骤 3 与步骤 4 之间存在窗口
    cache.delete("user:" + str(user_id))

def read_aside(user_id):
    name = cache.get("user:" + str(user_id))
    if name is None:
        # 步骤 1 未命中，步骤 2 读到旧值
        row = db.query_one("SELECT name FROM users WHERE id = ?", user_id)
        cache.set("user:" + str(user_id), row.name, ttl=600)  # 步骤 5 回填旧值
        return row.name
    return name
```

如果换成"先删缓存，再更新数据库"，窗口换成另一种形态：删除之后、更新完成之前，
另一个读线程可能把数据库里的旧值回填。两个方向都有关不掉的窗口，这就是在分布式环境下
协调两个副本的固有代价，任何方案只是把窗口从毫秒压到亚毫秒，或者把一致性责任转移给
另一个组件。

定位残留旧值可以直接比对数据库与缓存的最新更新时间：

```sql
-- 找出最近五分钟内被更新过的行，用于和缓存逐条比对
SELECT id, name, updated_at
FROM users
WHERE updated_at > NOW() - INTERVAL '5 minutes'
ORDER BY updated_at DESC
LIMIT 20;
```

### 3.2 延迟双删与 binlog 订阅

延迟双删是对窗口的工程妥协：更新前先删一次缓存，执行业务事务，间隔一个主从同步加
一次读回填的时间（通常 200 毫秒到 1 秒）之后再删一次。第二次删除兜住的是
"第一次删除后被回填的旧值"。它的代价是写请求的尾延迟变长，且间隔时间只能凭经验设定，
主从延迟抖动时会漏删。

binlog 订阅把删缓存从业务代码里拿走：业务只管写库，由 canal 之类的变更数据捕获组件
订阅 binlog，按表名与主键解析出要删除的 key 异步执行。好处是彻底解耦，多个缓存实例、
多个下游业务方可以复用同一路删除流；代价是引入新组件与运维面，删除延迟从毫秒变成
百毫秒级，且 binlog 乱序到达时需要按主键加版本号去重。

### 3.3 一致性级别要匹配业务容忍度

> 工程经验法则：先问业务"旧数据展示几秒能不能接受"，再决定花多大力气治一致性。
> 对余额、库存这类数据，用户对刚操作完还显示旧值的容忍度极低，应走强一致或短窗口方案；
> 对昵称、简介这类数据，几十秒的陈旧完全无感，Cache Aside 就足够了。

按写操作的业务语义分三档投入：

- **可丢失档**（计数、日志流）：Write-Behind 批量刷库，写入性能最好。
- **最终一致档**（商品信息、文章列表）：Cache Aside 起步，必要时上延迟双删。
- **强一致档**（库存扣减、账户余额）：跳过缓存直写数据库，或用分布式锁把同一 key 的
  读写串行化。

### 3.4 配套治理：穿透、击穿与雪崩

一致性方案之外，问题定义里提到的三个可用性问题也要一并治理，否则一致性讨论
失去落地的地基。标准处置如下：

- **穿透**：查询不存在的数据，缓存永不命中。布隆过滤器前置拦截是最常见做法，
  可能存在的 key 集合布隆化，不命中直接返回；空值也值得缓存，与正常值一样
  存一个短 TTL（三十秒以内），防止恶意随机 key 持续打穿。
- **击穿**：热点 key 过期瞬间并发回源。回源路径加互斥锁，同一 key 只放一个线程
  查数据库，其余等待；逻辑过期是另一种思路，物理 TTL 设长、逻辑字段控制过期，
  由后台线程异步重建，读路径永不阻塞。
- **雪崩**：批量过期或缓存整体故障。过期时间加随机抖动，把集中过期打散；
  缓存故障时打开熔断降级，限流后直连数据库，同时预热关键 key。
  本地缓存加分布式缓存的多级结构，能在分布式缓存故障时扛住一部分流量。

这三个问题与一致性方案共享同一套观测面：回源率、命中率、删除延迟、
旧值残留时长，四个指标放进同一个仪表盘，出问题按序排查，
而不是每个方案各配一套监控。实际落地时它们也彼此牵连：
空值缓存挡住穿透的同时，让"数据从无到有"的可见性延迟了一个 TTL；
互斥锁防住击穿，却让缓存故障时的读延迟变长。
分开归因的能力，本身就是一致性治理的一部分。

## 四、选型建议

按下面的清单逐项核对，多数系统会停在第二、三项：

- [ ] 统计写请求占比：低于百分之五才值得引入缓存一致性方案，高于这个比例应先优化
      数据库本身（索引、分区、读写分离）
- [ ] 找出最不能容忍旧数据的三个业务字段，对这些 key 单独使用短 TTL 或订阅删除
- [ ] 确认删除失败的可观测性：缓存删除失败必须有日志与告警，静默失败的一致性方案
      等于没有
- [ ] 压测竞态窗口：用并发读写脚本实测旧值残留时长，而不是靠读代码推断
- [ ] 排查页面显示旧值时，先分清是浏览器缓存还是服务端缓存，按 <kbd>Ctrl</kbd>+<kbd>F5</kbd>
      强刷只影响前者，后者要用接口比对工具确认

对中小团队，建议从 Cache Aside 起步，把 TTL 从 600 秒压到 60 秒，用监控观察回源率与
旧值投诉，投诉出现之后再引入延迟双删或 binlog 订阅。一致性方案是逐代升级的，
不是一次选型的终点。
