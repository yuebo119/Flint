大促前的压测报告出来那天，我们服务的 P99 从 40 毫秒涨到 2.3 秒，错误率 12%。根因不是某个接口慢，而是一个非核心的推荐查询把线程池占满，拖垮了核心的下单链路。修复方案是三板斧：限流挡住超额流量，熔断切断故障依赖，降级在压力下保住核心功能。这篇文章把整个过程写成教程，算法、代码、配置、检查清单都在，可以直接套用。先交代故障的完整经过：推荐服务本身没挂，只是它的下游特征服务超时，把推荐服务的线程池占满，推荐服务的响应从 50 毫秒变成 30 秒，而首页把推荐模块放在首屏同步位置上，于是整个首页被拖住，流量顺着首页涌进订单服务，把共用的数据库连接池耗尽。一个边缘模块的抖动，六步传导成核心链路故障。事后我们画传导链图贴在办公室墙上，每个环节都问一句"这里能不能断"，断的地方就是三板斧要落的位置。

## 第一层：限流

限流的本质是承认系统容量有上限，超过上限的请求快速失败比排队等死更体面。四种最常用的算法先做对比，其中令牌桶和漏桶的概念背景可以参考 https://zh.wikipedia.org/wiki/令牌桶 ：

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定窗口计数 | 每秒计数，超限拒绝 | 实现最简单 | 窗口边界可能两倍突发 |
| 滑动窗口 | 细分小格滚动统计 | 边界平滑 | 需要存多个计数点 |
| 漏桶 | 恒定速率流出，桶满丢弃 | 输出绝对平滑 | 无法应对合理突发 |
| 令牌桶 | 恒定速率放令牌，有令牌才放行 | 允许突发，业界主流 | 参数需要调 |

生产环境默认选令牌桶：平时按速率放行，空闲时积攒的令牌允许一定突发，这符合真实流量的形态。下面用 Go 的 `golang.org/x/time/rate` 实现一个按用户维度的限流中间件，注意 key 要带上调用方身份，全局限流会误伤大客户。

```go
func RateLimit(limiter *rate.Limiter) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 按用户限流，未登录请求按 IP 限流
        key := c.GetString("user_id")
        if key == "" {
            key = c.ClientIP()
        }
        if !userLimiters.Allow(key, limiter) {
            c.Header("Retry-After", "1")
            c.AbortWithStatusJSON(http.StatusTooManyRequests, gin.H{
                "code":    "RATE_LIMITED",
                "message": "请求过于频繁，请稍后重试",
            })
            return
        }
        c.Next()
    }
}
```

### 单机限流与分布式限流

单机限流只保护单实例，集群部署时限流阈值要除以实例数，弹性伸缩时实例数变化会让阈值漂移。更稳的做法是用 Redis 做分布式限流：令牌数和上次补充时间戳存在一个哈希键里，所有实例认同同一个数。核心是用一段 Lua 脚本把"取令牌"和"扣令牌"合成一次原子执行，脚本里先按时间差补充令牌，再判断是否放行，两个步骤之间不允许插入其他实例的请求。这样既避免了竞态，也把每次判定压成一次 Redis 往返，百万 QPS 的判定开销也在可接受范围。脚本本身不复杂，任何一家公司的中间件团队都写过，真正要小心的是 Redis 故障时的降级：连不上时退回单机限流，不要直接放行。

## 第二层：熔断

限流保护自己不被打垮，熔断保护自己不被依赖拖垮。熔断器是一个三态状态机：关闭态正常放行，统计错误率；错误率超过阈值进入打开态，请求直接失败不再调用依赖；打开态持续一段时间后进入半开态，放少量探测请求，成功则回到关闭态，失败则重新打开。

```go
type CircuitBreaker struct {
    mu           sync.Mutex
    state        State          // Closed / Open / HalfOpen
    failures     int
    successes    int
    openedAt     time.Time
    maxFailures  int            // 打开阈值
    resetTimeout time.Duration  // 打开态持续时间
    halfOpenMax  int            // 半开态探测请求数
}

func (cb *CircuitBreaker) Allow() bool {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    switch cb.state {
    case Open:
        if time.Since(cb.openedAt) > cb.resetTimeout {
            cb.state, cb.successes = HalfOpen, 0 // 进入半开态探测
            return true
        }
        return false
    case HalfOpen:
        return cb.successes < cb.halfOpenMax
    default:
        return true
    }
}
```

三个参数的经验值：打开阈值按 10 秒窗口内错误率超过 50% 且样本不少于 20 次；打开持续 5 到 30 秒，太短起不到保护，太长恢复太慢；半开探测请求 3 到 5 个，用真实流量的自然到达，不要主动加压。

### 熔断与重试必须一起设计

熔断和重试是一对必须一起设计的组合，很多故障是它们打架打出来的。熔断打开时，客户端的重试逻辑如果还在按固定间隔重试，等于用重试流量持续敲打一个已知故障的依赖，半开态的探测请求也会被自己的重试污染，永远测不出真实恢复。正确的组合是：熔断器感知重试，打开态下重试直接快速失败；重试次数不超过两次，且间隔指数退避加随机抖动；探测请求走单独的标记，不计入重试统计。我们把这条写进了接入规范，新依赖不按这个来不许上线。

## 第三层：降级

限流和熔断都是"拒绝"，降级是"给个次优答案"。降级要提前设计，按核心程度把功能分成三档。

> 降级不是认输，是把有限的容量留给还在为用户创造价值的路径。全都想保住的结果，往往是全都保不住。

- 核心链路（下单、支付）：不降级，只限流，容量优先供给
  - 容量不足时排队异步化，例如下单转"排队中"状态
- 重要功能（库存展示、优惠计算）：可降级为简化版
  - 实时库存降级为缓存值，页面标注"数据可能有延迟"
- 辅助功能（推荐、排行、足迹）：压力下直接关闭
  - 返回空列表或静态兜底数据，前端不报错

降级开关的粒度要到功能点，不要到服务。整个服务一个开关，要么全开要么全关，实际需要的是"关掉推荐但保留搜索"这种细粒度。我们的配置按功能点组织，每个开关有负责人、生效范围（按用户 ID 灰度百分比）和预期影响说明，配置中心里一页能看全。灰度放量时先 1% 观察五分钟，核心指标无劣化再逐档放大，这个节奏是多次半夜回滚换来的。

```yaml
guard:
  rate-limit:
    default:
      qps: 2000            # 全局限流阈值
      burst: 500           # 允许的瞬时突发
    by-user:
      qps: 50              # 单用户每秒请求数
      burst: 20
  circuit-breaker:
    inventory-service:    # 按依赖配置
      max-fail-ratio: 0.5
      min-samples: 20
      window: 10s
      open-duration: 10s
      half-open-requests: 5
  degrade:
    switch:
      recommendation: false   # false = 关闭推荐模块（降级生效）
      realtime-stock: false   # false = 库存改读缓存
    fallback:
      recommendation: "static://homepage-popular.json"
```

配置通过配置中心热更新，开关生效不重启。灰度时先开 10% 流量观察五分钟，确认核心指标无劣化再全量。

## 压测验证：不测的防护等于没有

防护上线前必须压测，标准有三个：限流阈值触发时错误率平稳而不是雪崩；熔断打开后依赖恢复能在 30 秒内自愈；降级开关生效后核心接口 P99 无变化。压测时观察错误类型分布，如果大量请求返回 500 而不是 429，说明限流中间件位置不对，排在业务逻辑之后了。

还有一步常被跳过：验证防护本身是有效的。做法是把依赖服务的响应时间人为改慢（比如在测试环境注入三秒延迟），看熔断是否按预期打开、限流是否按预期触发。如果注入故障后防护毫无反应，说明阈值配置、采样窗口或统计代码有 bug，此时的"压测通过"只是没测到坏情况。没验证过能失败的防护，等于没验证过。

## 上线前检查清单

- [ ] 每个外部依赖都有熔断配置，包括数据库连接池和缓存
- [ ] 限流 key 包含调用方身份，不只有全局限流
- [ ] 429 响应带 Retry-After 头，客户端能退避重试
- [ ] 降级开关接入配置中心，能分钟级生效
- [ ] 核心指标接入监控：限流触发次数、熔断状态变化、降级开关状态
- [ ] 压测报告归档，标注当时的容量水位，作为下次扩容依据
- [ ] 应急回滚方案明确：防护配置本身出问题时，如何一键关闭全部防护

防护体系的价值不在日常，而在那个"推荐服务挂了"的凌晨。真出事时，按 <kbd>Ctrl</kbd>+<kbd>C</kbd> 停掉压测流量，切换降级开关，核心链路保住，然后慢慢排查。这个顺序不能反。

最后提醒一个反直觉的点：防护配置本身也是代码，也要评审、要测试、要灰度。我们吃过一次亏，某个限流阈值改错一位数，把正常流量挡掉三成，比它防的故障还严重。现在所有防护配置的变更走和代码一样的流程，配置中心里有变更记录和回滚按钮。防护是系统的一部分，不是系统的补丁，用对待补丁的心态对待它，它就会在关键时刻给你补一刀。
