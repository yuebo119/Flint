这个案例来自一个六人后端团队，维护着三套 Kubernetes 环境和一个边缘节点集群。迁移前他们用 Jenkins 跑部署脚本，迁移到 GitOps 半年后，部署频率从每周两次变成每天十几次，回滚时间从四十分钟降到四十秒。这篇文章讲清楚他们做了什么、卡在哪里、哪些做法值得抄。

## 起点：脚本部署的三个顽疾

迁移前的部署流程是：开发合并代码，CI 构建镜像，然后运维在 Jenkins 上点一个带参数的构建，脚本 ssh 到目标集群执行 kubectl apply。三个问题反复出现：

> 当生产环境的每一次变更都能在 Git 历史里找到对应提交，值班的人才能睡得着。迁移前，这个团队没人能回答"线上现在跑的是哪个版本"。

1. **环境漂移**：有人在集群里直接改过配置救火，没人记得改了什么。下次 apply 时，改动被静默覆盖，或者更糟，被合并进一套谁都不认识的最终状态。
2. **权限黑洞**：Jenkins 上存着一份能操作所有环境的 kubeconfig，谁能点构建谁就有全部权限，审计只能看 Jenkins 的构建日志。
3. **回滚靠记忆**：回滚意味着"找到上次构建，再点一次"，点错构建号的事情每个季度都发生。

## 方案选型：从推送到拉取

团队对比过两种路线，结论很明确：

| 维度 | 推送式（CI 直接 apply） | 拉取式（GitOps） |
| --- | --- | --- |
| 凭证位置 | CI 平台持有集群凭证 | 集群内 agent 持有，按命名空间隔离 |
| 期望状态 | 脚本里描述过程 | Git 仓库描述结果 |
| 漂移检测 | 无，覆盖了才发现 | 持续比对，自动修复或告警 |
| 回滚 | 找旧版本重跑 | git revert，一次提交 |
| 审计 | 构建日志 | Git 提交历史 |

拉取式的核心优势不是自动化程度更高，而是**集群的期望状态有了唯一可信来源**。CI 只负责构建镜像，部署的全部事实都收敛到 Git 历史里，审查一次合并请求就等于审查一次发布。另一个容易被忽略的好处是网络边界：CI 平台不再需要直达生产集群的网络通道和凭证，集群内的 agent 主动外连 Git 仓库即可，生产网络的暴露面小了一圈，这对过等保的团队是实打实的加分。

## 落地过程

### 仓库结构：一个仓库，两个目录

团队没有搞多仓库，用单个配置仓库，按环境分目录：

```yaml
# clusters/prod/apps/web.yaml（Application 清单示例）
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: web-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: overlays/prod/web
  destination:
    server: https://kubernetes.default.svc
    namespace: web
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

镜像版本不在 Git 里硬编码，而是由 CI 更新镜像 tag 后自动提交一个 PR，合并即发布。这个细节让 GitOps 形成了闭环：**CI 产出制品，Git 记录期望，集群对齐 Git**。

### 部署流程：一条命令都不剩

```bash
# 迁移前：运维手工执行
ssh prod-bastion "kubectl -n web set image deploy/web web=registry.example.com/web:1.8.3"

# 迁移后：CI 自动提交，人类只做合并
git checkout -b release-web-1.8.3
yq -i '.images.web.tag = "1.8.3"' overlays/prod/web/kustomization.yaml
git commit -am "release: web 1.8.3"
gh pr create --fill
```

镜像 tag 的更新由 CI 在构建成功后自动提交，开发者不碰这行代码，运维也不再登录任何机器。半年下来，团队里再没有人记得上一次手工 kubectl 是哪年的事，这本身就是流程已经改变的证据。

### 密钥：不进 Git，也不进 CI

明文密钥进 Git 是红线。团队用 Sealed Secrets：公钥加密的密文可以安全提交，私钥只存在于集群内。数据库轮换密码的流程也顺势规范化了，因为改密等于改 Git 里的一份密文，有历史、有审查。

<details>
<summary>迁移期的兜底方案：双轨运行两周</summary>

切换不是一刀切。前两周新旧流程并行：Argo CD 负责同步，Jenkins 的部署脚本保留但只做只读校验。任何一边发现不一致就停下排查。兜底期的成本是每天多花半小时比对，但它让团队确认了"Git 状态等于集群状态"这个前提真的成立，而不是假设成立。

</details>

## 迁移前的评估清单

动手之前，团队先花了三周做评估，列出的问题后来被证明每一个都踩在了点上：

- **应用是否满足声明式部署的前提**：镜像 tag 固定、无状态、配置外置。有应用还在用启动脚本动态拼参数，这类要先改造再迁移。
- **谁来拥有这个仓库**：GitOps 仓库是新的基础设施资产，必须有 owner、有评审规则、有备份策略，不能是某个人的私人项目。
- **哪些环境先搬**：团队把顺序定为预发、边缘节点、最后生产，每一步跑满两周才进下一步。
- **失败预案**：Argo CD 整体不可用时，是否有手工 apply 的兜底通道？预案每季度演练一次。

这份清单没有标准答案，但"先评估再动手"和"逐步迁移"两条，帮团队避开了大多数团队第一次上 GitOps 就全量切换的莽撞。

还有一件事发生在流程之外，却决定了 GitOps 的成色：**权限与协作规范**。仓库设为保护分支，生产目录只允许两个人合并，所有变更必须走合并请求并至少一人评审。规则刚执行时有人抱怨"应急时候来不及"，团队为此开了应急通道：紧急变更可以事后补审，但必须在变更记录里标注原因，每周复盘时过一遍。有了例外机制，规则才不会在一周内被架空。

## 遇到的三个坑

- **自动同步的爆炸半径**：开启 `selfHeal` 后，一次误删 Namespace 导致 Argo CD 把整套环境重新创建了一遍。教训是自动同步按环境分级，生产保留人工确认的同步窗口，预发全自动。
- **PR 洪水**：镜像 tag 每次更新都提 PR，高峰期一天上百个。后来改成高频业务镜像自动合并、基础设施镜像人工确认，并用标签过滤把噪声降下来。
- **大仓库的性能**：Application 数量过百之后，Argo CD 的刷新延迟明显变长。最终按团队拆了 Application 集合，用 ApplicationSet 批量生成，控制器压力才降下来。

## 半年后的数据

| 指标 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 部署频率 | 每周 2 次 | 每个工作日 13 次 |
| 变更前置时间 | 3 天 | 47 分钟 |
| 回滚耗时 | 40 分钟 | 40 秒 |
| 环境漂移事件 | 每月 2 到 3 起 | 0 起 |
| 未经审查的生产变更 | 无法统计 | 0 次 |

最后一行比前四行加起来更重要。当"改生产"必须走一次可审查的合并请求，发布就从一项需要勇气的手艺变成了一条可追溯的记录。

## 多集群与灾难恢复：Git 仓库的隐藏红利

迁移半年后，团队才发现这项投资最大的回报不在日常发布，而在灾难恢复。一次区域故障后，他们要在新集群上恢复全部业务：因为所有期望状态都在 Git 里，流程变成了在新集群装好 agent、指向同一个仓库、等同步完成，整个过程四十分钟，且每个应用的状态都是可信的，不需要从备份里猜"生产当时到底是什么配置"。这件事彻底改变了团队对备份的理解：**Git 仓库就是配置的权威备份，集群本身反而是可丢弃的**。配套动作是把 Git 仓库本身也纳入备份和容灾，毕竟现在它成了单点。

## 经验总结

回头看，真正起作用的不是 Argo CD 本身，而是三条约束的确立：**集群状态以 Git 为准、人类只通过合并请求变更生产、CI 只构建不部署**。工具可以换成 Flux 或其他方案，这三条不变，收益就在。反过来，如果只是把 Argo CD 装上、同步策略却留着半自动，漂移和权限问题一个都少不了。

如果只给想借鉴的团队一条建议，我会说：**先想清楚你要用 Git 历史换什么**。换发布可追溯性、换回滚速度、换新人上手时"看仓库就知道系统长什么样"的透明，这三样都值回票价；如果只是想"把部署自动化一点"，那 Jenkins 流水线加几行脚本就能做到，不必请一尊需要长期维护的大佛。

还有一条经验关于节奏：**不要在一个月内同时引入 GitOps 和新的应用架构**。团队最初差点同时做两件事，把单体拆成微服务和切换部署方式放在同一个迭代里，幸亏及时拆开。变更叠加时，出问题分不清是架构不适配还是流程没走对，排查成本指数上升。一次只引入一种不确定性，是这场迁移能平稳落地的真正原因。
