两年前，我们决定把一套运行六年的单体 React 应用拆成微前端。动机很典型：三个团队共用一个仓库，发版互相阻塞；一次全量构建要二十多分钟；想试新框架，又不敢动存量代码。两年后回看，微前端确实解决了发版耦合，但代价比预期高，而且有两条弯路本来不必走。这篇复盘把方案对比、真实成本和教训都摊开讲。

## 先问要不要，再问怎么拆

复盘的第一条结论是流程性的：我们花了两个月做技术方案，却没花时间论证"要不要做"。微前端解决的是组织问题（团队自治、独立部署），不是技术问题。判断标准其实很朴素：

- 三个以上团队长期共改一个前端，发版需要互相等；
- 有明确的渐进迁移诉求，新框架要和老系统并存一年以上；
- 有专门的平台团队兜底（监控、构建、公共库、兜底页）。

三条都不满足，单体加好的模块边界就够了。我们当时只满足前两条，平台能力是边做边补的，这直接导致了后面一半的坑。

## 三种方案的对比与选择

主流的微前端方案分三类，我们都试过。

**iframe 方案**：每个子应用一个 iframe，天然的应用级隔离，JS 沙箱、样式隔离、路由隔离全都免费。问题在体验：弹窗画不出 iframe、滚动条断裂、全局加载态要逐层传递、通信只能靠 postMessage，路由状态同步能把人逼疯。我们用它嵌入了两个完全独立的第三方运营页，仅此而已，核心链路坚决不用。

**运行时集成**（以 qiankun 为代表）：主应用在浏览器里动态加载子应用，用 JS 沙箱（快照或 Proxy 劫持全局变量）隔离副作用，用样式加卸载机制防止 CSS 互相污染。接入成本低，存量应用改造成本小，是我们采用时间最长的方案。

**Module Federation**：构建期共享模块，运行时按需加载远程模块，可以做组件级共享而不必整页嵌入。粒度最细，但版本协调成本最高，一个公共库版本不一致就能引发连环故障。

| 维度 | iframe | 运行时集成 | Module Federation |
| --- | --- | --- | --- |
| 隔离强度 | 最强 | 中（JS 可隔离，DOM 不隔离） | 弱 |
| 用户体验 | 差 | 好 | 最好 |
| 接入成本 | 低 | 中 | 高 |
| 版本管理 | 独立 | 松耦合 | 强耦合 |
| 适用场景 | 第三方嵌入 | 整页级微前端 | 组件级共享 |

最终形态是混合的：核心业务用运行时集成做整页拆分，跨应用共享的登录态和埋点 SDK 用 Module Federation 共享，第三方页面用 iframe。这个组合本身没问题，问题是三条链路各有一套构建和部署，平台复杂度是单方案的三倍。

## 踩过的坑：隔离是有价格的

**JS 沙箱不是免费的**。运行时集成靠劫持全局变量（window 上的赋值、事件监听）做沙箱，Proxy 方案的兼容性尚可，但每个子应用运行时都有固定开销，且某些库直接在 window 上挂全局对象（尤其是统计脚本和地图 SDK），沙箱拦不住，多应用共存时互相覆盖。我们的解法是约定：全局命名空间统一走主应用分发的命名对象，第三方脚本由主应用统一加载，子应用不直接引入。

**样式隔离比想象的脆**。运行时方案一般用"子应用加载时注入 scope 选择器"的方式隔离，但子应用里直接操作 `document.body.style`、或者用了 `position: fixed` 的全局弹窗，隔离就漏了。我们出过一次线上事故：子应用的弹窗遮罩覆盖了主应用导航，原因就是遮罩挂在了 body 上。最后立了规矩：所有弹窗、Toast 必须渲染在子应用自己的容器内，容器外不渲染任何 DOM。

**公共依赖的版本地狱**。三个子应用各自打包 React，首屏要下三份；做成 external 共享，又出现 A 应用用 React 18、B 应用用 React 17 的撕裂。最后的方案是平台团队统一维护"公共依赖基线"，子应用锁版本、升级窗口由平台团队统一安排，不提供自由选择。这本质上是把微前端的"自治"收窄了，但比每个团队自选版本稳得多。

**路由是所有坑的源头**。多应用共存下，base 路径、嵌套路由、路由守卫三件事互相纠缠。我们的教训是：路由规则必须在主应用单点定义，子应用只认自己那一层 base，任何跨应用跳转都走主应用的路由 API，不允许子应用直接操作 history。这一条是用两次"刷新后 404"换来的。

**通信越少越好**。早期设计了一套完善的事件总线和共享 store，半年后发现九成事件是"登录态变化"和"路由跳转"这两个重复场景。砍到只剩 URL 查询参数、自定义事件和主应用分发的用户上下文三样，复杂度断崖式下降。微前端之间的通信，本质上是分布式系统的缩影：默认异步、默认可能失败、默认对方不按你的节奏来。

## 通信代码长什么样

### 通信机制的三次收敛

实际保留的通信机制朴素得近乎简陋。子应用向主应用要用户信息，主应用在挂载时通过 props 注入；子应用之间要跳转，派发一个带目标路径的自定义事件，主应用统一处理：

```javascript
// 子应用侧：请求跳转到另一个子应用的页面
function navigateTo(target, params = {}) {
  window.dispatchEvent(
    new CustomEvent("shell:navigate", {
      detail: { target, params },
    }),
  );
}
```

```typescript
// 主应用侧：统一监听并执行跳转，子应用不直接碰 history
interface NavigateDetail {
  target: string;
  params: Record<string, string>;
}

window.addEventListener("shell:navigate", (event) => {
  const { target, params } = (event as CustomEvent<NavigateDetail>).detail;
  router.push({ path: target, query: params });
});
```

## 两年后的五条教训

1. **先拆组织，再拆代码**。微前端按团队边界拆，不按技术边界拆；按"功能域"垂直切，不按"组件层"水平切。水平切出来的"共享组件层"是依赖地狱的开端。
2. **平台团队先行**。没有统一的构建、监控、公共库、兜底页之前，不要铺开微前端，否则每个子应用都要重复造一遍轮子。
3. **隔离做七分满**。追求完全隔离的复杂度指数上升，七分隔离加明确的团队约定，能挡住九成问题。
4. **独立部署是目的，技术自由不是**。锁死技术栈基线，把"自由"换成"稳"，收益反而更高。
5. **留好退路**。我们的主应用保留了"整包回退"模式，出重大故障时可以把所有子应用打成单体上线。这个开关在两次事故里救了命。

## 🧭 如果重来：分阶段路线图

把两年的弯路压缩成一份路线图，给准备动手的团队：

1. **第 0 个月：只做组织设计**。确定团队边界和功能域划分，明确平台团队职责，不动一行代码。这一步省下的时间，后面会十倍还回来。
2. **第 1 到 2 个月：建平台能力**。统一构建、统一监控、公共依赖基线、兜底页，先用单体应用验证这些基础设施。
3. **第 3 个月：切第一个边缘子应用**。选一个低风险、边界清晰的模块试点，把注册、通信、路由的流程跑通：
   - 候选模块的标准：有独立路由、少共享状态、出事不影响主流程
   - 帮助中心、设置页这类页面是理想试点
   - 试点通过的标准：一次完整迭代内没有平台团队介入救火
4. **第 4 到 6 个月：按域拆分核心模块**。一次只拆一个，每个子应用独立上线、独立回滚，观察一个完整的迭代周期再拆下一个。
5. **持续：治理**。版本基线、路由规则、样式纪律每季度复审一次，发现没人遵守的规矩就废除或自动化，别让规范文档烂掉。

这份路线图的核心是把"技术拆分"放到组织设计和平台能力之后。我们当初跳过前两步直接进入第四步，等于在地基没打的地面上盖楼，看起来快，实际慢。

> 微前端的复杂度不会消失，只会转移：从代码里转移到部署、版本和团队约定上。动工前先确认接收方接得住。

## 小结

微前端是一笔用架构复杂度换组织效率的交易。交易划不划算，取决于你的团队规模和部署痛点是否真实存在。我们的答案是：值得做，但要比规划中晚一年、小一半。如果重来一次，我会先做平台能力和团队边界划分，再动代码拆分。示例代码托管在 <https://example.com/micro-frontend-lessons>。
