代码评审是少数能同时提升代码质量、传播知识、统一风格的工程实践，却也是最容易流于形式的环节：评审变成点一个"通过"按钮，评论变成风格偏好的拉锯战，四百行的 PR 拖三天没人看。这篇指南给出可操作的做法：作者怎么准备、评审者看什么、评论怎么写、哪些事情交给工具，最后附一份可以直接抄走的评审清单。

## 评审到底解决什么问题

先对齐目标，评审中的很多分歧就不存在了。评审要解决四件事，按优先级排序：

1. **发现缺陷**：逻辑错误、边界遗漏、并发问题，这是评审最不可替代的价值。
2. **控制风险**：影响面大的改动需要第二双眼睛确认，这是流程性的保险。
3. **传播知识**：至少两个人理解这段代码，团队就不会被 bus factor 卡住。
4. **统一风格**：命名、结构、错误处理方式在碰撞中趋于一致。

风格问题排最后，且应该尽量交给工具。把评审会的主要时间花在风格空格上，是对评审者最大的浪费。

> 一条值得写进团队规范的判断标准：如果一条评论不改变代码的行为、不降低未来的维护成本，它最多是 `[nit]`，永远不该是 `[blocking]`。

## 提交前：作者的自检

评审质量的上限由作者决定。推送之前花五分钟做这些事，能省掉评审者大量时间[^1]：

- **自读 diff**：用 `git diff origin/main...HEAD` 完整过一遍自己的改动，八成以上的低级错误在这一步就被发现。
- **写清 PR 描述**：背景、方案、影响范围、验证方式四要素齐全（模板见下文），别让评审者从代码里猜意图。
- **控制体积**：超过四百行的 PR 主动拆分，或至少在描述里给出建议阅读顺序。
- **本地验证**：构建、测试、lint 全绿再推送，把红色的 CI 推给同事看等于浪费所有人的时间。
- **标注存疑点**：自己也没把握的地方主动标出来请评审者重点看，这比被当面问出来好得多。

```bash
# 评审前常用的几条命令
git fetch origin
git log --oneline origin/main..HEAD     # 本次分支的全部提交
git diff origin/main...HEAD --stat      # 改动文件与行数概览
git diff origin/main...HEAD             # 完整 diff，推送前最后过一遍
```

## 评审时看什么

按顺序检查，前两项不过关就可以直接打回，不必逐行看细节。

### 正确性与设计

- **正确性**
  - 逻辑是否覆盖了需求文档里的每一条，边界条件（空值、零、超限、并发）是否处理。
  - 错误路径是否显式处理：重试、降级、传播，还是静默吞掉。
- **设计与可维护性**
  - 改动是否落在正确的层里，有没有在错误的抽象上打补丁。
  - 公共 API 的变更是否考虑了调用方，是否必须现在改。

### 测试与数据

- **测试**
  - 新行为有新测试，测试断言的是行为而不是实现细节。
  - 失败路径与边界值有用例，不是只有 happy path。
- **安全与数据**
  - 输入是否校验，敏感信息是否可能进日志，权限检查是否到位。
  - 数据迁移是否可回滚，会不会锁表。

## 评论怎么写

评论分级表达，是评审礼仪的核心。同一句话带上标签，作者立刻知道哪些必须改、哪些可商量：

| 标签 | 含义 | 作者预期动作 |
|------|------|--------------|
| `[blocking]` | 必须修改，否则不合并 | 逐条处理，有异议当面讨论 |
| `[question]` | 不理解，需要解释 | 解释或补充注释 |
| `[suggestion]` | 建议方案，供参考 | 自行判断是否采纳 |
| `[nit]` | 吹毛求疵的小问题 | 可忽略，不阻塞合并 |
| `[praise]` | 做得好的地方 | 继续保持 |

写评论的三条规矩：指出问题的同时给出理由，不说"这里不好"而说"这里在 X 场景下会出问题，建议 Y"；一次评论只说一件事，把五个问题塞进一条评论等于都没说；对事不对人，评论代码而不是评论作者。

## 作者与评审者的分工

| 事项 | 作者 | 评审者 |
|------|------|--------|
| PR 体积与描述 | 负责拆分与写清 | 负责要求，过大的 PR 可以要求先拆 |
| 功能正确性 | 负责自测与声明验证方式 | 负责抽查关键路径 |
| CI 状态 | 负责修到全绿 | 不看未绿的 PR |
| 合并时机 | 负责跟进评审进度 | 负责在承诺时限内响应 |
| 合并后问题 | 负责第一时间响应 | 负责协助定位，不追责 |

一个常见误区是把评审当成质量关卡的全部。评审能发现的问题永远是样本，系统性的质量要靠 CI、测试和类型系统兜底，评审只是最后一道人工保险。

## 评审的节奏

评审是异步协作，节奏比强度重要。三条实践：

- **约定首次响应时限**：工作时间四小时内给出首次反馈，哪怕只是"已收到，下午详看"。拖延是评审流程的第一杀手，PR 挂得越久，作者的上下文丢得越多，返工成本越高。
- **固定评审时段**：把评审放进日程而不是碎片时间，早上到岗后半小时、午饭后半小时，比随时被打断高效得多。
- **批量处理小 PR**：零碎的文档修正、依赖升级凑在一起一次看完，减少上下文切换。

远程团队还要多考虑一条：重要分歧优先约短会，十五分钟视频聊完的事情，评论区可能要来回二十条，还容易读出语气问题。

## 自动化边界

能自动化的都不进评审，这是保护评审积极性的关键[^1]：

- **格式与风格**：交给 formatter 和 linter，评审里再争论缩进就是浪费。
- **依赖漏洞与许可证扫描**：CI 里跑，有高危直接拦下。
- **测试覆盖率底线**：设阈值卡住下降，但不追求数字好看。
- **提交信息格式、分支命名**：用 hook 校验，不靠提醒。

人应该只做机器做不了的事：判断需求理解是否正确、方案是否合理、风险是否被低估。

## 度量与反模式

评审效率可以用两个指标观察：首次响应时长、PR 从打开到合并的时长。指标只用来发现问题，不能当 KPI 考核，一旦和绩效挂钩，就会出现"秒批"这种最坏结果。三个高频反模式：只在评论里说"有问题"不说为什么；把个人风格偏好写成 blocking 意见；让最资深的人评审所有 PR，既拖慢节奏又制造瓶颈。

比指标更直接的信号是团队感受：如果大家开始回避开 PR、把改动攒成大包一次提交，说明评审流程已经重到影响交付了。这时候该做的是简化流程、拆分 PR、加自动化，而不是加更多的评审规则。

## 评审检查清单

- [ ] PR 描述包含背景、方案、影响范围、验证方式
- [ ] diff 已通读，无调试代码、无关改动混入
- [ ] 核心逻辑有测试，边界与错误路径被覆盖
- [ ] 无敏感信息、硬编码密钥、临时绕过逻辑
- [ ] 公共 API 变更已评估调用方影响
- [ ] CI 全绿后再请评审，不推半成品
- [ ] 评论分级标注，blocking 项给出理由
- [ ] 合并后关注线上指标，异常及时回滚

## 小结

代码评审的成熟度是团队工程文化的缩影。落地路径建议从三件事开始：PR 模板入库、评论分级写进规范、格式问题全部自动化。工具先兜底，人再看逻辑，评审才会从负担变成团队真正愿意做的事。Google 工程实践文档见 <https://google.github.io/eng-practices/review/>。

[^1]: 作者自检与自动化边界的划分方式，参考 Google 工程实践中的代码评审指南并结合国内团队常见流程整理。
