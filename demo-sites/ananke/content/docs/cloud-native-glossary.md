云原生相关的词汇在过去几年里迅速膨胀，同一个概念在不同厂商的文档里有不同叫法，新人常常被名词淹没。这份术语表按主题分组收录三十余个高频词条，每条用一句话说清本质，再补一个落地细节。词条依据云原生计算基金会（CNCF）的通行定义与社区常用语义整理[^1]，适合放在浏览器收藏夹，读到不懂的词时回来查。

读术语表的建议：不要试图一次背完，按当前工作涉及的主题分组读；遇到中文译法不一致时，以英文原名为锚点去查官方文档；每个词条重点记住"它解决什么问题、不用它会怎样"，而不是背定义。名词只有对应到自己的系统里才真正属于自己。

## 容器与镜像

| 术语 | 一句话解释 | 落地细节 |
|------|------------|----------|
| 容器（Container） | 共享宿主机内核、但拥有独立文件系统与进程视图的运行实例 | 启动毫秒级，是轻量级虚拟化，不是虚拟机 |
| 镜像（Image） | 构建容器运行起来的只读模板，由分层文件系统构成 | 分层可复用，改一层只需重传一层 |
| Dockerfile | 描述镜像构建步骤的文本文件 | 每条指令生成一个层，顺序影响缓存命中 |
| 多阶段构建 | 在一个 Dockerfile 内分阶段编译与打包，只保留运行时所需文件 | 能把镜像体积压掉一个数量级 |
| OCI | 开放容器倡议，定义镜像格式与运行时的开放标准 | 不同工具构建的镜像可互相运行 |
| 镜像仓库（Registry） | 存放与分发镜像的服务，如 Docker Hub、Harbor | 生产环境建议私有仓库加漏洞扫描 |
| 层（Layer） | 镜像的每一组文件变更，按顺序叠加成最终文件系统 | 把不常变的依赖安装放前面可提速 |
| 容器运行时（Runtime） | 负责真正创建和运行容器的底层程序 | 常见有 containerd、CRI-O |

### 容器与虚拟机的边界

理解这一组的关键：镜像是静态的类，容器是运行时的实例；镜像是分层的，所以构建顺序直接影响构建缓存命中率。容器与虚拟机的区别也值得一句话说清：虚拟机虚拟的是硬件，每个实例跑一整套完整操作系统；容器虚拟的是操作系统，进程间靠内核命名空间隔离，因此密度和启动速度高出一个量级，但隔离性弱于虚拟机，安全敏感的多租户场景仍倾向强隔离方案。

> 一个常见误解：容器不是"轻量虚拟机"。它没有自己的内核，也没有硬件虚拟化层，遇到需要特定内核版本或内核模块的场景，容器方案直接出局。

## 编排与调度

| 术语 | 一句话解释 | 落地细节 |
|------|------------|----------|
| 编排（Orchestration） | 自动完成容器的部署、扩缩、故障替换与网络接入 | 大规模场景下人工操作不可行 |
| Kubernetes | 目前事实标准的容器编排系统，简称 K8s | 核心对象是 Pod、Service、Deployment |
| Pod | K8s 中最小的调度单位，可包含一个或多个容器 | 同 Pod 容器共享网络与存储卷 |
| Deployment | 声明 Pod 的期望副本数与更新策略的对象 | 支持滚动更新与回滚 |
| Service | 为一组 Pod 提供稳定访问入口与负载均衡 | 通过标签选择器关联后端 Pod |
| HPA | 水平 Pod 自动伸缩，按指标自动增减副本数 | 依赖 Metrics Server 提供指标 |
| 边车（Sidecar） | 与主容器同 Pod 运行的辅助容器 | 常用于日志采集、代理、配置热更新 |
| 服务网格（Service Mesh） | 以边车代理接管服务间通信的基础设施层 | 提供流量治理与 mTLS，但有延迟代价 |
| 探针（Probe） | K8s 用于判断容器是否就绪、存活的检查机制 | 就绪探针控制流量切入，配置不当会引发滚动更新事故 |
| Ingress | 管理集群外部流量如何进入内部服务的规则对象 | 需配合 Ingress 控制器才能真正生效 |
| CRD | 自定义资源定义，用 K8s 的方式扩展自己的资源类型 | Operator 模式的基础，数据库中间件广泛使用 |

一个 HPA 的配置示例，按 CPU 使用率把副本数维持在二到十之间：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

## 交付与发布

| 术语 | 一句话解释 | 落地细节 |
|------|------------|----------|
| CI（持续集成） | 代码合并后自动执行构建与测试的实践 | 目标是快速反馈，单次流水线宜控制在十分钟内 |
| CD（持续交付/部署） | 自动把通过验证的产物发布到目标环境 | 持续交付留人工确认，持续部署全自动 |
| GitOps | 以 Git 仓库作为基础设施与应用状态的唯一事实来源 | 变更走 PR，工具自动同步集群 |
| IaC（基础设施即代码） | 用代码而非手工操作管理服务器与网络 | 常见工具有 Terraform、Pulumi |
| 滚动更新（Rolling Update） | 分批用新版本替换旧版本，全程服务不中断 | 需配合就绪探针控制流量切入 |
| 蓝绿部署 | 新旧两套环境并存，一键切换流量 | 回滚最快，但资源开销翻倍 |
| 金丝雀发布 | 先让小比例流量访问新版本，观察指标再全量 | 需要可靠的指标对比与自动回滚 |
| 制品（Artifact） | 构建产物的统称，可以是镜像、二进制包或压缩包 | 制品一旦生成就不可变，改配置要重新出包 |
| 不可变基础设施 | 服务器部署后不再原地修改，变更靠替换完成 | 消除配置漂移，回滚等于换回旧实例 |

查看发布状态的常用命令：

```bash
kubectl rollout status deployment/web     # 观察滚动更新进度
kubectl rollout history deployment/web    # 查看历史版本
kubectl rollout undo deployment/web       # 回滚到上一版本
```

## 可观测性

| 术语 | 一句话解释 | 落地细节 |
|------|------------|----------|
| 可观测性（Observability） | 从系统外部输出推断内部状态的能力 | 三大支柱：指标、日志、链路追踪 |
| 指标（Metrics） | 可聚合的数值型时间序列 | 适合做告警与趋势分析 |
| 日志（Logging） | 离散的事件记录 | 结构化日志才可高效检索 |
| 链路追踪（Tracing） | 记录一次请求在多个服务间的完整路径 | 依赖埋点与 trace id 透传 |
| SLI / SLO / SLA | 服务等级指标、目标、协议 | SLO 是内部承诺，SLA 是对外合同 |
| 错误预算 | 1 减去 SLO 得到的可容忍不可用比例 | 预算耗尽应冻结发布，先还技术债 |
| 告警（Alerting） | 指标越过阈值时通知值班人 | 告警必须可执行，否则就是噪声 |
| RED 方法 | 围绕请求量、错误率、耗时三个指标观测服务的方法论 | 适合在线服务，一分钟就能搭出最小看板 |
| USE 方法 | 围绕使用率、饱和度、错误三个维度观测资源的方法论 | 适合排查主机与容器层的性能瓶颈 |

日志、指标、追踪三者是互补关系：指标告诉你"哪里慢了"，日志告诉你"当时发生了什么"，追踪告诉你"请求走了哪条路"。只做其中一两个，排障时就会缺证据。

### 最小可观测集

一个刚起步的系统，先把这三样跑起来就够用：

- 用 `kubectl top pods` 看容器级 CPU 与内存水位，配上节点指标就能发现明显的资源瓶颈。
- 把访问日志与错误日志按 JSON 结构化输出，至少带 trace_id、用户标识、耗时三个字段。
- 给核心接口定义 SLI：请求量、错误率、P99 延迟三个指标，先有数据再谈 SLO。

可观测性的建设顺序永远是"先能看见，再谈分析"，一上来就追求全链路追踪往往坚持不到落地。

## 弹性与韧性

| 术语 | 一句话解释 | 落地细节 |
|------|------------|----------|
| 熔断（Circuit Breaker） | 下游持续故障时自动断开请求，定期探测恢复 | 防止故障沿调用链放大 |
| 重试（Retry） | 失败后按策略重新发起请求 | 必须配退避与次数上限，否则适得其反 |
| 超时（Timeout） | 为每次外部调用设置最长等待时间 | 没有超时的系统等于没有底线 |
| 背压（Backpressure） | 下游过载时向上游反馈，减缓上游发送速率 | 常见于消息队列与流处理 |
| 混沌工程（Chaos Engineering） | 主动注入故障来验证系统韧性的实验方法 | 先在小范围、可回滚的条件下做 |
| 降级（Degradation） | 非核心功能不可用时保障核心链路 | 提前设计好降级路径，别临时抱佛脚 |
| 限流（Rate Limiting） | 限制单位时间内的请求量，保护系统不被打垮 | 按调用方限流比全局限流更公平 |
| 舱壁隔离（Bulkhead） | 按业务划分资源池，一个模块故障不拖垮全部 | 借鉴船舱隔间思想，线程池与连接池都要分 |

定义列表形式补充三个高频概念：

云原生（Cloud Native）
: 一类构建和运行应用的方法论，核心是容器化打包、动态调度与微服务化，目标是在多云环境下快速交付与弹性伸缩。

十二要素应用（Twelve-Factor App）
: 一套云原生应用的设计原则，涵盖代码基、依赖、配置、日志等十二条约定，今天读来依然是检查应用云化程度的好清单。

微服务（Microservices）
: 把单体应用拆成一组小而独立的服务，各自开发部署并通过轻量协议通信。它换来的是团队自治与技术异构空间，付出的是分布式复杂度：调用链变长、数据一致性变难、排障跨度变大。团队规模与运维能力不足时，模块化单体往往是更务实的选择。

### 读词条的方法

术语表只是地图，真正的理解发生在把名词对回自己系统的过程里。推荐三个动作：打开自己的部署清单，把上面每个词条标到对应组件上；标不上的就是当前缺失的能力；再挑一个最近遇到的故障，用这套术语向同事复述一遍。讲不清楚的地方，就是还没读懂的地方。
