性能测试的目的不是"跑出几个数字"，而是回答决策问题：系统现在的容量上限在哪里？改动让系统变快还是变慢？什么配置下会触发雪崩？跳过方法论的压测只能得到一堆无法比较的数字，甚至得到错误的结论——比如把客户端瓶颈当成服务端瓶颈，把噪声当信号。这份参考手册覆盖指标、负载模型、环境准备、工具选型、结果分析与报告模板六个部分，作为团队开展性能测试的通用基线。

![负载曲线与分位数延迟的关系示意](/images/demo-10.svg)

先说三个最常用的术语，全文都会用到：**QPS**（每秒查询数）描述吞吐能力，**P99 延迟**描述百分之九十九请求的耗时上限，**错误率**描述失败请求占比。任何一份压测报告，先把这三个数报清楚，再谈其他。

## 指标体系

先定义要度量什么，再谈怎么压。核心指标分四类，缺一类结论就不完整：

| 类别 | 指标 | 说明 |
|------|------|------|
| 延迟 | P50 / P95 / P99 / P999 | 分位数比平均值更能暴露长尾问题 |
| 吞吐 | QPS / TPS | 单位时间完成的请求或事务数 |
| 错误 | 错误率、超时率 | 按错误类型分桶统计，不只看总数 |
| 资源 | CPU、内存、IO、连接数饱和度 | 判断瓶颈在哪个资源层 |

平均值是最具误导性的指标：一百个请求里九十九个十毫秒、一个三秒，平均值三十毫秒，看起来健康，但百分之一用户在受苦。看分位数，并且同时看 P99 和 P999，长尾才是体验杀手。

> 汇报性能数据时的一条纪律：任何只给平均值的报告都退回重写。分位数、错误率、资源水位三个维度齐全，结论才有讨论基础。

## 负载模型

负载形态决定结论的适用场景，四种基础模型要分清：

| 模型 | 负载形态 | 回答的问题 |
|------|----------|------------|
| 阶梯加载 | 逐级提升并发，每级稳定一段时间 | 容量上限在哪，拐点出现在什么水位 |
| 稳态负载 | 固定并发持续运行 | 当前配置下稳定表现如何 |
| 尖峰负载 | 瞬间拉到峰值再回落 | 突发流量下会不会崩，恢复得多快 |
| 浸泡测试 | 中等负载长时间运行 | 有没有内存泄漏、连接泄漏、磁盘写满 |

真实系统的流量往往混合多种形态，压测计划要按业务场景设计，而不是把工具自带的参数跑一遍就完事。判断负载模型是否选对，问自己一个问题：这轮压测要复现的是用户的哪种行为？是日常平稳访问、促销抢购，还是夜间批处理？行为决定模型，模型决定参数。

## 测试类型

- **负载测试**：在预期负载下验证性能指标是否达标，回答"日常够不够用"。
- **压力测试**：持续加压到系统崩溃，回答"极限在哪，崩溃方式是否可接受"。
- **容量测试**：结合成本测算最优资源配置，回答"买多少机器合适"。
- **稳定性测试**：长时间中负载运行，回答"能不能挂着不管"。
- **基准测试**：改动前后的固定场景对比，回答"这次优化到底有没有效"。

选基准场景有个窍门：挑一个覆盖读写的混合场景固定下来，改动前后用完全相同的参数跑，比如固定的并发数与持续时间。参数写进脚本而不是靠人记，才能保证多轮之间真的可比。

## 环境与数据准备

环境不一致是性能数据失真的第一大来源。四条准备原则：

1. **独立环境**：压测机与被测服务分离，压测工具本身要留足余量，否则先耗尽的是客户端。
2. **数据同构**：数据量、数据分布、索引状态与生产一致。拿一千条数据测出的查询计划，放到一亿条数据的表上完全不成立。
3. **依赖隔离**：下游第三方服务用 Mock 或录制回放，既避免打挂别人，也保证结果可复现。
4. **配置对齐**：被测服务的版本、参数、连接池大小与生产一致，改一个变量就要重新记录基线。

数据准备还要注意幂等：压测会写入大量数据，每轮之前把数据重置到同一状态，否则第二轮的数据分布已经变了，两轮结果不可比。

## 工具选型

| 工具 | 形态 | 适用场景 | 注意点 |
|------|------|----------|--------|
| wrk / hey | 命令行 | 快速探底、单接口基准 | 功能简单，无场景编排 |
| k6 | 脚本化（JS） | 复杂场景、CI 集成 | 需要写脚本，学习成本中等 |
| JMeter | GUI + 分布式 | 团队共享用例、多协议 | 自身消耗大，注意客户端瓶颈 |
| Locust | Python 脚本 | 需要灵活编写业务逻辑 | 分布式模式需自己搭 |

选型标准只有两条：团队能维护，结果可复现。再强的工具，生成的用例没人看得懂，半年后就是一堆不敢动的僵尸脚本。

## 压测安全与防污染

对生产或类生产环境压测时，安全是前置条件而不是注意事项：

- **流量染色**：压测流量打特殊标记（请求头或用户标识），服务端按标记识别，避免污染真实统计数据、触发真实通知、产生真实订单。
- **隔离数据**：写操作落到影子表或独立库，压测产生的垃圾数据不影响业务查询，也方便压测后一键清理。
- **开关与熔断**：压测前确认限流、熔断、降级开关可用，出现异常能立即切断压测流量，而不是看着系统雪崩。
- **知会相关方**：提前通知值班与依赖方，避免压测期间的告警被当成真实故障处理，也避免别人的发布动作污染你的数据。

## 执行与分析

压测执行前先把计划写成配置，人和工具都按同一份计划走。

### 计划与执行

```toml
# 压测计划示例：目标、负载曲线与通过门槛
[target]
base_url = "https://staging.example.com"
duration = "10m"
concurrency = 200

[profile]
type = "ramp"          # ramp / steady / spike
steps = [50, 100, 200, 400, 800]

[thresholds]
p99_ms = 300            # P99 延迟门槛
error_rate = 0.001      # 错误率门槛
```

```bash
# 每轮压测前后记录环境状态，保证可追溯
date; uptime; free -m; docker stats --no-stream

# 执行压测，输出带时间戳的结果文件
k6 run --out json=results-$(date +%H%M).json plan.js
```

解读时把 `p99_ms` 和 `error_rate` 两个门槛值和报告里的实际数字并排看，任何一轮超门槛都要在报告里单独说明原因，不能只写"波动"。

### 解读纪律

结果分析三条纪律：**先看客户端指标再看服务端**，确认压测机没有先耗尽 CPU 或连接；**和基线比而不是和感觉比**，没有历史基线的数字没有意义；**单变量验证**，一次只改一个变量（并发数、配置、版本），同时改两个就无法归因。特别注意协调遗漏问题：开环压测工具按固定速率发请求，不计入等待时间，测出来的延迟会偏低，高压下差距可达数倍，解读数字前先确认工具是开环还是闭环。

## 常见误区

- **用平均值汇报延迟**：必须给分位数，否则长尾问题被完全掩盖。
- **压测机比服务先耗尽**：客户端瓶颈伪装成服务端容量，结论反向。
- **每轮环境都在变**：数据没重置、邻容器在抢资源，两轮数字不可比。
- **把单轮结果当结论**：性能数据有波动，关键结论至少跑三轮取稳定区间。
- **只测 happy path**：缓存命中时一个样、未命中时另一个样，要测真实命中率下的混合场景。
- **优化前后不重录基线**：上一轮的水位已经失效，守着旧基线守不住新系统。

## 检查清单

- [ ] 测试目标写成可验证的指标门槛
- [ ] 压测环境与被测服务分离，客户端有余量
- [ ] 数据量、分布与生产同构，每轮可重置
- [ ] 负载模型与业务场景对应，不是默认参数
- [ ] 每轮前后记录环境快照与资源水位
- [ ] 结果与基线对比，单变量归因
- [ ] 报告含原始数据与脚本，可复现

## 小结

性能测试的可信度取决于方法而不是工具：指标看分位数、环境要同构、变量只改一个、结论对比基线。把这四条做成团队规范，压测报告才能进入技术决策，而不是躺在文档库里。更系统的延迟分析方法可以参考 Brendan Gregg 的性能工程资料 <https://www.brendangregg.com/>，以及 <https://zh.wikipedia.org/wiki/延迟_(电脑)> 中的基础概念。
