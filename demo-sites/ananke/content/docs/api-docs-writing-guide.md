接口文档是开发者与你的系统之间的合同，也是接入方对你团队专业度的第一印象。现实中的接口文档常常两种极端：要么只有几行"参数见代码"，接入方全靠猜；要么堆出几百页自动生成的字段说明，读者找不到任何一条能跑通的示例。好的接口文档应该做到一件事：让一个从未见过你系统的开发者，在十五分钟内完成第一次成功调用。这篇指南讨论怎么写才能做到这一点。

## 先想清楚读者是谁

同一份文档至少有三类读者，需求完全不同：

- **做技术选型的人**：关心能力边界、鉴权方式、限流策略、SLA，他们决定要不要用。
- **做接入的人**：关心快速上手、完整示例、错误码含义，他们要在半天内跑通第一个请求。
- **做排障的人**：关心字段语义、边界条件、错误细节、变更历史，他们在凌晨三点查问题。

动笔之前把这三类人写在纸上，每个章节问自己"这一段是写给谁看的"。写给选型者的内容放进概览，写给接入者的内容放进快速上手，写给排障者的内容放进参考手册，混在一起的文档对谁都不友好。

## 文档的基本结构

一套完整的接口文档建议包含六个部分，顺序即阅读顺序：

1. **概览**：系统做什么、Base URL、协议、鉴权方式、限流说明。
2. **快速上手**：一个五分钟可跑通的完整示例，从拿凭证到收到响应。
3. **接口参考**：每个接口的路径、方法、参数、响应、错误，逐条列清。
4. **数据模型**：公共对象、字段类型、枚举值、约束（必填、长度、取值范围）。
5. **错误码表**：错误码、HTTP 状态、含义、处理建议。
6. **变更日志**：每次变更的内容、影响范围、生效时间。

缺少概览的文档逼着读者从参数细节里反推设计意图；缺少变更日志的文档让老用户在新版本上线时才发现自己的调用挂了。这两块是性价比最高的投资。

快速上手是整份文档的试金石，写的时候按真实路径走一遍：注册账号、创建应用、拿凭证、发第一个请求、收到响应。任何一步需要跳出文档查其他资料，都说明这里有缺口。上手示例宁浅勿全，覆盖一个最简单的成功路径即可，复杂的组合用法留给参考手册，混在一起只会把主线淹没。

## 命名与一致性

接口的命名和字段规范占的篇幅不多，却决定了文档的长期维护成本。几条经过验证的约定：

- **路径用名词复数**：`/users`、`/orders`，动作用子资源或查询参数表达，`/users/{id}/orders` 而不是 `/getUserOrders`。
- **方法语义固定**：GET 查询、POST 创建、PUT 全量更新、PATCH 局部更新、DELETE 删除，不要发明新语义。
- **字段风格统一**：全站统一 snake_case 或 camelCase，混用会让接入方写大量适配代码。
- **时间用 ISO 8601 带时区**：`2025-07-22T10:30:00Z`，并在文档里明确标注是 UTC 还是本地时间。
- **分页参数同名同义**：`page` 与 `page_size`，或 `cursor`，全站一套，不要一个接口一个样。

> 一致性的价值在于可预测：接入方学会一个接口的用法，就能推测其他接口的用法，这种"猜得对"的体验比任何文案都加分。

## 用 OpenAPI 描述契约

手写文档会和代码渐渐脱节，推荐用 OpenAPI 规范描述接口，文档从描述文件生成。

### 路径与操作

每个接口由路径加方法唯一确定，参数分路径参数、查询参数、请求体三类，`required` 必须显式标注：

```yaml
openapi: 3.0.3
info:
  title: 用户服务 API
  version: 1.2.0
servers:
  - url: https://api.example.com/v1
paths:
  /users/{id}:
    get:
      summary: 查询单个用户
      operationId: getUser
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
            format: int64
          description: 用户 ID
      responses:
        '200':
          description: 查询成功
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'
        '404':
          description: 用户不存在
components:
  schemas:
    User:
      type: object
      required: [id, name]
      properties:
        id:
          type: integer
          format: int64
        name:
          type: string
          maxLength: 64
```

### 组件复用

公共的错误响应、分页结构、用户对象都放进 `components`，用 `$ref` 引用。复用带来的是一致性：所有接口的分页字段叫同一个名字，所有错误响应长同一个形状，接入方学一次就够。

规范的价值在于机器可读：可以拿它生成客户端代码、Mock 服务、自动化测试。维护规范文件应该成为接口开发流程的一环，而不是上线后补的功课。

## 示例比描述重要

参数说明写得再细，也不如一个能复制粘贴就跑通的示例。示例要包含完整上下文：请求头、完整 URL、请求体、真实响应，一个都不能少。

```bash
curl -X GET 'https://api.example.com/v1/users/1024' \
  -H 'Authorization: Bearer <你的访问令牌>' \
  -H 'Accept: application/json'
```

对应的响应：

```json
{
  "id": 1024,
  "name": "张三",
  "email": "zhangsan@example.com",
  "created_at": "2025-07-22T10:30:00Z"
}
```

构造示例有三个要点：值要真实感强但绝不用真实用户数据；响应只保留必要字段，但保留的字段必须和参考手册一一对应；把容易出错的地方（时区格式、分页参数、空数组）专门示例一次。✅ 一条简单的验收标准：接入方拿着文档的示例，不读任何其他章节就能跑通，就算达标。

## 错误信息设计

错误处理是文档中最能体现专业度的部分。设计原则：错误码稳定可枚举、HTTP 状态语义正确、错误信息可定位、处理建议可操作。

| 场景 | HTTP 状态 | 错误码 | 处理建议 |
|------|-----------|--------|----------|
| 参数缺失或格式错误 | 400 | `invalid_parameter` | 按响应中的 `field` 定位并修正 |
| 令牌无效或过期 | 401 | `unauthorized` | 重新获取令牌后重试 |
| 无权访问该资源 | 403 | `forbidden` | 检查账号权限，不要重试 |
| 资源不存在 | 404 | `not_found` | 确认 ID 是否正确 |
| 请求过于频繁 | 429 | `rate_limited` | 按响应头 `Retry-After` 退避后重试 |
| 服务内部错误 | 500 | `internal_error` | 保留 `request_id` 联系支持方 |

每个错误响应体里带上 `request_id`，排障时这一串ID能把用户、服务端日志、链路追踪串起来，是接入方最感激的设计。

## 版本与变更

接口一旦有人用，兼容性就是承诺。三条实践：URL 或请求头里带主版本号，主版本内只做增量变更；废弃字段先在文档和响应头标注 `Deprecated`，给足迁移窗口再下线；每次变更写进变更日志，写清"改了什么、影响谁、何时生效"。删除字段前先看调用统计，没有调用量的字段才是安全的删除对象，靠感觉删字段迟早引发事故。

**反模式一：文档即参考手册。** 只有接口列表没有快速上手，读者看了二十分钟还不知道 Base URL 是什么。解决办法：把最快跑通的路径放在最前面。

**反模式二：示例全是伪代码。** `<string>`、`xxx`、`你的值` 占满示例，接入方每次都要猜真实格式。解决办法：示例用贴近生产的脱敏数据，并注明"以下值为示例"。

**反模式三：错误码只列数字。** 一张表列了三十个错误码，没有任何处理建议，接入方只能逐个试。解决办法：错误码表必须带"什么原因、怎么办"两列。

## 文档检查清单

- [ ] 概览包含 Base URL、鉴权方式、限流说明
- [ ] 快速上手示例可原样复制执行
- [ ] 每个接口的参数、响应、错误三部分齐全
- [ ] 数据模型标注必填、类型、取值范围
- [ ] 错误码表包含 HTTP 状态与处理建议
- [ ] 变更日志记录最近三次接口变更
- [ ] 文档由接口定义文件生成，或与代码在同一次提交中更新

## 小结

接口文档的质量标准可以用一个场景检验：新同事不请教任何人，只读文档能否完成第一次调用。写文档时始终想着这个场景，结构自然就往"概览、示例、参考、错误、变更"上靠。OpenAPI 规范见 <https://swagger.io/specification/>，写作细节可以参考 <https://zh.wikipedia.org/wiki/应用程序接口>。
