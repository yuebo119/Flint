SQLite 是一个嵌入式的进程内数据库引擎，整个数据库就是一个文件，没有独立的服务进程，通过链接进应用程序的库来访问。它部署在数以亿计的设备里，从手机应用到浏览器再到飞机仪表，但日常使用中仍有几个问题被反复提起：并发写为什么锁、备份怎么才安全、什么时候该换客户端/服务器架构的数据库。这篇 FAQ 挑选了十个最高频的问题，按"结论先行、给出命令、说明原理"的方式回答。

## 基础问题

### Q: SQLite 适合什么场景，不适合什么？

**A：** 适合单机、读多写少、数据量在几百兆以内的场景：桌面与移动端应用、嵌入式设备、小型网站、单元测试、数据分析的中间存储。它的优势是零配置、零维护、单文件易备份。不适合的场景也很明确：高并发写入、多台机器共享同一份数据、需要细粒度用户权限、单表数据量到数十亿行且要做复杂关联查询。判断标准很简单：如果写入方只有你的应用一个进程，SQLite 大概率够用；如果需要多个服务同时写，就该考虑客户端/服务器架构的数据库。

### Q: 什么是 WAL 模式，应该开启吗？

**A：** 应该开启，除非你有特殊的兼容性要求。WAL（Write-Ahead Log，预写日志）模式把写入先追加到日志文件，读操作不再被写操作阻塞，读写可以并发进行，这是 SQLite 最重要的一个开关：

```sql
PRAGMA journal_mode = WAL;   -- 开启后持久生效，重启数据库依然保持
PRAGMA synchronous = NORMAL; -- WAL 模式下推荐值，兼顾性能与安全
```

不同日志模式的对比如下：

| 模式 | 写入方式 | 读写并发 | 崩溃恢复 | 适用场景 |
|------|----------|----------|----------|----------|
| DELETE | 回滚日志文件 | 读写互斥 | 好 | 默认兼容模式 |
| TRUNCATE | 截断回滚日志 | 读写互斥 | 好 | 无法创建额外文件的环境 |
| WAL | 追加预写日志 | 读不阻塞写 | 好 | 绝大多数场景首选 |

注意 WAL 模式会额外产生 `-wal` 和 `-shm` 两个文件，把数据库拷贝到别处时必须三个文件一起拷贝，或者先用 `PRAGMA wal_checkpoint(TRUNCATE);` 把日志合并回主库文件。

### Q: 多个进程同时写入为什么会锁，怎么减少冲突？

**A：** 因为 SQLite 的写锁是库级别的，同一时刻只允许一个写事务，这是它换来实现简单的代价，不是缺陷。减少冲突的实用手段按收益排序：

- 开启 WAL 模式，读者不再被写者阻塞，这一项解决八成 perceived 卡顿。
- 用事务批量写，把一百次 `INSERT` 合成一次 `BEGIN ... COMMIT`，持锁时间从一百段变一段。
- 写操作避开热点行，尤其是自增 ID 表尾和"计数器"这类被并发更新的行。
- 设置合理的忙等待：`PRAGMA busy_timeout = 5000;`，遇到锁时等待而不是立即报 `SQLITE_BUSY`。

如果写入并发压不下来，返回 Q1 的结论：换数据库，不要和 SQLite 的锁机制较劲。

## 使用问题

### Q: 删除大量数据后文件不变小，如何回收空间？

**A：** SQLite 删除数据后会在文件中留下空闲页，文件不会自动收缩。回收空间执行 `VACUUM;`，它会重建整个数据库文件。注意两点：一是 VACUUM 需要额外的磁盘空间（约原文件大小），磁盘紧张时可能失败；二是它会重写文件，耗时与数据量成正比，大库建议在低峰期执行，并且只对真正需要瘦身的库执行，频繁 VACUUM 反而增加写放大。

### Q: 备份数据库有哪些方式，哪种最安全？

**A：** 按可靠性从低到高有三种，生产环境只用第三种：

- 直接拷贝 `.db` 文件：风险最高。如果拷贝过程中正好有写事务提交，拷出来的文件可能处于不一致状态；WAL 模式下还会漏掉日志里的内容。
- 用 `.dump` 导出 SQL 文本：一致性有保证，但大库慢，且恢复时要重放全部语句。
- 用在线备份接口：最安全。它通过同一个连接读取一致性快照，不阻塞写入：

```bash
# 命令行方式，备份与压缩一步完成
sqlite3 app.db ".backup 'app-backup.db'"
gzip -9 app-backup.db

# 验证备份可用性：用只读方式打开并跑一次完整性检查
sqlite3 app-backup.db "PRAGMA integrity_check;"
```

无论哪种方式，备份文件都必须实际恢复演练一次，没有验证过的备份等于没有备份。另外建议把 `PRAGMA integrity_check;` 加入定期任务，它能发现文件级的静默损坏。

> 备份的三条底线：备份文件与源数据不在同一块磁盘；定期做恢复演练并记录耗时；保留多个时间点的副本，只留最新一份等于没留。

### Q: 日期时间应该存 TEXT 还是 INTEGER？

**A：** 存 INTEGER 时间戳，展示时再格式化。理由是 INTEGER 比较和索引效率最高，且不存在时区歧义；TEXT 形式的 `'2024-10-05 14:30:00'` 虽然可读性好，但字符串比较依赖格式严格一致，混用 `'2024-1-5'` 与 `'2024-01-05'` 时排序就会出错。推荐做法是建表时用 `created_at INTEGER NOT NULL` 存毫秒级时间戳，查询时用 `datetime(created_at / 1000, 'unixepoch', 'localtime')` 转成本地时间展示。时区换算放在展示层处理，数据库里只存 UTC，这是跨时区系统少踩坑的通用做法。

### Q: `LIKE '%关键词%'` 为什么用不上索引？

**A：** 因为前缀通配符让 B 树索引失去有序性，数据库无法定位扫描起点，只能全表扫描。三种优化路径：

- 只做后缀匹配改成前缀匹配：把通配符放右边，`LIKE '关键词%'`，配合索引即可走范围扫描。
- 数据量允许时加覆盖索引，让扫描只读索引不读表，能快数倍。
- 需要任意位置匹配或中文分词检索，直接用全文检索扩展（见下一个问题），不要用 LIKE 硬扛。

### Q: 需要全文检索能力怎么办？

**A：** 用内置的 FTS5 虚拟表，它是编译进 SQLite 的标准组件，无需额外服务：

```sql
CREATE VIRTUAL TABLE articles_fts USING fts5(title, body);

INSERT INTO articles_fts(title, body) VALUES ('标题', '正文内容');

-- 中文按字匹配，英文按词匹配；bm25() 给出相关度排序
SELECT title FROM articles_fts WHERE articles_fts MATCH '数据库 索引' ORDER BY bm25(articles_fts);
```

FTS5 会维护倒排索引，写入有额外开销，适合读频繁的检索场景。中文没有天然词边界，它按单字匹配，短关键词可能召回大量噪声，可以在查询侧加长度过滤或自己维护同义词表。

### Q: SQLite 有用户和权限体系吗，如何控制访问？

**A：** 没有。SQLite 没有用户、角色、权限的概念，能否访问完全取决于文件系统权限：进程能打开这个文件，就能读写全部内容。因此访问控制必须在外层做：把数据库文件放在应用专属目录，权限设为属主可读写；不要把数据库放在 Web 根目录或共享目录；多租户共库的场景要在应用层做好数据隔离，不要指望数据库层拦住越权访问。

### Q: 什么时候该迁移到 PostgreSQL 或 MySQL？

**A：** 出现下面任意两条信号，就该启动迁移评估：写入并发持续成为瓶颈，锁等待时间进入秒级；需要多个服务或多个机器共享同一份数据；需要行级权限、审计或更丰富的扩展生态；单库文件超过几十GB，备份时间开始影响恢复指标。迁移本身不难，难的是配套改造：连接池、备份策略、监控指标全都要重做。建议在业务平稳期做，先用 `pgloader` 这类工具做一次全量加增量的试迁，把停机窗口测出来再定方案。

## 小结

SQLite 的问题九成来自"把它当服务器数据库用"。守住单写进程、数据量适中、访问控制在外层这三条边界，它会是最省心的存储选择；边界被突破时果断迁移，比调优到底更划算。更多细节见官方文档 <https://www.sqlite.org/wal.html> 与 <https://zh.wikipedia.org/wiki/SQLite>。
