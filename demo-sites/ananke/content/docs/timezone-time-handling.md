## 一、问题定义

时间处理之所以反复出事，是因为"时间"在系统里其实有三个互不相同的语义：

- **时刻（instant）**：时间轴上唯一的一点，例如"2025 年 6 月 18 日 08:00:00 UTC"。
- **本地时间（wall time）**：挂在某个时区上的墙上时钟读数，例如"北京时间上午八点"。
- **时区（timezone）**：本地时间与 UTC 之间的偏移规则，IANA 时区数据库用
  `Asia/Shanghai` 这样的地区标识维护，且规则本身会随政治决策变更。

把三者混为一谈是万恶之源。典型的故障剧本：服务器设在东八区，开发机也在东八区，
测试全部通过；上线到 UTC 时区的机器，"凌晨执行一次的定时任务"跑在了北京时间早上八点，
报表归日错位一整屏。时间问题不挑技术栈，只挑有没有把语义分清。

Unix 时间戳是唯一没有歧义的中间表示：自 1970-01-01T00:00:00Z 起的秒数或毫秒数，
它与时区无关，只表示一个时刻。工程上的标准做法是**内部流转用时刻，展示层才做时区转换**，
这条主线贯穿后面的所有方案。

## 二、方案枚举

| 存储方式 | 语义 | 优点 | 陷阱 |
| --- | --- | --- | --- |
| Unix 时间戳（整数） | 纯时刻 | 无歧义、省空间、计算快 | 不可读，排查要手动换算 |
| 带时区时间类型 `timestamptz` | 存的是 UTC 时刻 | 数据库自动按会话时区展示 | 会话时区配置错误会误判 |
| 不带时区类型 `timestamp` | 裸墙上时间 | 语义贴近"日程表" | 不知道它属于哪个时区，等于没有语义 |
| ISO 8601 字符串带 `Z` 或偏移 | 时刻 + 偏移 | 自描述、跨语言通用 | 体积大，解析要统一 |
| 本地时间 + 时区字段 | 墙上时间 + 地区 | 保住"每年同一天"的日程语义 | 两列要一起用，容易只取一列 |

对绝大多数业务系统，推荐的组合是：**数据库用 `timestamptz`，传输用带 `Z` 的
ISO 8601 字符串，展示层按用户 IANA 时区转换**。裸 `timestamp` 只用在日程表这类
"每年重复的本地时间"场景。

## 三、深入分析

### 3.1 从存储到展示的三跳

时间数据在系统里通常要跳三下：写入时变成 UTC 时刻，查询时按需转本地，展示时
按用户时区格式化。用 Python 标准库可以完整演示：

```python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

# 第一跳：服务端内部流转一律使用"带时区的 UTC 时刻"，杜绝 naive datetime
now_utc = datetime.now(timezone.utc)

# 第二跳：存储与传输用 ISO 8601，Z 后缀显式声明 UTC
iso = now_utc.isoformat().replace("+00:00", "Z")

# 第三跳：展示层按用户时区转换；IANA 地区名比固定 +08:00 偏移更可靠，
# 因为它能正确处理夏令时与历史上的偏移变更
def for_user(instant: datetime, tz_name: str) -> str:
    local = instant.astimezone(ZoneInfo(tz_name))
    return local.strftime("%Y-%m-%d %H:%M %Z")

print(for_user(now_utc, "Asia/Shanghai"))
print(for_user(now_utc, "America/New_York"))
```

关键细节是 `astimezone` 只接受 aware datetime。如果传入 naive 对象，Python 会按
系统本地时区解释，同一份代码在开发机和服务器上给出不同结果，这类 bug 极难复现。
对策：代码规范里禁止裸 `datetime.now()`，一律 `datetime.now(timezone.utc)`，
并用静态检查兜底。

数据库侧的等价操作是按目标时区归日：

```sql
-- 按"用户当地日期"聚合：先把 UTC 时刻转到目标时区，再截断到天
SELECT DATE(created_at AT TIME ZONE 'Asia/Shanghai') AS local_day,
       COUNT(*) AS signups
FROM users
GROUP BY local_day
ORDER BY local_day DESC;
```

注意 `timestamptz AT TIME ZONE 'zone'` 的语义是"把这个 UTC 时刻表示成该时区的
本地时间"，结果是不带时区的 `timestamp`，正好可以交给 `DATE` 截断。反过来
`timestamp AT TIME ZONE 'zone'` 是"把这个本地时间解释成该时区的时刻并转成 UTC"，
方向正好相反，写错方向不会报错，只会让数据静默偏移若干小时。

### 3.2 夏令时：每年两次的集体补课

IANA 时区数据库里约半数地区有夏令时规则，切换日附近会出现两种畸形时间：
春季"消失的一小时"与秋季"重复的一小时"。

<details>
<summary>案例：2026 年 3 月 8 日美国东部"消失的一小时"</summary>

2026 年美国夏令时从 3 月 8 日开始：当地时间 02:00 直接跳到 03:00，这中间的一小时
不存在。如果排班系统写的是"当地时间 02:30 执行任务"，这一天任务永远不会触发；
反过来 11 月 1 日 01:30 会出现两次，"只执行一次"的语义必须显式声明选哪一次。
排班、计费、日志归日三类场景都必须换成 UTC 时刻存储，展示层再转本地时间，
由 IANA 数据库负责处理这些边界。

</details>

代码层要防的坑：用 `ZoneInfo` 做本地时间算术时，跨夏令时边界"加一天"可能不等于
加 24 小时；调度框架按本地 cron 表达式触发时，切换日会多跑或漏跑一次。
更稳的写法是一律按 UTC 做时间运算，只在最后一步格式化成本地时间。

### 3.3 环境层的暗坑

语义分清之后，剩下的事故大多来自环境：

- **容器时区**：官方基础镜像默认 UTC，宿主机时区不会自动带进容器。需要本地时间时
  显式设置 `TZ=Asia/Shanghai` 并挂载 `/etc/localtime`，不要依赖镜像默认值。
- **数据库会话时区**：连接池要统一设置会话时区，否则不同服务的同一查询会得到
  不同展示值。JDBC 连接串、psycopg 连接参数都要显式声明。
- **前端兜底**：用户系统时区可能被改错，展示时应显示时区名而非只给一个裸时间，
  并允许用户手动覆盖，设置存进个人资料。
- **2038 问题**：32 位有符号秒级时间戳在 2038-01-19 溢出，新系统一律用 64 位
  毫秒或秒，存量 32 位字段排期整改。

进容器排查时钟问题时，先执行 `date` 看容器内时间，再对照宿主机与数据库会话时区，
三层逐一比对，按 <kbd>Ctrl</kbd>+<kbd>D</kbd> 退出交互 shell。

### 3.4 展示层与测试的暗坑

后端理顺之后，前端还有两个高频坑。其一是**手写偏移**：为了省事把 UTC 时间
直接加八小时显示，遇到有夏令时的用户、跨夏令时切换日的展示全错，
必须换成 `Intl.DateTimeFormat` 或 dayjs 的时区插件，让 IANA 规则说话。
其二是**日期组件的假本地**：日期选择器返回的是本地墙上时间，
提交时必须带上用户时区名一起发，否则后端按自己的默认时区解释，
跨时区用户选的日子会差一天。列表页按天归一时，分组键要么由后端按目标
时区算好，要么把分组时区作为参数显式传入，不要让前端拿 UTC 时间自己截断，
那样聚合出来的"今日"与服务器语义的"今日"经常不是同一天。

时间逻辑的测试同样要工程化。把"当前时间"做成可注入的时钟，
而不是散落各处的 `now()`；测试用固定时刻驱动，
夏令时切换日用表驱动用例覆盖。移动端还要考虑设备时区被用户改错、
或人在海外设备仍是北京时间的情况：成熟的国际化产品会在设置里暴露
时区覆盖项，默认跟随设备、允许手动选择，结果存服务端。
别小看这个功能，它是跨国协作类产品的常见客诉来源。

数据库侧的测试也别忘：用不同的会话时区跑同一组查询断言，
把"时区配置错误导致静默偏移"挡在 CI 里。一条 `SET TIME ZONE`
加断言模板，成本极低，收益是消灭一整类环境相关故障。

> 一条可以写进规范的检查项：任何出现在日志与 API 响应里的时间，
> 都必须带时区标识（Z 或偏移量）。裸时间戳等于把解释权推给读数据的人，
> 而每个人都会按自己的处境解释。

## 四、选型建议

- [ ] 数据库字段统一 `timestamptz`，存量 `timestamp` 字段评估补时区列后迁移
- [ ] 代码规范禁止裸 `datetime.now()` / `LocalDateTime.now()`，CI 加静态检查
- [ ] API 传输格式统一 ISO 8601 带 `Z`，在接口文档里写死示例
- [ ] 前端用 `Intl.DateTimeFormat` 或 dayjs 的时区插件，禁止手写偏移计算
- [ ] 定时任务统一按 UTC 声明，跨夏令时边界的任务上线前用日历工具核对触发次数
- [ ] 时区数据本身要能更新：操作系统 tzdata、JVM、浏览器各自独立，纳入依赖升级清单

一句话收束：**永远存储时刻，只在边缘转换时区**。把这句话写进项目的编码规范，
能消灭一大半"本地没问题线上出错"的时间类故障。
