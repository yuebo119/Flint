提示词工程的尴尬处境是：它看起来太简单——不就是打字吗——但同一个模型，换个问法效果天差地别。这篇文章把常用模式整理成一份清单，每个模式讲清"解决什么问题、怎么写、什么时候别用"。与其收藏几十个"神奇提示词"，不如理解这十几个套路背后的共同逻辑。

## 模式一：角色与任务声明

最基础也最容易被低估。模型在预训练里见过海量"以某某身份写作"的文本，一个明确的角色声明能把它拉到对应的语体分布上。但角色不是越具体越好，"你是一位拥有二十年经验的资深会计师"不如"你是财务对账助手，负责把银行流水和企业账目逐条核对"。

### 三要素缺一不可

任务声明要给出**输入、动作、输出**三要素，缺一个都会漂：

- 输入是什么格式、有没有脏数据；
- 要做什么，是抽取、总结、分类还是改写；
- 输出成什么样，长度、格式、语言。

## 模式二：少样本示例

模型擅长模仿。与其费劲描述"抽取字段要简洁"，不如直接给三个示范。示例的选择比数量重要：要覆盖主要形态，也要包含一两个边界例子。

```python
PROMPT_TEMPLATE = """你是客服质检员。请从对话中抽取"用户诉求"和"处理结果"。

示例一：
对话：用户说订单三天没动，客服查到是地址模糊，已联系用户确认。
输出：诉求=催单；结果=地址模糊待确认。

示例二：
对话：用户问会员权益，客服介绍了积分规则，用户表示明白了。
输出：诉求=咨询权益；结果=已解答。

现在处理：
对话：{dialogue}
输出："""

def build_prompt(dialogue: str) -> str:
    return PROMPT_TEMPLATE.format(dialogue=dialogue.strip())
```

两个细节：示例的顺序会影响表现，把最接近目标形态的放最后；示例太多会挤占上下文，也稀释注意力，三到五个通常够。示例的另一个来源是失败案例：把线上被人工纠正过的典型 case 沉淀成示例，每周挑两三条加进提示词，提示词会随业务一起长。这比任何静态模板都更接近"活"的工程实践。

## 模式三：思维链

遇到多步推理——数学题、逻辑题、多条件判断——让模型"直接给答案"往往错得离谱，而加一句"请一步步思考"，正确率显著提升。相关论文见 [arXiv:2201.11903](https://arxiv.org/abs/2201.11903)。

有效的问法有两种：

1. "请一步步推理，再给出最终答案"——适用于需要过程的场景；
2. "先列出你依据的事实，再下结论"——把推理依据显式化，方便人工检查。

### 什么时候别用思维链

思维链不是没有代价的：中间步骤会拉长输出、增加时延和费用，简单分类任务上甚至可能因为"想太多"而跑偏。**简单任务不要滥用**，这是新手最常见的过度设计。

## 模式四：结构化输出

要把结果接进系统，就必须让模型说"机器话"。两种主流做法：提示词里给 JSON 模板，或使用模型原生的结构化输出能力。

```json
{
  "sentiment": "negative",
  "aspects": [
    { "target": "物流", "polarity": "negative", "evidence": "等了八天" },
    { "target": "质量", "polarity": "positive", "evidence": "做工扎实" }
  ],
  "summary": "物流慢，质量满意"
}
```

配一段约束说明效果更稳："只输出 JSON，不要任何解释；字段缺失时填 null，不要编造；数组为空则输出 []。"最后一定加**解析容错**：模型偶尔还是会多输出一段废话，服务端要做一次剥离和校验，而不是直接把解析失败的锅甩给上游。再往下走一步是约束解码：不靠提示词恳求模型守规矩，而是在解码层强制词表只能输出符合 JSON 语法的 token，从机制上消灭语法错误。模型原生的结构化输出大多走这条路，比提示词约束可靠得多。

## 模式五：自我一致与反思

让模型把同一问题用不同思路解三遍，取多数答案，正确率通常高于单次作答，代价是三倍调用。另一种是自我反思：先出答案，再追问"这个答案有什么漏洞"，让它自己修订。适合高风险场景——生成报告、拟定方案——对时效敏感的任务不划算。

## 模式六：任务分解

一个 Prompt 里塞三件事，不如拆成三次调用。先抽取、再分类、最后总结，每一步的输出作为下一步的输入，中间结果可检查、可复用、可缓存。分解的收益在出错定位上最明显：复合 Prompt 出错时你只知道"结果不对"，拆开之后能立刻看出是哪一环开始跑偏，只重跑那一环即可。代价是延迟和调用次数，所以分解的粒度要看任务：抽取后还要分发的，值得拆；一次性生成的，拆了反而丢上下文。一个实用判据：如果两个步骤的失败需要不同的修复手段，就拆开。

## 模式速查表

| 模式 | 解决什么 | 成本 | 慎用场景 |
|------|----------|------|----------|
| 角色声明 | 语体跑偏 | 零 | 任务本身足够明确时 |
| 少样本 | 格式不稳定 | 中 | 示例难覆盖的长尾形态 |
| 思维链 | 多步推理出错 | 高（输出长） | 简单分类、抽取 |
| 结构化输出 | 无法程序化 | 低 | 自由创作场景 |
| 自我一致 | 偶发错误代价大 | 很高 | 实时交互 |

<summary>进阶：工具调用与 ReAct 循环</summary>

当模型需要"查了再答"——查数据库、调接口、算日期——就在提示词里注册工具签名，让模型输出"调用哪个工具、传什么参数"，由你的代码执行后把结果回填，模型继续推理。这个"思考-行动-观察"循环来自 [arXiv:2210.03629](https://arxiv.org/abs/2210.03629) 提出的 ReAct 模式，是现代 AI Agent 的基石。工具描述要写给模型看：每个工具一句话说清"什么时候该用我"，参数含义和示例值一个都不能省。

## 提示词的版本管理

生产环境里的提示词每天都在被"微调"——运营改一个词、产品加一句话，改完不记、出事找不到原版。正确的管理方式朴素得近乎无聊：提示词全文进版本库，每次变更带一句改动说明；线上跑哪个版本可配置，出问题能一键切回；效果回归靠评估集，新版本在评估集上不差于旧版本才允许推全。做到这三条，提示词和代码就没区别了，剩下的只是纪律问题。

## 上线前检查清单

- [ ] 同一个提示词在十次调用里输出格式是否稳定（跑方差测试，不是看一次结果）
- [ ] 恶意输入测过吗：空字符串、超长文本、注入指令（"忽略以上要求"）
- [ ] 失败时有兜底吗：解析失败走重试还是走规则引擎
- [ ] 版本管理：提示词改了但效果回退，能一键切回旧版吗
- [ ] 提示词与评估集版本对应，新版本上线前评估集成绩有记录
- [ ] 观察十次真实调用的完整输出，不是只看日志里的摘要
- [ ] 十组真实样本的人工验收记录在案，不是"感觉还行"

> 提示词是代码，不是咒语。凡是代码该有的纪律——版本管理、测试、变更记录——都该有。把提示词当咒语供着的团队，每次模型升级都要重新算一卦。

最后说一个反直觉的观察：大部分"提示词失效"其实是需求没想清楚——你自己都说不清要什么，模型只能猜。写不出好提示词的时候，先把任务拆小、把示例摆正，比换任何模板都管用。
