同样的团队、同样的代码，有的组一天部署十几次，有的一组一个月部署一次，差距往往不在写代码的速度，而在提交之后发生的事。流水线设计的核心目标只有一个：**让每一次提交都能快速、可重复、安全地流向生产**，并且每一步失败都能尽早给出信号。这套实践属于持续交付的范畴，概念背景见[维基百科 DevOps 条目](https://zh.wikipedia.org/wiki/DevOps)。

> 一条没人敢点的部署按钮，比没有部署按钮更危险。前者制造"我们随时能发"的幻觉，后者至少诚实地暴露了问题。

## 一条流水线的骨架

不管用什么工具，一条健康的流水线都可以拆成六个阶段。阶段之间的契约是制品，而不是"上一步跑完就算完"。

| 阶段 | 输入 | 输出 | 关键约束 |
| --- | --- | --- | --- |
| 提交 | 代码推送或合并请求 | 触发事件 | 每个提交都触发，不挑食 |
| 构建 | 源码 | 可构建产物 | 环境固定，禁止手工步骤 |
| 测试 | 构建产物 | 测试报告 | 快，单测级别控制在分钟内 |
| 打包 | 构建产物 | 带版本号的制品 | 同一制品晋级所有环境 |
| 部署 | 制品 | 运行中的服务 | 声明式，可回滚 |
| 验证 | 运行中的服务 | 健康信号 | 失败自动阻断晋级 |

"同一制品晋级所有环境"这条最容易被违反。不少团队的流程是开发环境打一个包、测试环境重新打一个包，结果生产包的内容和测过的那个并不一致，问题到上线才暴露。制品的不可变性是流水线可信度的地基。

## 触发策略：短支干 + 合并触发

分支模型决定触发频率。实践下来最稳的组合是主干开发、短生命周期分支：

```bash
# 特性分支：只跑快速反馈（单测 + 静态检查）
on:
  pull_request:
    branches: [main]

# 主干：跑完整流水线，包括部署到预发
on:
  push:
    branches: [main]
```

原则是**提交时验证，合并时交付**。合并请求上跑足够严的检查保证主干永远可发布；完整流水线（含部署）只在主干跑，避免每个分支都消耗一套完整环境。长命分支看起来安全，实际上合并冲突大、反馈慢，是流水线效率的隐形杀手。

## 缓存：快，但要快得正确

### 缓存键怎么设计

缓存没配好，流水线要么慢得让人想跳过，要么错得让人不敢信。分层设计缓存，并且把缓存键和锁文件绑定：

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 恢复依赖缓存
        uses: actions/cache@v4
        with:
          path: |
            ~/.nuget/packages
            ~/.cache/go-build
          key: ${{ runner.os }}-deps-${{ hashFiles('**/*.csproj', '**/go.sum') }}
          restore-keys: |
            ${{ runner.os }}-deps-

      - name: 构建
        run: dotnet build --configuration Release

      - name: 上传制品
        uses: actions/upload-artifact@v4
        with:
          name: app-${{ github.sha }}
          path: ./artifacts/
```

三个要点：

1. **缓存键必须包含依赖清单的哈希**。go.sum、package-lock.json 变了而缓存键没变，等于用旧依赖编译新代码，错误会以最莫名其妙的方式出现。
2. **`restore-keys` 提供前缀回退**，命中不了精确键时用旧缓存起步，再增量更新。
3. **制品（artifact）和缓存分开**：制品带提交哈希命名，永久保留可追溯；缓存可以随时淘汰，丢了最多慢一次。

## 失败要快：并行与分层

一条串行跑四十分钟的流水线，等于每次反馈都要等四十分钟。拆分的办法：

- **纵向分层**：静态检查、单测、构建并行启动；集成测试等构建完成；端到端测试等部署完成。慢的和快的分开，快的先失败。
- **横向分片**：单测按目录或历史耗时切成 N 份并行跑，注意准备幂等的测试数据，否则分片之间会互相污染。
- **早失败**：把历史上最容易失败的任务排在最前面，用 30 秒的 lint 拦住问题，好过等 30 分钟的部署才发现拼写错误。
- **通知跟着状态走**：合并请求的检查失败，消息回到合并请求而不是发到群里；主干流水线失败，直接呼叫当前值班人。把告警接到人，而不是接到一个没人看的频道，是快速反馈闭环的最后一环。

<details>
<summary>密钥与权限：流水线里最容易被忽视的一层</summary>

流水线能碰生产，它自己就是高价值目标。几条硬规则：

- 用平台提供的 OIDC 换取短期云凭证，别把长期 AccessKey 写进仓库变量；
- 按仓库、按环境隔离密钥，预发环境的凭证不该能碰生产；
- 第三方 action 固定到具体 commit SHA，不用浮动的 tag，供应链投毒的第一入口就是这里；
- 日志脱敏：CI 日志往往对所有成员可见，打印连接串和 token 等于全员广播。

## 测试策略：金字塔在流水线里的位置

流水线的各阶段跑什么测试，很多团队是乱的：单测跑十分钟，集成测试散落在各处，端到端测试时好时坏。一个可落地的分层是：

| 层级 | 内容 | 目标耗时 | 失败含义 |
| --- | --- | --- | --- |
| 静态检查 | 编译、lint、类型检查、密钥扫描 | 1 分钟内 | 一律不许合并 |
| 单元测试 | 单模块行为，无外部依赖 | 5 分钟内 | 一律不许合并 |
| 集成测试 | 模块间协作，依赖真实或容器化的中间件 | 15 分钟内 | 阻塞合并 |
| 端到端测试 | 关键用户旅程，跑在预发 | 主干流水线内 | 阻断晋级生产 |

原则是**越靠下层越快、越多、越确定**。端到端测试贵且脆，只覆盖关键路径，比如登录、下单、支付回调，不要试图把所有边界情况都堆到这一层。另外，flaky test（时好时坏的测试）必须被当成故障处理： quarantine 机制加 48 小时修复时限，放任一个不稳定测试，两周内它会教会整个团队忽略流水线结果。

## 环境管理：用完即弃的预发

"预发环境和生产不一样"是无数"在我机器上好的"事故的源头。理想形态是每个合并请求自动拉起一套独立环境，合并后自动销毁。容器化普及后这套做法的成本已经很低，收益却直接：开发自测、产品验收、自动化测试都跑在和生产一致的配置上，再也不会出现"预发挂着三周，谁也不知道里面被改过什么"的状态。配套要求是**数据库 schema 变更在环境创建时自动执行**，并且用脱敏数据或种子数据，而不是生产数据的副本。

## 用指标度量，而不是凭感觉

流水线好不好，四个 DORA 指标说了算：部署频率、变更前置时间、变更失败率、服务恢复时间。把这些变成流水线自身的埋点：

- 每次部署记录：提交哈希、触发方式、流水线耗时、结果；
- 每次回滚记录：原因分类（代码缺陷、配置错误、环境问题）；
- 每周看趋势，而不是盯着单次快慢。

没有度量，流水线优化就会退化成"我感觉部署变快了"的主观题。指标采集本身也要克制：只在主干流水线记录，给每次运行打上触发原因（合并请求、主干推送、定时任务、手工重跑），否则定时任务的噪声会淹没真实交付数据。另外一个隐性收益是**新人 onboarding**：一条结构清晰的流水线就是活的系统文档，新成员读一遍流水线定义，就知道代码从提交到上线要经过哪些关卡、每关检查什么，比任何口口相传都准确。

## 回滚是流水线的一部分

设计流水线时，团队常默认"部署成功即终点"，但真正成熟的标志是把回滚也当成一条一等公民的流水线。可回滚的前提在部署前就要埋好：制品不可变且按提交哈希保留足够长时间，数据库变更兼容旧版本，配置以代码形式可快速 revert。验证回滚有效性的最低标准是**每季度真的演练一次**，像消防演习那样。很多团队直到第一次生产事故才发现，回滚脚本依赖的镜像早在两周前的清理策略里被删掉了。

## 小结

流水线设计的取舍可以归纳成三句话：**阶段之间传制品，不传"跑完了"这个状态；快速反馈并行化，慢速验证分层等；权限和密钥按最小化配置，并像代码一样被审查**。做到这三点，部署频率会自己涨上去，因为阻碍部署的从来不是勇气，是流水线每次给的反馈太慢、太不可信。
