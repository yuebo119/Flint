去年双十一前两周，运营后台的订单报表把订单主库打挂了。事情本身不复杂：报表要按十二个维度筛选，SQL 里十几个 join，跑一次四十多秒，运营还习惯连续点。三次限流之后业务方不干了，因为报表是他们每天上班的第一件事。我们最终用 CQRS 把命令侧和查询侧拆开，主库只扛写，报表走独立读模型。这篇文章记录完整过程：根因怎么定位、两侧怎么拆、读模型怎么同步、改造后效果如何。改造从立项到上线用了五周，其中三周花在读模型和同步链路上，真正拆命令查询只用了两天。这个时间比例本身就能说明问题：CQRS 的难点不在拆，在读模型怎么建、数据怎么来。

## 根因：一个库扛了两种负载

复盘数据摆出来，问题很清楚。订单主库峰值 QPS 六千，其中四千来自报表查询；报表 SQL 平均执行 3.2 秒，CPU 占用 40%；而写入路径的 P99 只有 8 毫秒，却要和报表抢连接池和 Buffer Pool。一次运营的连续点击，能把主库的连接池占满，下单开始超时。

根因不是 SQL 写得差，而是一个库同时服务两种形态完全相反的负载：写入是短事务、高并发、点查询；报表是长查询、低并发、全表扫描。两者对索引、Buffer Pool、连接池的诉求互相冲突，调优只能来回拉扯，没有共赢解。认识到这一点之后，拆分读写就是唯一方向。

### 三轮失败的调优

调优不是没试过，按顺序踩了三个坑。先是给报表 SQL 加索引，加了六个组合索引，写入性能掉两成，报表只快了三秒；然后加了只读从库，报表引到从库，结果从库延迟在报表长查询期间飙升，影响到另外两个依赖从库的业务；最后限制报表并发，运营直接投诉。三轮尝试全部治标不治本，反而确认了根因判断：两种负载放在一个存储上，任何一方优化都是另一方的成本。

## 拆分：命令侧与查询侧

命令侧保持原样：订单聚合、事务、领域逻辑，一行没动。改动全在查询侧。第一步，把报表需求翻译成查询模型：报表不看订单状态机，只看一张扁平的事实表，字段固定，筛选维度明确。

> 读模型不是写模型的拷贝，是另一个为查询而生的模型。把这句话想反了，CQRS 就白拆了。

第二步，用物化视图加汇总表搭读模型，报表 SQL 从十几个 join 变成单表筛选。

```sql
-- 读模型：订单报表事实表，按运营筛选维度扁平化
CREATE TABLE read_order_report (
    order_id       BIGINT PRIMARY KEY,
    member_id      BIGINT NOT NULL,
    channel        VARCHAR(32)  NOT NULL,   -- 下单渠道
    region_code    VARCHAR(16)  NOT NULL,   -- 收货地区
    category_id    INT          NOT NULL,   -- 一级类目
    amount         DECIMAL(12,2) NOT NULL,
    status         TINYINT      NOT NULL,
    paid_at        DATETIME     NULL,
    created_at     DATETIME     NOT NULL,
    KEY idx_created (created_at, channel, region_code)
) ENGINE=InnoDB;

-- 报表查询变成单表扫描，40 秒降到 80 毫秒
SELECT channel, region_code, COUNT(*) AS orders, SUM(amount) AS gmv
FROM read_order_report
WHERE created_at >= :start AND created_at < :end AND status = 2
GROUP BY channel, region_code;
```

命令侧保持不变有个直接好处：写入逻辑零风险。所有改动集中在投影和查询，出问题回滚只回滚半边，不用动下单主链路。

### 查询模型的设计取舍

查询模型的设计过程值得单独说。我们没有直接照搬现有表结构，而是先访谈了三位重度使用报表的运营，把他们真实的筛选动作列出来：按渠道看趋势、按地区看分布、按类目看占比、按时间下钻。四个动作覆盖了他们九成的使用场景，剩下的"其他维度组合"承认不支持。这个取舍很关键：想支持全部维度组合，读模型就得退化成通用宽表，查询性能优势会大打折扣。接受"覆盖九成场景"，才换来了 `read_order_report` 单表八十毫秒的稳定表现。

## 读模型同步：CDC 优先

读模型的数据从哪来？三个选项：业务代码双写、定时 ETL、CDC 订阅数据库日志。双写的问题是无法保证原子性，主库写成功而读模型失败时两边不一致，且每加一个读模型都要改业务代码；定时 ETL 延迟是分钟级，运营接受不了"刚下的单报表里没有"。我们选了 CDC：订阅订单库的 binlog，解析后投影到读模型，延迟控制在秒级，业务代码零侵入。

```sql
-- 投影任务：把 binlog 里的订单变更转成读模型行
-- 关键点：幂等 upsert，同一条 binlog 重放不产生重复行
INSERT INTO read_order_report
    (order_id, member_id, channel, region_code, category_id, amount, status, paid_at, created_at)
VALUES
    (:order_id, :member_id, :channel, :region, :category_id, :amount, :status, :paid_at, :created_at)
ON DUPLICATE KEY UPDATE
    status = VALUES(status),
    amount = VALUES(amount),
    paid_at = VALUES(paid_at);
```

CDC 链路自身的可靠性是重点：位点要持久化，重启后从断点续传；投影必须幂等，同一事件重放结果一致，核心是 upsert 语义；监控两个指标，`binlog` 延迟和投影落后条数，超过阈值告警。

上线前我们做了双跑验证：投影任务运行两周，期间不切流量，每天自动比对读模型和主库按同样条件统计的结果，连续十四天完全一致才切流。这两周里发现过投影逻辑的一个边界 bug（虚拟订单被算进了 GMV），如果直接切流，这就是一次线上数据事故。双跑的代价是两周等待，收益是发现问题时还有退路，这笔账永远划算。

<details>
<summary>投影失败的补偿：全量重建脚本的核心逻辑</summary>

读模型损坏或投影逻辑有 bug 时，需要全量重建。重建不是简单重放 binlog（历史位点可能已被清理），而是按主键范围分批从主库拉取，走与增量投影完全相同的 upsert 逻辑，保证幂等：

```sql
-- 按主键分批，每批一万行，游标推进，避免大事务
SELECT order_id, member_id, channel, region_code, category_id,
       amount, status, paid_at, created_at
FROM orders
WHERE order_id > :last_cursor
ORDER BY order_id
LIMIT 10000;
```

重建期间双写（增量投影继续运行），切换时校验行数与抽样比对金额合计，一致后下线重建任务。整个过程对查询侧的影响是读模型从"最终一致"短暂变成"部分缺失"，运营侧提前公告。

## 改造效果

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 报表查询 P99 | 42 秒 | 85 毫秒 |
| 主库写入 P99 | 220 毫秒（被报表拖累） | 8 毫秒 |
| 主库连接池打满次数（周） | 11 次 | 0 次 |
| 订单核心接口错误率 | 0.3% | 0.002% |
| 报表数据延迟 | 实时（主库） | 秒级（CDC） |

延迟从零变成秒级，是这次改造唯一被业务方质疑的点。解决办法不是把延迟压到零，而是把"数据更新时间"显示在报表页面上，运营看到"更新于 3 秒前"就不再纠结。可见性有时比一致性本身更重要。还有一件事改变了业务方的态度：改造后报表可以随时改维度，以前加一个筛选维度要排期开发，现在改读模型结构加一列就行，运营提需求当天就能验证。他们从"延迟不能接受"变成了"这个交换划算"。

## 什么项目适合 CQRS

改造做完复盘，我们认为 CQRS 的适用边界很清楚：命令和查询的负载形态差异大（一个高频短事务、一个低频大扫描），读模型和写模型天然不同构，且团队能接受最终一致。展开成可逐条核对的条件：

1. 读写负载形态差异大，加索引、调参数已经无法同时满足两边
2. 读模型和写模型天然不同构，报表需要的宽表写侧根本不需要
3. 业务能接受秒级延迟，且愿意把延迟显示在界面上
4. 团队能长期维护一条同步链路，包括它的监控和对账

三条都不满足的项目，拆 CQRS 只会得到两个半吊子模块和一套要维护的同步链路。反过来，只读副本解决不了的时候，才值得拆。

反过来说，如果报表需求只是偶尔出现，更便宜的做法是加一个只读副本，把报表流量引到副本上，改动一小时就能上线。CQRS 是当读写差异已经撕裂到调优无解时的方案，不是默认架构。判断标准就一条：现在的问题，加只读副本能不能解决？能，就别拆。[^1]

只读副本和 CQRS 的边界再强调一次：副本是"同一个模型的另一个拷贝"，查询逻辑不变，只是数据晚几秒；CQRS 是"另一个模型"，表结构、索引、甚至存储类型都可以不同。我们其实两步都走了：先加副本顶了两个月，确认读写模型的差异真实存在且无法靠索引调和，才启动 CQRS。中间那两个月不是浪费，是把"要不要拆"这个决策从猜变成了验证。

[^1]: Martin Fowler, "CQRS", https://martinfowler.com/bliki/CQRS.html
