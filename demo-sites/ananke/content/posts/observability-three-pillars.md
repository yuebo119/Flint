线上出了故障，老板的问题总是两个：哪儿坏了，多久能好。第一个问题需要可观测性，第二个问题依赖它给得够不够快。很多团队把可观测性等同于"装了 Prometheus 和 ELK"，但工具到位和数据能用之间隔着大量的设计工作。这篇文章讲三种核心数据各自的分工，以及它们怎样拼成一张能回答问题的网。

## 监控与可观测性的区别

先厘清一对常被混用的词。传统监控回答**已知模式的"是或否"**：CPU 是否超过 80%、接口是否 5xx 增多。它依赖人事先想到要监控什么。可观测性回答**未知模式的"为什么"**：系统第一次以你没见过的方式出错时，你手头有足够的数据推断出因果链。相关概念背景见[维基百科"可观测性"条目](https://zh.wikipedia.org/wiki/可观测性)。

区别落到实践上：**监控是"设阈值"，可观测性是"留数据"**。后者要为没预料到的问题保留现场，这意味着采集策略必须考虑成本和保留周期的平衡。一个常见的失误是把三个概念当成三个产品来买：买一套指标系统、一套日志系统、一套链路系统，各自为政，数据之间对不上。可观测性的价值恰恰在关联上，选型时先确认三者能否共享 trace_id 这类公共标识，比单独比较每个产品的功能列表重要得多。

> 监控像是仪表盘上的故障灯，告诉你发动机出了问题；可观测性像是能把发动机拆开检查的工具箱。灯亮之前，你不知道自己需要哪些工具。

## 指标：最便宜的问题发现手段

指标是按时间聚合的数值，存储成本最低，查询最快，适合做告警和趋势。暴露指标只需要应用提供一个端点：

```yaml
# Prometheus 抓取配置示例
scrape_configs:
  - job_name: "order-service"
    metrics_path: /metrics
    static_configs:
      - targets: ["order-service.monitoring.svc:9090"]
        labels:
          env: prod
          team: trade
```

指标的使用有一条铁律：**先想清楚每个标签的取值集合有多大**。一个 `user_id` 标签就能让时间序列数量随用户数线性膨胀，这就是基数爆炸。指标里适合放的是低基数的维度：环境、服务名、接口路径、状态码。高基数的信息交给日志和链路。

```json
{
  "ts": "2025-05-20T08:14:22.481Z",
  "level": "error",
  "service": "order-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "msg": "payment callback timeout",
  "order_id": "SO2025052000814",
  "latency_ms": 3001,
  "upstream": "payment-gateway"
}
```

## 日志：细节的海洋

日志的优势是信息完整，劣势是贵且吵。让它可用的关键在结构化：JSON 格式、字段固定、必须带 trace_id。没有 trace_id 的日志，在分布式系统里几乎无法和请求的其他环节对上。此外两个实践值得固定下来：

1. **采样与分级**：error 级别全量保留，debug 级别按比例采样。全量 debug 日志的账单和它的价值通常不成比例。
2. **敏感字段脱敏**：日志管道里加一道过滤，手机号、证件号、token 在入库前替换，别等审计时再补救。

## 链路：把局部串成整体

### 埋点边界与采样策略

链路追踪记录一个请求穿过所有服务的完整路径，每个环节是一个 span，span 之间用 trace_id 串联。它是三种数据里单位成本最高的，也是回答"慢在哪个服务"的唯一直接手段[^1]。链路数据要发挥价值，注意两点：

- **采样要有策略**：全量采样在流量大的服务上不现实，常见做法是错误请求和慢请求全采、正常请求按比例采。头部采样省资源但可能漏掉慢在尾部的请求，尾部采样贵一些却更准。
- **埋点要克制**：给每个函数都加 span， trace 会宽到没法读。按对外调用、数据库访问、消息投递这些边界打点就够了。

```yaml
# OpenTelemetry Collector 采样与导出配置片段
processors:
  tail_sampling:
    policies:
      - name: errors
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow
        type: latency
        latency: {threshold_ms: 800}
      - name: base
        type: probabilistic
        probabilistic: {sampling_percentage: 5}
exporters:
  otlp/tempo:
    endpoint: tempo.monitoring.svc:4317
```

## 三根支柱怎么接起来

数据之间的关联才是可观测性的本体，做法是让 trace_id 贯穿始终：

- 请求进入网关时生成或透传 trace_id；
- 日志、指标 exemplar、链路 span 都带上同一个 trace_id；
- 告警消息里直接附带相关日志查询链接和链路链接，值班人点一下就能从"服务 5xx 升高"跳到具体是哪个调用变慢。

做到了这一步，排查路径才是短的：指标发现异常，链路定位服务，日志给出细节。三者各司其职，缺任何一环都会在某个问题上卡住。

上下文传播是这条缝合线的技术前提：trace_id 要能从入口服务一路透传到最深的下游，哪怕经过消息队列也不能断。断链多发生在异步边界上，消息头里忘了带，或者用了不支持透传的客户端库。审计的方法很简单：随便挑一笔线上订单，看它的日志和链路能不能完整对上，对不上的环节就是治理缺口。

## 指标的四种类型与选择

指标不是只有一种。选错类型，查询和告警都会事倍功半：

| 类型 | 特征 | 典型用途 | 例子 |
| --- | --- | --- | --- |
| Counter | 只增不减 | 速率、错误计数 | 请求总数、5xx 次数 |
| Gauge | 可增可减 | 当前状态 | 队列深度、连接数 |
| Histogram | 分桶统计分布 | 分位延迟 | P50/P99 响应时间 |
| Summary | 客户端预聚合 | 低基数分位 | 单实例 P95 |
实践中最常用的是 Counter 加 rate 函数算速率，以及 Histogram 算分位。有一个容易混淆的点：**直接对平均值设告警会掩盖长尾**，P99 从 200 毫秒涨到 2 秒时平均值可能只动了几十毫秒。延迟告警必须用分位数，这是被无数"平均一切正常但用户在骂"的事故验证过的结论。

命名规范是另一件小事大事。统一的命名约定（比如 `http_requests_total{service, route, status}` 这种带服务名、路由、状态码的固定标签集）能让仪表盘跨服务复用，也让新人看得懂任何一个面板。没有规范的指标名，半年后就会长出一堆同义不同名的指标，查询时先花十分钟找指标名，可观测性就打了对折。

## 告警设计：症状优先于原因

告警是观测数据的出口，也是最容易失控的一环。健康的告警体系有三个特征：

1. **告症状，不告原因**："下单接口成功率低于 99%"是症状，"某台机器 CPU 80%"是原因。原因类告警批量涌现，值班人要在几十条里自己拼因果；症状类告警直接指向用户影响，且天然去重。原因分析留给仪表盘，不占用人的注意力。
2. **每条告警有明确的响应动作**：发现一条告警没人知道该干什么，就删掉它或改写到有动作为止。告警的价值等于响应动作的价值，与紧急程度无关。
3. **分级与路由**：致命问题打电话，一般问题进工单，趋势类问题周报里看。把所有告警都发到同一个群，等于把所有邮件都标为紧急。

## 从数据到决策：SLO

数据齐了，还要定义"多好算好"。SLO 是连接技术和业务的桥：把"可用性 99.9%"翻译成"每 30 天允许 43 分钟不可用"，再翻译成错误预算。错误预算耗尽就冻结发布、专心修稳定性，这比"出了故障再讨论要不要停发新功能"的扯皮高效得多。

## 小结

三种数据的分工可以概括为：**指标看趋势，日志看细节，链路看路径，trace_id 是缝合线**。落地顺序上，建议先指标和告警，再结构化日志，最后上链路。一次铺开三套系统、每种都只用三成功力，不如先把一条从告警到根因的路径跑通，再逐步扩展。可观测性建设没有终点，但每一次完善都应该能用"平均故障定位时间缩短了多少分钟"来衡量。

最后提醒一个组织层面的现实：可观测性不是运维一个团队的事。日志的字段规范需要业务开发遵守，链路埋点要落在代码里，指标命名要跨团队对齐。把这些约定写成团队的工程规范，配一个轻量的代码评审检查，比事后用管道清洗脏数据省力得多。工具买到手只是开始，数据质量才是可观测性的真正成本中心。

[^1]: 链路追踪的规范以 OpenTelemetry 为事实标准，Metrics、Logs、Traces 三种信号都有对应的数据模型和 SDK，主流语言均有官方实现。
