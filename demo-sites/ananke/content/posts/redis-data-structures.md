很多人把 Redis 当缓存用，键值一放了事。可 Redis 提供的不是笼统的键值存储，而是五种语义明确的数据结构，每种背后都有精心设计的命令族和底层编码。选错结构的代价，小则浪费内存，大则把复杂度推给业务代码。这篇按类型过一遍，说清每个结构适合解决什么问题。

## String：最简单的牌子，最多的用法

String 是最基础的类型，一个键对应一个字节序列，最大 512MB。它的命令族覆盖了缓存、计数、分布式锁三类高频场景：

```bash
# 缓存用户会话，带过期时间
SET session:u10086 '{"nickname":"阿明"}' EX 3600

# 文章阅读量计数
INCR article:2026:views

# 分布式锁：NX 只在键不存在时设置成功
SET lock:order:20260101 uuid-here NX EX 30
```

底层编码有三种：纯数字用 int 压缩存储，短字符串用 embstr，长字符串用 raw。计数场景要留神，`INCR` 的键过期后计数不会保留，业务上要把计数键与业务键的过期时间对齐管理。

## Hash：把对象摊开存

Hash 适合存结构化对象，字段可以单独读写，不必整存整取：

```bash
HSET user:10086 nickname 阿明 city 杭州 level 5
HGET user:10086 nickname
HINCRBY user:10086 level 1
```

用户信息这类"整体读、偶尔改一个字段"的场景，Hash 比把整个对象序列化成 JSON 字符串更省流量，也避免并发修改互相覆盖。字段多的时候底层编码从 listpack 升级为 hashtable，内存占用会跳一截，字段数量要克制。

## List：队列与最新列表

List 是双向链表，支持两端推入弹出，天然适合做队列和栈。三个典型用法：`LPUSH` 加 `LRANGE` 做最新列表，`LPUSH` 加 `BRPOP` 做简单任务队列，`LPUSH` 加 `LTRIM` 做定长时间线。List 的短板是按索引访问是 O(n)，且没有优先级语义，要优先级队列得换 ZSet。

## Set：去重与交集

Set 是字符串集合，提供去重和集合运算，是社交场景的基础设施。共同关注、共同喜好、抽奖去重，底层都是 `SINTER`、`SISMEMBER`、`SCARD` 这几个命令。集合大时用 `SPOP`、`SRANDMEMBER` 做抽样要注意，两者语义不同：一个真的移除，一个只随机读。

## ZSet：排行榜的唯一正解

ZSet 给每个成员挂一个分数，集合按分数有序，是排行榜场景的标准答案：

```bash
ZINCRBY rank:weekly 10 user:10086
ZREVRANGE rank:weekly 0 9 WITHSCORES
ZREVRANK rank:weekly user:10086
```

底层用跳表加哈希表：跳表维护有序性支持范围查询，哈希表提供成员到分数的快速定位。比分相同按成员字典序排，这是 Tiebreaker 规则，做榜单时要在产品层决定是否接受。

## 编码与内存：小对象的大道理

Redis 会根据元素数量和大小自动选择紧凑编码。Hash、ZSet、List 在元素少且小时用 listpack，把整个结构存进一块连续内存，省掉指针开销；超过阈值就升级为 hashtable、跳表、双向链表。这意味着一条几千成员的 ZSet 和一条十成员的 ZSet，单成员内存成本可能差出几倍。

监控上盯两个指标：`used_memory` 的增长斜率，以及用 `MEMORY USAGE key` 抽出来的大键。超过一万个成员的结构要考虑拆分，大键的读写和过期删除都会阻塞主线程。

## 持久化：RDB 与 AOF 的取舍

Redis 的数据在内存里，重启不能丢。两种持久化机制各有性格。

RDB 是某一时刻的内存快照，fork 子进程写入磁盘，文件紧凑、恢复速度快，适合做冷备和灾备副本。代价是两次快照之间的数据会丢，默认配置下一小时才触发一次，故障最多丢一小时的数据。

AOF 记录每一条写命令，追加到日志文件，按策略刷盘。everysec 是推荐档：每秒刷一次，故障最多丢一秒，性能损失可控。AOF 文件会膨胀，Redis 用重写机制压缩，把当前内存状态写成最短命令集。混合模式（AOF 前半段 RDB 快照加后半段增量命令）兼顾了恢复速度和数据完整性，生产环境建议直接开。

只把 Redis 当缓存的场景可以关掉持久化，用数据库重建缓存；但凡 Redis 里存了"数据库里没有"的数据（如分布式锁状态、限流计数器、会话），持久化和备份就必须当作正经事来做。

## 为什么单线程还这么快

Redis 的核心网络模型是单线程，却能做到十万级 QPS，初学者常觉得反直觉。原因有三层。

其一，纯内存操作，没有磁盘寻道这个大头，一次命令的耗时在微秒级。其二，避免了多线程切换和锁竞争，单线程按顺序执行命令，没有上下文切换开销，也没有加锁解锁的损耗。其三，IO 多路复用，一个线程同时监听成千上万个连接，用 epoll 在连接就绪时回调处理，等待网络的时间不占用执行时间。

真正可能成为瓶颈的是大 key 操作和阻塞命令。一个包含百万成员的 ZSet 做 `ZRANGE` 全量返回，或者 `KEYS *` 这种全库扫描，会把单线程占住，后面所有命令排队。所以才有大 key 拆分、慢命令禁用、必要时候用多实例分片这些实践。Redis 6 之后网络 IO 改成多线程，但命令执行仍然是单线程，这个设计一直保留到今天。

## 客户端侧的三个效率细节

命令设计对性能的影响不亚于服务端配置。

pipeline 把多条命令打包一次发送，省掉逐个命令的往返延迟。批量读取一百个 key，串行要一百次往返，pipeline 只要一次，在跨机房的部署里收益尤其明显。MULTI 事务保证一批命令原子执行，但注意它不是关系数据库意义上的事务，中间没有回滚能力，一条命令失败不影响其他命令的执行。

Lua 脚本把多条命令收进服务端一次执行，兼顾原子性和往返效率，常用于"读-判断-写"这类复合逻辑。脚本里不要写死循环和长耗时逻辑，它会占住单线程。另外，Lua 脚本在集群模式下要求所有 key 落在同一 slot，这是常踩的坑。

## 典型故障与应对

缓存用久了都会遇到三类经典故障，应对手段各不相同。

缓存雪崩是大量 key 同时过期，流量瞬间全部打到数据库。应对是过期时间加随机抖动，把集中过期摊平；热点数据额外做逻辑过期，永不过期由后台异步刷新。缓存击穿是单个热点 key 失效的瞬间，高并发一起回源，应对是互斥锁回源或者逻辑过期，保证同一个 key 只回源一次。缓存穿透是查询根本不存在的数据，缓存永远miss，应对是布隆过滤器前置拦截，或者把空结果也短时间缓存起来。

这三类问题的共同点是都会把压力传导到数据库，而数据库是整条链路里最不耐压的一环。设计缓存策略时先想清楚降级路径：Redis 挂了或者慢了，接口是报错、走数据库还是返回默认值。这个问题不想清楚，故障发生时就没有答案。

### 升级阈值与内存跳变

编码升级的触发条件是元素数量超过 128 且单个元素长度超过 64 字节，两个条件同时满足才升级。这套阈值意味着一条十成员的 ZSet 和一条一万成员的 ZSet 不只是内存差一千倍，单成员的成本也不同：前者所有数据挤在一个 listpack 里，后者每个成员要走跳表节点加哈希条目，指针开销占了大头。给业务做容量评估时，不能只按成员数线性估算，要按编码分段估算，中间的跳变点就是阈值附近。

## 🚀 上手清单

> 命令都会背不难，难的是知道每个结构会在什么场景下拖慢你。

刚开始用 Redis 的同学，按这个顺序过一遍最省时间：

- [ ] 五种结构各写一个 demo，感受命令语义差异
- [ ] 给自己的业务键设计一套命名规范，如 `业务:对象:ID`
- [ ] 给所有缓存键设置过期时间，并想清楚缓存与数据库不一致时的兜底
- [ ] 用 `MEMORY USAGE` 扫一遍线上大键
- [ ] 读一遍命令参考，把每个结构的复杂度表贴在工位上

| 结构 | 典型场景 | 单元素读写复杂度 |
| --- | --- | --- |
| String | 缓存、计数、锁 | O(1) |
| Hash | 对象字段级读写 | O(1) |
| List | 队列、最新列表 | 两端 O(1)，中间 O(n) |
| Set | 去重、交集 | O(1) |
| ZSet | 排行榜、延迟队列 | O(log n) |

更多背景可以参考维基百科的 Redis 词条（https://zh.wikipedia.org/wiki/Redis）。
