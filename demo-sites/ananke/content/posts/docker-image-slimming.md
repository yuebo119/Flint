![镜像分层与多阶段构建示意](/images/demo-1.svg)

CI 里一条平平无奇的推送，镜像上传耗时四分多钟；线上滚动更新，新 Pod 卡在 ContainerCreating 上，光拉镜像就花了半个多小时。这不是网络故障，是镜像本身有 1.2 GB。本文记录一次完整的瘦身过程：同一个服务、同一份代码，最终镜像 89 MB，节点拉取时间从 96 秒降到 7 秒。

## 镜像体积为什么值得计较

镜像不是打包完就扔进仓库的静态产物，它至少在三处持续产生成本：

- **分发成本**：每一次节点调度、每一台新机器、每一次扩容，都要完整拉取镜像。镜像每增大 100 MB，集群首次扩容的耗时近乎线性增加。
- **存储成本**：镜像仓库按层去重，但标签层面的反复推送会占用大量空间，节点本地缓存同样有限。
- **攻击面**：基础镜像里带着 shell、包管理器和一堆用不到的二进制，CVE 扫描器不会区分"安装了"和"使用了"，它们只会全部报出来。

第三条最容易被忽略。一个只跑单个二进制的服务，理想状态是镜像里只有这个二进制和它信任的证书，没有 bash、没有 curl、没有 apk。镜像分层机制的细节可以参考[维基百科对容器镜像的说明](https://zh.wikipedia.org/wiki/容器)。

## 先测量，再动手

瘦身之前先建立基线，否则改完很难说清收益来自哪一步。用 `docker images` 看体积只是起点，更细的层分析可以用 dive 之类的工具，逐层看哪些文件被写入、哪些文件后来又被改动。

瘦身前后的关键指标变化如下：

| 指标 | 瘦身前 | 瘦身后 |
| --- | --- | --- |
| 镜像体积 | 1.2 GB | 89 MB |
| 推送耗时 | 4 分 10 秒 | 28 秒 |
| 节点拉取耗时 | 96 秒 | 7 秒 |
| Pod 就绪耗时 | 11 分钟 | 40 秒 |
| 高危 CVE 数量 | 37 | 2 |

最后一行常被跳过，但它往往比体积更有说服力：去掉 1.1 GB 里绝大多数用不到的软件包之后，扫描器报出来的问题自然也随之消失。

## 第一步：换一张更小的底图

第一刀通常落在基础镜像上。以部署一个 Go 服务为例，常见选择的差别相当明显：

| 基础镜像 | 体积（约） | 含 shell | 适用场景 |
| --- | --- | --- | --- |
| ubuntu:22.04 | 78 MB | 是 | 需要完整工具链的构建阶段 |
| alpine:3.19 | 7 MB | 是（busybox） | 依赖可静态编译、对体积敏感 |
| distroless/static | 2 MB | 否 | 只跑静态二进制，追求最小攻击面 |
| scratch | 0 MB | 否 | 自行提供一切依赖 |

alpine 用 musl libc 替换 glibc，某些依赖 glibc 的二进制会遇到兼容问题；distroless 没有 shell，排查问题只能靠外部工具。我的选择是：**构建阶段用完整镜像，运行阶段用 distroless**。运行时不需要编译器，也不需要交互式 shell，把排查能力放到集群外部的工具里去。

## 第二步：多阶段构建

Docker 17.05 之后支持的多阶段构建，是镜像瘦身最重要的功能。思路很直接：把编译环境和运行环境拆开，只把编译产物拷进最终镜像。

```dockerfile
# 构建阶段
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app ./cmd/server

# 运行阶段
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app /app
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

几个细节值得说明：

1. `CGO_ENABLED=0` 让 Go 编译器产出静态二进制，运行阶段才敢用 distroless 或 scratch。
2. `go mod download` 单独成层并放在拷贝源码之前，利用层缓存：只要 go.mod 没变，依赖下载层就不会失效。
3. `-ldflags="-s -w"` 去掉符号表和调试信息，对 Go 二进制通常能再省两到三成。
4. `COPY --from=builder` 只取需要的文件，而不是整个工作目录。

同样的代码，单阶段构建 1.2 GB，多阶段之后降到 120 MB 以内，剩下的体积几乎全是二进制本身。

> 构建阶段要什么有什么，运行阶段要什么给什么。多阶段构建的全部哲学就在这句话里。

## 顺手把构建上下文减减肥

`.dockerignore` 是最便宜的一招，却最常被忘记。它决定哪些文件会被发送给 Docker 守护进程构建，写坏了不只是慢，还可能把敏感文件 COPY 进镜像：

```
# .dockerignore
.git
**/node_modules
**/bin
**/obj
**/*.log
**/.env*
docker-compose*.yml
Dockerfile*
```

两条经验：一是通配符覆盖要全，node_modules 在一层还是三层目录都得排除；二是 `.dockerignore` 不影响 COPY 已引用的路径，它的作用是防止误 COPY，不是给 COPY 做过滤。上下文从几百 MB 降到几 MB，构建的等待感会立刻改善。

## 第三步：合并层与清理缓存

### 包管理器缓存的正确清法

如果必须在同一阶段安装依赖，注意每条指令都会产生一个层，安装包留下的缓存会永久留在镜像里。

```bash
# 反例：卸载软件包并不会删掉它下载的缓存
RUN apt-get update && apt-get install -y curl && apt-get remove -y curl

# 正例：同一条指令内清理，缓存不会进入任何一层
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

`--no-install-recommends` 值得养成习惯：apt 默认会安装一堆"推荐"包，对运行时镜像来说绝大多数是噪音。每条 RUN 里顺手清理，累积起来就是几十 MB 的差距。

## 容易踩的坑

- **.dockerignore 没配**：构建上下文里混着 .git、node_modules 和本地数据文件，既拖慢构建，又可能被意外 COPY 进镜像。
  - 至少要排除 `.git`、`node_modules`、`vendor` 和本地数据目录；
  - 镜像里出现来路不明的调试文件，多半是上下文没设排除规则。
- **在错误的阶段清理**：多阶段构建里，builder 阶段的垃圾不会进入最终镜像，在最终镜像里纠结 builder 的缓存是白费力气。
- **为了缩小镜像牺牲可观测性**：没有 shell 的镜像排查问题确实困难，折中做法是另备一份带调试工具的镜像 tag，排障时临时替换，日常运行仍用最小镜像。
- **基础镜像钉死不动**：distroless 与 alpine 都在持续发安全更新，基础镜像建议跟随小版本定期重建，而不是钉一个大版本再也不动。

## 一份可复用的瘦身清单

下次审查镜像时，可以逐项过一遍：

- [x] 构建上下文配置了 .dockerignore，排除 .git 与本地依赖目录
- [x] 采用多阶段构建，最终镜像不含编译工具链
- [x] 运行阶段基础镜像选 distroless 或 alpine，并验证过二进制可运行
- [x] 每条 RUN 内联清理包管理器缓存
- [x] 使用具体版本 tag，不用 latest
- [ ] 将镜像体积纳入 CI 指标，超过阈值时告警

最后一项很多团队还没做。体积不是一次性任务，它会随着依赖更新缓慢膨胀，只有纳入日常指标才不会失控。具体做法是在 CI 里给镜像体积设一条水位线：`docker build` 之后用 `docker image inspect` 拿到体积，和上一次成功构建比较，涨幅超过 10% 就让流水线标黄，超过 25% 直接标红。不需要一开始就追求自动化到发告警，先在合并请求的评论里带上体积变化，团队自然会开始在意这个数字。

## 把安全一起瘦了

体积瘦下来之后，顺手做两件和安全有关的事，成本几乎为零。第一是**以非 root 用户运行**：上面示例里的 `USER nonroot` 就是为此，配合 `readOnlyRootFilesystem: true` 的安全上下文，容器逃逸的利用难度会上升一个档次。第二是**把镜像扫描接进流水线**：每次构建后用 Trivy 扫一遍，高危漏洞让合并请求挂红。扫描器也会有误报和"修不了"的系统包，处理办法是维护一份豁免清单并写清理由，而不是直接关掉检查。

## 小结

这次瘦身的收益可以量化：镜像 1.2 GB 降到 89 MB，推送耗时从 4 分钟降到 30 秒，扩容时 Pod 就绪时间从 11 分钟降到 40 秒。方法上并没有魔法：**多阶段构建、精简基础镜像、层内清理、排除构建上下文**，四件事做到位，大部分镜像都能缩小一个数量级。真正的长期收益来自把体积当成一个被持续观测的指标，而不是一次性的清理运动。

补一句提醒：瘦身不是越极端越好。如果团队需要经常进容器排障，distroless 会明显增加时间成本，这时选带 busybox 的 alpine 是更平衡的答案。工具服务于人，镜像大小只是手段，交付速度才是目的。

最后一个常被问到的问题：**要不要用最新的基础镜像大版本**。建议是"跟随小版本，观望大版本"。小版本更新只带安全补丁，风险低，应该设成每月自动重建；大版本可能换 libc、换包管理器，带来的兼容问题需要专门验证，排进计划再升。把这两类更新分开处理，既不会因为钉死版本攒下一堆已知漏洞，也不会因为追新把生产搞挂。
