整洁架构这个词被说得太多，落地时常常变形：四层目录摆得整整齐齐，`Application` 层每个用例一个文件夹，`Domain` 层里躺着一堆只有 getter 的"实体"，一次改一个字段要穿过五个文件。团队很疲惫，架构图很好看，交付速度没有变化。问题出在哪？出在把整洁架构理解成了目录结构，而它本质上是一条约束依赖方向的规则。这篇文章讲三件事：依赖规则到底约束什么、边界应该长在哪里、以及什么时候不该用。

先给一个可操作的检验标准，看完文章可以用它回看自己的项目：随机打开你项目里领域层的十个文件，数一下 import 列表里出现了几次框架和数据库类型。答案是零，规则在；答案大于零，再整齐的目录也只是装修。这个标准不美观，但它不会说谎。

## 依赖规则：源码依赖只能指向内层

Robert Martin 画的那圈同心圆，最容易被忽略的是箭头方向，而不是圈本身。规则只有一句话：**源码依赖只能从外层指向内层，内层永远不知道外层的存在**。数据库是细节，Web 框架是细节，消息队列是细节，它们都在最外圈；业务规则在最内圈，不 import 任何基础设施的命名空间。

这条规则的价值在于可测试性和抗腐化。领域代码不依赖 Entity Framework，单测就能在毫秒级跑完；换掉 ORM 时，改的是外圈映射代码，动不了内圈一行。反过来，一旦领域实体上出现 `using Microsoft.EntityFrameworkCore`，规则就被打破，后面所有的"分层"都只是目录摆设。

腐化是怎么开始的？通常是一个"临时"决定：为了少写一个 DTO，领域事件直接复用了 EF 的实体类型；为了图方便，用例类里直接注入了 `DbContext`。单个看都能解释，累积半年之后，领域层的编译依赖里躺着 ASP.NET Core 和 SQL Server 驱动，想跑单测要先起数据库。这时候再想拆，比重写一遍还贵。

### 规则的维护要靠机械检查

规则的维护不能靠自觉。代码评审会累，会漏，会在 deadline 前妥协，唯一不会妥协的是 CI 里那条永远运行的架构测试。这也是我们把它排在三条纪律第一位的原因：它是唯一不需要人下决心的那条。

```java
// 内层：用例与端口，只依赖领域概念
public interface OrderRepository {              // 端口定义在内层
    Optional<Order> findById(OrderId id);
    void save(Order order);
}

public class PlaceOrderUseCase {
    private final OrderRepository orders;        // 依赖抽象
    private final PaymentGateway payment;         // 支付也是端口
    private final DomainEventPublisher events;

    public OrderId execute(PlaceOrderCommand cmd) {
        Order order = Order.draft(cmd.memberId());
        cmd.items().forEach(i -> order.addItem(i.product(), i.quantity()));
        order.place(new PricingRules());
        orders.save(order);
        events.publish(order.domainEvents());
        return order.id();
    }
}

// 外层：适配器，依赖端口并注入实现
@RestController
public class OrderController {
    private final PlaceOrderUseCase placeOrder;
    // HTTP 细节（DTO、状态码）全部挡在适配器里，用例只认命令对象
}
```

## 边界应该长在有变化的地方

边界的维护成本是真实的：每加一个用例要建命令、处理器、端口、DTO、映射，五件套。所以边界的密度应该和变化频率匹配，不该均匀铺满。判断方法很朴素：问这块代码的变更原因是什么，答案不同就该有边界，答案相同就该合并。

| 变化原因 | 该放在哪 | 例子 |
| --- | --- | --- |
| 业务规则变化 | 最内层，领域模型 | 优惠计算规则、订单状态机 |
| 用例流程变化 | 应用层，用例编排 | 下单要不要发券 |
| 技术选型变化 | 最外层，适配器 | 数据库、缓存、框架升级 |
| 展示形式变化 | 最外层，接口适配 | REST 改 GraphQL |

一个纯 CRUD 的后台管理模块，业务规则约等于零，它的变化原因全是展示形式和技术选型。给它套五件套，等于给一个本来只该有三层的东西套了八层，每次加字段要改的文件从两个变成六个。这种情况下，薄薄一个控制器加一个服务就是最"整洁"的架构。

还有一个对比能帮你想清楚边界：微服务边界和整洁架构边界回答的是两个问题。前者问"谁和谁应该分开部署"，切分依据是团队自治和故障隔离；后者问"谁的变更不应该影响谁"，切分依据是依赖方向。两个边界经常重合，但没有必然关系：一个单体内部可以、也应该有清晰的整洁架构边界，一个微服务内部也可能是一锅粥。用部署边界的存在替代架构边界的思考，是常见的偷懒。

## 贫血模型在 CRUD 系统里是合理选择

"贫血模型是反模式"这句话被引用得太滥。事务脚本加贫血模型的组合，在规则稀薄的系统里完全成立：逻辑就是校验、保存、返回，没有不变式需要守卫，把行为硬塞进实体只会得到一堆只有一个私有字段被用到一次的"丰富模型"。真正该避免的不是贫血，是**把业务规则散落在服务层的私有方法里**：规则既不属实体也没有显式位置，改一处要通读整个服务类。

判断标准：问"这段规则的自然主语是谁"。如果答案是"订单"（状态机、金额计算），就该进领域模型；如果答案是"某个流程"（先校验再保存再通知），留在应用层就是对的。强行给流程规则造一个实体方法，是另一种混乱。

补一个历史语境：Martin Fowler 提出贫血模型批评时的原文参见 https://martinfowler.com/bliki/AnemicDomainModel.html ，他针对的是"实体只有 getter/setter、全部逻辑散落在服务层"且服务层没有清晰分层的代码。他的主张是行为归位，不是"每个项目都必须用富域模型"。后来的读者把结论简化成了"贫血即罪"，这是以讹传讹。规则稀薄的系统用事务脚本完全成立，真正该反对的是把业务规则摊成一地私有方法、谁也找不到改哪里的服务类。

## 三条落地纪律

真正让架构不变形的不是分层图，是纪律：

1. 依赖方向可机械检查
   - 用架构测试断言：`Domain` 程序集不引用任何基础设施包
   - CI 里跑，违反即失败，不靠评审时人眼盯
2. 内层不出现外层类型
   - 领域事件、DTO、ORM 实体不许出现在领域层签名里
   - 需要传递数据时用领域自己的类型，映射放外层
3. 评审时问"变了改哪"
   - 每个 PR 问一句：这个变化如果发生，要改几个文件
   - 答案超过三个，说明边界没画在变化线上

第一条展开说，因为它是唯一不需要人下决心的一条。架构测试写起来不到三十行，用 NetArchTest 这类库就能表达：

```csharp
// 领域层不许引用基础设施与 Web 框架，违反即构建失败
var result = Types.InAssembly(typeof(Order).Assembly)
    .Should().NotHaveDependencyOn("Infrastructure")
    .And().NotHaveDependencyOn("Microsoft.EntityFrameworkCore")
    .GetResult();
result.IsSuccessful.Should().BeTrue();
```

这条测试我们第一天就写上了，三个月后它拦下了两次"临时"引用：一次是有人为了少写映射在领域层用了 EF 实体，一次是有人把 ASP.NET 的 `IHttpContextAccessor` 注入了用例。两次都是好心图省事，两次都在 CI 里被挡下。没有这条测试，这两处现在还在，而且会各自繁衍出十个引用点。

## 什么时候不拆

最后说不适用的场景。三个以内的接口、一个数据库、没有第二套技术选型预期的项目，整洁架构的全部收益是"将来可能好换数据库"，而这个"将来"大概率不会来。此时更该投入的是把业务逻辑写清楚、把测试写扎实。架构的复杂度应该来自问题本身，而不是来自对问题的想象。约束依赖方向值得每个项目遵守，为它配上五件套，只在变化真的多到需要时才行。

### 一个可以立刻执行的最小版本

不建四层目录，只做两件事。第一，把业务规则从控制器里搬出来，集中到一个不引用 Web 框架的类里；第二，给这个类写架构测试，锁住它不依赖基础设施。两件事半天完成，依赖方向从此有了守卫，将来需求真的复杂了，在它的基础上长层也来得及。架构是演进的，不是一次画完的，画得太满的架构图，通常死得最快。

> 好的架构不是让系统看起来专业，而是让下一次改动落在该落的地方。
