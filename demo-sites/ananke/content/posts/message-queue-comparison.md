选消息队列大概是后端最频繁的技术决策之一，也是最容易变成"我们公司用什么我就用什么"的决策。去年我们做过两次选型，一次给日志管道选了 Kafka，一次给订单事件流选了 RocketMQ，中间还在一个小工具项目里裸用过 RabbitMQ。这篇文章把三次选型的判断依据整理成一份对比，不评优劣，只回答一个问题：什么场景下该选谁。先说一个容易被忽略的前提：选型约束里，运维成本经常比性能更重要。团队只有两个基础设施运维时，一个需要三节点加协调服务的集群本身就是风险来源，这时候"能单机起步"的权重应该调到最高。下面所有结论都建立在"你有基本的中间件运维能力"这个前提上，没有这个前提，选你团队现在能睡个好觉的那个。

## 先分清你的场景

选型之前先回答三个问题，答案会直接淘汰掉一半候选：消息是任务还是日志？能容忍消息丢失吗？消费方需要按 key 顺序消费吗？

- 任务：每条消息对应一次待执行的工作，要求不丢、要确认、要重试，典型如下单后发券
- 日志：持续产生的事件流，关注吞吐和回放，丢几条可以接受，典型如用户行为埋点
- 顺序：同一订单的状态变更必须按序处理，乱序会导致状态机错乱

任务场景看重确认机制，日志场景看重留存和回放，顺序场景看重分区策略。三个场景都占的团队，最后往往是两套队列并存，这不是不优雅，是职责不同。我们线上就是 Kafka 管埋点和行为日志，RocketMQ 管订单和支付事件，两套集群、两套监控，看起来重复，实际各自的配置和运维手法完全不同，硬要统一到一个中间件上，两边都要妥协。共存的前提是消息 schema 和接入规范统一，运维界面分开，这比强行统一实现要现实得多。

## 三个候选的正面对比

| 维度 | Kafka | RabbitMQ | RocketMQ |
| --- | --- | --- | --- |
| 核心模型 | 持久化提交日志，按 offset 拉取 | AMQP 消息代理，推送给消费者 | 提交日志加标签过滤，拉取为主 |
| 吞吐 | 百万级每秒 | 万级每秒 | 十万级每秒 |
| 端到端延迟 | 毫秒级，批量攒大会抬高 | 微秒到毫秒级 | 毫秒级 |
| 消息留存 | 可配，默认七天起，支持回放 | 消费后即删，难回放 | 可配，支持按时间回放 |
| 顺序保证 | 分区内有序，按 key 分区 | 单队列单消费者才有 | 队列内有序，支持全局顺序消息 |
| 事务消息 | 无原生事务消息 | 发布确认，无分布式事务 | 支持半消息事务 |
| 运维成本 | 中，依赖 ZooKeeper 或 KRaft | 低，单机即可起步 | 中，NameServer 加 Broker |

## Kafka：日志与流处理的默认答案

Kafka 的本质是持久化的分布式提交日志，生产者追加写，消费者按 offset 拉取，读多少次都不影响别人。这个模型带来两个别的队列没有的能力：回放和背压。回放意味着消费方挂了三天，修好之后能从三天前的 offset 重新读；背压意味着消费慢只是 offset 追得慢，不会把 broker 压垮。

### 分区是 Kafka 的一切

分区是 Kafka 全部设计的核心。消息按 key 哈希进分区，同一 key 永远落同一分区，这是顺序保证的来源，也是消费者并行度的上限。分区数设小了，扩容只能加分区，而加分区之后旧 key 的映射会变，顺序承诺只对新分区的 key 成立。这个限制让"分区数一旦定了就不能随便改"成为 Kafka 使用的第一纪律。我们的埋点 topic 一开始设了 3 个分区，流量涨上来后加到 12 个，结果历史 key 的顺序全乱了，只能新建 topic 双写切换，教训很贵。

代价是细节多。分区数定了不能随便减，consumer group rebalance 会有短暂停顿，消息不是"发给谁"而是"谁自己来拿"。下面是一份生产可用的最小配置，注意 `acks=all` 和 `min.insync.replicas` 是一对，单独调任何一个都会破坏耐久性承诺。

```yaml
# Kafka 生产者最小可用配置
bootstrap.servers: kafka-1:9092,kafka-2:9092,kafka-3:9092
acks: all
retries: 3
enable.idempotence: true          # 幂等生产者，避免重试导致重复
max.in.flight.requests.per.connection: 5
compression.type: lz4
key.serializer: org.apache.kafka.common.serialization.StringSerializer
value.serializer: org.apache.kafka.common.serialization.StringSerializer
# topic 级别要求：replication.factor=3, min.insync.replicas=2
```

按 <kbd>Ctrl</kbd>+<kbd>C</kbd> 可退出控制台消费者，注意退出前先记录好当前 offset，否则重新进入会从 latest 开始，容易误判成消息丢失：

```bash
# 查看 topic 各分区的最新 offset 与消费组滞后
kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 \
  --describe --group order-events

# 从指定 offset 起实时消费，用于验证消息内容
kafka-console-consumer.sh --bootstrap-server kafka-1:9092 \
  --topic order-events --from-beginning --max-messages 10
```

如果消费组 lag 持续增长，先确认是消费逻辑慢还是 rebalance 太频繁，两者的解法完全不同。

## RabbitMQ：任务队列的稳妥选择

RabbitMQ 是教科书式的消息代理：交换机、队列、绑定，支持多种路由规则，消息确认、死信队列、优先级开箱即用。它的强项是可靠投递，生产者确认加消费者手动 ack，可以做到消息不丢且只被处理一次（配合业务幂等）。吞吐比 Kafka 低一个量级，但绝大多数内部系统的量级根本碰不到它的天花板。

适合 RabbitMQ 的典型场景：异步任务（发邮件、生成报表）、请求削峰、需要复杂路由（按 topic 和 direct 混合）的内部集成。它的路由模型基于 AMQP 协议，协议细节可以参考 https://zh.wikipedia.org/wiki/高级消息队列协议 ，理解交换机和绑定规则之后，复杂路由基本都能表达出来。

### 死信队列与延迟消息

RabbitMQ 有两个开箱即用的能力值得单独提。一是死信队列：消费失败超过次数、消息 TTL 过期、队列长度超限，三种情况都能自动转入死信队列，人工介入或延迟重试都有据可查，不会让失败消息凭空消失。二是延迟消息：用死信队列加 TTL 就能实现"三十分钟后提醒"这类定时任务，不必额外引入调度系统。我们的订单超时取消用的就是这个方案，比轮询数据库干净，也比引入一套延迟队列中间件轻。下面是一条 JSON 消息的约定，我们在三个项目里都用这个结构，关键是 `trace_id`，排障时能省一半时间。

```json
{
  "message_id": "9f2c1a34-7b1e-4c2d-9a55-1e0f3c8d2b77",
  "trace_id": "3c9a1f0e2d8b47c5a6f0e1b2d3c4a5e6",
  "type": "order.paid",
  "occurred_at": "2024-08-20T09:31:02+08:00",
  "payload": { "order_id": "O202408200001", "amount": 328.00 },
  "retry_count": 0
}
```

## RocketMQ：事务消息与顺序的折中

RocketMQ 在国内电商场景里打磨得很深，两个能力是另外两家没有原生支持的：事务消息和按队列的顺序消费。事务消息用半消息加回查解决"数据库事务提交了但消息没发出去"的问题，顺序消息用 MessageQueueSelector 把同一订单的变更钉在同一个队列。如果你的链路同时要求最终一致和顺序，它是三个里最省事的。

它的代价是 API 抽象比 Kafka 厚，排查问题要同时看 NameServer、Broker 和控制台三层。另外 RocketMQ 5.x 之后架构向 Kafka 靠拢，老项目升级要注意兼容。

事务消息的执行分两步：先发一条半消息，消费者此时不可见；本地事务提交后发提交确认，消息才对消费者可见；如果提交确认中途丢失，Broker 会按递增间隔回查生产者的接口，由生产者根据本地事务的实际状态决定提交还是回滚。这个回查接口必须实现幂等，因为重试期间它会被反复调用，不幂等的实现对数据库就是一次 DDoS。另外半消息的 topic 对消费者不可见，误把它当普通 topic 订阅是新手常见困惑。

## 选型结论

把三个问题带回来看，结论其实很窄：埋点和行为日志选 Kafka，要回放和流处理也选 Kafka；异步任务和内部集成选 RabbitMQ，团队小、运维预算低时尤其如此；涉及支付、库存这类要事务消息和强顺序的链路，选 RocketMQ。

> 队列不是数据库。把业务数据长期存在队列里当事实来源，出问题时没有任何工具能帮你找回一致的状态。

还有一个跨选项的共性问题：消息的 schema 要有注册表。我们在三个项目里都因为字段类型悄悄改过（字符串改数字）导致消费方解析失败，后来所有消息结构进 Schema Registry，破坏性变更直接拒绝发布。这件事的投入是半天，省下的排障时间以天计，比选哪个队列本身更值得先做。
