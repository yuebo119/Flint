传统数据库擅长精确匹配：`WHERE status = 'paid'` 一查一个准。可用户输入"帮我找上周买的那双透气跑鞋"时，精确匹配就束手无策了，因为数据库里存的是商品标题和属性，没有"透气"这个字段。向量数据库解决的就是这类问题：把文本、图片变成向量，用距离衡量语义相似度。这篇从最基础的概念讲起，一直讲到一次检索的完整链路。

## 什么是向量与嵌入

嵌入是把一段内容映射成一个固定长度的浮点数组，这个数组叫向量。比如一句话经过嵌入模型处理后，可能变成一个 768 维的向量：

```json
{
  "doc_id": "article-1001",
  "title": "B+ 树索引原理",
  "embedding": [0.021, -0.114, 0.087, 0.043, -0.152, 0.096]
}
```

向量的神奇之处在于语义相近的内容，向量距离也相近。"怎么让查询变快"和"索引优化方法"字面完全不同，向量距离却很近；"今天的晚饭吃什么"和前者距离就远。这个性质是语义搜索的地基，而嵌入模型的质量决定了地基有多牢。

## 三种相似度度量

有了向量，接下来要定义"远近"。常用三种度量：

- 余弦相似度：看两个向量方向的夹角，范围从 -1 到 1，只关心方向不关心长度
  - 文本语义搜索最常用，长文本和短文本也能比
  - 值为 1 表示完全同向，0 表示正交，-1 表示完全反向
- 欧氏距离：两点间的直线距离，关心绝对位置
  - 向量各维度量纲一致时更合适，如图像特征
- 内积：两个向量对应位相乘再求和
  - 归一化后的内积等价于余弦相似度，计算最快

### 三种度量的对比

| 度量 | 定义 | 适用场景 | 计算开销 |
| --- | --- | --- | --- |
| 余弦相似度 | 向量夹角 | 文本语义搜索 | 点积加两次模长 |
| 欧氏距离 | 空间直线距离 | 量纲一致的特征 | 逐维差平方再开方 |
| 内积 | 对应位相乘求和 | 归一化后的向量 | 最低 |

归一化后的内积与余弦相似度排序结果一致，所以追求速度的引擎常常先归一化再算内积。选度量要看嵌入模型的训练目标：模型训练时用什么度量做对比学习，检索时就用同一度量，混用会让召回率打折。

用 Python 手算一次余弦相似度，比读十页公式直观：

```python
import math

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb)

query = [0.8, 0.2, 0.1]
doc_a = [0.9, 0.1, 0.2]   # 语义相近
doc_b = [0.1, 0.9, 0.3]   # 语义较远

print(round(cosine(query, doc_a), 3))  # 0.978
print(round(cosine(query, doc_b), 3))  # 0.612
```

生产环境不要自己写这个循环，调用数据库或向量库的内置函数，性能差着数量级。手算版的价值在于理解计算在做什么。

## 近似最近邻索引：HNSW 与 IVF

精确找最相似的 K 个向量叫 KNN，要把查询向量和库里每个向量都比一遍，一千万条就是一千万次距离计算，延迟不可接受。实际系统用的都是近似最近邻（ANN），用少量精度换数量级的速度。

<details>
<summary>点开：两种主流 ANN 索引的工作原理</summary>

HNSW（分层可导航小世界图）把向量组织成多层图，上层稀疏做高速跳转，下层稠密做精细查找，像高速公路加城市道路的组合。查询从顶层入口开始，每层贪心跳到更近的节点，逐层下降。优点是召回率高、查询快，代价是内存占用大，图结构本身要常驻内存。

IVF（倒排文件）先用聚类把向量空间切成若干簇，建索引时记录每个向量属于哪个簇，查询时只找离查询最近的几个簇。优点是内存省、构建快，缺点是召回率受簇划分质量影响，数据分布不均时性能抖动。

工程上的常见组合是 HNSW 加标量量化，或者 IVF 加乘积量化，在召回率、内存、延迟之间找平衡点。

## 一次检索的完整链路

把概念串起来，一次语义搜索在系统里是这样流动的：

1. 用户输入查询文本
2. 调用嵌入模型，把查询变成向量
   - 注意查询和文档必须用同一个嵌入模型，换了模型历史向量全部作废
3. 向量库在 ANN 索引里找最相似的 K 个文档 ID
4. 用文档 ID 回业务库取完整记录
   - 这一步是过滤条件的战场，按权限、按时间、按状态过滤后再算相似度
5. 按相似度排序，返回结果

第 4 步容易被忽略。纯向量检索不过滤权限，会把用户不该看的文档捞出来；不过滤时间，会把三年前的过期文章排在最前。过滤与向量检索的先后顺序，直接决定产品的正确性。

## 典型应用场景

- 语义搜索：换关键词也能搜到内容，容忍同义表达
- RAG 检索增强：给大模型找参考资料，答案有据可查
- 推荐系统：用行为序列生成用户向量，匹配物品向量
- 去重与聚类：海量文本里找近似重复，比哈希去重更能容忍改写

## 量化与内存账

向量数据很占内存，这是向量数据库选型时最实际的约束。一条 768 维的浮点向量占 3KB，一千万条就是 30GB，这还没算索引结构。HNSW 的图本身也要常驻内存，总占用通常是原始向量的 1.5 到 2 倍。

量化是主要的压缩手段。标量量化把每个浮点维度压成一个字节甚至更短，内存降到四分之一到八分之一，召回率损失可控；乘积量化进一步把向量切成若干段，每段用码本里的一个编码代替，压缩率更高，但查询前要算距离表，延迟会上升。工程上的决策树大致是：数据量在内存放得下就不量化，放不下先上标量量化，内存极度紧张再考虑乘积量化加磁盘存储。

粗过滤加精排是另一条路。先用少量维度的粗向量快速圈出候选，再用完整向量精排。这套思路和传统检索的两段式设计同源，用一点召回率换大量内存和延迟。

## 什么时候不要用向量数据库

技术选型的清醒在于知道边界。下面几种情况，向量数据库解决不了问题，甚至帮倒忙。

> 向量检索回答的是"像不像"，精确匹配回答的是"是不是"。两个问题都有价值，也都有各自的工具，混用是灾难的开始。

条件明确的精确查询，用关系数据库。按 ID 取记录、按状态过滤、按时间范围分页，这些查询的语义是精确的，B+ 树索引又快又准，向量检索的近似性反而是负担。

数据量小的场景，先用现成方案。几十万条文档，PostgreSQL 加 pgvector 扩展就能支撑语义检索，引入一套新的存储系统意味着新的运维、新的备份、新的故障模式，成本远超收益。

语义相似帮不上忙的场景。电话号码、身份证号、错误码这类数据，相似没有业务含义，向量检索找不到有意义的邻居。另外，短文本的嵌入质量普遍低于长文本，搜索词只有两三个字时，embedding 的区分度很差，这种场景关键词检索仍然更可靠。

## 与关键词检索的混合使用

成熟系统的检索层很少只用向量。用户搜"iPhone 15 手机壳"，语义检索能找到"苹果十五保护套"，但用户搜具体型号"iPhone 15 Pro Max 透明"时，精确匹配反而更准，向量检索可能把"iPhone 14"也排进来。

所以生产检索通常是混合架构：关键词检索（倒排索引）保证精确命中，向量检索补充语义泛化，两路结果用排序公式融合。常见的融合策略是按分数加权，或者用排序模型对两路候选统一重排。选型时别把向量数据库当成唯一入口，它的定位是候选召回的一路，最终排序往往还要交给更精细的打分逻辑。

这也是很多团队踩过的坑：上了向量数据库就废弃关键词索引，结果精确查询的准确率先掉了一截，语义提升的那部分又没人感知，最后两边不讨好。检索质量是精确率和召回率的平衡，两路都要留。

## 选型时的三个提醒

第一，嵌入模型是最大的技术决策，换模型等于重建索引，先用离线评测把候选模型比出高下。第二，先评估数据规模，几十万条用 PostgreSQL 的 pgvector 扩展足够，千万级以上再考虑专用向量库。第三，向量检索是锦上添花不是雪中送炭，精确条件查询该用 B+ 树索引，两者是互补关系。

相似度的数学定义可以参考维基百科的余弦相似度词条（https://zh.wikipedia.org/wiki/余弦相似度）。
