业界有句老话：数据和特征决定了模型的上限，模型和参数只是逼近这个上限。但在 AutoML 和深度模型大行其道的今天，这句话不仅没过时，反而更值得强调——自动调参能替你搜出好模型，却不能替你理解业务里哪些信号真正预示结果。这篇文章按特征类型过一遍实战手法，每类给出代码、坑和检查点。

## 数值特征：缩放、分桶与变换

### 三个常规动作

数值特征进模型前有三件常规动作。**缩放**把不同量纲拉到同一区间，树模型不需要，但线性模型和神经网络离不了；**分桶**把连续值切成区间，把"三十岁和三十一岁差别很大"这种非线性直接编码进特征；**变换**处理长尾分布，收入、访问量这类右偏数据取对数后更接近正态，模型才学得动。

```python
import numpy as np
import pandas as pd

def log1p_amount(df: pd.DataFrame, col: str) -> pd.DataFrame:
    """右偏金额列取对数，压缩长尾；负值业务上不该出现，先查出来而不是硬转。"""
    if (df[col] < 0).any():
        raise ValueError(f"{col} 出现负值，先修数据再谈特征")
    df[f"{col}_log"] = np.log1p(df[col])
    return df

def bucketize(df: pd.DataFrame, col: str, bins: list[float], labels: list[str]) -> pd.DataFrame:
    """等边界分桶；注意边界值默认左闭右开，要和业务口径对齐。"""
    df[f"{col}_bucket"] = pd.cut(df[col], bins=bins, labels=labels, right=False)
    return df

df = pd.DataFrame({"amount": [0, 9.9, 199, 8888, 520000]})
df = log1p_amount(df, "amount")
df = bucketize(df, "amount", bins=[0, 50, 500, 50000, np.inf], labels=["小", "中", "大", "超大"])
```

### 边界要落在业务断点上

分桶的边界不要凭空拍。先看分布直方图，在自然断点（比如包邮门槛、会员档位）上切，比等宽或等频切更有业务含义。树模型虽然能自己切分，但显式的分桶特征仍然有两个好处：抗异常值、可解释。

## 类别特征：从独热到目标编码

低基数类别（性别、渠道、城市）用独热编码简单可靠，维度爆炸的场景（上千个类目）就要换手段：

- **目标编码**：用该类别对应的目标变量均值替代类别本身，"北京"变成一个数字，比如历史转化率 0.042；
- **WOE 编码**：信用评分领域的老将，把每个类别换算成对目标的对数几率贡献，天然适配逻辑回归；
- **Embedding**：高基数类别（用户 ID、商品 ID）进神经网络时，用嵌入层把每个 ID 学成向量，是深度推荐的标准配置；
  - 神经网络场景下还能顺带缓解稀疏问题，共现实例少的 ID 也能分到像样的向量。

目标编码效果猛，但坑也最深，下一节的折叠块专门讲。独热和 WOE 的对比：

| 编码方式 | 适用基数 | 主要风险 | 备注 |
|----------|----------|----------|------|
| 独热 | 低（几十以内） | 维度灾难 | 最稳，默认首选 |
| 目标编码 | 中高 | 泄漏 | 必须交叉统计加平滑 |
| WOE | 中 | 同样需防泄漏 | 风控领域标配 |
| Embedding | 很高 | 需数据量支撑 | 深度模型专属 |

## 时间特征与滑窗

涉及时间的问题，时间本身就是最强的特征之一。基础的是拆解：小时、星期几、是否节假日、是否月初月末。进阶的是**滑窗统计**：过去 7 天下单次数、过去 30 天平均客单价、最近一次登录距今天数。滑窗特征把"行为趋势"压缩成数字，比单条最新行为更有预测力。

```sql
-- 为每个用户计算过去 30 天的行为滑窗特征
SELECT
    user_id,
    COUNT(*) AS orders_30d,
    SUM(amount) AS amount_30d,
    AVG(amount) AS avg_amount_30d,
    MAX(created_at) AS last_order_at,
    DATE_DIFF(CURRENT_DATE(), DATE(MAX(created_at)), DAY) AS days_since_last_order
FROM orders
WHERE created_at >= CURRENT_DATE() - INTERVAL 30 DAY
GROUP BY user_id;
```

滑窗窗口的选择是业务问题不是数学问题：预测次日留存，看 7 天；预测季度 LTV，看 90 天。多个窗口一起上（7 天、30 天、90 天）让模型自己学权重，是更省心的做法。

<details>
<summary>目标编码为什么是最常见的泄漏源</summary>

最朴素的实现是"用全量数据计算每个类别的目标均值"，问题就出在全量：验证集里的样本也参与了统计，它们的目标值通过这个均值漏进了训练特征，线下指标虚高，上线现原形。正确做法是交叉统计——用其他折的数据计算当前折的编码值，再对每个编码加平滑：

```python
def target_encode(train: pd.DataFrame, col: str, target: str, smoothing: float = 20.0) -> pd.DataFrame:
    """带平滑的目标编码：样本少的类别向全局均值收缩，避免小样本噪声被当成信号。"""
    global_mean = train[target].mean()
    agg = train.groupby(col)[target].agg(["mean", "count"])
    smooth = (agg["mean"] * agg["count"] + global_mean * smoothing) / (agg["count"] + smoothing)
    return train[col].map(smooth).fillna(global_mean)
```

线上推理时用的是训练阶段存下来的映射表，类别没出现过就填全局均值——这条路径要在代码里显式写出来，否则线上遇到新类目直接报错。

## 交叉特征与业务先验

单特征之外，把两个特征组合往往能撞出预测力：用户年龄段 × 商品类目、渠道 × 是否新客。GBDT 能自动学交叉，但显式构造的交叉特征有三类场景特别值：线性模型（不会自己交叉）、交叉本身有强业务含义（要给人看的解释）、组合数可控（别把十万维交叉扔给任何模型）。

业务先验是最被低估的特征来源。客服团队知道"晚上十点后的投诉升级率最高"，风控团队知道"凌晨注册的账号风险高"——这些know-how 无法从数据里自动挖出来，只能靠访谈和复盘变成特征。做特征工程的一半时间在和数据打交道，另一半在和人打交道。

## 缺失值与异常值：先处理还是让模型学

缺了一小时的数据，填零还是留空？这是特征工程里最日常的抉择。树模型（XGBoost、LightGBM）能原生处理缺失值，自己学"缺失时往哪边分"，这种情况保留缺失即可（缺失值路由的默认行为可以参考 [XGBoost 的公开文档](https://example.com/xgboost-docs)），甚至可以把"是否缺失"本身作为一个二值特征——缺失往往本身就是信号，比如风控场景里紧急联系人缺失，本身就在预示风险。线性模型和神经网络没有这个能力，必须显式填充，中位数、均值，或者训练一个模型来预测缺失值，成本依次上升，优先前两种。

异常值是另一端的坑。录入错误导致年龄三百岁、金额多一个零，这类值经过标准化后被拉到离群位置，把模型的注意力带偏。处理顺序是：先用业务规则圈出不可能值（负的年龄、未来的生日），查来源而不是直接删；剩下的疑似异常用统计方法标记（三倍标准差外或箱线图规则），标记后让模型或后续规则决定怎么处理。直接删除最省事，也最危险——你删掉的可能是最值钱的欺诈样本。

## 特征选择的减法

特征不是越多越好。维度灾难真实存在：几百维无关特征堆进去，树模型尚能扛住，线性模型直接过拟合，训练和推理成本还线性上涨。做减法的三招：一看重要性，用模型的特征重要性或置换重要性砍掉垫底的；二看相关性，两个特征相关性超过 0.95，留业务含义更清晰的那个；三看稳定性，在时间窗上重要性忽高忽低的特征，多半是在拟合噪声，砍掉不可惜。减法做完，模型更小、更快、更稳，也更容易向业务方解释。

## 上线前的一致性检查

特征工程最后一道坎是训练与服务的一致性。同一个逻辑两套实现（Python 算训练、Java 算线上）是经典事故源。三条防线：

1. **单一来源**：特征逻辑用同一种语言同一份代码生成训练集和线上请求的特征；
2. **快照比对**：上线前用同一批历史请求，对比线上特征与离线复算结果的差异，超阈值就报警；
3. **监控兜底**：线上特征分布持续监控，某天某列突然全零或分布剧变，立刻回滚并报警。

> 特征做错了，模型越准错得越远。一个静默错误的特征会让整个模型"自信地"学歪，而且因为是静默的，往往几周后才在业务指标上爆出来。

特征工程没有魔法，套路就这几类：数值会变换、类别会编码、时间会开窗、相关会交叉。真正的门槛不在手法，在于对业务的理解深度——知道什么信号预示什么结果，才是数据科学家和调包侠的分水岭。
