垃圾回收是个少有的"六十年后仍在演进"的经典问题。内存管理的目标从来没变过：不泄漏、不悬空、不浪费。变的是约束条件：堆从几兆到几十 G，停顿从没人管到亚毫秒级，核数从单核到上百核。这篇按年代讲主线：每一代方案要解决什么具体问题，付出了什么代价，又为什么被下一代接棒。

## 1958：标记清除的开端

John McCarthy 在 Lisp 里第一次实现自动内存管理。想法朴素得可爱：从根（全局变量、调用栈）出发遍历所有可达对象并标记；遍历整堆，没标记的统统回收。Lisp 的链表结构让"遍历"和"紧凑"都变得自然，标记清除（mark-sweep）就此诞生。它解决了忘记释放的问题，代价是两次遍历堆和随之而来的停顿，以及回收后堆的碎片化。

标记清除最致命的短板是停顿和堆的不可控增长：标记期间应用必须停住，否则一边标一边改，标记结果就是过期的。这个"应用停住等 GC"的模式，后面五十年的算法演进，本质上都在跟这两个字较劲。

Lisp 的创造者 McCarthy 后来被追认为 AI 领域奠基人之一，地址在 <https://zh.wikipedia.org/wiki/Lisp>，这页顺带能看清早期动态语言和 GC 的共生关系。

## 1960 年代：引用计数的兴衰

### 为什么它看起来很美

每个对象配一个计数器，多一个引用加一，少一个减一，归零即回收。回收时机均匀分布，没有长停顿，实现也直观：

```text
incref(obj):
    obj.count += 1

decref(obj):
    obj.count -= 1
    if obj.count == 0:
        for child in obj.children:
            decref(child)
        free(obj)
```

对象一死就被发现，堆占用曲线平滑，调试时心里有底。这些优点让它至今活在文件句柄、音频缓冲区这类"生命周期明确、数量可控"的场景里。

### 为什么它慢慢退场

三个问题慢慢磨掉了它的光环。循环引用让互相牵手的对象永远归不了零，泄漏照常发生，检测环还要额外算法；每次指针赋值都要更新计数，开销摊到每一次写操作上；计数本身在多线程下要同步，成本再涨一截。它没有死透，只是从通用方案退成了特定场景的补充。

## 1980 年代：分代假说

转机来自一个经验观察：绝大多数对象朝生夕死。临时字符串、中间结果、一次性请求上下文，用完就扔。这就是弱分代假说[^1]，它直接催生了分代收集：堆分成新生代和老年代，新生代只存新对象，回收时只扫新生代，成本降到整堆扫描的零头；熬过若干次回收的对象晋升到老年代，后者收集频率低得多。

配套的新生代算法叫 scavenge：把堆分成两半，只从一半里复制存活对象到另一半，整块清零原空间。存活率低的时候，复制量小得惊人，停顿自然短。分代收集还有个工程细节值得知道：新生代的 scavenge 需要一块空闲空间做复制目标，所以内存 footprint 永远大于存活对象。这也是为什么 JVM 堆给大了反而更稳，不是浪费，是给 scavenge 留跑道。

谱系走到这里长成了这样：

- 标记清除
  - 标记-紧凑（Mark-Compact）：回收时顺带整理碎片
  - 并发标记清除（CMS）：标记与清除同应用线程并发
- 引用计数
  - 延迟引用计数
  - 环检测（trial deletion 等）
- 分代收集
  - 新生代 scavenge：复制存活对象到另一半空间
  - 老年代收集
    - G1：整堆切 region，按收益排序回收
    - ZGC / Shenandoah：并发压缩，目标亚毫秒停顿

## 1990 年代到 2000 年代：并发与增量

交互式应用兴起后，停顿时间成了新战场。CMS 让标记和清除与应用线程并发执行，代价是引入浮动垃圾和复杂的重置逻辑；增量式 GC 把一次收集切成小片，穿插在应用执行之间，用总吞吐换单次停顿。

并发标记的真正难点是"应用一边跑一边改引用"：漏掉新生成的引用，就会漏标活对象，酿成悬空访问。解法是写屏障：在引用赋值这个动作里插一小段检查，把改动记录给 GC。写屏障是几乎所有现代并发 GC 的心脏，也是它们比教科书算法复杂一个数量级的原因。GC 设计从此进入"拿复杂度换停顿"的阶段，每一毫秒的改善背后都是成倍的实现成本。

## 2010 年代至今：区域化与低延迟

G1 把堆切成等大的 region，按回收收益排序挑选集合，停顿时间变得可预测、可设置；ZGC 和 Shenandoah 把目标定到亚毫秒级，染色指针和读屏障轮番上阵，连压缩都能并发做。Go 的 GC 走了另一条路：并发三色标记加写屏障，目标不是零停顿，而是"短到不碰延迟指标"，实现上刻意保持简单。三色标记把对象分成白、灰、黑三种状态：根对象染灰，从灰对象出发把引用对象染灰、自己染黑，直到没有灰对象，剩下的白色就是垃圾。并发执行的麻烦在于应用线程一边跑一边改引用，可能把白色对象挂到黑色对象底下，漏标成垃圾。Go 1.8 起用的是混合写屏障，插入屏障加删除屏障双保险，不用像早期方案那样暂停第二阶段，代价是每次指针赋值都多一点开销。这套设计换来的结果：默认配置下停顿在亚毫秒级，吞吐损失控制在个位数百分比，对大多数服务端负载是划算的。

在 Go 里可以这样观察 GC 的呼吸：

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m runtime.MemStats
	for i := 0; i < 3; i++ {
		churn := make([][]byte, 0, 1000)
		for j := 0; j < 1000; j++ {
			churn = append(churn, make([]byte, 1024))
		}
		runtime.GC()
		runtime.ReadMemStats(&m)
		fmt.Printf("第 %d 轮：存活堆 %d KB，累计 GC %d 次\n",
			i+1, m.HeapAlloc/1024, m.NumGC)
		_ = churn
	}
}
```

```bash
GODEBUG=gctrace=1 go run main.go
```

`gctrace` 输出里最该看的是 `->` 前后的堆大小和 `(n)` 里的 GC 次数：两次之间堆涨得越快，说明分配速率越高；GC 次数涨得快而堆不涨，说明存活对象少，正是分代假说生效的样子。这三十行代码的价值不在输出本身，在于建立手感：亲手看过堆的涨落，再看监控曲线时，数字背后就是分配和回收的具体动作，而不是抽象指标。

## 停顿、吞吐与内存的不可能三角

六个十年的方案差异，最后都能归到一个三角上：停顿短、吞吐高、内存 footprint 小，三者最多取二。CMS 和 ZGC 选了短停顿，交出去的税是吞吐或内存；Go 选了平衡，换取实现的简单和可预测；分代 scavenge 选了吞吐和低延迟，代价是内存利用率打折（永远有一半空间空着）。

选运行时的时候，值得先问自己落在三角的哪一角：批处理在乎吞吐，交互服务在乎尾延迟，嵌入式在乎内存 footprint。答案没有高下，只有合不合身。还有一个常被忽略的变量是负载形状：分配速率、存活率、对象大小分布，三个数字一变，同一套 GC 的表现能差出数倍。看 GC 调优文章时先看对方的负载，再抄参数，否则等于拿别人的药方治自己的病。

[^1]: 弱分代假说通常追溯到 David Ungar 1984 年关于 Generation Scavenging 的论文，它至今仍是几乎所有主流 GC 的设计前提。

| 年代 | 代表算法 | 停顿特征 | 主要代价 |
|------|----------|----------|----------|
| 1958 起 | 标记清除 | 长且不可控 | 两次遍历、碎片化 |
| 1960 起 | 引用计数 | 均匀无长停 | 循环引用、指针开销 |
| 1980 起 | 分代收集 | 短且频繁 | 晋升策略调优 |
| 2000 起 | 并发 CMS / G1 | 可预测 | 实现复杂度陡增 |
| 2010 起 | ZGC / Shenandoah | 亚毫秒 | 读屏障与染色指针开销 |

## 尾声

> 停顿、吞吐、内存，最多取二。看 GC 配置先看它落在哪个角，再决定要不要动手，这句话能省掉大部分无效调优。

六十年看下来，GC 的主线不是"更聪明的回收"，而是"把停顿从秒级搬到毫秒级再搬到微秒级"的工程长征。每一代方案都不是在原理上推翻前代，而是在新的硬件和应用约束下重新权衡。今天的服务器动辄几百个核，低延迟要求又逼近实时系统，这个三角大概还要被拉扯很多年。下一次演进的种子，可能已经埋在某个论文的写屏障里了。对使用者的启示只有一个：GC 不是黑盒，理解手上运行时的算法形状，排查性能问题时才知道该看哪几个指标。
