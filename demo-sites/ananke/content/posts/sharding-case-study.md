订单表是电商系统的心脏，也往往是第一个撞墙的表。我们这张表在去年秋天到了八亿行，日均新增两百万，主库磁盘打到七成，凌晨批处理窗口从四十分钟拉长到三个小时，运维三次在凌晨被 IO 告警叫起来。这篇文章记录整个拆分方案从选型到落地的过程，以及踩过的坑。

## 方案选型：三条路的取舍

摆在面前的有三条路，团队用一周做了评估。

1. 垂直拆分：按业务把订单相关表拆到订单主库、订单明细库、支付库
   - 好处是改动小，各库职责清晰
   - 坏处是订单主表本身还是八亿行，磁盘问题原样存在
   - 适合表宽、跨业务耦合重的场景，治标不治数据量
2. 水平拆分：按某个维度把行切到多个库表
   - 直接解决单表数据量问题，理论上可继续扩展
   - 代价是跨片查询、分布式事务、运维复杂度全部上来
   - 数据量与查询模式都集中在一张表时，这是主路
3. 迁移到 NewSQL：交给 TiDB 这类分布式数据库
   - 业务改造成本最低，分片细节被屏蔽
   - 团队对分布式数据库的运维经验不足，当时版本对部分 SQL 兼容有坑
   - 列为后续演进方向，本次不动

结论很清晰：垂直拆分解决不了行数，NewSQL 风险不可控，水平拆分是当下唯一能落地的选择。

## 分片键怎么选

分片键决定数据怎么分布，是整套方案里最不能拍脑袋的一步。三个候选：

- 用户 ID 取模：同一用户的订单落在同一片，按用户查订单全部命中单片
  - 运营按时间范围查全量订单要扫全部十六片，聚合压力大
  - 大客户订单量悬殊，可能把单片打歪
- 订单创建时间按周归档：新表按周建，天然适合冷热分离
  - 跨周查询要走多张表，且热点集中在最新表
  - 适合订单只按时间查、不按用户查的业务
- 用户 ID 加时间基因：`shard_key = user_id % 16`，订单号里嵌入分片位
  - 按用户查、按订单号查都命中单片
  - 时间范围查询仍需广播，这一点绕不开

### 三个候选的横向对比

| 维度 | 用户 ID 取模 | 时间归档 | 基因法 |
| --- | --- | --- | --- |
| 按用户查 | 命中单片 | 可能跨片 | 命中单片 |
| 按时间查 | 广播十六片 | 命中少数表 | 广播十六片 |
| 数据均衡 | 依赖用户订单分布 | 热点在最新表 | 依赖用户订单分布 |
| 订单号直查 | 需映射表 | 按周推断 | 直接解析 |
| 实现复杂度 | 低 | 中 | 中 |

我们的查询模式是用户端看订单占九成，运营后台按时间查占一成。最终选用户 ID 取模，十六个分片，运营查询走离线数仓，不在线库上跑。

## 配置落地

分片规则用配置文件描述，中间件按规则路由：

```yaml
sharding:
  datasource:
    - name: ds_0
      url: jdbc:mysql:<SECRET_811d998b>
    - name: ds_1
      url: jdbc:mysql:<SECRET_10d296b7>
  rules:
    - logic_table: orders
      actual_nodes: ds_${0..15}.orders_${0..15}
      sharding-column: user_id
      algorithm:
        type: MOD
        props:
          sharding-count: 16
```

一条查询进来，中间件先解析 SQL，取出 `user_id` 代入算法，路由到 `ds_7.orders_7`。路由结果对业务透明，DAO 层代码不用改，这是分片中间件存在的意义。

```json
{
  "sql": "SELECT * FROM orders WHERE user_id = 10086 AND created_at > '2026-01-01'",
  "routing": {
    "logic_table": "orders",
    "actual_table": "ds_13.orders_13",
    "sharding_value": 10086,
    "hit_shards": 1
  }
}
```

## 迁移实施：双写、校验、切换

八亿行数据不可能停机搬完，迁移分五个阶段走了十一天。

1. 全量拷贝：用 DataX 按主键分片导出旧库，并行写入十六个新分片，全程不限速跑满带宽
2. 增量追平：全量拷贝期间旧库仍在写入，按自增 ID 持续追赶增量，直到落后控制在秒级
3. 双写灰度：应用层同时写旧库和新库，读仍然走旧库
   - 双写组件对写入失败做补偿队列，新库写失败不阻塞主链路，但必须落告警
   - 灰度按用户 ID 尾号分批放开，从百分之一到百分之十再到全量
4. 一致性校验：逐分片比对行数与关键字段校验和，金额类字段逐行核对
   - 校验不通过的定位到单条，人工确认是迁移问题还是双写窗口期的正常时差
5. 读切换与旧库下线：读流量切到新库观察三天，旧库置为只读保留一周做兜底

最危险的阶段是双写切换的那几个小时。灰度比例每提升一档，都要盯新库的写入延迟和主链路的错误率，出现错误率抬头立刻回切。回切开关那天演练了两次，确保真出事时三十秒内能切回旧库。

## 运维对象的变化

拆分完成后，运维团队的监控盘整个换了一遍。单库时代盯的是几个核心指标：连接数、QPS、慢查询、主从延迟。拆分之后，每个分片都是独立的观测对象，十六个分片乘以原有指标就是一百多个监控项，再加上中间件自身的路由指标、连接池状态、分片间耗时分布。

我们上线了一周后才补上两个关键看板。一个是分片均衡度，每个分片的行数、数据量、QPS 分布，用来及时发现数据倾斜，倾斜超过两成就启动重平衡评估。另一个是慢查询归属，同一条逻辑 SQL 在不同分片上的耗时差异，能定位到单分片的数据热点。

日常操作也多了新动作：扩容要从某个分片迁一半数据到新库，在线迁移期间该分片的读写延迟会抖，要挑低峰期执行；版本升级要逐个分片滚动进行，任何一步失败都要能回退。这些操作手册写了三版才稳定，每一页都是演练试错换来的。分库分表买到的是容量，付出的是把一套数据库的运维变成十六套加一套中间件。

## 踩过的坑

- 分布式 ID：自增主键在分片后不再全局唯一，改造为雪花算法发号，订单号同时保留可读性
- 跨片 JOIN：订单表关联商品表时两边分片键不一致，改为在订单表冗余商品快照字段
- 分布式事务：扣库存与建订单跨两个服务，最终一致性用本地消息表加对账补偿，不用强一致协议
- 深分页：`LIMIT 1000000, 20` 在跨片场景要先聚合再排序再切页，改为游标翻页
- 历史数据迁移：八亿行双写加校验加回放，跑了十一天，灰度期间以旧库为准

## 如果重来一次

复盘时有两个决定会做得不一样。其一，分片数从十六改到三十二。分片越细，单分片数据量越小，未来扩容时重切分的代价越低；当时选十六是出于运维对象数量的顾虑，事后看十六个和三十二个的连接管理成本差别不大，而数据密度差一倍。其二，订单号里嵌入分片位（基因法）应该在初期就做，用户 ID 取模虽然简单，但订单号查询要额外维护一张订单号到用户的映射表，这块成本在改造完成三个月后才暴露出来。

还有一条教训属于流程：查询模式盘点应该拉上运营和产品一起做，不能只问开发。我们最初以为时间范围查询很少，实际上运营每月初都要跑一次全量对账，只是没人把它当成"查询模式"提出来。低估了这个比例，导致数仓那边的需求比预期提前了一个季度。

## 效果与遗留问题

拆分后单表五千万行，凌晨批处理回到三十五分钟，主库 IO 从七成降到四成。遗留问题有两个：十六分片的容量规划还能撑两年，再往上要么重切分要么上 NewSQL；运营的全量时间查询仍依赖数仓 T+1，实时看板的需求排在下个季度。

> 分片键一旦选定，数据的物理分布就定了，改一次等于迁移一次。这个决定值得花一周调研，不值得拍一下脑袋。

分库分表是一次性成本极高、收益也极高的改造。动手前把查询模式盘清楚，比选哪个中间件更重要。一致性哈希作为另一种分布思路，可以参考维基百科的词条（https://zh.wikipedia.org/wiki/一致性哈希）。
