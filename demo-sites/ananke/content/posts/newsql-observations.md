NewSQL 这个词喊了十几年，中间经历了论文惊艳、创业潮、泡沫质疑、稳步落地几个阶段。作为一个在第二现场看了很多年的人，我把印象深的节点按时间记下来，附上每个阶段自己的一点评注。这不是编年史正传，更像技术观察者的笔记。

## 2012：一篇论文立了个flag

Google 在这一年发表 Spanner 论文，核心主张是数据库可以在全球范围提供外部一致性：跨数据中心的读写像单机一样讲顺序，靠的是原子钟加 GPS 时钟把时间误差压到毫秒级。这个组合拳在当时的分布式系统圈子里震动不小，原来一致性、可用性、分区容忍之间还有这种解法。

问题是硬件门槛太高，原子钟不是谁都用得起的。但论文给整个行业指了方向：关系模型的易用性和分布式系统的扩展性可以兼得。

## 2015 到 2017：创业潮起，两个 1.0

这三年是 NewSQL 的创业窗口期。PingCAP 在 2015 年成立，TiDB 立项，思路是 MySQL 兼容协议加计算存储分离，用 Raft 做数据多副本；CockroachDB 同年创立，走 PostgreSQL 兼容路线，事务模型参照 Spanner 的提交方式设计。2017 年两家先后发布 1.0，标志着产品从 demo 变成可以谈生产的东西。

### 两条技术路线

这一阶段分化出两条路线。一派自研分布式内核，用 Raft 或 Paxos 做数据分片的多副本，计算存储分离，TiDB 和 CockroachDB 是代表；另一派改造存储层，把单机引擎的存储换成分布式存储，计算层仍保持单机语义，Aurora 是这条路线的样板。两条路线的取舍集中在一点：分布式事务的实现代价。前者把分布式事务做进内核，协议开销每笔都付；后者靠存储层的日志复制，事务仍走两阶段提交，但对应用透明。

同一时期云厂商也没闲着，AWS 在 2014 年发布 Aurora，把计算与存储解耦，存储层按需扩展，用兼容 MySQL 和 PostgreSQL 的接口圈住大量存量用户。三条路线在这几年基本定型：自研分布式内核、云厂商托管兼容层、以及后来的 HTAP 混合负载。

## 2019：TPC-C 与第一次正名

2019 年，蚂蚁的 OceanBase 在 TPC-C 基准测试中拿到当时的世界第一，成绩是六千多万笔每分钟。这个数字的意义不在绝对值，在于它出自一个分布式关系数据库，而榜单历史上长期被传统商业数据库占据。2020 年成绩又被刷新到七亿笔以上。对新阵营来说，这是一次公开的正名：分布式数据库不是玩具，能扛住最苛刻的事务基准。

那两年我帮两个客户做过 PoC，感受很直接：单机 MySQL 扛不住的场景，迁移到新阵营后扩容从"停机迁移"变成"加节点"，运维心智模型变化很大。代价是运维对象从一台实例变成一套集群，监控项翻了几倍。

## 2021 到 2022：HTAP 与云原生

2021 年 TiDB 发布 5.0，主打 HTAP，同一份数据同时支撑在线交易和实时分析，行存列存之间自动同步。这个方向戳中了真实痛点：很多公司的痛点是业务库和分析库两套链路，数据同步延迟按小时算，业务想看实时报表只能干等。

云原生是另一个关键词。数据库上 Kubernetes 成为标配，存算分离架构让计算节点可以按需扩缩，存储层独立计费。Google 在 2022 年发布 AlloyDB，把 PostgreSQL 生态和自家存储引擎结合起来，说明传统阵营也在往这个方向重构。

## 2023 至今：选型回归理性

热闹过后，选型反而冷静了。我接触到的团队里，真正把 NewSQL 用作主力库的仍然集中在几个典型场景：数据量自然增长到单机极限的、需要弹性扩缩容的、多活容灾要求高的。其余场景，大家发现单机 PostgreSQL 或 MySQL 加读写分离仍然够用，而且运维简单。

还有个变化是采购逻辑。早年团队自建 NewSQL 集群是主流，近两年直接用云厂商的托管服务成了默认选项，自建的多是有数据合规要求的行业。托管服务把扩缩容、备份、升级这些脏活包掉，按量计费，对小团队友好；代价是绑定和议价能力，用到深处再迁走会很痛。这个取舍没有标准答案，但值得在签约前就想清楚。

## 接口之争：协议兼容的账

新阵营早期拼的是"像不像 MySQL"，后来发现兼容性是一笔算不清的账。协议层兼容让客户端和驱动零改动接入，这是获客的敲门砖；可兼容到语义层就难了，自增列的行为、隐式提交的时机、`GROUP BY` 的宽松模式，处处是差异。

我见过一个团队把业务从 MySQL 迁到新阵营，压测全绿，上线第三周炸了一个奇怪的问题：依赖了 `INSERT ... ON DUPLICATE KEY UPDATE` 在并发下的一个行为细节，新阵营的实现语义不同，导致少量数据重复。这类问题没有银弹解法，只能靠迁移前的逐项验证：把现有 SQL 全量导出来跑一遍，重点标记存储过程、自定义函数、隐式类型转换这三类高危区域。

到 2021 年之后，战场变了。新阵营开始讲标准 SQL 和生态兼容，比如兼容 PostgreSQL 的 wire protocol，让配套工具链直接复用。反过来，传统厂商也在补分布式能力，界限越来越模糊。我的判断是：接口兼容会继续改善，但"零改动迁移"在可见的未来仍然是营销话术，认真的团队都会预留一个月的验证期。

## 成本结构：新阵营贵在哪

账要算全。新阵营省下的是分库分表的改造人月，加上去的是另一套成本。

机器成本上，多副本和 Raft 的写放大意味着同样的写入量，新阵营通常要三到五台机器的资源，单机 MySQL 一台就够。运维成本上，监控项从几十个变成几百个，扩容、缩容、副本修复、leader 迁移都是日常操作，需要专人负责。人力市场上，懂分布式数据库运维的工程师比懂 MySQL 的贵一截，小团队未必养得起。

所以我的选型建议向来保守：单机扛得住就别动，读写分离能撑就加从库，真到了数据量和写入量的物理极限，再评估新阵营。被"技术更先进"说服的迁移，失败率远高于被"今晚磁盘又满了"驱动的迁移。

## 产品速览

| 产品 | 查询接口 | 一致性模型 | 部署形态 |
| --- | --- | --- | --- |
| Spanner | SQL | 外部一致性，TrueTime | 云托管 |
| TiDB | MySQL 协议 | Raft 多数派提交 | 私有部署或云 |
| CockroachDB | PostgreSQL 协议 | Raft 加串行化隔离 | 私有部署或云 |
| OceanBase | MySQL 协议 | Paxos 多数派 | 私有部署为主 |
| Aurora | MySQL/PostgreSQL | 单写多读，存储层复制 | 云托管 |

一个典型的私有部署集群配置长这样：

```yaml
server_configs:
  tidb:
    log.level: info
  tikv:
    storage.block-cache.capacity: 8GB
pd_servers:
  - host: 10.0.1.11
tidb_servers:
  - host: 10.0.1.21
  - host: 10.0.1.22
tikv_servers:
  - host: 10.0.1.31
  - host: 10.0.1.32
  - host: 10.0.1.33
```

## 选型考量清单

- [ ] 数据量和写入量是否真的超过单机极限，还是缓存和索引没用对
- [ ] 团队有没有分布式数据库的运维能力，出问题谁兜底
- [ ] 现有 SQL 兼容性逐条验证，特别是存储过程和自定义函数
- [ ] 事务语义与隔离级别是否满足业务，别默认都跟单机一样
- [ ] 备份恢复、扩缩容、版本升级的操作手册是否成文

十二年过去，NewSQL 从论文里的激进想法变成了选型清单上的一个常规选项。它解决了扩展性问题，也带来了集群运维的新成本。值不值得，取决于你的数据量和团队形态，跟技术新不新关系不大。## 我的观察方法

> 看一门新技术，要看它怎么失败，而不是看它怎么成功。

最后交代一下这些判断是怎么来的，供参考。看新技术我习惯三个动作：读一手论文和官方文档，不读二手解读；在生产或准生产环境至少跑一个月的 PoC，不看 demo 环境；找用过的人聊失败案例，而不是成功案例。三个动作都做完，形成的判断才敢往报告里写。

这些年见过太多"PPT 上完美"的技术，落地时死在小处：一个 SQL 方言不兼容、一个监控盲区、一次扩容时的抖动。NewSQL 是这样，别的技术也是这样。技术选型没有圣杯，只有与团队能力、数据规模、成本约束相匹配的合理解。把新技术的承诺打折到七成，再算收益，通常是更接近真实的估算。

背景可以参考维基百科的 NewSQL 词条（https://zh.wikipedia.org/wiki/NewSQL）。
