代码合并只完成一半工作，另一半是让它安全地到达用户。发布策略要解决的核心问题只有一个：**如果新版本有问题，受影响的面有多大**。滚动、蓝绿、金丝雀、功能开关，本质上都是对"爆炸半径"的不同切法。这篇对比四种策略，重点拆解蓝绿和金丝雀的取舍，相关背景见[维基百科持续交付条目](https://zh.wikipedia.org/wiki/持续交付)。

> 发布能力的试金石不是部署有多快，而是出问题时，把影响面收回到零需要几分钟。一切策略都是为这分钟数服务的。

## 四种策略概览

| 策略 | 流量切换方式 | 爆炸半径 | 回滚速度 | 资源成本 |
| --- | --- | --- | --- | --- |
| 滚动更新 | 分批替换旧实例 | 中，逐步扩大 | 中，需反向滚动 | 无额外 |
| 蓝绿部署 | 整体切换入口 | 大，一瞬间全部 | 快，切回即恢复 | 双倍资源 |
| 金丝雀发布 | 按比例导流 | 小，可精确到 1% | 快，权重归零 | 少量额外 |
| 功能开关 | 代码内控制可见性 | 极小，按用户或比例 | 最快，改配置即生效 | 无额外 |

四种不是互斥的。成熟的团队常常组合使用：金丝雀放流量做技术验证，功能开关做业务验证，两者叠加，发布才真正可控。

选策略前先问一个前置问题：**你的系统有没有"版本"的概念**。移动端 App 受应用商店审核制约，用户手里同时存在十几个版本，任何"切换"都改变不了旧版本的存在，此时真正的发布控制只能靠服务端的功能开关和接口兼容。而纯 Web 和内部系统版本迭代快，蓝绿和金丝雀才是主战场。忽略这个前提，策略选得再精致也会在客户端生态面前失效。

## 蓝绿部署：全量切换的豪赌

蓝绿的做法是维护两套环境，蓝跑旧版、绿跑新版，验证通过后把入口整体切到绿。它的优点是**切换动作原子化**：用户不会同时看到新旧两个版本混服务，回滚也只是切一次入口，秒级完成。

```bash
# 蓝绿切换示例：把 Service 的选择器指向新版本的 Deployment
kubectl -n web patch service web-svc \
  -p '{"spec":{"selector":{"version":"green"}}}'

# 出问题时的回滚：切回蓝色，同样是一条命令
kubectl -n web patch service web-svc \
  -p '{"spec":{"selector":{"version":"blue"}}}'
```

代价是资源：两套环境要同时存在，高峰期等于双倍容量。另外它假设**新版本切换前已经充分验证**，如果验证不充分，切换的瞬间就是把全部用户推给一个有问题的版本，半径反而最大。所以蓝绿适合：有成熟的预发环境、发布窗口固定、对版本一致性要求高的场景，比如内部系统和强一致性业务。

## 金丝雀发布：用真实流量试错

金丝雀的思路相反：先放 1% 的流量给新版本，观察指标，逐步放大比例，全量后旧版本下线。它的核心价值是**用真实流量做验证**，问题在小流量阶段就会暴露。

```yaml
# 基于 Ingress 注解的金丝雀权重示例（以 nginx ingress 为例）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"   # 5% 流量进入金丝雀
spec:
  rules:
    - host: www.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-canary
                port:
                  number: 80
```

进阶做法是用 Argo Rollouts 这类工具做指标门禁：金丝雀期间自动分析成功率与延迟，跌破阈值自动把权重退回零，全程不需要人盯屏。**金丝雀的真正门槛不在技术，而在有没有定义好"什么指标变坏就自动退"**。

## 正面交锋：蓝绿还是金丝雀

| 维度 | 蓝绿部署 | 金丝雀发布 |
| --- | --- | --- |
| 验证方式 | 发布前在预发验证 | 发布中用真实流量验证 |
| 风险暴露时点 | 切换瞬间集中暴露 | 小流量阶段逐步暴露 |
| 版本共存 | 不共存，用户体验一致 | 新旧版本同时在线，需保证兼容 |
| 资源开销 | 双倍环境 | 少量金丝雀实例 |
| 回滚 | 切回入口，秒级 | 权重归零，秒级 |
| 适用系统 | 版本一致性强、有完善预发 | 高并发、需要渐进信任 |

一句话选择：**有完善预发环境、要求版本一致性，选蓝绿；面向海量用户、希望用流量逐步建立信任，选金丝雀**。两者也可以杂交：先金丝雀 5% 建立初步信心，再一次性切全量，兼顾渐进与一致。

回滚命令本身该按"灾难模式"设计：短、无参数、可盲打。理想状态是值班工程师在终端里按 <kbd>↑</kbd> 从历史记录调出上次的回滚命令，看一眼确认没有多余参数，直接 <kbd>Enter</kbd>。需要查文档、拼参数、找令牌的回滚流程，在真实事故的几分钟窗口里，约等于没有。

## 功能开关：最快的一层回滚

功能开关（Feature Flag）常被看作"灰度工具"，其实它是所有策略里回滚最快的一层：改一个配置，秒级生效，不需要重新部署，也不需要动流量入口。它和其他策略是正交关系：金丝雀管"请求打到哪个版本"，功能开关管"版本里的功能给谁可见"。一个成熟的组合是：新功能先用功能开关对内部员工开放，再按用户 ID 白名单放开，最后脱掉开关成为默认路径。

用好功能开关有三条纪律。第一，**开关必须有生命周期**：临时开关定好过期时间，到期要么转正要么删除，否则代码里会积累几百个没人敢动的死开关。第二，**开关状态和代码分离**：存在配置中心而不是硬编码，紧急时不需要发版就能改。第三，**开关组合要可测试**：同时存在十几个开关时，组合爆炸足以让测试用例失效，把开关矩阵纳入自动化测试，是灰度规模变大后必须补的课。

## 指标门禁：金丝雀的自动刹车

金丝雀真正的难点不是按比例分流，而是"观察什么、谁来判断"。靠人盯仪表盘做晋级决策，慢且不稳定，成熟做法是把晋级标准写成自动化的指标门禁：

```yaml
# Argo Rollouts 的指标分析模板示例
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
    - name: success-rate
      interval: 1m
      successCondition: result[0] >= 0.99
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="web",status!~"5.."}[2m]))
            / sum(rate(http_requests_total{app="web"}[2m]))
```

门禁指标选业务结果，而不是资源指标：成功率、下单转化率、支付完成率，比 CPU 和内存更接近用户体验。再配一条硬规则：**金丝雀期间核心业务指标跌破阈值，自动回退权重并暂停晋级**，不需要任何人拍板。自动刹车的价值在凌晨三点的发布里体现得最清楚，那时没人有精神做可靠判断。

## 数据库：发布里最难的一半

### 扩展、迁移、收缩

应用可以回滚，数据不能。涉及 schema 变更时，两条军规：

```bash
# 军规一：schema 变更与代码发布解耦，先做向后兼容的变更
# 例如只加列不删列、加索引用在线方式（pt-osc 或 gh-ost）
gh-ost --alter="ADD COLUMN coupon_id BIGINT NULL" \
       --database=shop --table=orders --execute

# 军规二：回滚前先确认新代码写的数据，旧版本能否容忍
# 新增列旧版本不读写，可安全回滚；改语义的列必须先双写再切流
```

删列、改语义这类破坏性变更，标准做法是**扩展、迁移、收缩**三步走：先扩展让新旧版本都能工作，再迁移数据，最后收缩清理旧结构。三步分散在多次发布里，任何一步都能单独回滚。把破坏性变更和代码发布塞进同一个窗口，是数据事故最常见的配方。补一个容易被忽略的顺序问题：**数据修复脚本和回滚代码必须同步就绪**。很多团队只准备了"怎么改上去"，没准备"改坏了怎么退回来"。破坏性变更执行前，先在从库上完整演练一遍逆向操作，确认耗时和影响都在预期内，再动主库。数据变更没有彩排，演练就是唯一的安全带。

## 选型决策树

按顺序问自己四个问题：

1. 有成熟的预发环境和自动化验证吗？没有，先补验证，蓝绿和金丝雀都救不了没测过的代码。
2. 新版本和旧版本能同时在线吗（API、数据格式兼容）？不能，选蓝绿。
3. 需要小流量验证来建立信心吗？需要，选金丝雀。
4. 变更能按用户或百分比隐藏吗？能，加一层功能开关，它是所有策略里回滚最快的一层。实现上把开关判定放在离用户最近的一层（网关或前端配置），状态读取走 `feature-flag` 这类专用 SDK，别自己用 if-else 散落在业务代码里，否则清理开关时会变成考古。

## 小结

发布策略没有银弹，只有匹配：**蓝绿买的是版本一致性和秒级回滚，代价是双倍资源和集中暴露的风险；金丝雀买的是渐进信任和最小半径，代价是版本共存带来的兼容性要求**。再叠加上数据库的扩展迁移收缩和功能开关，一套完整的发布体系才立起来。衡量发布能力的最终指标只有一个：从"用户报告问题"到"影响归零"，你的团队需要几分钟。

这个指标可以被拆解：发现（监控多久发现异常）、决策（多久决定回滚）、执行（回滚动作多久生效）。三段里最短的往往是执行，几分钟足够切回旧版本；最长的是发现和决策，而这两段恰恰是金丝雀、功能开关和指标门禁要优化的对象。把发布能力的建设聚焦在"缩短发现与决策"上，而不是堆更花哨的部署工具，方向就不会错。
