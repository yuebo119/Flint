"事务隔离级别"是数据库面试的固定题，标准答案也固定：四个级别，对应三种异常。可背下这张表的人，未必说得清可重复读是怎么实现的，也未必知道 MySQL 的可重复读已经用间隙锁在很大程度上防住了幻读。这篇文章把每个级别拆到实现层，看它们各自让了什么步、守住了什么。

## 四个级别与三种异常

SQL 标准定义了四个隔离级别，以及它们要对抗的三种读取异常：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交（READ UNCOMMITTED） | 可能 | 可能 | 可能 |
| 读已提交（READ COMMITTED） | 不可能 | 可能 | 可能 |
| 可重复读（REPEATABLE READ） | 不可能 | 不可能 | 可能（标准定义） |
| 串行化（SERIALIZABLE） | 不可能 | 不可能 | 不可能 |

脏读是读到了别人未提交的修改，它可能在对方事务回滚后变成从未存在过的数据。不可重复读是同一事务内两次读同一行得到不同结果，因为别的事务在中间提交了更新。幻读针对的是集合，同一条件两次查询返回的行数不同，别的事务插入或删除了符合条件的行。

MySQL InnoDB 默认 REPEATABLE READ，PostgreSQL 默认 READ COMMITTED，Oracle 没有可重复读这一级。选默认值就是选业务对一致性与并发的权衡，理解实现才能理解代价。

## 快照读：MVCC 怎么让重复读成立

InnoDB 让可重复读成立的核心是 MVCC，多版本并发控制。每行记录除了业务字段，还带几个隐藏字段：最近修改它的事务 ID、回滚指针，以及可选的隐藏主键。回滚指针指向 undo log 里的上一个版本，多个版本串成一条版本链。

事务发起第一次快照读时，引擎生成一份 ReadView，记录当前活跃事务的 ID 集合。之后每次读某一行，都沿着版本链从新到旧找第一个对当前 ReadView 可见的版本：修改它的事务已提交，或在 ReadView 生成后才开始，这个版本才能被看见。

举个时间线的例子。事务 A 在 T1 时刻开始，ReadView 里活跃事务有 A 自己和 B。B 在 T2 修改了某行但未提交，A 读到旧版本。B 在 T3 提交，A 在 T4 再读同一行，看到的仍是旧版本，因为 ReadView 在 T1 就固定了，B 的修改对 A 始终不可见。只有 A 自己提交后开新事务，才能看到 B 的修改。这就是可重复读的机械解释：不是锁住了行，而是每个事务都活在自己开始那一刻的快照里。

### 版本链为什么不能无限长

每次更新都会在 undo log 里留一个旧版本，版本链随之变长。读一行时要沿链找到可见版本，链越长读得越慢。InnoDB 的 purge 线程会清理没有活跃事务引用的旧版本，正常情况下链长有界。但如果有一个跑了几个小时的大事务，它 ReadView 引用的版本谁也清不掉，链会一直涨，查询延迟跟着涨。线上看到某张表的查询突然变慢，先查 `information_schema.innodb_trx` 里有没有长事务，这个习惯能省很多弯路。

## 当前读：快照照不到的地方

MVCC 只覆盖快照读，也就是普通的 `SELECT`。下面这些读取读的是最新版本，叫当前读：

- `UPDATE`、`DELETE` 执行前对目标行的读取
- `INSERT` 时的重复键检查等内部读取
- 显式加锁的 `SELECT ... FOR UPDATE` 与 `SELECT ... LOCK IN SHARE MODE`

当前读不加锁约束时，两个事务可能同时基于旧版本计算新值，造成更新丢失。业务上常见的库存扣减、余额变更必须用悲观锁或乐观锁（版本号、CAS）兜住，这是 MVCC 管不到的地带。

## 幻读与 InnoDB 的解法

标准里 REPEATABLE READ 允许幻读，MySQL 在此级别用 next-key 锁把幻读也堵上了。next-key 锁是记录锁与间隙锁的组合：锁住索引记录本身，同时锁住记录之间的间隙，阻止别的事务在范围内插入新行。

举个例子。`SELECT * FROM orders WHERE amount BETWEEN 100 AND 200 FOR UPDATE` 不仅锁住已存在的行，还锁住 100 到 200 之间的空隙，别的事务想插入一条 150 的订单就得等待。间隙锁的代价是并发度下降，且容易死锁，两个事务以相反顺序加锁时间隙锁互相堵住，InnoDB 靠死锁检测回滚代价小的一方。

## 锁的粒度：行锁、间隙锁与意向锁

InnoDB 的锁分三个层次，理解它们才能看懂死锁日志。

行锁锁住具体的索引记录，粒度最细。注意它锁的是索引记录而不是数据行，更新不走索引的语句会把整行甚至整表锁住，这是"更新没走索引导致锁表"的来历。间隙锁锁住记录之间的空隙，阻止新记录插入，next-key 锁就是行锁加间隙锁的组合，左开右闭区间是它的标准形态。意向锁是表级别的标记，表示"这张表里有行被锁了"，让引擎在加表锁前能快速判断有没有冲突，省去逐行检查。

锁等待有明确的超时参数，默认五十秒。业务语句的锁等待应该配成秒级，等五十秒的连接会把连接池占满，雪崩就是这么开始的。监控上盯 `Innodb_row_lock_waits` 和 `Innodb_row_lock_time_avg`，两个数一起涨说明锁竞争在恶化。

## 死锁是怎么发生的

死锁的充要条件是互相等待对方持有的锁。两个事务以相反顺序更新两行，就容易构造出来：

```sql
-- 事务一                                 -- 事务二
UPDATE stock SET n = n - 1 WHERE id = 1;  UPDATE stock SET n = n - 1 WHERE id = 2;
UPDATE stock SET n = n - 1 WHERE id = 2;  UPDATE stock SET n = n - 1 WHERE id = 1;
```

事务一持着 id=1 的锁等 id=2，事务二持着 id=2 的锁等 id=1，环形成。InnoDB 的死锁检测会主动回滚其中一个事务，应用层收到 1213 错误码，正确的处理是重试而不是直接把错误抛给用户。

生产环境防死锁有三个习惯：多行更新按同一顺序（比如按主键升序）；大事务拆小，减少持锁时间；批量操作排序后执行。间隙锁场景下死锁更难排查，两个事务锁的区间稍有重叠就可能互相堵住，`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段落是定位的第一现场。

## 业务代码里的三个实战习惯

隔离级别落到代码层，有三条被反复验证的习惯。

第一，事务里只放必要的语句。事务越长，持有的锁越多，版本链拖得越久，死锁概率随锁的数量超线性增长。常见错误是把 HTTP 调用、文件读写放进事务里，一个外部接口抖动三秒，事务里的锁就挂三秒。正确做法是把外部交互挪到事务外，事务只包住数据库操作。

第二，先读后写的逻辑显式加锁。`SELECT` 出来算一算再 `UPDATE`，中间的任何提交都会让计算结果过期。要么把读取改成 `SELECT ... FOR UPDATE`，要么给表加版本号字段做乐观锁，用更新时比对版本号的方式检测冲突。库存扣减用前一种，配置更新冲突少的场景用后一种。

第三，给每个写接口标注隔离级别假设。代码评审时最常出现的对话是"这里依赖了可重复读吗"，没人答得上来。把假设写在注释里，将来换数据库、改隔离级别时，风险点是可检索的，不是靠记忆。

## 快照生成的时机：RC 与 RR 的真正差别

读已提交和可重复读在实现上只差一件事：ReadView 什么时候生成。读已提交每条语句执行前都生成新的 ReadView，所以别的事务提交后，下一条语句立刻能看到。可重复读只在第一条语句时生成一次，之后整个事务都用同一份快照。

这个差别带来两个实际影响。其一，可重复读里做数据校验类的循环，比如"逐行检查再逐行更新"，两次读到的值永远一致，不会出现前脚查完后脚变。其二，长事务在可重复读下会拖住版本链，undo log 无法清理，历史库的 purge 线程干着急。生产上看到 `history list length` 持续增长，第一反应就是查有没有跑了好几小时的事务。

## 选型建议

> 隔离级别是用并发换一致性的旋钮，拧到哪里都不对，只有拧到业务需要的位置才对。

隔离级别不是越高越好，每一级都是用并发换一致性。只读报表类业务理论上可以放到 SERIALIZABLE 规避所有异常，但通常没人这么做，因为吞吐会塌。常规做法是：多数场景用库的默认级，把一致性要求高的局部操作用显式锁或乐观锁兜住，写业务前先想清楚这段代码能不能接受幻读和不可重复读。

理解了 MVCC 的版本链与 ReadView，四个名词就能顺着机制推导，不必背诵。更多细节可参考维基百科对事务隔离的整理（https://zh.wikipedia.org/wiki/事务隔离）。
