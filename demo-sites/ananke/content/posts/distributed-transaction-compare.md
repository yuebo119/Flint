跨库写是分布式事务问题的根源：下单要扣库存、扣余额、写订单，三个库三个事务，任何一个失败，其他两个怎么办？这个问题没有银弹，只有取舍。这篇文章对比四种常见方案：2PC/XA、TCC、Saga、本地消息表，先说结论：互联网链路里，Saga 加接口幂等能覆盖绝大多数场景；对一致性要求严格的资金链路，TCC 更合适；2PC 只在能接受锁等待的传统系统里使用。

场景先摆出来：用户下单，订单库插入订单，库存库扣减库存，余额库扣减优惠金。三个库三个事务，库存扣减失败时，订单和余额都要退回。这个需求我们评估过五种写法，每一种都在某个维度上要命，最后选了 Saga。评估过程比结论有价值，所以四种方案都展开讲。

## 四种方案的正面对比

| 维度 | 2PC/XA | TCC | Saga | 本地消息表 |
| --- | --- | --- | --- | --- |
| 一致性 | 强一致 | 最终一致，隔离性好 | 最终一致 | 最终一致 |
| 性能 | 差，同步阻塞加锁 | 中，无全局锁 | 好，无锁 | 好，异步 |
| 业务侵入 | 低，靠数据库驱动 | 高，三个接口都要实现 | 中，要定义补偿 | 低，加一张表 |
| 复杂度 | 低（如果数据库支持） | 高 | 中 | 中 |
| 适用规模 | 同构数据库、低并发 | 资金、库存等核心链路 | 长流程业务链 | 异步通知类场景 |

## 2PC/XA：能不用就不用

两阶段提交由协调者先问所有参与者"能不能提交"，全部回答能之后再正式提交。它的强一致是真实的，代价也是真实的：准备阶段所有参与者锁住资源直到第二阶段结束，任何一方慢或挂，全局阻塞。

> 强一致的代价不是"慢一点"，是把全局可用性绑在最慢的那个参与者的心跳上。

在互联网的延迟和可用性要求下，一个参与者的抖动会放大成整条链路停摆。它真正适合的场景是同机房、同构数据库、低并发的管理系统，比如一个单体拆成两个库但还在一个集群里。我们在一套内部运营系统上用过 MySQL XA，并发不到二十，跑得很稳，代码几乎零侵入。但同样的配置搬到订单链路上，压测第一轮就把连接池打满，协调者成了全局单点。同一个方案，换个场景就是灾难，这就是分布式事务选型没有标准答案的原因。

## TCC：为资金链路设计

TCC 把每个参与者的操作拆成 `Try`、`Confirm`、`Cancel` 三步：Try 预留资源（冻结库存而非扣减），全部 Try 成功则逐个 Confirm 提交，任何一步失败则逐个 Cancel 释放预留。它把锁的粒度从"全局事务期间"缩到"资源预留"，性能比 2PC 好得多，且隔离性靠业务层的预留实现，比 Saga 的裸补偿更安全。

```go
// TCC 参与者的标准三段式接口
type InventoryParticipant interface {
    // Try: 冻结库存，不实际扣减；记录事务分支，保证幂等
    Try(ctx context.Context, txID string, sku string, qty int) error
    // Confirm: 确认扣减已冻结的库存；重复调用必须返回成功
    Confirm(ctx context.Context, txID string) error
    // Cancel: 释放冻结的库存；Confirm 之后的 Cancel 要拒绝
    Cancel(ctx context.Context, txID string) error
}

func (s *InventoryService) Try(ctx context.Context, txID, sku string, qty int) error {
    // INSERT INTO frozen (tx_id, sku, qty) — 唯一索引兜幂等
    if err := s.repo.InsertFrozen(ctx, txID, sku, qty); err != nil {
        if errors.Is(err, ErrDuplicate) { return nil } // 已预留，幂等返回
        return err
    }
    return s.repo.FreezeStock(ctx, sku, qty)
}
```

TCC 的三个坑按踩到的频率排：Confirm 和 Cancel 的幂等没做好，重试导致重复扣减；空回滚，即 Try 没执行就直接收到 Cancel，要能识别并直接放行；悬挂，Cancel 比 Try 先到（网络重排），此时必须拒绝后续迟到的 Try。这三个问题靠事务分支表的状态机加唯一索引解决，没有捷径。

### 幂等、空回滚与悬挂

三个边界情况的共同根因是：网络不保证顺序，重试不保证只来一次。所以每个参与者的三个接口都必须按 `tx_id` 查分支状态再动作，状态机驱动，不靠代码里的 if 嵌套。补一个实现细节：Try 阶段的冻结记录不要只写"冻结了多少"，要写"可用库存减 N、冻结库存加 N"两条，否则超时释放时要反推原值，并发下会算错。事务分支表的主键用全局事务 ID 加分支 ID 的复合键，Confirm 和 Cancel 都先查分支状态再动作，状态机驱动，不靠代码里的 if 嵌套。

## Saga：长流程的默认答案

Saga 把长事务拆成有序的本地事务序列，每个本地事务有对应的补偿操作。失败时从失败点开始反向执行补偿。它的模型简单直接，代价是没有隔离性：两个并发 Saga 修改同一份数据时，可能互相看到对方的中间状态，需要业务层处理（如加状态校验、悲观锁字段、或语义上接受）。

```
下单 Saga：创建订单 -> 扣库存 -> 扣余额 -> 通知仓库
补偿链：  通知仓库补偿 <- 余额返还 <- 库存返还 <- 订单取消
```

### 两种编排方式

工程上有两种编排方式：choreography（事件驱动，每个服务完成本地事务后发事件触发下一步）和 orchestration（一个协调器按状态机依次调用）。参与者少于四个、流程稳定时用 choreography 更简单；流程长、分支多时用 orchestration，状态机集中在一处，排障时能看到全貌。补偿的执行顺序必须是正向的严格逆序，因为后面的步骤可能依赖前面的结果，跳过依赖直接补偿会留下中间状态。我们的下单 Saga 第一次上线时就漏了顺序，补偿并行执行导致库存返还时订单还没取消，运营在后台看到了十分钟的"幽灵订单"。

## 本地消息表：把可靠性交给数据库

本地消息表的思路是把"发消息"变成本地事务的一部分：业务表和消息表在同一个库里，业务操作和消息写入在同一个本地事务里提交，之后由后台任务扫描消息表投递到 MQ，消费方处理成功后删除或标记消息。它不追求协调多个事务，而是保证"业务成功则消息必达"，特别适合异步通知类场景，比如订单支付成功后发券、加积分。

它的局限是消息表在业务库里，轮询有延迟（通常百毫秒到秒级），且消息表要自己清理，否则无限增长。超过秒级延迟不能接受、或消息量极大的场景，用支持事务消息的队列更合适。消息表的清理策略要一开始就设计：发送成功的消息保留七天供排查，之后归档或删除，不清理的表一年就能到几亿行，轮询查询自己先变慢。另外轮询要有取模分片，多实例部署时每个实例只处理自己那片，否则同一批消息会被多个中继重复投递。

## 选型建议

- 同集群低并发管理链路：2PC，别折腾
- 资金、核心库存，要求隔离性：TCC，接受实现成本
- 长流程、多参与方、容忍中间态可见：Saga，配好补偿的幂等
- 异步通知、允许秒级延迟：本地消息表或事务消息
- 任何方案：补偿接口必须幂等，这是底线，没有例外

回到开头的下单场景走一遍：订单和优惠金用本地事务保证，库存扣减走 TCC 的预留语义，通知仓库用本地消息表异步发送。为什么不全套 Saga？因为库存是资金敏感资源，Saga 的裸补偿在并发下会出现超卖，而 TCC 的冻结语义能把超卖挡在预留阶段。这个混合方案听着不"纯粹"，但它每一段都选在了对应维度上最稳的方案，纯粹留给教科书，生产要的是每段都不出事。

最后提醒一句，选型前先确认问题真实存在。单库多表用本地事务，跨模块调用大部分可以用"先做重要的事，失败后异步补偿"绕过，真正需要分布式事务的链路比想象中少得多。[^1]

最后一公里是对账。无论方案多严谨，都要有一个每日对账任务：比对发起方的业务单据和所有参与方的最终状态，找出"该成功没成功、该回滚没回滚"的孤儿事务，进工单人工处理。分布式事务的方案保证的是大概率正确，对账保证的是小概率错误最终被发现，两者缺一不可。我们对账任务上线第一个月就捞出了两笔半年前的挂起事务，都是极端网络抖动造成的，没有对账它们会永远躺在那里。

[^1]: Hector Garcia-Molina 与 Kenneth Salem, "Sagas", ACM SIGMOD Record, https://example.com/papers/sagas-1987.pdf
