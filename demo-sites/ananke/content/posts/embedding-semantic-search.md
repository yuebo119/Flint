传统搜索的困境人人见过：搜"电脑重启慢"，搜不到写"开机速度优化"的文档——字面上一个词都不重合。语义搜索换了一条路：把文本变成向量，意思相近的文本向量距离就近，匹配从"字面相同"变成"意思相近"。这篇文章把这条路的三个关键环节——嵌入、相似度、索引——逐一扒开。

## 从词到向量：嵌入模型的来路

词向量的思想在 word2vec 时代就成熟了：用上下文预测中心词，训练完成后每个词得到一个稠密向量，语义关系体现在向量运算里。但词向量有个死穴——多义词只有一个向量，"苹果"到底是水果还是公司，分不开。

BERT 之后，上下文嵌入成为主流（[arXiv:1810.04805](https://arxiv.org/abs/1810.04805)）：同一个词在不同句子里得到不同向量，因为 Transformer 的注意力把整句上下文都揉了进来。今天的检索用嵌入模型基本都属于这一类，输出的是一个固定长度的向量，常见维度是 768 或 1536。

选嵌入模型时看三件事：中文效果（不少模型英文强中文弱）、向量维度（维度高表达强但存储和计算贵）、以及有没有针对检索任务优化过。通用嵌入模型和专门的检索模型，在同样的数据上差距可能超出一倍。

## 嵌入模型是怎么练出来的

检索用的嵌入模型不是天然就懂语义，它是被对比学习"喂"出来的。训练数据的形态是三元组：一个查询、一条相关文档、若干条不相关文档。模型的目标是把相关文档的向量拉近查询，把不相关的推远。常用的损失函数是 InfoNCE，把"认出正样本"变成一个多分类问题：从一堆负样本里把对的挑出来，温度参数控制推开与拉近的力度。

$$ \mathcal{L} = -\log \frac{e^{\text{sim}(q, d^+)/\tau}}{\sum_{j} e^{\text{sim}(q, d_j)/\tau}} $$

这个训练目标解释了一个常见困惑：为什么通用嵌入模型在通用语料上表现好，到了你的领域就拉胯——训练时它没见过你的领域用语。补救办法是用领域数据继续训练，哪怕只是几千条查询加文档的配对，效果也常有肉眼可见的提升。它也解释了另一个现象：不同嵌入模型的向量空间互不相通，维度也不一样，混库检索等于拿北京坐标系量纽约的距离。

## 相似度怎么算

向量有了，"像不像"靠数学定义。最常用的是余弦相似度，衡量两个向量方向的接近程度，取值范围从 -1 到 1：

$$ \cos(\theta) = \frac{a \cdot b}{\lVert a \rVert \lVert b \rVert} = \frac{\sum_{i=1}^{n} a_i b_i}{\sqrt{\sum a_i^2} \sqrt{\sum b_i^2}} $$

分子是点积，两个分母把向量的长度归一化掉。### 归一化：抹掉长度的干扰

为什么要归一化？因为嵌入向量的长度往往携带了"文本长度"这类噪声信息，两个向量即使方向一致，长度差太多也会让原始点积失真。维基百科的[余弦相似度条目](https://zh.wikipedia.org/wiki/余弦相似度)给出了更形式化的定义。工程上还有一个更省事的做法：入库前把所有向量归一化成单位向量，之后点积就等于余弦相似度，一次乘法同时算完距离和相似度，排序阶段能省一层开销。

```python
import numpy as np

def normalize(v: np.ndarray) -> np.ndarray:
    """把向量归一化成单位长度，之后点积即余弦相似度。"""
    norm = np.linalg.norm(v)
    if norm == 0:
        raise ValueError("零向量无法归一化")
    return v / norm

def cosine(a: np.ndarray, b: np.ndarray) -> float:
    na, nb = normalize(a), normalize(b)
    return float(na @ nb)

# 两段意思相近的中文，嵌入模型给出的向量夹角通常很小
query = embed("怎么清理磁盘空间")
doc = embed("释放硬盘容量的几种方法")
print(cosine(query, doc))  # 典型值 0.85 以上
```

## 向量索引：从暴力到近似

语料几千条，暴力算余弦完全没问题，逐个算完排序，代码三十行。语料到百万级，每次查询算一百万次高维点积，延迟就不可接受了；到亿级，暴力检索连存储都成问题。近似最近邻（ANN）索引是解法：牺牲一点点召回，换数量级的速度。

### 三派索引，没有免费午餐

主流索引分三派：

| 索引类型 | 代表 | 原理 | 特点 |
|----------|------|------|------|
| 倒排聚类 | IVF | 先聚类分桶，查询只扫最近的几个桶 | 建库快，`nlist` 影响精度/速度平衡 |
| 图索引 | HNSW | 把向量连成多层导航图，查询像坐飞机转高铁再步行 | 召回高、查询快，内存占用大 |
| 量化压缩 | PQ / SQ | 向量分段量化成短码，用查表近似距离 | 内存降一个量级，精度有损 |

HNSW 的论文见 [arXiv:1603.09320](https://arxiv.org/abs/1603.09320)，思想很像"高速公路网加小路网"：粗粒度层快速逼近目标区域，细粒度层精确定位。选型上没有免费午餐，内存宽裕选 HNSW 换召回，内存紧张用量化压缩换容量。

内存账也要提前算。一百万个 768 维的 float32 向量，光原始数据就约 3GB，HNSW 的图结构再让占用翻一倍；量化到 int8 能压到四分之一，PQ 压得更狠但精度有损。容量规划和检索参数要一起定，否则上线第一天就是 OOM 复盘会。

调 ANN 参数的核心是拿召回率换延迟：`ef`（搜索广度）调大，扫的候选多、召回升、延迟涨。标准动作是固定查询集，画一条"延迟-召回"曲线，在满足业务延迟预算的点上选参数，而不是拍脑袋。

## 混合检索：向量不是万能的

向量检索有一个结构性盲区：**精确匹配**。搜错误码 "ERR-4092"、搜型号 "X200-Pro"、搜人名，嵌入模型可能把语义上"差不多"的东西排得更靠前，而包含精确关键词的文档反而沉底。传统倒排索引（BM25）恰好擅长这个。

成熟的搜索系统两条腿走路：向量一路负责语义泛化，BM25 一路负责精确命中，两路分数加权融合，通常还要过一道重排。效果上，混合检索几乎总是优于任何单一路线——代价是两套索引都要维护。

## 查询侧的一个细节：改写

用户的问题经常不是好的检索查询。"那个东西怎么弄不好使了"直接拿去检索，向量再强也救不了。查询改写是在检索前把口语化、指代不清的问题改写成结构清晰的查询，再用改写后的查询去检索。简单的做法是用大模型做一次改写加扩写，把同义词和可能的规范术语补上；讲究的做法是训练专门的改写模型，用真实点击日志监督。这一步成本极低，收益却经常排进所有优化项的前三，属于那种"没人做只是因为不知道"的优化。

## 效果怎么评估

"感觉搜得挺准"不算数，要有量化指标：

- **Recall@K**：前 K 条结果里包含正确答案的比例，检索场景的第一指标；
- **MRR**（平均倒数排名）：第一个正确结果排得越靠前得分越高，适合问答场景；
- **人工抽检**：每周抽二十条查询人工判定，指标之外的最后一道防线。

评估集从真实查询日志里采，覆盖高频词、长尾词、错别字、多义词。用内部构造的"标准问句"评出来的高分，经常在真实用户的错别字面前现原形。

> 语义搜索的调优闭环是：收集真实查询日志 → 标注评估集 → 换嵌入模型或调索引参数 → 重跑评估。没有这个闭环，所有"优化"都是碰运气。
