并发模型的选择像选扳手：问题从来不是"哪把最好"，而是"哪把能拧动你手里这颗螺丝，还不打滑"。同一道题，五种主流模型给出五种解法，成本结构和陷阱各不相同。更麻烦的是，选型时的讨论常常停在"哪个更现代"上，而现代与否和能不能解决问题基本无关。这篇先给一张大表，再逐个看它们的心智模型和代码里的真实样子，最后给一份决策清单。顺便交代一个前提：这里的对比默认服务端场景，嵌入式实时系统和浏览器各有额外约束，结论要打折看；另外所有模型在足够大的流量下都会露出真性情，纸面对比只是起点，压测才是终点。

## 一张表看清五种模型

| 模型 | 调度方 | 栈 | 通信方式 | 代表语言 | 典型陷阱 |
|------|--------|----|----------|----------|----------|
| 线程池 | 操作系统 | 每线程 MB 级 | 共享内存加锁 | Java、C# | 锁竞争、死锁 |
| goroutine | Go runtime | KB 级可伸缩 | channel | Go | goroutine 泄漏 |
| 事件循环 | 自身（单线程） | 共享一个栈 | 回调、Promise | JavaScript、Node | 一次阻塞卡死全局 |
| async/await | 语言运行时 | 状态机 | 任务与同步上下文 | C#、Python | 上下文捕获、异步 void |
| Actor | 框架或运行时 | 每 actor 一个信箱 | 消息 | Erlang、Akka | 信箱溢出、消息乱序假设 |

看表的姿势：先看"调度方"，它决定你的并发单位是重是轻；再看"通信方式"，它决定你的代码怎么组织结构。剩下三列都是这两列的下游后果。并发模型的差异，说到底就落在这两个格子里。

## 逐个模型说清心智模型

下面逐个过一遍。每个模型只讲三件事：它怎么调度、怎么通信、最容易在哪翻车。看完你会发现，五种模型没有一种是全能的，也没有一种是全错的，差别只在代价摆在哪里。

### 线程池：直接但要自己看住共享状态

线程池是最符合直觉的模型：任务扔进队列，线程们取出来执行。操作系统负责调度，语言只管借还线程。好处是直接，CPU 密集任务能真正占满多核；坏处也直接，多个线程碰同一份数据就得加锁，锁的粒度、顺序、死锁预防，全靠人盯。线程数量还有上限，几千个线程的上下文切换成本会吃掉全部收益。

### goroutine：把并发的单位做到便宜

Go 的思路是把"一个执行体"的成本压到可以忽略：创建只要几微秒，栈从 2KB 起按需长。于是"一个请求一个 goroutine"这种在别的语言里奢侈的写法，在 Go 里是默认风格。通信靠 channel，把数据的所有权转移写进类型。代价是 runtime 常驻的调度开销，以及 goroutine 泄漏这类新型故障，泄漏的 goroutine 不会报错，只会让内存悄悄爬升。

### 事件循环：一个人干所有活

事件循环把并发简化成一个排队系统：所有任务排一队，一个挨一个执行，谁都不许霸占。IO 等待期间线程腾出来处理别的任务，靠的就是"非阻塞"三个字。它的心智模型最简单，没有锁，因为根本没有第二个执行流。代价也最硬：任何一个同步长计算都会卡住所有人，而且异常处理天然分散在无数回调里。

### async/await：事件循环的语法糖，但不止糖

async/await 让异步代码长得像同步代码：编译器把挂起点之间的代码切成状态机，遇到 await 就把当前任务挂起，IO 就绪后恢复。它解决了回调地狱，却引入了新课题：`async void` 的异常没人接，同步上下文捕获在 UI 和 ASP.NET 里有不同表现，一个不小心 `ConfigureAwait(false)` 的取舍就能吵半天。它是事件循环的工程化封装，糖衣底下还是那台单线程机器。

### Actor：不共享，只传话

Actor 模型把"不共享内存"推到极致：每个 actor 有自己的状态和信箱，彼此只能发消息。没有共享状态，就没有锁；故障可以按 actor 隔离，一个 actor 崩了有监督者重启它。Erlang 用它做到了电信级的可用性，Akka 把它带进 JVM 生态。代价是消息的语义：信箱会溢出，消息顺序和到达保证取决于协议设计，排查问题时看到的是"消息丢了"而不是"变量坏了"，调试范式整个换掉。

现实里的系统很少只押注一种模型。一个典型后端服务：HTTP 层是事件循环或 async/await，请求处理是 goroutine 或线程池，跨服务通知走消息队列加 actor 风格的消费者。分层的意义在于让每层用最趁手的模型，接缝处用明确的边界隔开。选型真正要回答的不是"用哪个模型"，而是"哪一层用哪个模型，边界画在哪"。

## 代码里的样子

### JavaScript：事件循环

```javascript
async function loadAll(ids) {
  const results = await Promise.all(
    ids.map(id =>
      fetch(`https://example.com/api/items/${id}`).then(r => r.json())
    )
  );
  return results;
}
```

这段代码对 IO 密集的场景很合适：请求并发发出，结果按 promise 汇总。但只要里面混进一个同步的长计算，比如解析一个巨大的 JSON，整个循环立刻停摆，后面的定时器、响应全部推迟。事件循环对阻塞零容忍，这是它全部优点的代价。所以 Node 服务里有一条不成文规矩：任何超过几毫秒的计算都要拆成小片，或者丢给 worker 线程，宁可多写调度代码，也不能让主循环卡住，这是用自由度换吞吐的账。

### Rust：线程加消息

Rust 的标准库路线是 OS 线程加 channel，类型系统保证消息跨线程安全：

```rust
use std::thread;
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::channel();
    for id in 0..4 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(id * id).unwrap();
        });
    }
    drop(tx);
    let sum: i32 = rx.iter().sum();
    println!("平方和: {sum}");
}
```

注意 `drop(tx)`：发送端全部销毁，`rx.iter()` 才会结束，否则主线程永远等下去。这行删除就是 Rust 线程版的"退出路径"，和 Go 里 goroutine 的 done channel 是同一个思想：并发单元的收尾必须显式，这是五种模型的共同底线。

## 五个模型的共同底线

模型之间吵得再凶，有几条谁都跑不掉：

1. **并发单元必须有退出路径。** goroutine 要能取消，actor 要能 PoisonPill，异步任务要能取消传播。没有退出路径的并发单元，就是泄漏预备役。
2. **失败必须能被观察到。** 吞掉异常的 worker 是最危险的代码，它让故障从"响一声"变成"沉默地烂掉"。
3. **共享状态越少越好，能不共享就不共享。** channel、消息、不可变数据，本质上都是把"共享"这个动作本身变成显式操作。
4. **先证明需要，再引入。** 五个连接的服务不需要 actor，一个计算任务不需要事件循环。模型的复杂度应该匹配问题的形状。

这四条听起来像废话，但每一次线上并发事故复盘，结论几乎都落在其中一条上。模型决定事故的形状，底线决定事故有没有被拦住。选型会议多花半小时，返工的成本是它的十倍。

## 怎么选

按问题形状选，不按时髦程度选：

- [ ] 任务以 IO 为主、连接数万级起步，选 goroutine 或 async/await
- [ ] 需要跨机器分布、故障隔离、监督树，选 Actor
- [ ] 跑在浏览器或 Node 这类单线程环境，事件循环没得选
- [ ] 计算密集要压满多核，选线程池加数据分片，别跟共享状态较劲
- [ ] 团队没人说得清所选模型的退出机制，先补课再上线，模型无罪、滥用有责

> 没有最好的并发模型，只有你能看住的那一个。看得住的标准很具体：任何一个并发单元，你都能一句话说清它怎么开始、怎么结束、失败时谁收拾现场。说不清的时候就别上线，先补设计，补不上就换更笨的模型，笨模型看得住，聪明模型看不住，前者赢。

最后提醒一个通用动作：压测时按 <kbd>Ctrl</kbd>+<kbd>C</kbd> 中断，然后检查进程是优雅退出还是直接消失。优雅退出的实现难度，往往和并发模型的复杂度成正比，这也是选型时最容易被跳过的一课。模型选对了，退出逻辑写漏了，凌晨的告警一样响。下次选型时，先问形状，再问底线，最后问团队谁能看懂，三个问题都有答案，这个模型就错不到哪去。
