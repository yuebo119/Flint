微调是个被严重高估的动作。不少团队遇到问题第一反应是"微调一个自己的模型"，折腾两个月发现，换套提示词、接个检索就能解决。这篇文章先把"该不该微调"说清楚，再把全量微调、LoRA、QLoRA 这几条主流路线放在同一张桌上对比，最后给出按资源选型的建议。

## 什么时候才值得微调

先问三个问题，有一个答不上来就缓一缓：

1. 任务是否是**稳定且重复**的？（天天变的活儿别微调，改提示词更快）
2. 少量示例能否说清要求？（说不清，说明数据本身就定义模糊，微调也学不会）
3. 提示工程和 RAG 是否真的试过且不够用？（这两条路成本低一个数量级）

三个都答"是"，微调才进入候选。典型值得微调的场景：固定输出格式的抽取、特定文风改写、垂直领域术语密集的分类。

## 全量微调：最贵也最直接

全量微调更新模型全部参数，效果上限最高，代价也最直白：一个 70 亿参数的模型，仅优化器状态（Adam 的一阶、二阶动量）就要占用约 16 字节/参数，加上权重和梯度，轻松吃掉上百 GB 显存。多卡训练还要处理并行切分，工程复杂度陡增。

更隐蔽的风险是**灾难性遗忘**：模型在新数据上滚几遍，原来会的通用能力开始退化，回答变得狭隘。全量微调适合数据量充足、算力充足、且确实需要深度改造模型行为的团队，多数应用方够不着这条线。

## 参数高效微调家族

参数高效微调（PEFT）的共同思路是：冻结主干，只训练一小撮新增参数。按注入位置和形态分：

### 冻结主干，外挂增量

- **LoRA**：在注意力层的权重矩阵旁挂一对低秩矩阵，训练只更新这对小矩阵；
  - 秩 `r` 通常取 8 到 64，`r` 越大容量越大、显存开销线性涨；
  - 缩放系数 `alpha` 常设为 `r` 的 2 倍，控制增量对原权重的影响强度；
  - 不动的层可以指定，常见做法是只挂 `q_proj` 和 `v_proj`。
- **QLoRA**：LoRA 加量化——基座权重压到 4 bit，反量化只在计算时发生，训练时依然是 LoRA 那套小矩阵；
- **Prefix/Prompt Tuning**：在输入序列前拼接一段可训练向量，不动网络结构；
- **Adapter**：在层间插入小型瓶颈网络，逐层训练。

LoRA 的原始论文见 [arXiv:2106.09685](https://arxiv.org/abs/2106.09685)，QLoRA 见 [arXiv:2305.14314](https://arxiv.org/abs/2305.14314)。

## 对比总表

| 维度 | 全量微调 | LoRA | QLoRA |
|------|----------|------|-------|
| 可训练参数 | 100% | 约 0.1%–1% | 约 0.1%–1% |
| 70 亿模型显存（含训练态） | 上百 GB 量级 | 约 30–40GB | 约 10–16GB |
| 效果上限 | 最高 | 接近全量，多数任务差距可忽略 | 略低于 LoRA，通常仍够用 |
| 训练产物 | 整套新权重 | 几 MB 的增量权重 | 几 MB 的增量权重 |
| 多任务切换 | 每任务一套完整模型 | 基座共用，换适配器即可 | 基座共用，换适配器即可 |
| 实现门槛 | 高（并行、通信、容错） | 低（主流库开箱即用） | 中（量化配置有讲究） |

最后一行"实现门槛"最影响决策：一个 70 亿模型，全量微调要张罗多卡互联，LoRA 一张消费级显卡就能跑起来，QLoRA 能把门槛压到更低的显存预算。对绝大多数团队，答案已经很明显了。

## LoRA 到底改了什么

### 一行数学，两个小矩阵

LoRA 的数学只有一行。设原权重矩阵为 $W \in \mathbb{R}^{d \times k}$，训练时它被冻结，在旁边学一对矩阵 $B \in \mathbb{R}^{d \times r}$、$A \in \mathbb{R}^{r \times k}$，前向计算变成：

$$ h = Wx + \Delta Wx = Wx + BAx $$

其中秩 $r \ll \min(d, k)$。妙处在于：微调带来的权重变化 $\Delta W$ 被认为是低秩的——模型"学会新任务"这个变化，并不需要动整个矩阵，只动少数几个方向。$BA$ 的参数是 $r(d+k)$，相比 $dk$ 小两个数量级，这就是显存和存储双降的来源。推理时更爽：把 $BA$ 加回 $W$ 得到合并权重，**完全不增加推理延迟**，不像 Adapter 那样多一层计算。

```json
{
  "model": "internal-base-7b",
  "method": "lora",
  "target_modules": ["q_proj", "v_proj"],
  "r": 16,
  "lora_alpha": 32,
  "lora_dropout": 0.05,
  "bias": "none",
  "task_type": "CAUSAL_LM"
}
```

这是训练框架里常见的 LoRA 配置。`lora_alpha` 与 `r` 的比值决定了增量的实际强度，固定 `alpha/r` 不变时，调 `r` 主要影响容量而非步长。

用伪代码看训练循环，和普通微调的差别只在优化器可见的参数集合：

```python
# 冻结基座，只把 LoRA 参数交给优化器
for name, param in model.named_parameters():
    param.requires_grad = ("lora_" in name)

trainable = [p for p in model.parameters() if p.requires_grad]
optimizer = torch.optim.AdamW(trainable, lr=1e-4)

for batch in dataloader:
    loss = model(**batch).loss
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
```

保存时只导出那几 MB 的适配器权重，基座全站共用。换任务 = 换适配器，部署侧一次加载多个适配器按请求路由，存储和运维成本随之摊薄。

## 按资源选型

把决策压缩成三步：

1. **先算显存账**：能拿出多少训练显存，直接砍掉一半选项；
2. **再定数据账**：千条以内高质量样本优先 LoRA/QLoRA，数据匮乏时堆方法不如先补数据；
3. **最后做小规模对照**：同一评估集上跑全量与 PEFT 各一轮，差距小于一个点就选便宜的。

![不同微调路线的显存占用与效果对照](/images/demo-3.svg)

> 微调不是万能药。格式不统一、数据有噪声、评估集和训练集同分布泄漏，任何一个问题都能让微调白干。方法选对只解决"能不能训起来"，数据质量才决定"训出来有没有用"。

## 落地细节清单

- **学习率**：LoRA 常用 1e-4 到 3e-4，比全量微调的 1e-5 高一档，因为可训练参数少，步子可以大；
- **训练轮数**：过拟合来得比全量快，通常 1 到 3 个 epoch，靠早停和评估集守着；
- **评估先行**：动手前先把评估集和指标定下来，否则训完连"有没有变好"都说不清；
- **格式对齐**：训练数据的输入输出格式必须和线上调用格式逐字节一致，差一个系统提示词都可能让效果打折。

最后补一个冷门但实用的点：微调后的模型要做推理侧评估。合并 LoRA 权重后的模型，在推理框架下的实际吞吐和原版可能有差距，量化、编译优化、批处理策略都要在新模型上重测一遍，别让训练阶段省下的钱在推理账单里还回去。

## 数据准备：微调成败的真正分水岭

方法之争的热度，远高于它应有的权重。真实项目里，微调失败的头号原因不是方法选错，而是数据没准备好。高质量微调数据的标准很朴素：输入输出对要覆盖真实调用形态，包括线上会遇到的脏输入；输出风格要统一，十个标注员十种写法，模型只会学到一团和稀泥；数量上，几千条精心构造的样本，往往打败几万条粗制滥造的样本。数据构造的具体做法，一类是从真实日志里挖，历史问答、人工修改过的工单都是富矿；另一类是用大模型生成再加人工筛选；两类混用效果最好。动手训练前，先人工过一百条样本：如果你自己都能看出格式不一致、答案有错，模型救不了你。

## 训完之后：评估与回归测试

微调最大的风险是"新技能学会了，旧能力忘了"。只在新任务的评估集上看分数，很容易被单边胜利迷惑。完整的回归测试要包含三类评估集：目标任务集、通用能力集（常识问答、指令遵循，可借用公开基准）、安全集（诱导违规、敏感问题）。三类全绿才算可上线，任何一类明显退化，就要回调训练轮数、混入通用数据，或者直接放弃这次微调。这份回归测试集要长期维护，它是后续每次模型升级和重新微调的守护网——没有它的团队，每次微调都是一次裸奔。

![微调前后的能力迁移与遗忘边界示意](/images/demo-11.svg)

总结成一句话：全量微调是重炮，LoRA 是步枪，QLoRA 是把步枪的后坐力又砍一半。多数应用团队用步枪就能完成任务，把重炮留给确实需要深度改造模型的人。
