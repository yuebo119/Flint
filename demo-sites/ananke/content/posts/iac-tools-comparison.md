基础设施即代码的概念早已普及：用代码而不是控制台来创建和变更云资源，详见[维基百科相关条目](https://zh.wikipedia.org/wiki/基础设施即代码)。但落到选型，团队之间差异巨大，有人默认 Terraform，有人只信云厂商原生工具，还有团队直接用通用编程语言写基础设施。选错的代价不只是学习成本，更是未来两年每次变更都要忍受的摩擦。这篇对比按六个维度拆开讲。

## 参赛选手

先快速认识一下主要选手：

- **Terraform**：事实上的行业标准，HCL 语言，插件生态覆盖上千家厂商。2023 年许可证变更后，社区分叉出 OpenTofu，由 Linux 基金会托管。
- **OpenTofu**：Terraform 的分叉，语法与生态基本兼容，许可证友好，社区驱动。
- **Pulumi**：用 TypeScript、Python、Go 等通用语言写基础设施，复用编程语言的抽象能力。
- **AWS CloudFormation**：AWS 原生服务，YAML 或 JSON 模板，与 AWS 控制台深度集成。
- **Azure Bicep**：Azure 原生，比 ARM 模板简洁得多的 DSL，编译为 ARM 模板执行。
- **Ansible**：以配置管理为主，也能编排云资源，无状态、推模式。

后三者通常和前几种不构成直接竞争：单云团队用原生工具往往更顺，多云团队才更需要中立方案。

## 六个维度横向对比

| 维度 | Terraform / OpenTofu | Pulumi | CloudFormation | Bicep |
| --- | --- | --- | --- | --- |
| 描述语言 | HCL 专用 DSL | 通用编程语言 | YAML / JSON | 类 HCL 的 DSL |
| 状态管理 | 显式 state 文件 | 托管或自建后端 | 云厂商托管 | 云厂商托管 |
| 供应商覆盖 | 全云 + 上千插件 | 全云 + 插件 | 仅 AWS | 仅 Azure |
| 漂移检测 | plan 时对比 |  refresh 时对比 | 自动检测并报告 | 部署时对比 |
| 测试能力 | 弱，依赖集成验证 | 强，可用语言测试框架 | 弱 | 弱 |
| 学习曲线 | 中等，需理解 state | 中高，但无新语言门槛 | 低（AWS 团队） | 低（Azure 团队） |

两个关键差异值得展开。

### DSL 与通用语言

HCL 的写法是声明式的，读起来像配置：

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c7217cdde317cfec"
  instance_type = var.instance_type

  root_block_device {
    volume_size = 50
    volume_type = "gp3"
  }

  tags = {
    Name        = "web-${var.env}"
    Environment = var.env
  }
}
```

它的优点是意图清晰、diff 直观，缺点是一旦需要循环、条件、复用，就要依赖 HCL 有限的表达式能力，复杂逻辑写起来别扭。Pulumi 用通用语言绕开了这个问题：

```yaml
# Pulumi 程序的逻辑在代码里，配置在 YAML 中
# pulumi.yaml 片段
name: web-infra
runtime: nodejs
config:
  instanceType:
    type: String
    default: t3.medium
```

```ts
// index.ts：用熟悉的语言写资源
const web = new aws.ec2.Instance("web", {
  ami: "ami-0c7217cdde317cfec",
  instanceType: new pulumi.Config().require("instanceType"),
  rootBlockDevice: { volumeSize: 50, volumeType: "gp3" },
});
```

代价是：通用语言允许你用图灵完备的方式写出无法预测的计划，评审基础设施 diff 的难度上升。**DSL 换来了可预测性，编程语言换来了表达力**，这是选型时最根本的取舍。

> 好的基础设施代码，标准不是写得优雅，而是评审者能看懂"这一改动将在生产里发生什么"。可预测性优先于表达力，这是 DSL 存在的理由。

### 模块化与复用：DRY 的边界

基础设施代码的第一个月总是整洁的，第三个月开始出现复制粘贴。成熟的代码库都有明确的复用层次：

- **官方与社区模块**：网络、集群这类通用模式直接用社区维护的模块，别自己从零写 VPC；
- **团队内部模块**：把"一套带监控的数据库实例"封装成内部模块，业务团队传参即可，标准内建；
- **组合而非继承**：模块之间用输入输出拼接，避免做出一个参数上百个的"万能模块"，那种模块比复制粘贴更难维护。

复用的边界也要讲清楚：**不要为了复用把差异很大的资源硬捏进一个模块**。三套环境用同一套参数化模块是合理的，让模块同时支持"单 AZ 测试库"和"跨区域生产库"两种形态，往往比复制两份更糊涂。判断标准很简单：如果传入的开关参数比资源本身还复杂，就是过度设计。

模块之外还有一层容易被忽略的复用：**文档化的参考架构**。把"一套标准的 Web 服务该有什么"写成参考实现（模块加文档加示例），新服务照葫芦画瓢，比每个团队从空白文件开始更可靠。IaC 的终极目标不是把基础设施写成优雅的代码库，而是让"正确的基础设施"成为阻力最小的默认选项。

## plan 评审与策略即代码

Terraform 系列最大的工程优势是 `plan`：应用之前先生成一份"将要发生什么"的清单，这份清单应该进合并请求，像代码 diff 一样被评审。配套两条实践：

1. **plan 结果自动贴到 PR 评论**，评审者重点看"销毁"和"替换"标记的资源，这两类操作最危险；
2. **策略即代码**：用 OPA 或 Sentinel 写几条硬规则，比如禁止创建公网读写桶、禁止关闭加密。策略在 CI 里强制执行，比依赖人记手册可靠得多。

云厂商原生工具在 plan 评审上通常弱一些，变更集（Change Set）机制存在但生态不如 HCL 成熟，这也是中立工具在多团队协作时的隐性优势。

## 状态管理

Terraform 系列显式维护 state 文件，这是它最大的能力来源，也是最大的运维负担：state 丢失、并发写入冲突、手动改资源导致漂移，都是真实世界的高频问题。团队必须一开始就配远程后端和状态锁，并把 state 文件当敏感数据保管。

漂移检测应该被自动化：每天定时跑一次 `plan`，输出为空说明实际与代码一致，非空则自动建工单。这件事的价值在事故复盘里最明显：当被问"这个改动是谁做的、什么时候做的"，漂移报告和 Git 历史能直接回答，而不是一群人翻控制台操作记录。对强合规的行业，这条自动化还顺带满足了审计对变更可追溯的要求。云厂商原生工具把状态托管在服务端，少一个负担，但也被锁定在单云。

## 选型建议：按场景分流

选型不该是"哪个工具更好"，而是"哪个工具匹配当前约束"：

- [x] 多云或混合云，或需要中立的社区生态：优先 OpenTofu 或 Terraform
- [x] 团队强项是编程而非配置，且需要复杂抽象：评估 Pulumi
- [x] 全部资源在单一云，追求最省心：用云厂商原生工具（CloudFormation 或 Bicep）
- [x] 需要管配置而不只是管资源：Terraform 加 Ansible 组合，各管一段
- [ ] 尚在观望：先在一个非关键项目上用 Terraform 语法试水，OpenTofu 可无缝承接

最后一项对很多团队是务实路径：HCL 生态沉淀最深，先学它不亏，将来真需要换，语法兼容的分叉能降低迁移成本。

选型里还有一类现实问题常被忽略：**团队招聘与知识储备**。市场上会写 Terraform 的工程师远多于会写 Bicep 的，用冷门工具意味着知识锁在少数人手里，人一走模块就成了黑盒。工具的人气本身就是一种资产，这点在对比表格里看不到，却在每次人员流动时真金白银地体现出来。

## 混合使用是常态

现实里很少有团队只用一种工具。更常见的组合是：Terraform 管理跨云的基础设施（网络、集群、数据库），云厂商原生工具或 Helm 管理云上的 PaaS 资源和应用发布，Ansible 处理虚拟机和中间件配置。工具之间用清晰的边界划分职责，比强行统一更重要。边界画在"谁拥有生命周期"上：一个资源只应有一个工具负责创建和销毁，否则一定会互相打架。

多出一个容易被追问的问题：**要不要追新版本**。IaC 工具的大版本升级（Terraform 到 OpenTofu、Provider 的大跳变）可能带来语法和行为的双重变化，稳妥策略是核心模块先在非生产环境验证一个完整周期，再逐步推广；工具本身保持小版本勤更，大版本计划性升级。把工具锁在远古版本不升级，省下的心力会以安全漏洞和生态脱节的形式还回来。

## 小结

IaC 选型的结论取决于约束而非信仰：**语言偏好决定 DSL 还是编程语言，云策略决定中立工具还是原生工具，团队结构决定要不要叠加配置管理**。真正拉开差距的也不是工具本身，而是三条纪律：state 或等价状态被妥善托管、所有变更走代码评审、漂移被定期检测。这三条做到位，用任何主流工具都能把基础设施管好。
