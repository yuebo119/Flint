数据团队的工作日常，是把业务库的数据搬到数仓，再加工成报表和特征。搬数据这件事听起来是体力活，真做起来才发现，管道一旦设计错，后面每天都在给前面的懒惰还债。这篇文章讲三个让管道活得久的支柱：幂等、增量、可重放，每个都配可运行的示例。

## ETL 与 ELT 的分界

经典 ETL 是抽取后在独立引擎里转换再加载，数据仓库侧的负载可控，但转换逻辑要重写一遍。ELT 是先原样加载到数仓，再利用数仓的算力转换，云数仓普及后这条路更流行。

两条路没有绝对的优劣，选择依据是转换复杂度：轻量清洗用 ELT，数仓里几条 SQL 搞定；重量级逻辑、跨源关联用 ETL，中间层可控。多数团队最后是混合架构：ODS 层用 ELT 原样落库，DWD 层用 ETL 精细加工。

## 支柱一：幂等

幂等指同一个任务跑一次和跑 N 次，结果完全一致。夜间调度失败重跑是常态，任务跑到一半失败再跑一次，如果管道不幂等，数据就翻倍或者对不上。

做到幂等的常见手法：

- 按分区覆盖写：每次运行先删目标分区再写，如 `INSERT OVERWRITE PARTITION (dt = '2026-04-15')`
- 按主键合并：用 `MERGE` 或 `ON DUPLICATE KEY UPDATE`，重复执行只更新不插入
- 先删后插加事务：删除与插入包在一个事务里，失败整体回滚

反面教材是每次 `INSERT` 追加，重跑一次多一份，对账时差一倍，查起来要命。

## 支柱二：增量抽取

全量抽取在数据量小的时候最省事，表过了几亿行就是灾难。增量抽取只搬变化的数据，水位线是最常用的机制：

```python
from datetime import datetime, timedelta

def extract_increment(source_conn, watermark_store, extract_date):
    """按业务日期水位增量抽取，幂等：重复执行同一天结果一致"""
    # 读取上次成功的水位，失败时回退一天兜底
    last_ok = watermark_store.get("orders") or (extract_date - timedelta(days=1))

    rows = source_conn.query(
        """
        SELECT order_id, user_id, amount, status, updated_at
        FROM orders
        WHERE updated_at >= %s AND updated_at < %s
        ORDER BY updated_at
        """,
        (last_ok, extract_date + timedelta(days=1)),
    )

    loaded = load_to_staging(rows, partition=extract_date)
    if loaded == len(rows):
        # 只有全量写入成功才推进水位，失败则保持旧水位等下次重跑
        watermark_store.set("orders", extract_date + timedelta(days=1))
    return loaded
```

水位推进放在写入成功之后，这是增量抽取不出错的关键顺序。先推进水位再写入，一旦写入失败，这段数据就永久丢失。

更新型数据用 `updated_at` 做水位，纯插入型数据用自增 ID 或创建时间。要注意源库 `updated_at` 没有索引时，增量查询会退化成全表扫描，抽取前先确认索引存在。

## 支柱三：可重放

可重放指任何一天的数据都能从零重新加工出来。这要求管道保留原始数据副本，也就是数仓分层里的 ODS 层：源库原样落一份，之上所有加工都可以推倒重来。

可重放的价值在修历史数据时体现得最清楚。上游修了一个bug字段，下游要重新加工最近半年，没有 ODS 层就得回头找业务库要历史，对方早就查不到了。有 ODS 层，半年内的任意一天都是几次调度的事。

调度配置把这三个支柱固化下来：

```python
DAG = {
    "name": "orders_daily",
    "schedule": "0 2 * * *",           # 每天凌晨两点
    "max_retries": 3,                  # 失败自动重试，配合幂等安全
    "retry_delay_minutes": 10,
    "depends_on": ["ods_orders_loaded"],
    "timeout_hours": 2,
    "alert_on_failure": "data-oncall",
}
```

## 监控与数据质量

管道跑起来只是开始，要盯的是三类信号：

- 及时性：任务是否在 SLA 前完成，延迟趋势在变差要预警
- 数据量：行数、金额合计与昨日同期对比，波动超过三成自动标红
- 质量：主键唯一率、非空率、枚举值合法性，每天抽样校验

### 告警怎么分级

管道告警分两级。P0 是任务失败或数据量为零，打电话，值班同学十五分钟内响应；P1 是数据量波动超阈值或延迟超 SLA，发消息，当天处理。告警太全会导致麻木，我们按这个分级砍掉了七成噪音告警，剩下的每一条都有人跟。分级的判断标准很简单：这个告警响的时候，如果没人处理，业务半小时内会不会受影响。会的就是 P0，不会的就是 P1，灰度地带的加一条人工确认，不要全设成 P0。

数据质量 checks 要建在加载之后、下游消费之前，坏数据停在 DWD 层，不要流到报表层才发现。

## 一个失败案例

反面教材最有说服力。曾经有一条用户行为管道，三个支柱一个都不满足，运行了八个月后崩掉。

它每次运行都全量抽取行为日志表，不管增量；目标表只追加不分区，重跑一次数据翻倍；没有 ODS 层，下游加工直接读业务库。出事那天，上游给一张表加了个字段，管道解析失败，而历史数据已经无处可找，业务库只保留三十天。最终结果是报表断了四天，用三条临时脚本手工补了三天数据，团队两个人通宵两次。

复盘归因，根因是图省事：全量抽取省得设计水位，追加写省得管分区，跳过 ODS 省得搭一层。三个月里每次都是"这次先这样"，八个月后一次性还债。三个支柱不是理论洁癖，是让管道在半夜不出事、出事能重跑、跑偏能倒带的底线。

## Schema 变更怎么处理

上游改表结构是管道的日常扰动，处理不好就是事故源。三个环节要把住。

抽取层做字段白名单：只取管道声明过的字段，上游加字段不影响管道，删字段或改类型必须显式评估。加载层用宽松写入：新字段先进 JSON 扩展列，别急着改表结构，观察两周确认真实用途再提升为正式列。血缘层靠元数据管理：哪张表的哪个字段被哪些下游消费，出事时能顺着血缘找到影响面，而不是全表猜。

约定一个变更流程：上游 DDL 变更提前一周通知数据团队，双方确认管道影响后再执行。听起来官僚，执行起来是一条消息加一张表的事，比起半夜被叫起来排查 schema 不匹配，成本低到可以忽略。

## 任务拆分与依赖编排

管道大了之后，单脚本必然拆成任务图。拆分的粒度有个实用标准：一个任务失败后，重跑成本要低到值班同学敢在半夜点下去。按这个标准，抽取、清洗、关联、聚合、报表通常是五个任务，而不是一个五千行的大脚本。

依赖编排要防两类问题。一类是循环依赖，A 等 B、B 等 C、C 又等 A，多数是分区设计不一致造成的，解法是统一按业务日期分区，所有上游产出同一分区，消费才能对齐。另一类是惊群，上百个任务同时启动抢数据库连接，解法是配置并发度和优先级，抽取类任务错峰启动。

任务之间传数据用分区表而不是消息队列，这是数仓场景的特点：消息队列适合触发信号，不适合搬运数据本身。上游写完分区后写一条完成信号，下游收到信号才开始读分区，信号丢了有兜底：下游启动时主动检查上游分区是否存在，存在就认为完成。信号机制和分区检查双保险，比单纯依赖消息可靠。

## 小结

管道设计做决策时问三个问题：重跑一次会出问题吗？只搬变化的数据吗？半年前的数据还能重放吗[^1]。三个答案都是"能"，这条管道就能交给下一个值班的人，半夜也不会被叫起来。

> 好的数据管道是无聊的：每天准时跑完，没人注意到它；坏的管道天天上头条。

这三个原则的落地顺序也有讲究。我的建议是先在第一个管道上把幂等做扎实，它是另外两个的地基：不能重跑的任务谈不上可重放，分区覆盖写本身也约束了增量的边界。等第一个管道稳定运行一个月，再把同一套模板复制到其他管道，比一开始就追求大而全的框架靠谱。数据管道的复杂度永远跟随业务数据量增长，起步阶段够用、结构清晰，就是最好的设计。
