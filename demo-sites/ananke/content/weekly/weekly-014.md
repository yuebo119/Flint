## 开场白

本期聊前端。浏览器是用户侧唯一不受我们控制的环境：设备、网络、耐心都不可控，
能控制的只有发过去多少字节、多久出现首个内容、操作多久有响应。本期五个条目都
围绕"把不确定性变成可度量、可预算的指标"展开。

> 前端性能的本质是与不确定性共处：你控制不了用户的设备与网络，
> 只能控制发过去的字节数和首屏的关键路径。

## Core Web Vitals：三个数字定义体验

Google 把用户体验收敛成三个核心指标：LCP（最大内容绘制，加载性能）、
INP（交互到下一次绘制，响应性能，2024 年起正式取代 FID）、
CLS（累积布局偏移，视觉稳定性）。三个数字的意义不在分数本身，
而在它们都是**真实用户数据**：实验室里的 Lighthouse 分数只是诊断工具，
字段数据来自 Chrome 用户体验报告，反映真实设备与网络。

优化手段与指标一一对应：LCP 看首屏资源链路，预加载关键字体与首图、
服务端推送或流式渲染；INP 看主线程被什么占着，长任务拆分、
第三方脚本延后、输入 handler 防抖；CLS 看谁在跳，图片与广告位给尺寸占位、
字体用 `font-display: swap` 配合预加载。设一条内部门槛，
比如移动端 LCP 两秒五、INP 两百毫秒、CLS 零点一，超了的需求不以上线收尾。

实验室数据与字段数据要配合用：Lighthouse 单次分数波动大，
适合做优化前后的回归对照；RUM 趋势才反映真实用户体验，适合定门禁。
两者混用是常见误用，拿一次 Lighthouse 的九十五分汇报"用户体验达标"，
是自欺欺人。INP 的治理比 LCP 更依赖 profiling：打开性能面板录一段交互，
看长任务分布。常见的元凶是第三方脚本（统计、客服、广告），
它们的执行时机完全不受你控制，对策是延迟加载加沙箱 iframe，
把主线程占用从"同步执行"改成"有空才跑"。

参考链接：[Core Web Vitals 指标说明](https://zh.wikipedia.org/wiki/Google)

## 产物体积：预算比优化更重要

前端工程里最有效的约束不是某个优化技巧，而是**体积预算**：
在配置里写明每个入口的产物上限，超了就 CI 失败。有了预算，优化从"感觉变大了"
变成"红了必须处理"，团队对体积的感知也自动建立起来。

```json
{
  "bundlesize": [
    { "path": "dist/assets/*.js", "maxSize": "150 kB" },
    { "path": "dist/assets/*.css", "maxSize": "30 kB" },
    { "path": "dist/assets/fonts/*.woff2", "maxSize": "45 kB" }
  ]
}
```

预算的常见来源有三个：竞品同页面对标、历史版本中位数加一成、
按网速与转化率的估算反推。三种都合理，关键是数字要写进配置而不是记在文档里。
配合分析工具（webpack-bundle-analyzer、rollup-plugin-visualizer）定位大头，
多数页面的体积问题集中在三五个依赖上，换掉它们比全局抠字节有效得多。

预算的例外通道也要设计：大版本升级、新页面首次接入，
允许带审批的超额，但必须同步给出回落计划。没有例外通道的预算
会被各种"就这一次"磨成筛子；有通道没回填计划的预算，
则会积累成一堆技术债欠条，两者是配套的。
具体到依赖替换，最经典的案例是日期库：moment 加上全部语言包
动辄两三百 KB，换 dayjs 或 date-fns 后体积掉一个数量级，
API 迁移成本一到两天。同类可审的还有工具库全家桶
（lodash 全量引入改按需）、图标库（全量包改按需打包）、
以及 polyfill（按浏览器支持矩阵只发必要的部分）。

参考链接：[体积预算配置实践](https://example.com/frontend/performance-budget)

## 图片格式：AVIF 之后的一站式选型

图片常年占页面字节的一半以上，格式选型是最划算的优化。当前的经验排序是：
AVIF 优先（同画质体积最小，兼容性已过九成），WebP 兜底（兼容性最广），
PNG/JPEG 只作最后回退。配合 `picture` 元素与 `srcset` 让浏览器自选：

```html
<picture>
  <source srcset="/img/hero.avif" type="image/avif">
  <source srcset="/img/hero.webp" type="image/webp">
  <img src="/img/hero.jpg" alt="首屏主图" width="1200" height="630" loading="eager">
</picture>
```

两个细节决定成败：`width` 与 `height` 必须写，浏览器据此预留空间，
这是零成本的 CLS 修复；首屏图 `loading="eager"` 加 `fetchpriority="high"`，
首屏之外的图一律 `loading="lazy"`。静态站点生成器普遍内置图片处理流水线，
把多尺寸、多格式、懒加载都自动化，配一次全站受益。

懒加载的边界也要注意：首屏图绝不能用 lazy，浏览器要先下载完那张
四像素的占位图才触发真实加载，反而拖慢 LCP。正确的组合是首屏 eager
加 `fetchpriority="high"`，其余 lazy，并且每张图都写死宽高。
这套规则可以固化进图片组件的默认值，不让每个调用点自己决定。
响应式还有一层是按屏宽给不同尺寸：`srcset` 的 `w` 描述符列出多个宽度，
`sizes` 告诉浏览器这个图片实际占多宽，浏览器自行选择最接近的文件。
省流量的关键是 `sizes` 写得准，写大了白下大图，写小了糊屏。
静态站的图片流水线通常能自动生成多尺寸，需要人工写对的只有 `sizes`。

## 容器查询：组件级的响应式

媒体查询的局限是它按视口判断，而组件只关心自己容器多宽。容器查询
（`@container`）把响应式的判断依据从视口换成容器，同一个卡片组件放进
侧栏是竖排、放进主区是横排，样式跟着容器走，不需要给每个使用场景
起一个修饰类。写法上先声明 `container-type: inline-size`，再在子元素里
`@container (min-width: 400px)` 断点。

对设计系统这是质变：组件真正自包含了，布局逻辑不再泄漏到使用方。
兼容性上主流浏览器均已支持，渐进增强写法是默认样式按最窄容器设计，
容器查询只做增强，老浏览器拿到可用的窄布局也不算坏。

容器查询还带了一批容器单位（`cqw`、`cqi` 等），组件内的字号、
间距可以按容器宽度比例缩放，"组件级流体排版"成为可能。
这让设计系统里"卡片字号永远十六像素"这类硬编码有了替代：
卡片在窄栏里十六、在主区里十八，同一份样式自己适配。
落地路径上，容器查询适合新建组件直接采用，存量组件按改造时机顺带迁移，
不必专门排期。判断标准很简单：这个组件在项目里出现过两种以上宽度形态，
就是容器查询的候选；只以一种宽度使用的组件，媒体查询甚至都不需要。

参考链接：[容器查询语法说明](https://zh.wikipedia.org/wiki/CSS)

## 键盘可达性：Tab 走一遍就知道

无障碍的最低门槛是键盘：只用 <kbd>Tab</kbd>、<kbd>Shift</kbd>+<kbd>Tab</kbd>、
<kbd>Enter</kbd>、方向键能否完成所有操作。自检方法很朴素，
把鼠标推到一边，从地址栏开始 Tab 走全页：焦点是否可见、顺序是否符合视觉顺序、
弹层打开时焦点是否圈在弹层内、关闭后焦点是否回到触发元素。

三个高频修复：自定义按钮要用 `button` 或加 `role="button"` 与键盘事件，
别用 `div` 加 click；焦点样式用 `:focus-visible` 而不是粗暴 `outline: none`；
图标按钮必须配 `aria-label`，屏幕阅读器用户听到的不能是"按钮 按钮 按钮"。
在 Chrome DevTools 里按 <kbd>Esc</kbd> 打开抽屉，可以直接查看焦点顺序与渲染信息。

语义 HTML 是可达性的地基：能用 button 不用 div，能用 a 不用 span
加 click，列表就是 ul 与 ol。这些标签自带键盘行为与读屏语义，
等于免费拿到全部默认实现。自定义控件的代价从你决定重写那一刻开始，
确认过必要性再付。自动化能覆盖一部分：eslint 的 a11y 插件拦常见错误，
axe-core 可以在 CI 里对关键页面跑扫描。但自动化查不出"焦点顺序
是否符合视觉逻辑"这类语义问题，那仍然要人走一遍。
工具降低重复成本，人的走查保证判断质量，两个都要，谁替代谁都会漏。
