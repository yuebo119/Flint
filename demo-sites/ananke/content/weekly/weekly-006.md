类型的价值常被说成"防止出错"，这个说法太笼统。更准确的说法是：类型决定了错误在哪个阶段暴露。编译期暴露的错误最便宜，测试期贵一个量级，生产环境贵到没法算。这周聊粒度的学问：约束该编码到多细、空值怎么处理、渐进类型到底给了我们什么，以及什么时候该收手。四个条目，都来自被动态语言和静态语言分别毒打过的经历。

## 条目一：从 stringly-typed 到 newtype 🧩

stringly-typed 代码的特征是万物皆字符串：用户 ID 是字符串，邮箱是字符串，状态是字符串，于是任何字符串都能传进任何参数，错误要等到运行时才以一句难懂的异常现身。newtype 的思路是把约束编码进类型：一个 `UserId` 和一个 `OrderId` 是不同的类型，编译器替你挡住张冠李戴；一个 `Email` 类型只能在构造时通过校验，拿到手的实例天然合法。解析时验证一次，受益的是后面所有代码，这笔账怎么算都划算。

```python
from typing import NewType
from dataclasses import dataclass

UserId = NewType("UserId", str)
OrderId = NewType("OrderId", str)

@dataclass(frozen=True)
class Email:
    value: str
    def __post_init__(self) -> None:
        if "@" not in self.value:
            raise ValueError(f"非法邮箱: {self.value}")

def send_receipt(user: UserId, contact: Email) -> None:
    ...  # 参数类型说清了意图，误传 OrderId 在编辑器里就标红
```

实践上的分界线在哪？我的判断是：跨模块边界的数据、有格式约束的输入、含义容易混的同构值，这三种值得建新类型；函数内部的临时变量不值得，那只会把代码搅成一锅类型粥。粒度的目标是让"传错"在写下的瞬间就被发现，不是让每个变量都有族谱。

把约束编进类型的进阶版是消除不可能状态：与其在运行时检查"已取消的订单不能发货"，不如让类型系统里根本不存在这个组合。这个思路来自 ML 家族，在状态机建模上收益极大。代价是类型定义的代码量上升，读代码的人需要先在脑子里展开类型才能看懂流程。

> 好的类型让错误在写下的瞬间暴露，而不是在凌晨三点的报警里。这句话值得贴在每一个推崇动态类型便利的讨论开头。

收益和代价都真实存在，判断标准是非法状态被触发的历史频率：从没发生过的组合，不值得为它建三层类型。

## 条目二：空值的几条路线

空值问题被称为十亿美元错误，但真正贵的不是 null 本身，是"每个引用都可能为空且没人知道"。业界还债的路线大致三条：可空类型加强制解包检查（Kotlin、Swift、Rust 的思路）、Option 单子加模式匹配（Haskell 一脉）、以及空对象模式。三条路线没有银弹，共同点是把"可能没有值"这件事写进签名，让调用方无法装作看不见。

| 路线 | 代表语言 | 优点 | 代价 |
| --- | --- | --- | --- |
| 可空类型 | Kotlin、Swift | 学习成本低 | 解包噪音 |
| Option 单子 | Rust、Haskell | 组合性强 | 心智负担重 |
| 空对象 | 各语言通用 | 无侵入 | 隐藏了语义缺失 |

渐进类型的语言里，`Optional[str]` 配合检查器也能拿到八成收益，前提是团队真的开严格模式。我们吃过一次反例：代码库 `Any` 满天飞，检查器开着但警告没人看，结果类型注解成了行为艺术，看起来严谨，跑起来和没有一样。空值治理的第一件事是把警告清零，第二件事才是讨论路线选型。

三条路线落地时都有些细节值得知道：可空类型配安全调用和猫王运算符，可以把判空噪音压到很低；空对象模式最怕的是"看起来有值其实没有"的假对象，它把缺失藏起来，缺陷定位反而更难；Option 单子在组合多个可能为空的操作时最优雅，但团队整体转型成本最高。路线可以混用，前提是团队对"什么算空"有统一答案，最怕的是三种风格在同一个代码库里各说各话。

参考：[空安全设计漫谈](https://example.com/null-safety-design)

## 条目三：渐进类型的真实收益

TypeScript 和带类型提示的 Python 证明了一件事：类型不必全有或全无，可以按收益逐步渗透。真实收益不在覆盖率数字上，在三个地方：编辑器的补全和跳转、重构时的安全网、以及接口变更时的传播警报。反过来说，为覆盖率硬写的注解是负资产：`Any` 满天飞的签名比没有签名更糟，因为它制造了"已经安全"的幻觉[^1]。

### 类型渗透该从哪开始

```yaml
# OpenAPI 片段：类型约束写进契约，上下游共享同一份真相
components:
  schemas:
    CreateOrder:
      type: object
      required: [userId, items]
      properties:
        userId:
          type: string
          format: uuid
          description: 用户标识，创建后不可变
        items:
          type: array
          minItems: 1
          items:
            $ref: "#/components/schemas/OrderItem"
```

顺序上，先公共 API 的边界，再数据模型的骨架，最后才是业务逻辑内部。边界类型是契约，收益最高；内部类型是自便，够用即可。关于覆盖率还有一个反直觉的观察：从零到六成最省力，从六成到九成最费力，最后那四成往往要给祖传代码补签名，风险高于收益。所以别把全量类型化当目标，把"新代码全类型化、公共接口全类型化"当目标就够，老代码跟着 churn 热点慢慢渗透。还有一个实用技巧：把类型当文档写，好的签名替代注释，比如 `def charge(order: Order, card: TokenizedCard)` 比三行注释说得清楚，而且它不会过期。类型渗透的进阶姿势是把验证往边界推：入口处把原始输入解析成类型化的领域对象，之后的代码拿到的全是合法值，防御性检查自然消失。这叫解析而非校验，是边界清晰化的核心手法。反过来，在函数内部到处 `assert isinstance(x, str)` 是类型系统漏水后的补丁，补丁越多，越说明该在入口修屋顶。

参考：[渐进类型采用指南](https://example.com/gradual-typing-adoption)

## 条目四：警戒线，类型复杂度也是债务

最后唱唱反调。类型的粒度不是越细越好，为不可能的状态建模之前，先问它会不会发生。见过把"状态机的四个互斥字段"编码成四个嵌套泛型的代码，半年后加第五个状态，改类型定义花了一天，而当年防范的非法组合从未出现过。类型复杂度是真实的维护成本，它和它防范的错误一样，都要付利息。

判断收手的信号有三个：新增一个类型要改超过三处定义；读代码要先在脑子里展开两层类型运算；新人问"这个泛型参数到底约束了什么"而你答不上来。出现任何一个，就该做减法了。好的类型系统像好的语法糖：存在的时候你感觉不到，需要的时候它刚好在。

类型复杂度本身的代价有三个可观测的出口：编译时间变长、错误信息变得像天书、新人的第一个 PR 拖成三个星期。类型级编程强大的语言几乎都栽过跟头，复杂的泛型约束让"读错误信息"变成独立技能。实用的平衡点是：让常见错误不可能发生，让罕见错误至少可以诊断，剩下的交给测试。类型是安全网，不是枷锁，这个比喻值得常驻桌面。

参考：[类型设计的适度原则](https://example.com/type-design-moderation)

类型的粒度是品味问题，也是经济问题：每细一分，编译期多挡一批错误，维护期多背一袋复杂性。下期聊开源协议入门，换到完全不同的坐标系。
