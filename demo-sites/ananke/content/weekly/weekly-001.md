不少团队都在用增量构建，但缓存失效的问题有一种独特的气质：它不报错，只是让 CI 悄悄变慢，或者更糟，让构建结果静默地不一致。这周我们把缓存失效拆开来看：键怎么设计、依赖追踪到什么粒度、命中率为什么说掉就掉。五个条目全部来自踩坑之后的复盘，没有一条是纸上谈兵。

## 条目一：缓存键只哈希源文件是不够的

很多团队的缓存键是 `sha256(src/**)`，看起来严谨，其实漏掉了两类输入：工具链和环境。编译器升级一个小版本，产物可能完全不同；环境变量里多一个 `DEBUG=1`，链接结果就换了模样。Bazel 这类系统的做法，是把一次构建行动的全部输入统一纳入哈希，源码、工具、平台配置一项都不少，缺任何一项都是给未来的自己埋雷[^1]。

### 一个更诚实的键

我的习惯是把工具链指纹和源码指纹分开算再拼起来，出问题时能立刻分辨是代码变了还是工具变了：

```bash
# 缓存键 = 源码指纹 + 工具链指纹
TOOL_FP=$(cc --version | sha256sum | cut -c1-12)
SRC_FP=$(git ls-files 'src/**' | xargs sha256sum | sha256sum | cut -c1-12)
echo "build-${SRC_FP}-${TOOL_FP}"
```

哪些东西必须进键，可以按这份清单自查：

- 源码与生成规则
  - 生成物本身要排除，否则自己踩自己
- 工具链版本
  - 编译器、链接器、代码生成器，以及构建脚本自己
- 平台与配置
  - 操作系统、CPU 架构、编译选项、目标 ABI
- 真正影响输出的环境变量
  - 逐个确认过再进键，不要图省事全量哈希

我们吃过一次亏：缓存键里没有 protoc 的版本号，升级依赖之后生成的代码还是旧格式，编译通过、测试局部红，排查了两天才定位到生成物陈旧。从那以后，团队把工具链指纹写进了缓存键规范，类似的灵异事件再没出现过。哈希输入清单化还有一个附带好处：它顺带成了文档，新人问"这个缓存为什么 miss"，答案就贴在构建配置旁边，不用口口相传。反过来说，清单缺项的代价常常延迟爆发，你今天漏掉一个环境变量，可能三个月后才在某次发布里炸出来，而那时候配置已经换过两轮，没人记得当初漏了什么。

参考：[增量构建缓存键设计笔记](https://example.com/incremental-build-cache-keys)

## 条目二：时间戳与内容哈希的战争

make 用 mtime 判断要不要重建，便宜，但会说谎。`touch` 一下文件，整个目标白建一遍；从旧分支切回来，mtime 的时序乱了，要么漏建要么全建，而漏建是最危险的那种：你拿到一个看起来正常的旧产物，错误要等到运行时才暴露。内容哈希（sccache、Bazel、Ninja 的 deps 日志）贵在每次都要算，赢在确定。我的经验法是：本地交互开发用 mtime 没问题，CI 和发布构建必须内容寻址。

```toml
# 构建缓存配置片段：内容寻址加远程缓存兜底
[cache]
mode = "content-addressed"   # 关闭 mtime 比较，宁可多算不可漏建
remote = "s3://build-cache/prod"
max_local_size = "10GB"
```

Ninja 的做法介于两者之间：它维护一份 deps 日志，记录每个目标真实读取过的头文件，头文件内容变了就重建包含它的目标，没读过的文件 mtime 再新也不碰。这是用运行时观测补全依赖图的思路，比手工维护依赖清单可靠，又比全量内容哈希便宜。ccache 则默认对预处理后的源文件做哈希，头文件的内容变化天然被包含在内，这是直接模式里聪明的折中。小项目手动列依赖还行，依赖图一大，人肉的清单必然烂掉，这是被验证过无数次的规律。

> 时间戳回答"文件什么时候动过"，内容哈希回答"文件变成了什么"。前者便宜，后者诚实。构建系统可以两者都用，但发布链路只配诚实的那个。

参考：[内容寻址构建入门](https://example.com/content-addressed-builds)

## 条目三：CI 缓存命中率下降的玄学

"昨天还九成命中，今天剩三成"，这类抱怨多半与缓存算法无关：缓存是被挤出去的。CI 平台的缓存有容量上限，LRU 淘汰、分支间缓存隔离、key 里混进 commit id，都会让命中率跳水。排查顺序建议固定成三步：先看 key 的构成，再看平台侧的淘汰日志，最后才怀疑构建系统本身。

| 症状 | 常见原因 | 处理办法 |
| --- | --- | --- |
| 每天首次构建必慢 | 夜间缓存被淘汰 | 加预热任务 |
| 只有主分支慢 | key 带了 commit id | 改用分支名或内容哈希 |
| 命中率阶梯式下降 | 依赖频繁升级 | 锁定依赖版本 |
| 时快时慢无规律 | 并发任务互相覆盖缓存 | 错峰或拆分缓存池 |

顺带一句算账方式：缓存容量除以单次产物体积，就是"能记住几次构建"。记住的次数少于团队每天的提交波峰，命中率掉下来只是时间问题，和算法好坏关系不大。还有一类玄学出在"恢复即用"上：某些平台的缓存 restore 是尽力而为，缓存包损坏或超限时任务悄悄回退到无缓存状态，日志里只有一行不起眼的 warning。把缓存命中率画成趋势图，比每次出事再人肉排查便宜得多，这条经验来自三次深夜排查换来的醒悟。

参考：[CI 缓存排查手册](https://example.com/ci-cache-troubleshooting)

## 条目四：失效粒度，别让一行改动炸掉全船

公共头文件改一个宏，全量重建半小时，这多半不是增量构建的错，是编译单元切分太粗。把稳定接口与易变实现分开、避免在公共头里塞模板和宏定义、生成代码独立成目标，都能把失效半径从全船缩到单舱。改完之后回头看 diff：如果一次改动触发八成重建，问题在架构，不在构建系统。

- [ ] 公共头文件里没有频繁变动的宏
- [ ] 接口与实现分文件，改实现不触发下游重编
- [ ] 生成代码是独立目标，输入不变就不跑
- [ ] 有定时全量构建兜底，防止漏建攒成大坑

判断失效半径有个土办法：改一个底层文件，看 CI 的构建耗时曲线。如果耗时阶梯式跳升，说明失效沿着依赖链扩散到了原本无关的模块，这时候该拆的是依赖方向，不是编译参数。依赖倒置在构建期同样值钱。再补一个反向操作：代码库太大、编译单元太小太碎的时候，unity build 把多个源文件合成一个翻译单元反而更快，这是用失效粒度换编译开销的极端例子。取舍永远存在，关键是知道自己站在哪一端。

参考：[编译单元分层实践](https://example.com/compilation-unit-layering)

## 条目五：增量构建的测试面

最后说一个容易被忘掉的角落：测试也要增量，但测试的增量比编译凶险得多。漏一次编译，你拿到旧产物；漏一次测试，你拿到绿色的假象。稳妥的做法是分层：提交时跑受影响测试， nightly 跑全量，发布前跑一次干净的完整构建加全量测试。干净的意思是清空缓存和产物目录，从零开始，这一笔时间花得值，它买的是"发布物确实来自当前代码"的确定性。

- 提交级：按变更文件反查受影响测试，分钟级反馈
- nightly 级：全量测试，抓那些漏网的累积问题
- 发布级：清缓存全量构建加全量测试，买一个确定性

参考：[分层测试策略](https://example.com/layered-test-strategy)
