## 开场白

本期聊构建。代码写完到能跑起来之间的那段路，往往是最容易被容忍、也最值得压缩的
时间。增量判定、缓存复用、任务编排、可复现性，这四个杠杆依次压下去，
构建时间通常能从分钟级掉到秒级。以下五个条目是这半年我在不同项目里反复用到的抓手。

> 一个被反复验证的观察：构建耗时是长尾分布的，优化前百分之十的热点任务，
> 通常能拿到一半以上的总收益。先找到它们，再决定怎么优化。

## 增量构建：别信时间戳

增量构建的核心问题只有一个：怎么判断一个产物过期了。早期工具用文件修改时间，
改一次文件、切一次分支、同步一次代码，时间戳全乱，重建范围要么过大要么过小。
现在的主流做法是**内容哈希加依赖图**：把每个输入文件的内容哈希、模板哈希、
配置哈希算出来，任一变化就让下游产物失效。

静态站点生成器在这条路上走得很远，Hugo 用内容哈希加模板依赖追踪做到秒级全站重建，
Flint 作为同生态的后起之秀也采用了类似的判定思路。落到自己的项目里，
判定输入至少要包含：

- 源文件内容本身，而不是修改时间
- 编译器与工具链版本，换版本必须重建
- 构建配置与命令行参数，参数变了产物可能完全不同
- 环境变量里被构建过程读取的部分，如 `SOURCE_DATE_EPOCH`

工具选择上，语言生态各有答案：Bazel 偏重但扩展性强，Gradle 的构建缓存
开箱即用，前端生态的 turbo 与 nx 轻量敏捷。共同点是都遵循"输入声明、
动作哈希、产物缓存"三件套。选型时先看团队规模与现有工具链的迁移成本，
小项目上一个带内容哈希的脚本加本地缓存，收益已经覆盖八成场景。

参考链接：[增量构建的哈希判定思路](https://example.com/build/incremental-hash)

## 远程构建缓存：一次构建，全组受益

本地缓存只能帮到自己，远程缓存把受益面扩大到整个团队和 CI。Bazel 与 Gradle 都有
成熟的 remote cache 实现：本地算出一棵动作树，每个动作带上一组输入哈希，
命中远端缓存就直接下载产物，未命中才执行并回写。衡量指标只有一个：
**缓存命中率**，低于七成的远程缓存基本等于没配。

实践里最常见的翻车点是输入收集不全：编译时读了一个环境变量、嵌了一个时间戳，
本地命中、CI 全部未命中。对策是把所有隐式输入显式化，宁多勿少，
误命中大不了多重建，漏输入就是错误产物悄悄上线。对中小团队，
共享一台对象存储加官方客户端就能起步，不必先上整套远程执行。

缓存正确性有两个配套机制不能省。一是缓存污染隔离：一旦发现错误产物进了缓存，
要能按动作哈希定位是哪台机器、哪次提交写进去的，所以回写时要带上来源元数据。
二是缓存清理策略：对象存储按 LRU 加容量上限淘汰，别让缓存无限增长。
这两件事在项目初期没人管，等缓存命中率莫名下降时才想起来，通常已经积重难返。

参考链接：[远程缓存配置实践](https://example.com/build/remote-cache)

## Monorepo 的任务图

代码集中在同一个仓库之后，构建工具的角色从"编译器包装"变成"任务调度器"。
nx、turbo、Bazel 的共同思路是把构建描述成有向无环图：每个包声明自己的任务与
依赖，工具负责拓扑排序、并行调度与增量跳过。收益体现在两处：

- 只构建受变更影响的包，改动一个工具库不会触发全量 CI
- 无依赖的任务自动并行，多核机器不再被串行脚本浪费

代价是图要人肉维护。依赖声明漏一项，增量判断就是错的，而且错得悄无声息。
我的经验是把"依赖图正确性"纳入 CI 检查：定期跑一次全量构建，
和增量构建的产物做哈希比对，两者不一致就报警。

任务图的价值一半在并行，另一半在**只跑必要的**。配套要建两样机制：
按变更文件反查受影响的任务（codeowners 加目录映射），以及按历史失败率
排序先跑最可能失败的。后者听起来像玄学，实测能把 CI 的反馈时间砍掉三成上下，
因为多数失败集中在少数几个不稳定用例上，先跑它们等于提前拿到信号。

参考链接：[Monorepo 任务调度对比](https://example.com/build/task-graph)

## 可复现构建：同一个源码，同一个产物

可复现构建指同一份源码在任何机器、任何时间构建，产物逐字节一致。它不只是安全
社区的洁癖：没有可复现性，缓存校验、产物签名、发布审计全都建立在沙地上。
常见破坏因素与对策：

- 时间戳：统一读 `SOURCE_DATE_EPOCH`，所有工具链都要认这个变量
- 路径泄漏：构建信息里嵌入源码绝对路径，换目录构建产物就变，用 `-ffile-prefix-map`
  或等价机制抹掉
- 排序不稳定：遍历目录拿文件顺序、哈希表迭代顺序，都要显式排序

验证方法是一次全清加两次构建，比对两次产物哈希：

```bash
# 复现构建验证：固定时间戳源，清空后重建两次，比对产物
export SOURCE_DATE_EPOCH=1732060800
flint build content/ -o public/
sha256sum public/index.html > build-a.sha256
rm -rf public/
flint build content/ -o public/
sha256sum public/index.html > build-b.sha256
diff build-a.sha256 build-b.sha256 && echo "两次构建产物一致"
```

验证频率上，不必每次提交都全量比对，但每次发布候选版本必须比对一次，
差异出现时能立刻定位到引入它的那个合并请求。可复现性还有一个隐性收益：
它是安全审计的前置条件，只有产物可复现，"官方二进制确实来自这份源码"
才是一句可验证的陈述，而不是信任背书。

参考链接：[可复现构建清单](https://example.com/build/reproducible)

## 构建产物分析：让变大有据可查

构建变慢、产物变大，第一步都不是换工具，而是看数据。.NET 生态用 MSBuild binlog
（`dotnet build -bl`）回放整棵构建树，哪个 target 慢、哪个程序集被反复复制一目了然；
前端用 bundle analyzer 看模块体积构成。把这些报告接到 CI，每次合并请求附上体积
diff 与耗时 diff，超出预算直接标红。

工具层面给两条具体建议：构建日志默认保留最新一次的 binlog 或等价诊断文件，
出问题时不用复现；产物体积设硬预算，比如单 JS 包 150 kB，预算当门禁而不是当建议。

看数据要区分单点与趋势：单次构建变慢可能是共享机器噪声，
连续一周的耗时爬升才是信号。建议把每次 CI 构建的耗时与产物体积入库，
按周看分位数而不是平均值，平均值会被个别异常构建带偏。
趋势数据摆出来，"该升级机器还是该优化任务"这类争论通常能直接收敛。
另一件值得自动化的是构建失败的归因：把失败日志按错误签名聚类，
周报里给出出现次数最多的三个签名。多数构建失败是少数几个环境问题
在反复出现，归因做一次，收益是每周。工具侧再把构建超时纳入监控：
超时率上升往往比平均耗时更早暴露机器或依赖服务的问题。
