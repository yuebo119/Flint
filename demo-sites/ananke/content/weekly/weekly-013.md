## 开场白

本期聊安全。安全建设最容易犯的错是只防最吓人的攻击，忽略最常发生的失误：
误提交的密钥、没锁版本的依赖、拼出来的 SQL。本期五个条目按"出事故的概率"
从高到低排，每条都以一个可以今天就做的检查动作收尾。

> 安全的反直觉之处：报道里最贵的攻击往往用得最少，真正得手的多半是
> 没人看的疏忽。防御资源应该按概率分配，而不是按吓人程度分配。

## .env 进仓库：删文件救不了你

`.env` 连同真实密钥被提交进仓库，是出现频率最高的泄露事故。事后的标准处置分两步，
顺序不能反：**先轮换密钥，再清理历史**。因为文件进了 git 历史，
clone 过仓库的人、CI 缓存、镜像层里都可能留有副本，单纯删掉当前文件毫无意义。

预防同样分两层。第一层是 `.gitignore` 前置：项目初始化时就忽略所有 `.env*`，
只提交 `.env.example`，里面的值一律写成占位符。第二层是 pre-commit 钩子扫描：

```bash
# 提交前扫描：确认工作区没有疑似密钥
gitleaks detect --source . --no-git --redact
grep -rn "sk-" --include="*.cs" src/ || echo "未发现硬编码密钥字样"
```

规则里要覆盖常见形态：`sk-` 开头的 API key、`AKIA` 开头的云厂商访问键、
长十六进制串、`BEGIN PRIVATE KEY`。扫描器误报可以加白名单，
但不要为了清静把整类规则关掉。

CI 环境同理：密钥进 CI secrets 或密钥管理服务，不进代码仓、
不进流水线配置明文。本地开发用 `.env` 加 `.env.example` 模板，
新人照着模板填自己的值。这条链路上任何一环把真密钥写进仓库，
前面的忽略规则都白费，所以扫描要同时覆盖提交前与 CI 两个时点，
漏一个就等于没扫。

参考链接：[密钥泄露处置清单](https://example.com/security/secret-incident-response)

## 依赖供应链：锁文件是第一道闸门

供应链攻击的载体是依赖：抢注的仿冒包、被劫持的维护者账号、传播恶意安装脚本的小版本。
工程对策的核心是让依赖**可复现、可审计、可回滚**：

- 锁文件（`package-lock.json`、`poetry.lock`、`packages.lock.json`）必须提交，
  CI 用 `--frozen-lockfile` 或等价模式安装，杜绝"安装时解析到新版本"
- 新依赖引入前过一遍审查：周下载量、维护活跃度、安装脚本、依赖树大小
- CI 固定跑漏洞扫描（`npm audit`、`dotnet list package --vulnerable`），
  按严重级别决定门禁还是告警
- 能自动升级的（Dependabot、Renovate）配上，但合并前跑全量测试

一个反直觉的经验：依赖数量比依赖版本更危险。每个传递依赖都是一段没人审的代码
和一次供应链暴露，合并重复功能的包、定期清理未使用的依赖，
比追着 CVE 打补丁更根本。

企业内网还有一层：私有源与镜像代理。把外部包仓库镜像到内部，
构建只从内部拉取，既挡住"上游某天被投毒"的直达路径，
也让依赖清单收敛到一个可审计的入口。代价是要维护镜像的同步与可用性，
值不值得按团队规模判断，但一旦决定做，它比任何单点扫描都根本。

参考链接：[依赖加固实践](https://example.com/security/supply-chain-hardening)

## 参数化查询：注入没有中间态

SQL 注入经久不衰，原因不是不知道防，而是"就这一次图方便"。规则只有一条：
**所有用户输入都不许拼进 SQL 字符串，一律走参数占位符**。
ORM 的参数化 API（如 EF Core 的 `FromSqlInterpolated`、Dapper 的匿名对象参数）
默认安全，危险的永远是 `FromSqlRaw` 加字符串拼接、以及"动态排序"这种
把列名也当参数的地方。

动态排序的正确做法是白名单映射：把前端传来的排序键在代码里映射到固定列名，
不在表里就直接拒绝，绝不让输入的任何字符进入 SQL 的语法位置。
同类问题还有：拼标识符时用引号包裹并校验字符集、`IN` 列表按参数个数展开而不是
拼字符串。注入类漏洞的测试也要进 CI，一条包含常见 payload 的冒烟用例即可。

ORM 也不是免死金牌。`FromSqlRaw` 系列方法接受字符串拼接，
把用户输入拼进去照样注入；日志框架把 SQL 与参数分开记录是好事，
但把参数重新拼回 SQL 打印的日志组件等于把参数又拼了回去。
审计时不只 grep `SELECT` 拼串，要把"日志里的完整 SQL"也纳入检查面。
顺便提醒存储过程与库内动态 SQL：用 EXECUTE 拼接同样会注入，
参数化在存储过程里一样适用，别因为"在数据库里"就放松。
代码审计时把拼接 SQL 的检查加进 CI 的静态扫描规则，
比人工评审可靠，也不依赖评审人当天的心情。

参考链接：[SQL 注入防护模式](https://example.com/security/sql-injection-defense)

## 日志脱敏：先证明日志里没有

日志泄露的隐蔽在于没人主动查。结构化日志框架都支持脱敏过滤器：
把手机号、身份证、邮箱、token 字段按正则替换成掩码，
在日志管线的入口统一处理，而不是指望每个调用点记得。

光配置不算数，要像测试功能一样测试脱敏：构造一条含敏感字段的请求，
打出来 grep 一遍，搜不到原值才算过。这条用例可以并进安全测试集：

```bash
# 脱敏自测：在最近日志里搜索敏感模式，应当只命中掩码后的形态
grep -E "1[3-9][0-9]{9}" logs/app.log | grep -v "\*\*\*\*\*" || echo "未发现明文手机号"
```

正则要防住变体：带空格分隔的手机号、部分打码的邮箱、
Base64 编码后的 token。脱敏规则本身也要版本化，
新字段接入时同步更新规则，否则过滤器对陌生字段静默放行。

出口侧还要设防：日志平台按角色控制访问，敏感字段的检索权限单独授权，
导出走审批。脱敏、权限、审计三件套齐了，日志泄露的爆炸半径才可控。
只做脱敏不做权限，相当于把掩码后的数据对全员开放，
排查问题是方便了，但"方便"本身不该以敞口为代价。

参考链接：[日志脱敏规则设计](https://example.com/security/log-redaction)

## 密钥轮换：把泄露当必然事件

安全设计的成熟标志是假设密钥终将泄露，问题是"泄露后多久失效"。
轮换机制包含三个部件：双活窗口（新旧密钥同时有效一段时间，
让滚动部署期间的服务不中断）、自动触发（按周期或按事件，
而不是等运维想起）、使用面清单（每个密钥被哪些服务引用，
轮换时按清单逐项切换）。

落地建议按密钥分级：数据库与云厂商根凭证最短轮换周期、最高保护级别；
第三方 API key 中等；内部服务间令牌可长但必须可即时吊销。
把轮换演练纳入年度计划，没演练过的轮换流程等于不存在，
真出事时你会发现备份密钥也打不开。

滚动顺序有个细节：先让新密钥在全链路生效，再吊销旧密钥，
中间保留一个覆盖两轮部署周期的窗口。顺序反了就会出现
"一半服务用新密钥、一半用旧密钥"的对撞期，故障表现还是间歇性的，
排查体验极差。双活窗口的长度按最长部署间隔定，留一倍余量。
轮换的另一半是应急吊销：怀疑泄露时不等计划周期，按使用面清单即时吊销
并触发重建。吊销流程要演练到"十分钟内完成全链路切换"，
做不到说明清单不全或自动化有断点，演练的价值就在提前暴露这些断点。
