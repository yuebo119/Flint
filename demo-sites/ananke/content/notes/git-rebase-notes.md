这篇笔记记的是我每周都在用的 rebase 命令组合。不追求全面，只收日常真正高频的场景：整理本地提交、把 fixup 归位、把特性分支变基到最新主干、处理变基冲突。每条命令都配一句"什么时候用、注意什么"，方便以后翻。笔记按场景组织，不按命令组织；查得到但没在用的命令，宁缺毋滥，免得笔记变成第二份 man page。

## rebase 到底改写了什么

初学 rebase 最大的误区，是把它理解成"移动提交"。它不是移动，是重放：把你的提交逐个应用到你指定的新基线上，每次应用都生成一个全新的 commit hash。原来的提交还躺在 reflog 里，但分支历史已经换了一批对象。

理解这一点，两条纪律就顺理成章：第一，已推送的公共分支不要 rebase，你改写了历史，别人的历史就对不上了，合并时会重复冲突；第二，rebase 之前确认工作区是干净的，半成品改动混进去，重放过程和结果都会变得难以预料。团队约定里通常还有第三条：只 rebase 自己名下的分支，别人的分支要同步用 merge。Git 的分布式设计细节可以参考 <https://zh.wikipedia.org/wiki/Git>。

## 常用姿势

### 交互式 rebase：整理本地提交

本地攒了一串"改 A"、"改 A 第二遍"、"手滑回滚"的提交，推送前应该整理成几条说得清的记录：

```bash
git rebase -i HEAD~5
```

编辑器会列出最近五条提交，每条前面一个动作词。最常用的四个：`pick` 保留、`squash` 把这条并进上一条并合并信息、`fixup` 同样并进去但丢弃这条的信息、`reword` 只改提交信息。保存退出，Git 按新剧本从旧到新重放全部提交。整理历史的黄金标准是：每条提交都能独立通过测试，这样以后 bisect 才有效。挑选动作词有个实用顺序：先 reword 把提交信息改成将来看得懂的版本，再 squash 把碎提交并掉，最后通读一遍清单确认每条提交自洽。顺序反了容易白改。

### autosquash：fixup 的半自动整理

评审后的小改动不要新建一条普通提交，用 fixup 标记到要修的那条上：

```bash
git commit --fixup=a1b2c3d
```

需要几条就标记几条。全部完成后一次整理：

```bash
git rebase -i --autosquash origin/main
```

fixup 提交会被自动排到目标提交旁边，动作词也自动填好，通常只需要确认保存。这个组合是我用得最多的 rebase 场景，比手动编排清单可靠得多。

### 变基到最新主干

特性分支开发期间，主干一直在前进。合并前先把分支挪到最新主干上，自己先在本地解决冲突，别把冲突留给合并提交：

```bash
git switch feature
git rebase main
```

远端场景一步到位用拉取加变基：

```bash
git pull --rebase origin main
```

变基后分支历史是一条干净的直线，review 时看到的就是纯粹的改动。注意如果这条分支已经推送过，变基之后需要强推，而强推前必须确认没有别人在这个分支上工作。

## 命令速查

| 命令 | 作用 | 注意点 |
|------|------|--------|
| `git rebase -i HEAD~n` | 整理最近 n 条提交 | 先确认工作区干净 |
| `git commit --fixup=<hash>` | 创建归位提交 | 配合 autosquash 使用 |
| `git rebase --continue` | 解决冲突后继续 | 先 `git add` 再执行 |
| `git rebase --abort` | 放弃本次变基 | 回到变基前状态 |
| `git pull --rebase` | 拉取并变基 | 已推送分支会改写历史 |

## 冲突处理实战

变基冲突和合并冲突的解决流程一样，差别在于合并冲突一次解决完，变基冲突是每个冲突提交解决一次。遇到冲突别慌，Git 会把现场保持在半路，随时可以 abort 重来，这也是它比传说中温和的地方。

<details>
<summary>点开：变基冲突的标准处理流程</summary>

```bash
# 1. 看是哪条提交卡住了，冲突文件有哪些
git status

# 2. 打开冲突文件，处理 <<<<<<< ======= >>>>>>> 标记
#    改完后标记为已解决
git add <file>

# 3. 继续重放剩余提交
git rebase --continue

# 4. 任何时候想回到变基之前
git rebase --abort
```

</details>

一个经验：如果同一条分支连续多个提交都改同一个文件，冲突会反复出现，越改越烦。这种情况下更划算的做法是先用交互式 rebase 把这几条提交 squash 成一条，再变基，冲突只解决一次。

## 我的命令组合

日常基本是这两条路径，按场景选：

- 本地开发收尾
  - 交互式 rebase 整理提交
    - `reword` 改信息
    - `squash` 合并碎提交
  - 自测通过后推送
- 合入主干之前
  - `git pull --rebase origin main`
    - 有冲突就地解决
    - 解决完 `rebase --continue`
  - 再跑一遍测试，确认变基没改坏行为

两条路径的共同点是：测试永远在推送前跑一遍。rebase 改写历史之后，行为对不对只有测试知道，历史干净不等于代码还对。

## 别名与配置

把最常用的组合设成别名，手指比脑子先到：

```bash
git config --global alias.ri 'rebase -i'
git config --global alias.fixup 'commit --fixup'
git config --global rerere.enabled true
```

`rerere` 值得单独说：它记录你解决过的冲突方案，同样的冲突再次出现时自动复用。频繁在主干和长命分支之间切换的仓库，它能省下大量重复劳动。开启一次，受益一整年，属于 Git 里少有的"设置完就忘掉"的配置。

## rebase 与 merge 怎么选

两种整合分支的方式没有高下，只有场景。判断标准只有一条：这段历史有没有被别人看见过。

已经推送、别人可能基于它工作的分支，用 merge。合并提交是一次显式的汇合记录，保留了"这里曾经分叉过"的事实，出问题时能按图索骥。纯本地、还没推送的分支，用 rebase。把提交重放到最新主干上，历史是一条直线，review 时看到的每一条 diff 都是净增量，不会掺进"先改对又改错"的中间态。

还有一个折中姿势值得知道：merge 时加 `--no-ff`，即使可以快进也强制生成合并提交。这样每条特性分支的边界在历史里清晰可见，"这个功能是哪几个提交"一眼可查。很多团队的主干策略就是禁止快进加强制合并提交，在历史好看和排查好用之间选了后者。

交互式 rebase 还有第三个用途：给提交重新排序和拆分。一个大改动拆成"重构"和"功能"两条提交，review 效率翻倍，回滚也能只回滚一半。这条用得少，但关键时刻能救命，属于值得练一次的技能。

## 踩过的坑

第一个坑是变基后忘记历史已改写，直接 `git push` 被拒绝，下意识加了 `--force`，把同事当天推的两个提交一起覆盖了。正确做法是先 `git fetch` 看一眼远端，确认没有新提交再强推，有条件就开分支保护，让强推需要二次确认。

第二个坑是 rebase 中途想看看改到哪了，直接关掉编辑器，留下一堆游离 HEAD 的现场。后来养成习惯：变基前看一眼 `git reflog`，任何一步错了都能找到回来的路。reflog 是本地操作的安全网，默认保留九十天，够用。

第三个坑是 autosquash 之后提交顺序和预期不同。原因是 fixup 标记的目标提交在整理过程中位置会变，Git 按提交在旧历史里的位置归位。养成习惯：创建 fixup 之后尽快 autosquash，别攒着，攒得越久错位风险越大。

第四个坑来自持续集成：有些流水线按提交逐个跑测试，rebase 之后哈希全变，全部重跑一遍，时间成本翻倍。后来团队约定，本地验证充分后再整理历史，整理完只跑一次全量，把 rebase 放在推送前的最后一步。工具没有银弹，把顺序排对，同样的命令组合效率完全不同。

> 一句话总结：rebase 是给"还没人看见的历史"用的工具，给"已经共享的历史"用的叫 merge。分不清边界时，选 merge 永远安全。
