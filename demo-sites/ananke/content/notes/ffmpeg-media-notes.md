# ffmpeg 音视频处理笔记

## 一句话定位

ffmpeg 是开源音视频处理工具里的瑞士军刀：转格式、改码率、剪时间轴、抽音轨、烧字幕、做直播推流，一个二进制文件全包。它没有图形界面，所有意图都靠参数表达，好处是同一套命令既能跑在笔记本上，也能原样搬进服务器脚本里。维基百科对 [FFmpeg](https://zh.wikipedia.org/wiki/FFmpeg) 的定位是"录制、转换和流式传输音视频的完整跨平台方案"，日常使用抓住一条主线就够了：先看清输入里有什么流[^1]，再决定输出要什么流，中间按需重新编码。

![ffmpeg 命令行工作流示意](/images/demo-1.svg)

## 安装与环境

Linux 直接用发行版仓库，版本偏旧但稳定；想要新版可以加第三方源或下载静态构建。macOS 用 Homebrew 最省事；Windows 推荐下载官网静态版，解压后把 bin 目录加进 PATH。装完先跑版本命令，重点确认 `libx264`、`aac`、`libmp3lame` 这些常用编码器在不在编译特性里。缺什么编什么，能省掉后面一半的困惑。容器用户可以直接用官方镜像 `linuxserver/ffmpeg` 或 `jrottenberg/ffmpeg`，把宿主目录挂进去，省掉安装环节；CI 里跑转码任务时，静态构建版比发行版包更省镜像层。另外注意授权：ffmpeg 本身是 LGPL/GPL 混合，带了 `--enable-gpl` 编译出的二进制会包含 GPL 组件，商业分发前要确认编译选项，这一点在法务评审时经常被问到。

安装命令很短：Debian/Ubuntu 用 `sudo apt install ffmpeg`，macOS 用 `brew install ffmpeg`，Windows 用 `winget install Gyan.FFmpeg`；容器场景直接挂载官方镜像的目录，连安装环节都省掉。

## 核心用法

### 先诊断，再动手

拿到陌生文件，第一步不是转码，而是用 `ffprobe` 看它内部到底有哪些流、什么编码、多高码率。凭扩展名猜封装是很多事故的起点：后缀是 mp4，里面的音频可能是 AAC，也可能是 AC3 或者 PCM，处理方式完全不同。ffprobe 的输出很长，用 `-select_streams` 和 `-show_entries` 只取关心的字段，才能做到一眼看完。

```bash
# 看封装格式与全部流信息
ffprobe -show_format -show_streams input.mp4

# 只取视频流的编码与分辨率
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,width,height -of csv=p=0 input.mp4
```

### 格式转换：拷贝与重编码

在同一个容器里换封装（比如 MKV 换 MP4），用 `-c copy` 把流原样拷过去，不重新编码，速度快、无画质损失，前提是目标容器真的支持这些编码。真正跨编码（比如 Motion JPEG 转 H.264）才需要动 `libx264`，此时 `crf` 是质量档、`preset` 是速度档，两个旋钮要配合调：压体积先动 preset，再考虑调高 crf，不要一上来就把 crf 拉到 30，画面细节掉得很快。

```bash
# 同编码换封装：秒完，无质量损失
ffmpeg -i input.mkv -c copy output.mp4

# 通用兼容转码：H.264 视频 + AAC 音频
ffmpeg -i input.mov -c:v libx264 -preset medium -crf 23 -c:a aac -b:a 128k output.mp4
```

### 裁剪、提取与画面处理

`-ss` 放在 `-i` 前是"跳到最近关键帧再解"，速度快但切割点可能差一两秒；放在 `-i` 后是逐帧精确，代价是全段解码。抽音频用 `-vn` 丢掉视频流；压字幕用 `subtitles` 滤镜把字幕烧进画面；缩放用 `scale`，抽帧用 `fps`，一个滤镜字符串里能串很多步，逗号分隔，顺序会影响最终结果，比如先缩放后加水印和水印跟随原分辨率，效果完全不同。

```bash
# 快速截取：从 10 秒起取 30 秒（输入侧定位）
ffmpeg -ss 00:00:10 -t 30 -i input.mp4 -c copy clip.mp4

# 精确切割：输出侧定位 + 重编码
ffmpeg -i input.mp4 -ss 00:00:10 -t 30 -c:v libx264 -crf 20 clip.mp4

# 提取音轨为 MP3（-vn 表示丢弃视频）
ffmpeg -i input.mp4 -vn -c:a libmp3lame -q:a 4 audio.mp3

# 每秒抽一帧做预览图
ffmpeg -i input.mp4 -vf fps=1 -q:v 3 frame_%03d.jpg
```

### 批量与自动化

目录里几十个文件要统一转码，用 shell 循环最直接，注意输出目录不要和输入混在一起，`${f%.mov}` 是去掉后缀的参数展开，写脚本时很好用；一个文件一个进程，单个失败也不影响整轮。有独显或核显的机器还可以开启硬件编码，`h264_vaapi`（Intel/AMD）或 `h264_nvenc`（NVIDIA）比软编快数倍，但它不是银弹：部分播放器对硬编输出支持不佳，低码率下细节也比软编容易糊，家庭影音优先软编保兼容，只有转码时长成为瓶颈再开硬件。推流直播用 `-f flv rtmp://...`，关键参数是 `-preset veryfast`、`-g` 设关键帧间隔、`-b:v` 给足码率；拉流录制则反过来，`-c copy` 原样保存最稳。

```bash
# 批量转码：一个文件一个进程，失败不拖垮整轮
mkdir -p out
for f in *.mov; do
  ffmpeg -y -i "$f" -c:v libx264 -crf 23 -c:a aac "out/${f%.mov}.mp4" || echo "failed: $f"
done

# NVIDIA 硬件编码（需装对应驱动）
ffmpeg -i input.mp4 -c:v h264_nvenc -preset fast output.mp4

# 推流直播：视频硬编，音频拷贝，2 秒一个关键帧
ffmpeg -re -i input.mp4 -c:v h264_nvenc -g 60 -b:v 3000k -c:a copy -f flv rtmp://live.example.com/app/key

# 录制直播流，原样保存
ffmpeg -i rtmp://live.example.com/app/key -c copy live.flv
```

### 一个完整的实战例子

把前面零散的用法串起来，看一个完整例子：手机拍的横屏视频要发到网站，要求 1080p、体积不超过 20MB、带一张封面。第一步照例 ffprobe，确认源是 4K60 帧，顺便估算预算：20MB 除 8 得 2.5MB 每秒，时长两分钟的话目标码率 2500k 左右，H.264 在这个档位画质完全够用。

第二步写命令：`scale` 缩到 1920 宽度，`fps` 降到 30，`crf` 先试 24，再加 `-movflags +faststart` 把元数据提到文件头，网页播放才能边下边播。先截 5 秒小样验证参数，看画面、看体积，确认无误再跑全量，几十分钟的转码不至于白等。

第三步补封面和元数据：从第 5 秒抽一帧当封面图，用 `-metadata title` 写上标题，网站展示时直接读取。封面单独抽、单独压缩成 webp，比从正片里截更灵活，正片则可以继续用 `-c copy` 的处理结果。

这套流程的唯一经验是：永远先小样后全量。体积不达标时先降帧率再降 crf，画面糊比体积大更难接受；写成脚本之后，以后所有视频都是一条命令的事，人也从重复劳动里解放出来。

## 高频场景速查

下表按使用频率排序列出常见需求，先用它定位"该动哪个参数"，再回到上面的用法示例取完整命令。表里的参数大多是"最小可用集"，真实命令还要配合输入输出路径；建议把常用几行抄成自己的别名或脚本，比每次查表快。

| 场景 | 关键参数 | 说明 |
| --- | --- | --- |
| 压缩体积 | `-crf 23 -preset slow` | 先动 preset 再动 crf，收益更稳 |
| 提取音频 | `-vn -c:a libmp3lame` | 丢弃视频流，只留声音 |
| 裁剪片段 | `-ss` 配 `-t` | 输入侧定位快，输出侧定位准 |
| 拼接视频 | concat 解复用器 | 编码参数一致的片段才能无损拼 |
| 加封面图 | `-i cover.jpg -map 0:v -map 1` | 把静帧封进容器当附加流 |
| 录屏 | `-f x11grab` / `-f gdigrab` | Linux 与 Windows 用不同采集模块 |
| 提取关键帧 | `-vf fps=1` | 每秒一帧，适合生成预览图墙 |
| 改分辨率 | `-vf scale=1280:-1` | `-1` 表示按比例自动计算高度 |
| 压制字幕 | `-vf subtitles=cn.srt` | 字幕烧进画面，播放器无法关闭 |
| 调音量 | `-af volume=1.5` | 大于 1 是放大，注意削峰失真 |
| 静音检测 | `-af silencedetect` | 找出无人说话的时间段，方便剪掉 |
| 看源信息 | `ffprobe -show_streams` | 动手前的标准侦察动作 |

## 踩坑记录

下面五条都是实际项目里交过学费的，每条都给了"现象、原因、处理"，遇到类似现象先来这里对一遍，能省掉大量盲试时间。

> **坑一：`-c copy` 剪出来的片段开头花屏。** 非关键帧无法独立解码，快速定位只能落在最近的关键帧上。要精确切割就得重新编码，或者提前用 `-force_key_frames` 在切割点附近补关键帧，事后再 copy。

> **坑二：MOV 转 MP4 后声音消失。** 多半是源文件用了 PCM 音频而目标容器不兼容，显式加 `-c:a aac` 转一道就能解决。先用 ffprobe 确认流类型，不要看后缀下结论。

> **坑三：长任务像卡死。** ffmpeg 的进度写在 stderr，日志量大时看起来像不动。加 `-hide_banner -loglevel error` 干净很多，长任务用 `-stats_period 5` 控制刷新频率。

> **坑四：批量循环中途失败。** 某个文件损坏会让整轮任务中断。建议一个文件一个 ffmpeg 进程，单个失败记录后继续下一个，最后统一看日志；`-y` 加上，避免中途停下问要不要覆盖。

> **坑五：直播推流音画不同步。** 推文件而不是采实时流时，必须加 `-re` 按原始帧率发送，否则音频缓冲会把画面甩开；播放端花屏就先降低关键帧间隔与码率保流畅。

## 速查小结

- 先 `ffprobe` 看流，再决定参数；不要凭扩展名猜封装。
- 同封装换容器用 `-c copy`，跨编码才动 `-c:v` / `-c:a`。
- `-ss` 的位置决定速度与精度：放前面快，放后面准。
- CRF 是质量档不是码率档[^2]，压不动先调 preset，不要一味拉低 crf。
- 滤镜串用逗号连接，顺序会影响结果，比如先缩放后加水印。
- 批量任务先拿单个文件验证参数，再全量跑，避免几小时编码跑偏。
- 硬件编码先确认驱动可用，拿不准就软编，画质下限更有保证。

掌握这几条，日常九成的音视频处理都不需要再打开重型视频编辑软件，一条命令的事。真正复杂的项目仍然需要非编工具，但"改个格式、剪一段、压个体积"这种活，命令行永远是最快的入口。

[^1]: `ffprobe` 是 ffmpeg 套件自带的流分析工具，`-show_format` 看容器，`-show_streams` 看每条流的编码器、码率、时长与语言标签，是动手前的标准侦察动作。

[^2]: CRF（Constant Rate Factor）是 x264/x265 的质量模式：数值越小质量越高、体积越大，18 视觉上接近无损，23 是默认值，28 以上能看出明显压缩痕迹。
