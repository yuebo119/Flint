# Makefile 编写笔记

## 一句话定位

make 是最经典的构建工具：一个 Makefile 描述"目标、依赖、配方"，靠文件时间戳决定什么该重新做。它四十年来没被淘汰，是因为足够通用：编译 C、打包前端、跑测试、发版，任何"输入文件变了就重跑某段命令"的场景都适用。维基百科对 [Make](https://zh.wikipedia.org/wiki/Make) 的介绍强调它是"自动判断源代码哪部分需要重新编译的工具"，写 Makefile 的核心思维就是管理依赖图。它的适用边界也很清晰：增量编译是本职，任务编排是兼职；复杂流水线（多阶段、远程缓存、矩阵构建）交给专业 CI 工具，Makefile 管好本地"一条命令跑起来"就够，贪多会把简单工具用复杂。

## 安装与环境

Linux 装 `build-essential`（Debian/Ubuntu）或单独的 `make` 包；macOS 随 Xcode 命令行工具提供，首次运行 `make` 会提示安装；Windows 上用 MSYS2、Cygwin 或 WSL。执行时默认找当前目录的 `Makefile` 或 `makefile`，指定名字用 `make -f build.mk`；`make -n` 空跑看命令、`make -p` 打印数据库，是调试两大件。Windows 用户如果不想装整套 MSYS，可以在编辑器里装 Makefile 扩展获得语法高亮与目标浏览，实际构建仍在 WSL 或容器里跑，两头都清净。

Debian/Ubuntu 装 `build-essential`，macOS 跑一次 `xcode-select --install`，Windows 用 MSYS2 或 WSL。常用执行方式：`make` 跑默认第一个目标，`make -f build.mk` 指定文件名，`make -n test` 空跑只看命令，`make VAR=debug` 在命令行覆盖变量，这四条覆盖日常九成场景。

## 核心用法

### 规则三要素与 .PHONY

一条规则三段：目标、依赖、配方。配方每行一个 shell 命令，**行首必须是 Tab**（这是 Makefile 最著名的坑）。`clean`、`test` 这类不对应文件的目标要声明 `.PHONY`，否则同名文件一存在，目标就被认为"最新"而永不执行。`@` 开头不回显命令，`-` 开头忽略错误继续。配方里每条命令都在独立 shell 里执行，上一句 `cd` 不影响下一行，这个反直觉的设定坑过无数人；需要延续状态就写成一条命令用 `;` 或 `&&` 连接，或者把多步逻辑收进一个脚本文件再调用。规则的依赖是图不是线：一个目标可以被多条规则贡献依赖（自动合并），配方却只允许一段，多段配方要用 `define` 或拆目标。`make -d` 能打印 make 的完整决策过程，查"为什么它不重建"时逐行看，比猜快得多。

```makefile
.PHONY: all build test clean

all: build

build: main.o utils.o
	gcc -o app main.o utils.o

test: build
	./app --selftest

clean:
	rm -f app *.o
```

### 变量与自动变量

变量有四种赋值：`=` 递归展开（用时才算）、`:=` 立即展开、`?=` 未定义才赋值（给默认值）、`+=` 追加。自动变量是规则里的快捷键：`$@` 目标文件、`$<` 第一个依赖、`$^` 全部依赖。依赖用不上记，写规则时这几个符号能省一半重复。还有两个不常用但救命：`$(@D)` 取目标所在目录，`$(*F)` 取模式匹配到的基名，写"按目录分产物"的规则时配合 `$(dir ...)` 函数能少写一堆重复路径。

```makefile
CC      := gcc
CFLAGS  ?= -O2 -Wall
SRCS    := $(wildcard src/*.c)
OBJS    := $(SRCS:src/%.c=build/%.o)

app: $(OBJS)
	$(CC) $(CFLAGS) -o $@ $^

build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p build
```

### 函数与多环境

常用函数就几个：`$(wildcard ...)` 收集文件列表，`$(patsubst ...)` 批量改名，`$(shell ...)` 执行命令拿结果，`$(if ...)` 条件分支。多环境靠变量覆盖：`make CFLAGS="-O0 -g"` 或 `make ENV=release`，配合 `ifeq` 分支，一份 Makefile 同时服务开发与生产构建，版本号还能在构建时从 git 注入。注意 `$(shell ...)` 在解析期执行，里面别放慢命令（网络请求、全盘搜索），否则每次 make 都卡一下；需要缓存就存进变量只算一次。

```makefile
ENV ?= dev
ifeq ($(ENV),release)
  CFLAGS := -O2 -DNDEBUG
else
  CFLAGS := -O0 -g
endif

VERSION := $(shell git describe --tags --always 2>/dev/null || echo dev)

release:
	tar czf app-$(VERSION).tar.gz app
```

### 调试与组织

Makefile 变长之后要学会拆：公共变量与规则放 `common.mk`，各子目录 include 进来；敏感或环境相关的值（路径、密钥）放 `config.mk` 并加进 `.gitignore`，用 `-include` 容错。调试三板斧：`make -n` 看命令、`make -d` 看决策、`$(info ...)` 在解析期打印变量值，比猜快得多。

```makefile
# 在解析期打印变量，排查"值不对"问题
$(info CFLAGS = $(CFLAGS))

# 拆文件：主 Makefile 只做组装
include common.mk
-include config.mk
```

变量是 Makefile 里最易错的一环，赋值符号差一个字符，语义就变。展开下面这张对照表，对着自己写的配置检查一遍。

<details>
<summary>展开：四种变量赋值的区别</summary>

同样给 `A` 赋值，写法不同语义不同：

- `A = 后续展开`：惰性，引用时才算，能引用后面才定义的变量。
- `A := 立即展开`：赋值时就算，之后的修改不影响已展开的值。
- `A ?= 默认值`：仅当 `A` 未定义时赋值，给外部覆盖留口子。
- `A += 追加`：在原有值后追加，空格分隔。

典型搭配：`CFLAGS ?= -O2` 设默认，命令行 `make CFLAGS=-O0` 覆盖；`LDFLAGS += -lm` 让使用方继续加库。

### 从脚本到 Makefile 的迁移

什么值得迁：三行以内的命令别迁，参数多、步骤多、有依赖关系的构建才值得。顺序也重要：先有能跑的脚本，再改成 Makefile，别反过来——从零写 Makefile 的人，一半时间花在调试 Tab 和变量展开上，正事反而耽误了。

迁移期新旧并存：Makefile 目标里先调老脚本，逐步把逻辑搬进去，验证无误再删脚本；一步到位的重构最容易两头空，想回滚都没地方退。每次只迁一个目标，迁完跑一遍全量验证，节奏稳比速度快重要。

团队约定三件套：统一用 Tab、非文件目标一律 `.PHONY`、提供一个 `help` 目标把可用目标列出来。新人第一眼知道有哪些命令可跑，比在 Makefile 里翻注释体验好得多，这也算 Makefile 的自文档化——文档和实现永远同步，因为本来就是同一份文件。

和 CI 的关系：CI 里同样跑 `make test`，本地与云端共用一条命令，环境差异只剩依赖版本；这正是 Makefile 在容器时代仍未过时的原因——它不管理环境，它管理步骤，而步骤永远是团队最需要共识的那部分。

## 高频场景速查

八个场景从单文件编译到多环境发布，按引入顺序排列，前面的用熟了再看后面的。

| 场景 | 写法要点 | 说明 |
| --- | --- | --- |
| C 项目编译 | 模式规则 + 自动变量 | `$@ $< $^` 省重复 |
| 伪目标 | `.PHONY: clean test` | 防同名文件导致不执行 |
| 目录自动创建 | 订单目标 `| build` | 依赖目录先于产物生成 |
| 默认变量 | `CC ?= gcc` | 保留外部覆盖能力 |
| 版本注入 | `$(shell git describe)` | 构建时把版本号编进去 |
| 并行加速 | `make -j$(nproc)` | 前提是目标间无隐式依赖 |
| 条件分支 | `ifeq ($(ENV),release)` | 一份文件多套配置 |
| 包含公共配置 | `include config.mk` | 子目录共用的变量集中放 |

## 踩坑记录

> **坑一：`missing separator` 报错。** 配方行首用了空格而不是 Tab。编辑器要显式配置"Makefile 用 Tab"，自动格式化工具是重灾区；把空格粘贴进去的那一刻起，这一行就废了。

> **坑二：`clean` 怎么都不执行。** 目录里有个叫 `clean` 的文件，make 认为目标已最新。声明 `.PHONY: clean` 一劳永逸，所有非文件目标都该声明。

> **坑三：并行 `make -j` 偶发失败。** 两个目标同时写同一个文件，或目录还没建就开始产文件。用订单目标（`| dir`）声明目录依赖，输出文件按目标分目录，别共用临时文件。

> **坑四：命令失败整条链还继续。** 行首加 `-` 会忽略错误，`make -k` 也是。CI 里这会让"失败的构建"显示成功。只在"允许失败的检查"上加 `-`，并注释原因。

> **坑五：变量展开时机踩坑。** `A = $(B)` 是惰性的，B 在后面改值，A 引用到的也是新值；想要快照就用 `:=`。搞混这两者会出现"改了没生效"的灵异现象。

> **坑六：`include` 的文件不存在直接报错。** 用 `-include config.mk`（带减号）让缺失变成警告，配合"不存在就生成默认值"的模式，新机器 clone 下来第一条命令就能跑。

> **坑七：`make` 提示"没有规则可制作目标"。** 目标名拼写错、依赖文件不存在且没有生成它的规则，都会这样。先用 `make -n` 看它想干什么，再用 `make -p` 搜目标是否在数据库里；文件路径里有空格是另一个隐蔽原因，Makefile 对空格的切分规则很朴素，尽量别用。

## 速查小结

- 规则 = 目标 + 依赖 + 配方；配方行首永远用 Tab。
- 非文件目标一律 `.PHONY`，这是 Makefile 卫生的第一条。
- 自动变量 `$@ $< $^` 和模式规则配对，消灭重复规则。
- 变量选 `:=` 还是 `=` 看你要快照还是惰性，`?=` 留给外部覆盖。
- 并行构建前先理顺目标间的真实依赖，用订单目标管目录。
- 大文件要拆：`common.mk` 管公共规则，`config.mk` 管环境值并 ignore。
- `make -n` 空跑是调试利器，先看命令再真执行。

Makefile 写好之后，构建这件事就从"记命令"变成了"描述依赖"。调试顺序也固定：`-n` 看命令、`-d` 看决策、`$(info)` 看变量，三步定位，很少需要翻手册；真正难的问题，`make -p` 打印的数据库里有全部答案。
