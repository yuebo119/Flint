缓存是后端最常用的性能手段，也是最容易埋雷的地方。线上大部分"数据偶尔不对，过一会儿又好了"的问题，根子都在缓存一致性的细节上。这篇文章深扒最常用的 Cache Aside 模式，把读写时序、并发竞态、延迟双删到底解决什么问题逐个讲清楚，最后梳理穿透、击穿、雪崩三类问题的对策。先给结论：Cache Aside 是默认选择，但它的正确性依赖"删缓存而不是改缓存"这个纪律，以及一个兜底的 TTL。

这个结论来自一次真实故障。去年我们把商品价格接入缓存后，客服接到投诉：有用户看到的价格和结算时不一致，最长的持续了二十分钟。根因是写路径上"更新缓存"的实现：两个并发的价格修改，网络延迟让后提交的请求先写了缓存，旧价格从此住进了缓存，直到 TTL 到期。把"更新"改成"删除"之后，同类投诉再没出现过。这个教训值得每个用缓存的人记住：缓存不是数据库的镜像，它是可能随时丢失、随时重建的加速层，设计时就要假设它骗你。

## 读路径与写路径

Cache Aside 的规则只有两句话：读的时候先读缓存，未命中读数据库，回填缓存；写的时候先更新数据库，成功后删除缓存。这个模式的命名来自经典的缓存策略分类，背景可以参考 https://zh.wikipedia.org/wiki/缓存 。注意写路径是删除，不是更新缓存。为什么？因为写路径上更新缓存是一次"计算后写入"，两个并发写如果顺序颠倒，缓存里会留下旧值，而且这个旧值可能一直存活到 TTL 到期；删除则把不一致的窗口收敛到"下次读时回填"，让数据库始终是唯一事实来源。

### 为什么先写库再删缓存

再往深想一层：为什么"先更新数据库，再删缓存"而不是反过来？如果先删缓存再写库，删除和写入之间有一个窗口，这期间的读请求会把旧值重新回填进缓存，而且这个旧值会活到 TTL 到期。先写库后删缓存，窗口只存在于"读请求读到旧值之后、写请求删缓存之前"，同样存在，但删除动作一定发生在写提交之后，不一致的最长存活时间被压到一次读加一次删的间隔，而不是整个 TTL。两个顺序都不完美，但后一个的上界小得多，这就是选它的理由。

```java
public class UserCacheService {
    private final RedisTemplate redis;
    private final UserMapper userMapper;

    public User getById(long id) {
        String key = "user:" + id;
        User cached = (User) redis.opsForValue().get(key);
        if (cached != null) return cached;

        User fromDb = userMapper.selectById(id);   // 未命中走数据库
        if (fromDb != null) {
            redis.opsForValue().set(key, fromDb, Duration.ofMinutes(30));
        }
        return fromDb;
    }

    public void update(User user) {
        userMapper.update(user);
        redis.delete("user:" + user.getId());      // 先写库，再删缓存
    }
}
```

## 四种缓存模式

Cache Aside 只是四种模式之一，先看清全貌再谈细节，很多争论其实是拿错了模式。

| 模式 | 读路径 | 写路径 | 一致性 | 适用 |
| --- | --- | --- | --- | --- |
| Cache Aside | 应用先读缓存，未命中读库回填 | 应用先写库，再删缓存 | 最终一致 | 绝大多数读多写少 |
| Read Through | 缓存自己读库，应用无感 | 同 Cache Aside | 最终一致 | 缓存客户端能力强时 |
| Write Through | 同 Cache Aside | 先写缓存，缓存同步写库 | 强一致，写慢 | 写少且要求即时可见 |
| Write Behind | 同 Cache Aside | 只写缓存，异步批量刷库 | 弱一致，可能丢 | 计数、日志类可丢数据 |

Write Behind 是双刃剑：写入性能极高，但缓存挂了就丢一批数据，只敢用在"丢了也无所谓"的场景，比如页面浏览量。我们给内容站点的阅读数用过一次，重启缓存丢了约两千的计数，业务方表示无所谓，这类场景才是它的位置。

## 并发竞态：删除也可能留下旧值

> 删除缓存压缩的是不一致窗口，消除窗口靠的是 TTL。设计时假设缓存会骗你，才不会在半夜被它骗。

删缓存并不等于绝对一致。考虑这个时序：线程 A 读未命中，从数据库读到旧值；线程 B 完成写库并删了缓存；线程 A 随后把旧值回填进缓存。这个旧值会一直存活到 TTL 到期。理论上无法完全消除，工程上的缓解手段是给缓存值设置合理的 TTL，把不一致窗口从"永久"压到"分钟级"。

延迟双删是针对更严格场景的做法：写库前删一次，写库后等一小段时间再删一次。第二次删除覆盖的是"读请求在写期间回填旧值"的窗口。等多久？大于一次主从同步延迟加一次读请求耗时即可，常见取一两秒。代价是写请求变慢、且仍非强一致，所以只在少数对一致性敏感的字段上使用，全表铺开是自欺欺人。

需要说明的是，延迟双删解决的是"旧值回填"窗口，并不能覆盖主从同步延迟本身。如果缓存未命中时读到了主库还没同步到的从库旧值，回填的依然是旧值，第二次删除的时间窗口要按最坏的主从延迟估算。这也是为什么真正对一致性敏感的字段，建议读请求直接走主库：一次主库读的代价，换来的是不用给每个字段设计补偿方案。我们的商品价格最终就是这么做的，缓存的归缓存，强一致字段的归主库。

## 三类典型问题

| 问题 | 成因 | 对策 |
| --- | --- | --- |
| 穿透 | 查询根本不存在的 key，缓存数据库一起被打 | 布隆过滤器前置；空值也缓存并设短 TTL |
| 击穿 | 热点 key 过期瞬间，大量请求同时打到数据库 | 互斥锁重建，或逻辑过期不删物理值 |
| 雪崩 | 大量 key 同一时刻集中过期 | TTL 加随机偏移；多级缓存；限流兜底 |

三个问题的解法都不复杂，难的是在平时就做进去。穿透场景里布隆过滤器是标准解，但它有误判率：说"不存在"一定准确，说"存在"可能骗你。所以布隆过滤器只用来挡"一定不存在"的流量，挡不住的漏网之鱼仍然会打到数据库，空值缓存的第二道防线不能省。另外空值缓存的 TTL 要设得短，一两分钟就够，设长了会把"新建的数据"也挡在缓存外，出现"刚加的商品查不到"的怪事。击穿的互斥重建是性价比最高的一项，核心是"只放一个请求去回填，其他请求短暂等待后读缓存"：

```java
public User getWithLock(long id) {
    User cached = (User) redis.opsForValue().get("user:" + id);
    if (cached != null) return cached;
    // 未命中：抢互斥锁，只有一个线程能重建
    String lockKey = "lock:user:" + id;
    Boolean ok = redis.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(10));
    if (Boolean.TRUE.equals(ok)) {
        try {
            User fromDb = userMapper.selectById(id);
            redis.opsForValue().set("user:" + id, fromDb, Duration.ofMinutes(30));
            return fromDb;
        } finally { redis.delete(lockKey); }
    }
    // 没抢到锁的请求稍等后重试读缓存
    LockSupport.parkNanos(50_000_000L);
    return (User) redis.opsForValue().get("user:" + id);
}
```

## 本地缓存与分布式缓存的边界

Caffeine 这类本地缓存的读延迟在微秒级，没有网络往返，适合变化极少、允许分钟级延迟的数据，比如字典表、配置。但它的更新只能靠广播失效或短 TTL，多实例之间必然有不一致窗口。判断标准：一份数据如果能接受"改错五分钟不生效"，本地缓存是首选；如果不能，用分布式缓存并接受一次毫秒级网络开销。

### 失效广播与预热

两层一起用时，本地缓存的 TTL 必须显著短于分布式缓存，否则失效广播到达前，本地值一直在服务旧数据。还有一个常被漏掉的点是缓存预热：服务刚启动时本地缓存是空的，第一波流量会全部打到数据库，正好撞上启动时资源还没就绪的最脆弱时刻。我们的做法是在健康检查通过之后、接受流量之前，用一份预设的热点 key 列表主动预热，列表来自历史访问统计，每周末更新。这个改动把发布后五分钟的数据库负载从峰值压到了三分之一。

验证缓存是否生效有个朴素办法：改完数据，在浏览器里按 <kbd>F12</kbd> 打开开发者工具的 Network 面板，按 <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> 强制刷新绕过浏览器缓存，再看接口返回和响应头里的缓存标识，比翻十页日志直观。

## 兜底纪律

最后是纪律问题。缓存是优化，不是正确性依赖：数据库挂了要能降级到读旧缓存或返回部分数据，缓存挂了要能直接读数据库并限流。上线前的缓存检查项，按我们踩过坑的顺序列：

- 每个 key 都有 TTL，没有例外，包括"永远不变"的字典数据
- 热点 key 已识别，完成预热，且预热任务有失败告警
- 大 key 已拆分，单 key 序列化后不超过 10 KB
- 空值缓存的 TTL 是分钟级，不是小时级
- 缓存宕机时有降级路径：直连数据库加限流，页面标注数据延迟
- 删缓存失败有兜底：至少记日志，关键字段走对账补偿

把缓存当成"查不到就报错"的必需组件，一次 Redis 抖动就会演变成一次故障。TTL 是最后的保险，再自信的一致性方案，也请给每个 key 加上过期时间。

最后说 key 的设计。好的 key 要自带三样信息：业务前缀、主键、版本或租户标识。`user:1001:v2` 比 `user_1001` 多出的信息，在结构变更和排查时都是救命的。批量操作时用哈希标签控制 slot 分布，多 key 操作尽量走 Lua 脚本一次执行，减少往返的同时避免竞态。这些细节不性感，但缓存出问题的夜里，能救你的从来不是架构图，是 key 命名。
