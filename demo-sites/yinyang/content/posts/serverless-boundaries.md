先亮观点：**Serverless 是一项优点和边界同样清晰的技术，把它当成通用计算平台来用，几乎必然以迁移收场**。函数计算在特定负载形状上极其优秀，超出这个形状，每一项优势都会反过来变成约束。这篇文章的目的不是劝退，而是把边界画清楚，让选型发生在理解之后。

> 选型前先问自己：我愿意为省下的闲置开销，付出多少延迟和可控性？这个问题的答案因人而异，但它必须被问出来，而不是被宣传材料代替。

## 函数计算的甜蜜点

函数计算适合的负载有共同形状：**事件驱动、短时执行、流量起伏大、无持久状态**。对号入座的典型场景包括：

- 文件上传后的转码、压缩、病毒扫描；
- 定时任务与数据批处理的分片执行；
- Webhook 接收与协议转换；
- 流量波峰波谷明显的对外接口，比如促销活动页的查询服务。

这些场景的共同点是"按需执行"：没有请求时不付钱，请求来了毫秒级扩容。传统常驻服务要么为峰值长期付费，要么为省钱手动扩容忍受抖动，函数计算恰好落在两者之间。但请注意这句话里的前提：**"没有请求"必须是真的没有请求**。一个每秒都有几十个请求打进来的接口，实例根本不会被回收，所谓"按需付费"的弹性优势并不存在，付的却是函数计算的溢价单价。

## 边界一：冷启动是物理课，不是玄学

函数实例空闲后被回收，下一个请求到达时要重新初始化运行时，这就是 `cold start`（冷启动）。不同运行时的冷启动量级差别很大：

| 运行时 | 典型冷启动 | 体感 |
| --- | --- | --- |
| Node.js / Python | 几十到几百毫秒 | 多数交互场景无感 |
| JVM（Java / Kotlin） | 数百毫秒到数秒 | 需要常驻实例兜底 |
| .NET AOT 编译 | 接近原生 | 依赖镜像与包体积 |
| 自定义容器 | 秒级起步 | 取决于镜像层大小 |

同步接口遇到冷启动，用户端就是一次明显的卡顿。缓解手段存在：预留实例、JIT 预热、精简依赖，但每一项都在把函数计算改造成"常驻服务"，只是计费方式还是函数。**对延迟敏感的同步接口上函数计算，本质上是在和物理规律谈判**，能谈，但筹码有限。

## 边界二：稳定流量下，成本拐点会到来

### 成本核算的三个输入

"没有请求不花钱"是函数计算最大的卖点，也是最大的误解来源。看一笔账：一个日均百万次调用的接口，每次执行 200 毫秒、配 512 MB 内存。

```yaml
# 函数配置与计费相关的关键参数
runtime: python3.12
handler: app.main
memorySize: 512        # MB，CPU 随内存等比分配
timeout: 30
concurrency: 200       # 并发上限，防止打爆下游
environment:
  DOWNSTREAM: https://api.example.com/v1
```

按调用次数费加执行时长费计算，日均百万次、每次 0.2 秒的负载，月账单换算下来和两台常驻的 4 核 8 GB 机器相当。而利用率一旦稳定，常驻实例的单价只会更低。**经验拐点大致在日均十万次调用以下函数计算占优，稳定高流量下容器化常驻更划算**。当然各家定价不同，上线前用自己的真实流量数据算一遍，比任何宣传数字都可靠。

## 冷启动优化的四个层次

如果业务确实需要函数计算承载同步接口，优化冷启动有四个由浅入深的层次：

1. **精简依赖**：Java 项目只保留用到的类，Node 项目别为一个小工具引入整个 SDK。包体积每小一半，初始化就快一截。
2. **编译型运行时优先**：Go、Rust 或 .NET AOT 编译的产物冷启动在毫秒级，比解释型运行时快一个数量级。这是选型期就该做的决定，不是上线后能补的课。
3. **预留实例**：对已知的高峰时段（比如每天上午十点的对账接口）预留常驻实例，用钱换确定性。
4. **客户端配合**：异步链路把同步等待改成轮询或回调，冷启动被彻底藏在用户感知之外。这通常是架构上最优雅的解。

四个层次可以叠加，但每一层都在把函数计算往"常驻服务"推。推到全预留，你得到的就是一台按调用次数计费的常驻服务器，账单会比容器贵。这就是边界：**优化到极致，函数计算就失去了它存在的理由**。

## 并发、限流与下游保护

函数计算的弹性是把双刃剑。一次突增流量可能瞬间拉起上千个实例，把下游数据库连接打满，或者把第三方 API 的配额消耗殆尽。函数计算里的"弹性"必须是**有刹车的弹性**：

- 给函数设置并发上限，防止无限扩容；
- 在下游客户端配连接池和熔断，别让每个实例各建一条连接；
- 有状态的外部依赖（数据库连接数、第三方配额）单独设保护，宁可函数排队，不可下游雪崩。

这些约束和容器化服务没有区别，但因为函数"看起来会自动扩展"，团队反而更容易忘记设限，这是函数计算架构里最常见的人为失误。

最后补一个组织层面的观察：**函数计算改变了 on-call 的形态**。传统服务出问题，值班人登机器看日志；函数出问题，值班人面对的是一个没有 shell、日志分散在云厂商控制台的环境。团队必须提前把函数的日志出口、告警渠道、应急开关准备好，否则第一次故障时的慌乱会放大影响。工具链不跟着架构走，弹性优势会被运维劣势抵消。

## 边界三：状态、长连接与协议

有些限制来自架构而非性能，绕不开：

- **WebSocket、gRPC 长连接**：函数实例短命，长连接需要额外的连接保持层，多数厂商提供但属于额外组件，复杂度陡增。
- **有状态服务**：会话、缓存、连接池要么外置到托管服务，要么放弃。外置之后，函数计算就退化成了"无状态的胶水层"。
- **执行时长上限**：几分钟的硬顶，长任务必须拆成步骤函数或改用批处理平台。

```json
{
  "event": {
    "source": "oss",
    "eventName": "ObjectCreated:Put",
    "objectKey": "uploads/2026/03/report.xlsx",
    "size": 1048576
  },
  "context": {
    "requestId": "req-8f2c41d6",
    "remainingTimeInMillis": 2870000
  }
}
```

## 我的判断：三类负载的归属

基于以上边界，我的归属建议是：

1. **事件型短任务**：函数计算的舒适区，放心用，注意幂等和重试语义。
2. **稳定流量的同步 API**：优先容器化常驻。函数计算可以做灰度或峰值兜底，别做主力。
3. **长连接、有状态、复杂编排**：不要碰函数计算，用容器或托管 PaaS，这里的复杂度差价早晚要还。

---

## 混合架构才是终态

成熟的团队很少二选一。更常见的形态是：**核心同步服务跑在容器或虚拟机上，事件型旁路逻辑用函数计算，两者通过消息队列和对象存储事件衔接**。核心链路保持可预测的延迟和成本，旁路获得弹性与零闲置开销。函数计算在这个架构里的角色是"胶水"，而不是"地基"，这恰好是它最擅长的位置。

## 结论

Serverless 不是"更先进的计算方式"，而是**一种针对特定负载形状的计费与调度优化**。判断能不能用，问三个问题：流量是否起伏、执行是否短促、状态是否外置。三个答案都是"是"，函数计算就是好选择；有一个"否"，就算清楚要额外付的代价再决定。选型里最危险的想法，是相信存在一种"因为无服务器所以更简单"的免费午餐。

最后补一个常被回避的话题：厂商锁定。函数计算的事件格式、SDK、触发器类型都是厂商私有的，写深的业务很难平移到另一家。这不是反对用函数计算，而是提醒把**可迁移的业务核心留在函数之外**：让函数只做协议适配和轻量编排，真正的业务逻辑打包成可以被任何运行时调用的独立模块。这样将来要迁，换的是一层薄薄的胶水，而不是整棵业务树。
