## 条目一：端口转发三件套，先把方向搞清楚

SSH 的端口转发只有三个参数，但方向搞反的人排成队。记住一个口诀：-L 是把远端借到本地，-R 是把本地送到远端，-D 是在本地开一个动态跳板。排查内网数据库连不上，用 -L 把库的端口搬回本机；让外网访问你笔记本上的开发服务，用 -R；访问只有内网能到的管理后台又懒得逐条加规则，用 -D 配一个 SOCKS 代理，让浏览器整体走隧道。

```bash
# -L：把内网数据库借到本地 15432
ssh -N -L 15432:db.internal:5432 jump.example.com

# -R：把本地 8080 的开发服务送到公网服务器的 9090
ssh -N -R 9090:localhost:8080 relay.example.com

# -D：本地开 SOCKS 跳板，浏览器指向 127.0.0.1:1080
ssh -N -D 1080 jump.example.com
```

三个参数都可以叠，一条命令开多条隧道，但别叠成毛线球。我的做法是一条隧道一个用途，写在 `~/.ssh/config` 里起名字，比如 `tunnel-db`、`tunnel-web`，用的时候 `ssh -N tunnel-db`，断线重输一遍命令的事，交给后面的 autossh 解决。

调试隧道有个固定的检查顺序：先看认证，能不能登上中转机；再看转发请求，SSH 有没有报告 forward 失败；最后看目标，端口通了但服务拒绝，说明隧道是好的，问题在对端。`ssh -v` 的输出会把这三个阶段标得很清楚。多数人卡住，是因为只看到最后一步不通，就回头怀疑整条链路，方向反了，越查越乱。

## 条目二：反向隧道的保活，是默认需求

内网机器没有公网 IP，想从外面连进去，标准答案是反向隧道：内网机器主动连出去，把端口挂在公网中转机上。裸用的问题是脆：网络抖一下隧道就断，而断了的隧道不会自己好，等你想用的时候才发现连不上，这种事故每月都有人交学费。autossh 就是为这个存在的，它盯着隧道，断了自动重连，配两条心跳参数就能用：

```bash
# autossh：心跳保活，断了自动重连
autossh -M 20000 -f -N \
  -o "ServerAliveInterval=15" \
  -o "ServerAliveCountMax=3" \
  -o "ExitOnForwardFailure=yes" \
  -R 9090:localhost:8080 relay.example.com
```

如果中转机上跑着 systemd，也可以不用 autossh，把 SSH 隧道写成一个服务单元，靠 `Restart=always` 保活，日志还能进 journald 统一查。两种方案没有高下：autossh 胜在零配置，systemd 胜在日志和启动时序可控。选一个，写进部署文档，别让每个人用自己的偏方，否则隧道断了没人知道该看哪份日志。

### 保活的三个细节

`ExitOnForwardFailure=yes` 这条别省：它让隧道建立失败时 SSH 直接退出，autossh 才有机会重试，否则你会得到一个"活着但端口没监听"的僵尸连接，比彻底断掉更难排查。还有一个常踩的坑在中转机侧：默认情况下 -R 绑定的端口只监听中转机的回环接口，外面够不着，需要中转机的 sshd 打开 `GatewayPorts yes` 或者用 `ssh -R 0.0.0.0:9090:...` 指定绑定地址。改这个选项前想清楚：你把内网服务暴露给了整个互联网，还是只暴露给可信来源。更稳的做法是反向隧道只绑中转机的回环地址，外面再加一层 Nginx 或另一条 SSH 做二次跳转，顺带把认证和访问日志补上。链路每多一跳，排查难度就上一档，所以两跳基本是实用上限；再多，不如直接用 frp 这类带面板的方案，至少每条隧道的连接状态是可视的，出问题不用猜。

## 条目三：现代穿透方案，省事的代价写在审计里

不想维护中转机的话，现成的工具一排一排：frp 自建中转、Cloudflare Tunnel 走边缘节点、Tailscale 组虚拟内网，各有各的舒适区。选型时我只看三个问题：流量过不过第三方、谁能看到连接记录、客户端怎么认证。这三个问题的答案，基本决定了方案适合开发调试还是生产暴露。

| 方案 | 流量路径 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| SSH 反向隧道 | 自己的中转机 | 临时访问、管理通道 | 保活和审计靠自己 |
| frp 自建 | 自己的中转机 | 多服务、要面板 | 多一套中间件要维护 |
| Cloudflare Tunnel | 边缘节点 | HTTP 服务出网 | 数据过第三方网络 |
| Tailscale | 打通的虚拟内网 | 设备互联、异地组网 | 依赖协调服务器状态 |

Cloudflare Tunnel 的凭证是一份 JSON 文件，里面有隧道标识和密钥，泄露了就等于把隧道送人，提交进仓库是经典事故：

```json
{
  "AccountTag": "0123456789abcdef",
  "TunnelID": "6ff42b02-0000-4000-8000-000000000000",
  "TunnelSecret": "base64-encoded-secret-goes-here"
}
```

> 穿透工具的差别不在"能不能通"，在"出了事你能不能说清谁在什么时候连过哪里"。开发环境随便选，生产环境先答这个问题再选工具。

这条经验来自一次复盘：一条裸 SSH 反向隧道挂了两年，没人知道有多少人从上面连过内网数据库，最后靠中转机上残缺的 auth.log 才拼出大概。从那以后，团队的规矩是：任何穿透方案，先配好日志和认证，再谈通不通。

补一个观测层面的细节：sshd 的日志默认只记录隧道的建立与断开，隧道里过的连接它一概看不见。想弄清"谁通过隧道连了数据库"，要么在出口的应用层记，要么临时开调试级日志抓现场。穿透链路天然是监控盲区，接受这个现实，然后在两端补齐记录，别在隧道本身较劲。

## 条目四：SSH 卫生清单

SSH 是暴露面管理的重灾区，因为开起来太容易。这份清单不追求加固到满分，追求的是"抄走就能用"：禁用密码认证只留密钥、改默认端口降低扫描噪音、上 fail2ban 挡暴力尝试、root 禁止直接登录。四条做完，日常扫描器的噪音能去掉九成。

- 认证：`PasswordAuthentication no`，只留密钥
  - 密钥加口令短语，丢了也不怕裸奔
- 暴露：改端口加防火墙白名单，能少暴露就少暴露
  - 白名单优先用 VPN 或跳板机，不对公网裸奔
- 防护：fail2ban 加 `MaxAuthTries 3`
  - 日志轮转别忘了，否则磁盘先满
- 审计：定期看 `last` 和 auth.log
  - 至少每月一次，出事时它就是唯一线索

再补一条连接复用的甜点：`ControlMaster` 让同一台服务器的多个会话共享一条 TCP 连接，开终端像开本地标签一样快，Git 频繁推拉的体验提升立竿见影。写在 `~/.ssh/config` 里一次生效，唯一的注意点是主连接断开时所有会话一起断，升级服务器时心里有数就行。

最后是密钥治理，一句话版本：算法选 ed25519，私钥必须加口令短语，口令交给 ssh-agent 托管；团队规模上来之后换 SSH 证书，用 CA 签发、带有效期，别在 authorized_keys 里堆公钥。`ssh-keygen -lf` 随时核对指纹，人离职或换机器，先吊销再重建。这套动作做一次只要十分钟，漏一次的代价是所有人都进得去。
