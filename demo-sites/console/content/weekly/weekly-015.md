## 开场白

本期聊 AI 工程。把模型接进产品之后，真正的工程问题才刚开始：效果怎么量、
成本怎么控、变更怎么管、产出怎么审。本期五个条目按一个功能从原型到上线的
顺序排，每条都是踩过坑之后的结论。

> AI 工程的分水岭不在模型多先进，在有没有评估：没有度量之前，
> 所有调优都是盲改，指标动了也不知道为什么动。

## RAG：先建评估，再调优

检索增强生成（RAG）的坑在于"看起来能跑"和"真的能答对"之间隔着一条鸿沟[^1]。
调 prompt、换 embedding 模型、改分块大小之前，必须先有评估集：
几十条带标准答案的问答对，覆盖高频问题、边界问题与明确答不出的问题。
评估分三层，逐层定位：

- **检索命中率**：该被召回的文档有没有进 top-k，这是天花板
- **答案忠实度**：生成内容是否忠于检索到的上下文，而不是模型脑补
- **答案准确性**：最终答案和标准答案对不对得上

一个最小评估脚本的骨架：

```python
def evaluate(rag_answers, goldens):
    """三层指标：检索是否命中、答案是否忠于上下文、是否答到点上"""
    hit = sum(retrieval_hit(a) for a in rag_answers) / len(rag_answers)
    faithful = sum(is_faithful(a) for a in rag_answers) / len(rag_answers)
    correct = sum(matches_golden(a, g) for a, g in zip(rag_answers, goldens)) / len(goldens)
    return {"retrieval_hit": hit, "faithfulness": faithful, "accuracy": correct}
```

没有这个基线，所有调优都是盲改：指标涨了不知道为什么涨，
掉了也不知道回滚到哪。评估集要像测试代码一样管理，每次改动 prompt 或
检索参数都跑一遍，指标回归就回退。

评估集的大小不必贪多：三十到五十条覆盖主要意图的问答对，
比五百条随手拍脑袋的更有效，关键是每条都人工核对过标准答案。
评估集本身也要版本管理，问题分布漂移时（用户开始问新类型的问题），
先扩评估集再谈优化，否则你在优化一个过时的靶子。

参考链接：[RAG 评估方法综述](https://example.com/ai/rag-evaluation)

## prompt 缓存：把不变的前缀往前放

主流模型的 prompt 缓存按前缀匹配计费：命中的部分价格打到一折上下。
工程含义直接：**把系统提示、工具定义、少样本示例这些稳定内容放前面，
把每次请求变化的内容放后面**。实践中两个改动就能看到账单变化：

- 系统提示词固定下来，不要在里面塞当前时间、用户昵称这类变动字段
- 多轮对话历史按追加顺序自然排列，历史部分天然是缓存友好的前缀

缓存的收益要能观测：记录每次请求的缓存命中 token 数，算出命中率，
低于预期的请求把前缀 diff 打出来，通常能发现某个"不小心变动的前缀"，
比如隐藏的时间戳或随机排序的文档列表。

缓存命中的观测要做成日常指标：每次请求记录命中与未命中的 token 数，
按天看命中率曲线。命中率突然下滑，九成是某个前缀被无意改动，
把最近改动的前缀 diff 拿出来，一分钟就能定位。另外注意缓存命中
与响应质量无关，它只降本，不提质，别把两个目标混在一个指标里。

参考链接：[prompt 缓存计费说明](https://example.com/ai/prompt-caching)

## 提示词管理：当代码管，不当玄学管

提示词是产品的行为逻辑，值得和代码同等的工程待遇：版本化、可回滚、有测试。
落地三件套：提示词模板存仓库，和代码一起评审；每次改动关联评估集指标，
指标不动不许合并；线上按版本号路由，出问题秒级回滚到上一个版本。
反对两种做法：把提示词散落在业务代码的字符串常量里，改了无从追踪；
以及在聊天窗口里反复试出一个"感觉对了"的版本直接上线，
没有评估数据兜底，模型一升级行为漂移都不知道。

配套把**模型版本**也纳入管理：换模型版本等于换了一次提示词，
同样要走评估回归。两者的组合爆炸靠矩阵化处理，别靠人肉。

配套把**模型版本**也纳入管理：换模型版本等于换了一次提示词，
同样要走评估回归。两者的组合爆炸靠矩阵化处理：
每个模型版本跑全量评估集，提示词版本只在主模型上全量、
其余抽检，别靠人肉硬扛。变更记录里同时留痕提示词版本与模型版本，
回滚时两个一起回，只回一个大概率回不到原来的行为。

## 本地小模型：量化的边界

本地推理的吸引力是隐私与零边际成本，现实是能力边界。量化到 4-bit 的
7B 级模型在分类、抽取、摘要这类窄任务上完全可用，在开放问答、
复杂推理上仍和云端旗舰有明显差距[^2]。选型前先做任务分级：

1. 结构化抽取、情感分类、简单改写：本地小模型优先，延迟低、无数据出境
2. 长文档摘要、多轮工具调用：云端大模型，本地做前置过滤与后置校验
3. 混合架构：本地模型做粗筛，只把不确定的样本送云端复核，成本与质量的折中

推理框架层面，GGUF 格式加 llama.cpp 系运行时是当前最通用的组合，
显存估算按参数量乘每参数字节数，再给上下文预留一成。别忽视推理服务的
工程面：批处理、并发限制、显存监控，一个没有背压的本地推理端点
照样能被流量打挂。

## AI 生成代码：审查纪律不降级

AI 写代码的吞吐上来了，事故率也跟着来，因为审查环节最容易在"看起来对"的
代码上放水。几条硬纪律：

- 生成的代码必须先过测试：没有对应测试的生成代码不进主干，
  尤其涉及安全、数据迁移、并发控制的路径
- diff 逐段读，不整文件批：AI 最爱在"顺手改进"时改掉你的边界条件
- 不变量显式验证：循环不变量、空值路径、错误分支，AI 天然只写 happy path[^2]
- 涉及公共 API 的改动，找第二个独立视角复核，生成者不审自己的产物

把 AI 当高产但缺乏责任心的实习工程师：产出量大，需要结对审查、
需要测试兜底、需要有人对最终结果负责。这个定位准确了，
效率提升与质量底线就不冲突。

还有一条经验：让 AI 先写测试再写实现。它写测试时对边界的覆盖
通常比对实现更认真，而测试恰好是审查实现时的抓手。
顺序反过来（先实现后补测试），测试会不自觉地迁就实现的形状，
把 bug 一起测成"预期行为"。

## 结尾

AI 工程和传统工程的分界不在模型，在评估：有效果度量、有成本预算、
有变更管理、有审查纪律，AI 功能才是工程而不是 demo。本期周刊到此，
下期选题路上见。

[^1]: RAG 指检索增强生成：先从知识库检索相关文档，再把文档作为上下文交给模型生成答案，
      用以缓解模型的幻觉与知识过期问题。
[^2]: 这里指训练数据与生成机制的结构性偏差：模型倾向补全常见模式而非覆盖边界情况，
      空值、并发、异常路径必须由测试显式覆盖，不能依赖模型自觉。
