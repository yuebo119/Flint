两年前我参与过一个电商中台项目。系统从一套单体被拆成十九个服务，团队规模没有变化，发布频率反而从每周一次降到了每月两次。一个"下单"需求要改五个仓库，等四个团队排期；联调环境里十八个服务的端口清单打印出来，比需求文档还长。复盘时我们得出一个结论：问题不出在拆分这个动作上，而出在拆分的方向上。当时团队按 Controller、Service、Dao 这样的技术分层来切服务，而不是按业务能力。这篇文章把复盘结论整理成四条原则，供你在下一次动手拆分前对照。

## 原则一：边界是组织边界，不是技术边界

康威定律说，系统结构会复刻组织的沟通结构。这句话在微服务场景里的含义非常具体：如果公司按前端组、后端组、DBA 组来分工，那么无论架构师怎么画图，最终落地的服务一定是按技术层切的，因为任何一个业务需求都要横跨三个组才能上线。反过来，如果一个八人小队能独立拥有"营销活动"这个业务能力的全栈，包括代码、数据、部署和值班，那么拆出来的服务才可能贴合业务边界。

拆分的收益来自独立性：独立部署、独立扩容、独立选型、独立排期。缺少任何一项，拆分就只是把单体搬进了分布式泥潭。一个只能独立编译、不能独立部署的服务，比模块化单体里的一个包强不了多少，却多付出了网络调用的延迟和排障成本。

反例就在我们身边。那个十九个服务的项目里，有一个"订单查询服务"和一个"订单管理服务"，区别只是前者给 C 端读、后者给运营写。两条链路的团队是同一批人，数据是同一个库，发布却要协调两次，任何一边发版，另一边都要陪着回归。这类按调用方拆分的服务，本质上还是技术分层，只是分层维度从"前后端"变成了"读写两端"。判断边界划得对不对，只需看一个问题：这个服务出故障时，需要几个团队一起上线才能恢复？答案超过一个，边界就有问题。

> 如果你连一个能管理好单体的团队都没有，先不要考虑微服务。
> —— Martin Fowler, Microservice Prerequisites[^1]

## 原则二：数据归属优先于代码归属

代码拆开了而数据库还共享，是最常见的伪拆分。两个服务读写同一张表，看起来是两个部署单元，实际上任何一个服务的表结构变更都会变成全公司的发布阻塞点。判断标准只有一条：一张表只能有一个写主，其他服务需要这份数据时，通过 API 调用或事件订阅获取自己的副本，并且接受这份副本是有延迟的。

```csharp
// 反模式：订单服务直连库存库，两个服务共享数据表
public async Task<bool> ReserveAsync(string sku, int quantity)
{
    using var conn = new SqlConnection("Server=inventory-db;Database=Inventory");
    var stock = await conn.QuerySingleAsync<int>(
        "SELECT stock FROM sku_inventory WHERE sku = @sku", new { sku });
    if (stock < quantity) return false;
    await conn.ExecuteAsync(
        "UPDATE sku_inventory SET stock = stock - @qty WHERE sku = @sku",
        new { qty = quantity });
    return true;
}

// 正确做法：订单服务只依赖库存服务发布的契约
public async Task<bool> ReserveAsync(string sku, int quantity)
{
    var response = await _inventoryClient.ReserveAsync(new ReserveRequest(sku, quantity));
    return response.Code == ReserveResult.Success;
}
```

下面这张表把实践中看到的信号做了对照，左边是应该拆的信号，右边是最常被误当成信号的噪音。

| 真实拆分信号 | 常被误当成信号的噪音 |
| --- | --- |
| 两个功能的发布节奏长期冲突，互相阻塞排期 | 某个功能这次改动特别大 |
| 一个模块的流量是其他模块的十倍，扩容策略完全不同 | 代码文件太多，看起来该整理 |
| 故障会跨模块传导，库存抖动拖垮下单 | 新来的架构师想换个技术栈 |
| 两个团队为一个需求的方案反复争论 | 单体编译慢，但部署并不频繁 |

数据副本的同步方式也要提前定。API 拉取适合查询路径，消费方在需要时主动来取，实现简单，代价是实时压力和耦合；事件推送适合状态变化，比如商品改价之后所有下游各自更新自己的副本，发布方不需要知道谁在订阅。两条路线可以混用，但同一个概念不能两条路都走，否则系统里会出现"同一个商品两个价格来源"的怪事，排查时无从下手。另外，副本字段要显式标注更新时间，让使用方一眼看出自己读的是快照，这是上下游团队之间少吵架的好习惯。

## 原则三：拆分是单向门，先忍受单体的疼痛

Martin Fowler 给过一条朴素建议：先写单体（Monolith First）。单体不是敌人，无法演进的单体才是。绝大多数系统在第一天既没有业务量的压力，也没有组织规模的支撑，此时拆分的成本是实打实的，收益是想象中的。更麻烦的是，边界画错之后想收回单体，代价远超当初拆出去的成本，因为调用已经变成了网络协议，回滚意味着重写一遍。

拆分前先问三个问题：现在部署真的互相阻塞吗？现在故障真的互相牵连吗？现在团队真的互相等待吗？三个答案都是"是"，拆分才有依据；只有一个"是"，更常见的解法是把模块边界理清楚，先拆代码，而不是拆进程。模块化单体给未来的拆分保留了全部选项，而草率拆出去的边界，收回来要付双倍代价。

隐性成本也值得算一笔账。每次跨服务调用多一次网络往返和一次序列化，P99 从毫秒变成十几毫秒是常态；原来一个本地事务能保证的事，现在要 Saga 或消息最终一致；排查一个下单失败，从翻一个日志文件变成查五个服务的链路追踪。这些成本在服务数量少的时候不显眼，服务一多就会复利式累积。所以粒度原则是：一个服务能扛住的不要拆成两个，能异步通知的不要同步调用。

## 原则四：先定契约，再定实现

服务之间的每一次调用都是一次跨越网络、跨越团队的承诺。契约先行有两个直接好处：消费方可以基于契约并行开发，服务方可以在不破坏消费方的前提下自由重构实现。契约要包含三样东西：接口定义、错误语义、版本策略。前两样靠代码生成和评审保证，第三样最容易被忽略却最贵，因为一次不兼容的发布会让所有上游团队在深夜集体回滚。落地时把契约当代码管：接口定义进契约仓库，用消费者驱动的契约测试替代手工联调，消费方在测试里声明自己依赖的字段，提供方一改就红。没有契约测试的团队，联调环境永远在修别人的 jar 包。

## 一套可操作的拆分步骤

真到要拆的那天，按下面五步走，每一步做完确认结论再走下一步，不要跳：

1. 访谈与事件风暴
   - 拉上业务、开发、测试，把系统处理的所有业务事件列出来
   - 每个事件标注触发方和受影响方，找出高频协作的聚类
2. 划分限界上下文
   - 按事件聚类的内聚度切上下文，一个上下文对应一个团队的所有权
   - 上下文之间的共享概念要显式建模，比如商品在销售域和物流域是两个模型
3. 确定数据归属
   - 每个上下文独占自己的存储，跨上下文只持有副本，不共享表
   - 历史数据归属有争议时，按"谁产生谁拥有"裁决
4. 选择通信方式
   - 同步调用只保留在查询路径和强一致性要求的路径上
   - 状态变化一律用事件通知，允许秒级延迟
5. 固化契约
   - 接口定义进契约仓库，配消费者驱动的契约测试
   - 版本策略写进发布流程，破坏性变更必须先发新版本并行运行

## 拆完之后，组织要跟上

服务拆完只是开始，真正的收益要靠组织调整兑现。每个服务要有明确的负责人，值班轮值覆盖它，出事能找到人；监控按服务维度聚合，错误率、延迟、饱和度有独立看板，而不是一个总览大屏；发布权限下放到服务团队，不需要集中审批排队。少了这些，拆出来的服务只是换了一种方式互相等待，团队会有强烈的"拆了还不如不拆"的挫败感。微服务转型一半是技术，一半是组织，只做一半，通常以悄悄回滚收场。

## 拆分前的自检清单

动手之前，用下面三组问题给现状打分，三组里有两组答"是"再启动拆分，只有一组答"是"的，先做模块化改造。

### 部署与发布

- 两个模块的发布是否需要互相等待排期
- 一个模块发版是否要全量回归另一个模块的测试
- 联调环境是否经常因为等别人的服务而空转

### 故障与容量

- 一个模块的故障是否会传导成另一个模块的故障
- 两个模块的扩容策略是否已经明显不同（一个要加机器，一个要减机器）
- 慢查询、大促脉冲是否集中在同一个模块

### 团队与协作

- 两个团队是否在为一个需求的技术方案反复争论
- 修改一个模块是否需要跨团队评审三天以上
- 值班同学能否独立定位本模块的故障

其中"部署是否互相等待"是最硬的一条，可以直接观测：打开发布系统，统计过去三个月每个模块的发布时间，如果两个模块的发布总是前后脚出现，等待就是真的。这条结论配合 `git log` 的时间戳就能得出，不需要凭感觉争论。

## 什么时候不拆

最后说反话。如果系统日活不到一万，如果团队不足十人，如果核心链路一条 SQL 就能跑完，那么你需要的是一套边界清晰的模块化单体，而不是十九个需要服务网格互相发现的微服务。拆分的勇气不在于迈出那一步，而在于顶住"别人都拆了"的压力，先把边界想清楚。先划边界，再谈服务，顺序反了，拆得越多还债越多。
