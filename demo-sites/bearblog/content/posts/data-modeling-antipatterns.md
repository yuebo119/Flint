好的数据模型各有各的精巧，坏的数据模型总是坏得相似。这些反模式在代码评审里反复出现，每一条背后都是加班、故障或者一次尴尬的迁移。这篇文章按三类整理十二条，每条给出症状、后果和正确做法，可以当评审清单用。

## 结构与形状类的反模式

### 一、EAV 实体-属性-值

把每一条属性都存成一行，表只剩实体 ID、属性名、属性值三列。症状是所有字段都要运行时解释，类型校验、索引、约束全部失效，一条查询要自连接十几次。正解是把稳定属性提为列，只把真正稀疏的属性放 JSON 列，并为高频查询建生成列索引。

### 二、逗号分隔的一列多值

一个 `tags` 字段存成 `"数据库,索引,性能"`。查包含某标签的订单只能靠 `LIKE '%索引%'`，全表扫描且误匹配"反索引"。正解是建子表或用数组类型，让数据库的索引和连接能力发挥作用：

```sql
-- 反模式：字符串里找标签
SELECT * FROM articles WHERE tags LIKE '%索引%';

-- 正解：子表加索引
SELECT a.* FROM articles a
JOIN article_tags t ON t.article_id = a.id
JOIN tags g ON g.id = t.tag_id
WHERE g.name = '索引';
```

### 三、树形结构只用邻接表

组织架构、分类树只存 `parent_id`，看起来直观，查一棵子树要在应用里递归，数据量大了以后每次查询都是性能灾难，而且递归深度不可控，几百层的异常数据能把查询打死。正解按读写比例选型：读多写少用嵌套集，一次查询取整棵树；写多读少用闭包表，写入时维护祖先关系表；PostgreSQL 可以直接用递归 CTE，但那是查询端的补丁，模型层的优化仍然值得做。

### 四、每张表都套一张字典表

美其名曰统一管理，实际把状态、类型、枚举全塞进一张 `dict` 表，用字符串键关联。结果是外键没法建，数据库层的约束全丢，改一个字典值要发版。正解是枚举值用数据库原生 ENUM 或检查约束，业务侧用常量类映射。

## 类型与约束类的反模式

### 五、浮点数存金额

`amount DECIMAL` 不用，用 `DOUBLE` 或 `FLOAT`。症状是对账永远差几分钱，累计交易额越算越歪，二进制浮点表示不了 0.1 这样的十进制小数。正解是 `DECIMAL`，或者整数分单位存储，展示层再做除法。

### 六、字符串存时间

`created_at VARCHAR(20)` 存 `"2026-03-01 10:00:00"`。范围查询退化成字符串比较，时区信息丢失，跨区部署直接错乱。正解是用 `DATETIME` 或 `TIMESTAMP`，统一 UTC 存储，展示层转本地时区。

### 七、滥用 NULL

NULL 同时表达"不存在""未填写""不适用"三种语义，聚合查询里悄悄改变结果：`COUNT(col)` 跳过 NULL，`AVG` 的分母也跳过。正解是用有业务含义的默认值，必须三态时拆成两个显式字段。

### 七、滥用 NULL

NULL 同时表达"不存在""未填写""不适用"三种语义，聚合查询里悄悄改变结果：`COUNT(col)` 跳过 NULL，`AVG` 的分母也跳过，于是"平均订单金额"可能只统计了填了金额的那部分订单。三值逻辑还会让 `NOT IN` 子查询在遇到 NULL 时返回空集，这类坑排查起来极其耗时。正解是用有业务含义的默认值，必须三态时拆成两个显式字段，如 `is_deleted` 加 `deleted_at`，让每个状态都能被查询和索引命中。

### 八、魔法数字当状态

`status = 1` 是什么？只有原作者知道。正解是建状态字典表加外键约束，或者数据库层 ENUM，让库自己拒绝非法状态：

```sql
-- 反模式：status 是裸整数，什么值都能进
ALTER TABLE orders MODIFY status INT;

-- 正解：用 ENUM 限定取值
ALTER TABLE orders MODIFY status
  ENUM('created','paid','shipped','done','cancelled') NOT NULL DEFAULT 'created';
```

## 规模与演进类的反模式

### 九、UUID 主键一刀切

UUID 确实全局唯一，可随机 UUID 作 InnoDB 主键会让插入随机落页，索引碎片飙升。正解是用有序发号（雪花算法、时间前缀 UUID），或者自增主键加业务唯一键的组合。

### 十、把 JSON 列当垃圾桶

图省事把所有扩展字段塞进一个 `extra JSON`，半年后里面存了四十个键，没有 schema，没有校验，查询全靠应用程序解析。正解是 JSON 只存真正低频、结构不稳定的扩展信息，稳定字段及时提取为列。

### 十一、没有审计字段

没有 `created_at`、`updated_at`、`created_by`，出问题无法追溯，同步系统没有增量依据。正解是建模第一天就把审计列作为模板加上，更新类表再加版本号支持乐观锁。

### 十二条、外键缺席

"性能考虑"不加外键，脏数据靠业务代码兜底，而业务代码有十条写入路径。正解是单库场景把外键和检查约束开起来，分库分表后再评估替换方案，约束是最后一道防线。

## 共同根源：把约束当麻烦

十二条看下来，病因出奇地一致：把数据库的约束能力当成了麻烦。外键麻烦，于是脏数据靠应用兜底；ENUM 麻烦，于是裸整数加代码注释；DECIMAL 麻烦，于是浮点数凑合用；审计字段麻烦，于是出问题无法追溯。

数据库是数据质量的最后一道防线。应用代码有十条写入路径，就有十次绕过校验的机会，而约束在库里只有一份，绕不过去。很多人担心约束影响写入性能，这个担心在多数系统里不成立：外键和检查约束的开销相对于业务写入是零头，真正把写入拖垮的是大事务和坏索引。把该在库层解决的问题留在库层，是数据模型能长期演化的前提。

## 评审时怎么用这份清单

> 清单约束的是底线，不是上限；用法是逐条对照，不是全文背诵。

这份清单的正确用法是评审时逐条过，不是建表时全文背诵。三个使用建议：

- 新建表时至少过一遍"类型与约束"四条，这四条出问题最隐蔽，发现最晚
- 存量表改造按代价排序，先修魔法数字和字符串时间，再动树形结构和 EAV
- 每条反模式对应一个可执行的 grep 或查询，如搜全库 `LIKE '%` 用法、查 `IS NULL` 占比高的列

反模式不是一次做错就定型的，大多是"先这样吧，后面再改"累积出来的。每次改动都比正确做法差一点点，一年之后就是一笔还不完的债。评审时多问一句"这张表半年后谁来查它"，很多妥协当场就能避免。

## 速查表

| 反模式 | 直接后果 | 正确做法 |
| --- | --- | --- |
| EAV | 无类型无索引 | 稳定属性提为列 |
| 逗号多值 | 全表扫描误匹配 | 子表或数组 |
| 纯邻接表树 | 递归查询灾难 | 闭包表或嵌套集 |
| 万能字典表 | 约束丢失 | ENUM 加检查约束 |
| 浮点存金额 | 对账误差 | DECIMAL 或整数分 |
| 字符串存时间 | 时区混乱 | TIMESTAMP 统一 UTC |
| 滥用 NULL | 聚合失真 | 显式默认值 |
| 魔法数字状态 | 语义黑洞 | 字典表或 ENUM |
| 随机 UUID 主键 | 索引碎片 | 有序发号 |
| JSON 垃圾桶 | 无 schema | 稳定字段提取为列 |
| 无审计字段 | 无法追溯 | 建模即加审计列 |
| 外键缺席 | 脏数据 | 单库开约束 |

数据建模的规范化理论可以参考维基百科的数据库规范化词条（https://zh.wikipedia.org/wiki/数据库规范化）[^1]。

十二条清单看完，可能有人会问：规则这么多，模型会不会越建越僵化。不会。清单约束的是底线，不是上限。底线之上仍有大量设计自由：反范式化的冗余、宽表的取舍、JSON 列的边界，这些都要结合查询模式判断，没有标准答案。有争议的设计，把取舍理由写在数据字典里，后来的人至少知道当初为什么这么选，而不是推倒重来一遍。模型是演化的，清单是让演化不跑偏的路标。
