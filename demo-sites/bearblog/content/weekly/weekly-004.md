## 条目一：部署量之王 📦

说 SQLite 是"世界上部署最广泛的数据库"，这句话在它官网挂了十几年，听起来像营销，细想却是事实。每一部安卓手机、每一个主流浏览器、每一个 macOS 和 Windows 系统组件，甚至飞机上的娱乐系统，里面都躺着无数个 .sqlite 文件。它没有独立的服务器进程，数据库就是一个进程内的库加一个文件，这个形态决定了它不可能出现在"数据库服务器"的资产清单里，却让它渗透进了几乎所有设备的底层。你每天触发的查询次数，大概率比你知道的多。它在你生活里的具体位置也比想象中深：浏览器的书签和历史、Lightroom 的照片目录、无数移动 App 的本地缓存，格式都是 SQLite。这件事对备份策略有直接含义：这些库在运行时不建议直接拷贝，正确做法是用在线备份接口，或者先确认没有活跃写入。把"拷文件"当备份的团队，多半在某次恢复时才发现拷到的是写了一半的库。

进程内形态还有一个少被提及的优势：查询没有网络往返。客户端-服务器数据库的一次 SELECT 要过驱动、过连接、过协议，SQLite 就是在函数调用栈里多走一层，微秒级返回。这也是嵌入式设备和边缘计算偏爱它的原因：没有网络栈可依赖的地方，一个文件加一个库就是完整的持久层。

### 一个常被忽略的推论

因为 SQLite 是进程内库，它把"数据库"从一种服务变成了一种文件格式。这个身份转换带来一堆连锁反应：备份等于拷文件（在合适的前提下）、迁移等于搬文件、故障恢复靠文件系统而非 WAL 重放。很多团队对它的误用，根源就是把服务形态的直觉套到了文件形态上，比如指望它扛住几百个并发写连接，或者在没有文件锁语义的网络存储上跑它。前者会疯狂重试，后者可能直接损坏数据库，两个坑我们都见过人掉进去。

参考：[SQLite 部署规模漫谈](https://example.com/sqlite-deployment-scale)

## 条目二：文件格式即契约

SQLite 的文件格式在 2004 年定稿，之后十几年只增不破，官方明确承诺向后兼容：新版本读得懂老文件，老版本读不懂新特性但绝不损坏数据。在软件行业，一个数据格式能稳住十几年，是惊人的纪律。这背后的逻辑是把格式当契约：无数应用把 .sqlite 当自己的存储格式，格式一改，全世界的用户数据都成孤儿。所以它宁愿把新能力塞进新的 PRAGMA 和新的页结构，也不动老布局。

```python
# 文件格式的稳定性，意味着十年后的工具依然打得开今天的库
import sqlite3

con = sqlite3.connect("legacy.sqlite")
print(con.execute("PRAGMA journal_mode").fetchone())
print(con.execute("SELECT count(*) FROM sqlite_master").fetchone())
```

反过来这也解释了它的一些保守选择：没有内置的加密、没有内置的在线加字段、大字段默认走溢出页而不是专门的存储引擎。不是做不到，是做了就破坏"任何工具都能读"的承诺。

> SQLite 的简单不是功能缺失，是功能取舍的结果：它用放弃一部分能力，换来了二十年不变的格式契约。

用 SQLite 当应用格式时，你买到的正是这份契约，以及契约附带的全部克制。

格式稳定带来的另一个红利是跨平台可移植。同一个库文件从 x86 拷到 ARM、从 Windows 拷到 Linux，照样打得开，字节序和对齐都由格式自己处理，这是许多二进制格式做不到的。跨大版本升级也只需要 `sqlite3 old.db .dump | sqlite3 new.db` 一条命令，dump 出来的是标准 SQL，连版本差异都一并抹平。

参考：[SQLite 文件格式文档](https://example.com/sqlite-file-format)

## 条目三：WAL 与并发真相

SQLite 的 WAL 模式（Write-Ahead Logging）让读写不再互斥：读者读旧快照，写者追加日志，两不打扰。这个设计经常被误读成"SQLite 支持高并发了"。真相是：写者依然只有一个，WAL 解决的是读写互斥，不是写写并发。写密集的场景里，SQLite 依然会排队，区别只在于排队时读者不再被挡在门外。判断该不该换数据库，就看你的写流量是不是单写者扛得住。

| 维度 | SQLite | 客户端-服务器数据库 |
| --- | --- | --- |
| 写并发 | 单写者，其余排队 | 多写者，行级锁 |
| 部署形态 | 一个文件，进程内 | 独立服务加连接池 |
| 备份方式 | 备份 API 或停机拷贝 | 在线热备加时间点恢复 |
| 网络共享 | 不支持，别放网络盘 | 核心场景 |

换成客户端-服务器数据库的信号很明确：写入开始排队影响业务、需要跨机器共享状态、或者备份窗口长到不能停机。在这之前，SQLite 的简单性是实打实的红利：没有连接池、没有认证、没有网络故障模式，运维负担接近于零。我们的选型清单是这样的：

- [ ] 写入是单机的、低频的、串行来源的
- [ ] 数据文件不会被放到网络存储上
- [ ] 备份窗口内容忍一次备份 API 调用
- [ ] 没有第二个进程需要同时打开这个库

WAL 之下最常遇到的报错是 database is locked，解决办法朴素得让人意外：设置 busy_timeout，让写者排队等一会而不是立刻失败。另外 WAL 文件会持续增长，需要定期 checkpoint 把内容合并回主库，这个动作默认自动执行，但只读文件系统和网络盘上会失灵，而那两种场景本来也不该跑 SQLite。

参考：[WAL 模式工作机制](https://example.com/sqlite-wal-internals)

## 条目四：类型亲和性，列声明只是建议

最后一个趣味事实能让关系数据库老手愣住：SQLite 的列类型声明只是"亲和性"提示，不是约束。你声明一个 INTEGER 列，照样能塞进去一个字符串；声明 TEXT 的列存数字也合法。只有 INTEGER PRIMARY KEY 那一列是真的强类型，因为它是表的行号别名。这种松弛来自它的动态类型血统：每一行独立存储自己的类型，查询时按列亲和性做隐式转换。

```json
{
  "query": "SELECT typeof(value) FROM demo WHERE id = 1",
  "rows": [{"typeof(value)": "text"}],
  "note": "列声明为 INTEGER，实际存进去的是 '007'"
}
```

CLI 的 `--json` 输出模式很适合检查这类脏数据：直接把每行的类型查出来，一眼看穿"声明与现实的差距"。这个特性在受控数据源手里是灵活性，在用户输入直接进库的手里是陷阱。我们的规矩是：应用层做完整校验，数据库层只当保险，不把类型正确性寄托在亲和性上。毕竟一个存了 '007' 的 INTEGER 列，会在某次 JOIN 的时候让你记起今天这篇。

嫌类型太松的团队可以看看 STRICT 表：建表时加一个关键词，列就只接受声明的类型，插错直接报错，等于把动态类型的门留了一条缝。当然它治标不治本，约束的最终责任还是在应用层，数据库能做的只是把误操作挡在门外，而不是替你把验证逻辑写完。

参考：[SQLite 数据类型亲和性](https://example.com/sqlite-type-affinity)
