## 开场白

本期聊数据库。从嵌入式到分布式，多数性能问题到最后都落到几个朴素的事实上：
写入怎么落盘、连接怎么排队、查询怎么走索引。本期五个条目覆盖这五件事的
常见误区，每条都配了可以直接抄走的操作。

> 数据库调优的顺序是固定的：先测量，再看执行计划，最后才动索引与参数。
> 跳步的优化，大多在解决想象中的问题。

## SQLite 的 WAL 模式：读写不再互斥

SQLite 默认的 rollback journal 模式下，写事务会阻塞读，读也会阻塞写，
单机小应用经常莫名其妙卡住。切到 WAL（Write-Ahead Log）模式后，
写者追加日志、读者读快照，读写不再互斥，吞吐能提升数倍[^1]：

```sql
-- 开启 WAL 并做一次检查点，把 WAL 合并回主库文件
PRAGMA journal_mode = WAL;
PRAGMA wal_checkpoint(TRUNCATE);
```

两个配套认知：WAL 模式下会多出 `-wal` 和 `-shm` 两个附属文件，
拷贝数据库时要把三个文件一起拷，否则可能拿到损坏的副本；
另外 WAL 不支持跨机器的网络文件系统，多进程共享磁盘的场景要评估。
对读多写少的本地应用，这一行 PRAGMA 是性价比最高的调优。

两个使用边界值得知道。其一，WAL 不支持网络文件系统，数据库放 NFS 或 SMB
共享目录时锁机制失效，可能损坏数据，这类场景要么改本地存储，
要么换成客户端服务端架构。其二，WAL 文件会增长，默认自动检查点在一千页左右
触发，写突发的场景可能积累到几十兆，对磁盘紧张的设备要显式控制检查点频率。

参考链接：[SQLite WAL 模式说明](https://zh.wikipedia.org/wiki/SQLite)

## 连接池不是越大越好

"数据库慢就加大连接池"是最常见的误操作。PostgreSQL 每接入一个连接就 fork 一个
后端进程，连接数超过 CPU 核数后，上下文切换和锁竞争让总吞吐不升反降。
社区流传的经验公式是连接数约等于 CPU 核数加硬盘有效数，再乘以二以内。
真正该做的三件事：把慢查询消灭掉、把长事务缩短、给连接池设上限与等待超时。

排查手段：看数据库的活跃连接数、等待事件、CPU 使用率三者是否同时涨。
连接池打满且数据库 CPU 打满，说明池太小；连接池没满而数据库 CPU 打满，
说明查询太贵，加连接只会更糟。在 psql 里查看活动查询时，
结果超出一屏按 <kbd>q</kbd> 退出手动分页即可。

池的排队策略同样影响体感。有界队列加快速失败适合面向用户的请求：
拿不到连接就迅速返回"稍后重试"，让客户端决定退避，好过把线程全挂死在
等待上拖垮上游。无界等待适合后台任务：压垮数据库也比丢任务强。
两种策略没有高下，关键是和调用方的超时设置对齐，
连接等待时间必须小于客户端超时，否则等来的必然是超时。
Go 的标准库把这三个旋钮都暴露了出来：

```go
// 连接池上限按数据库处理能力设定，而不是按请求并发数
db.SetMaxOpenConns(2 * runtime.NumCPU())
db.SetMaxIdleConns(2 * runtime.NumCPU())
db.SetConnMaxLifetime(time.Hour)
```

参考链接：[连接池容量讨论](https://example.com/database/connection-pool-sizing)

## 慢查询诊断：先看计划，再谈优化

遇到慢查询，正确的顺序是固定的：先用执行计划看它实际怎么走，
再决定加索引还是重写。不要凭 SQL 长相猜：

```sql
-- 看真实执行计划与真实耗时，而不是估算
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid'
  AND o.created_at > NOW() - INTERVAL '7 days'
ORDER BY o.created_at DESC
LIMIT 50;
```

执行计划里重点看三处：有没有出现全表扫描、有没有出现"预估行数"与"实际行数"
差一个数量级（统计信息过期）、排序有没有走文件排序而非内存。定位到根因再动手：
缺索引就建复合索引，统计信息过期就 ANALYZE，写法问题就重写成子查询或 CTE。
另外把 `pg_stat_statements` 一类的聚合视图排进日常巡检，
按总耗时排序，前十条慢查询通常贡献了八成数据库负载。

诊断工具链要常备两件：数据库自带的慢查询日志（按耗时阈值记录），
以及聚合视图（`pg_stat_statements` 一类，按归一化 SQL 统计）。
前者抓单次异常，后者看全貌，缺一个都会漏。阈值不要设太松，
一毫秒的记录会把日志淹掉，也起不到聚焦作用。
还有一类慢查询藏在 ORM 里：N+1 查询在开发环境数据量小毫无感知，
上生产后放大成灾难。把每个请求的 SQL 条数打出来，
条数随数据量线性增长的接口就是候选。修复手段是急切加载或改写成连接查询，
改完用执行计划确认确实少了往返。索引维护也要定期做：
统计信息过期会让执行计划选错索引，表现为"昨天还快的查询今天突然全表扫描"，
把 ANALYZE 纳入维护窗口，大表批量变更后手动触发一次。

参考链接：[执行计划阅读指南](https://example.com/database/reading-explain-plans)

## JSONB：灵活字段的正确打开方式

JSONB 适合存真正的异构数据：第三方回调、用户自定义表单、配置快照。
不适合存需要频繁按子字段查询和连接的结构化数据，那应该建真正的列。
用 JSONB 的标配是三件套：生成列把热查询子字段提升为真实列
（写法如 `GENERATED ALWAYS AS (payload ->> 'type') STORED`）、
GIN 索引支持包含查询、CHECK 约束兜底字段形状。

一个反模式警告：把整个业务实体塞进一个 JSONB 大字段，
短期省了迁移，长期丢掉类型约束、索引能力和外键关联，
查询时还要为每次解析付出 CPU。灵活性与约束的边界，
应该按"这个字段会不会变"来划，而不是按"现在懒不懒"来划[^2]。

从 JSONB 提列回真实列的迁移也有成熟路径：先用查询日志统计哪些子字段
被高频访问，给这些字段加生成列与索引，灰度期间新旧字段并存双写，
确认查询全部切到新列后再删旧字段。整个过程是增量可回滚的，
比"推倒重建 schema"的激进方案风险小得多。

参考链接：[PostgreSQL JSONB 文档](https://example.com/database/jsonb-patterns)

## 复合索引：等值列在前，范围列在后

单列索引不够用时，复合索引的列序决定它能不能被用上。经验法则：
**等值条件的列放左边，范围条件的列放右边**。
对 `WHERE status = ? AND created_at > ? ORDER BY created_at` 这种查询，
索引应该是 `(status, created_at)`，等值先定位、范围内有序扫描、排序直接省掉。
写成 `(created_at, status)` 则要扫完整个时间范围再过滤状态，索引基本白建。

另一个常被忘的约束是最左前缀：索引 `(a, b, c)` 能服务 `a`、`(a, b)`、`(a, b, c)`
三种查询，跳过头列的查询用不上它。索引不是越多越好，
每个索引都拖慢写入并放大缓冲池压力，按真实查询模式建，
用未使用索引的统计视图定期清理。

还有一类隐藏浪费：重复索引。建了 `(a)` 又建 `(a, b)`，前者完全被后者覆盖，
纯属白付写入成本。数据库的索引统计视图能列出未使用与冗余的索引，
但"未使用"的判据要拉长到至少一个业务周期，月末报表季才用的索引
平时看是零命中。清理索引前先看慢查询日志，双源对照再动手。

## 结尾

数据库优化的入口永远是测量：执行计划、连接数、索引命中率，三个数据摆在一起，
多数争论会自行收敛。下期聊安全，从一次 .env 误提交说起。

[^1]: WAL 指 Write-Ahead Logging，写前日志：修改先追加到日志文件再合并进主库，
      读者看到的是最近检查点之前的一致性快照，因此读写互不阻塞。
[^2]: 这里的判断依据是 schema 变更频率：字段稳定就建列，字段真的会动态增减才进 JSONB，
      混合形态可以用 JSONB 加热查询子字段的生成列折中。
