每个数据团队都有过同款心碎时刻：研究员在笔记本里跑出 0.92 的 AUC，工程团队接手三个月，线上指标只有 0.7，而且谁也复现不出那个 0.92。问题不在模型，在中间那一公里——数据怎么来的、代码哪个版本、特征怎么算的、上线后怎么看着它，全都没有工程化。MLOps 就是把这一公里铺上铁轨的实践。行业里常被引用的成熟度分级，可以对照[这份公开整理](https://example.com/mlops-maturity)看自己团队处在第几级。这篇按搭建顺序走一遍。

## 一条流水线的全景

先看全景再动手。一条最小可用的流水线分六个阶段，前两段是地基，中间两段是核心，最后两段是保险：

1. **数据接入**：原始数据落湖，做校验和版本化；
2. **特征构建**：可复用的特征计算，训练与线上共用一份逻辑；
3. **训练编排**：实验可追踪，代码、数据、参数三元组落档；
4. **模型注册**：评估达标才准予发布，版本可回滚；
5. **部署上线**：灰度、影子流量，出问题能秒级切回；
6. **监控告警**：盯数据漂移和效果衰减，触发再训练。

![MLOps 流水线的六个阶段与反馈回路](/images/demo-6.svg)

这套结构里藏着一个关键思想：**流水线是给失败设计的**。任何一步失败，要能定位到步骤、版本和输入，而不是全员上机器前翻日志。

## 阶段一：数据可复现

数据是模型的"上一顿饭"。没有版本管理的数据，等于没有菜谱的菜——好吃也是偶然。数据层要解决三件事：

- **原始数据不可变**：落湖后只增不改，清洗作为新一层产出，随时可回溯；
- **数据校验**：行数、缺失率、值域、主键唯一性，进流水线前先过断言；
- **数据集版本化**：训练用的数据集对应一个不可变快照，模型注册时记下这个快照的编号。

数据校验的断言写进流水线，坏数据直接让步骤失败，而不是让模型"带病训练"。见过最隐蔽的事故，是上游某天开始往字段里灌空串，模型悄悄学偏，三周后才在业务指标上爆出来。

## 阶段二：特征工程即代码

特征计算最常见的坑是"两套实现"：训练时用 Spark 算，线上用 Java 重写一遍，两边逻辑差之毫厘，效果谬以千里。正确做法是特征逻辑单一来源：定义一次，训练和线上服务走同一套代码路径。

特征上线时还要记录**特征快照**：模型训练时用的每个特征的分布基线，这是后面判断漂移的参照物。

## 被跳过的基础：环境与依赖

翻车现场里，有一类比例高得离谱：模型在研究员机器上跑得好好的，进流水线就各种报错，最后发现是 numpy 版本差了一个小版本，或者 GPU 驱动对不上。环境管理的纪律只有三条，但每条都有人不遵守：一是容器化，训练和推理环境从同一个基础镜像构建，版本号跟着模型注册信息走；二是依赖锁死，lock 文件进版本库，禁止"差不多就行"的浮动版本；三是镜像与模型绑定，模型注册时记录它验证时所用的镜像，回滚时环境和权重一起回。这三条的成本是每次构建多等几分钟，收益是省掉无数次"我这跑得好好的"式扯皮。

## 特征平台：一次计算，处处复用

流水线跑到一定规模，会撞上同一堵墙：同一个特征，风控组算一遍、营销组算一遍、算法组再算一遍，三份逻辑三个口径。特征平台把特征计算收敛成资产：统一定义、统一计算、统一存储，消费方按名字取用。入门版甚至不需要专门产品，一张特征宽表加一个查询接口就能覆盖八成需求。判断要不要上正式平台的信号很简单：当特征口径吵架的会议每周超过一次，或者同一个滑窗逻辑出现了第三份实现，就该收敛了。收敛的收益不只是省人力，更是让模型之间可比——线上五个模型用的活跃度定义必须一致，否则效果对比就是关公战秦琼。

## 阶段三：训练编排与实验管理

训练步骤要满足三个纪律：随机种子固定、环境锁死（容器镜像加依赖清单）、超参数和代码版本随模型一起入库。一段声明式的流水线配置比一堆临时脚本可靠得多：

```yaml
# 训练作业定义：代码、数据、参数三元组全部显式落档
job:
  name: churn-model
  entrypoint: src/train.py
  code_version: git:a3f91c2
  image: registry.internal/train:2026.08.1

data:
  snapshot_id: ds-2026-08-11
  features: [tenure_days, avg_order_value, last_login_gap, support_tickets]

training:
  framework: xgboost
  params:
    max_depth: 6
    learning_rate: 0.05
    n_estimators: 400
    random_seed: 42

outputs:
  model: models/churn/$(date)/model.bin
  metrics: models/churn/$(date)/metrics.json
  feature_snapshot: models/churn/$(date)/features.parquet
```

评估门槛也写进配置：AUC 低于 0.85 或与线上版本的差置信区间不显著，自动判不通过，连注册的门都摸不到。

## 阶段四：模型注册与上线

模型注册中心记录每个候选的"身份证"：训练数据快照、代码版本、评估指标、审批记录。发布走受控流程，命令行一把梭：

```bash
# 候选模型通过评估后，注册并推送到灰度环境
mlflow models register -m runs:/$(cat run_id)/model -n churn-model

# 灰度：先 5% 流量影子验证，观察核心指标无回退再全量
kubectl -n ml-serving set image deployment/churn-api api=registry.internal/churn:2026.08.14
kubectl -n ml-serving rollout status deployment/churn-api
```

回滚路径要在上线前演练一遍。真出事时，"切回上一版本"这个动作要三十秒内完成，而不是临时翻部署文档。

> 上线流程的铁律：任何变更都必须有一条三十秒内可执行的退路。做不到这一条的部署流程，本质上是在赌运气，赌输的代价由值班工程师承担。

## 阶段五：监控与漂移

### 三类信号

模型上线那天，效果就开始折旧。盯三类信号：

| 信号类型 | 观察对象 | 典型告警 |
|----------|----------|----------|
| 数据漂移 | 输入特征的分布 vs 训练快照 | PSI 超阈值 |
| 概念漂移 | 特征与标签的关系变化 | 线上 AUC 连续下降 |
| 系统健康 | 延迟、吞吐、错误率 | P99 延迟翻倍 |

漂移不等于要立刻重训。先定位是季节性波动、上游数据故障还是真的世界变了——把重训当万灵药，只会得到一个永远在训练、永远追不上变化的流水线。

告警阈值要带静默期和分级：漂移指标连续三天越线才通知，一次性毛刺只进日志。告警太多等于没有告警——当值班工程师开始习惯性点忽略，监控系统就已经死了。

## 阶段六：再训练触发器

### 带守卫的触发

自动化重训不是"每晚定时跑"，而是带守卫的触发。一组实用的触发规则：

- [ ] 效果指标跌破阈值持续 N 天（不是瞬时抖动就触发）
- [ ] 数据漂移指标 PSI 超过阈值，且已排除上游数据故障
- [ ] 积累足够多的新标注样本（冷启动数据量翻倍之类）
- [ ] 新模型在锁定评估集上显著优于线上版本，才会被推上线

## MLOps 是组织问题

最后一个阶段没有代码可写，却是最容易烂尾的：分工。研究员觉得部署是工程的事，工程觉得模型是研究的事，中间的流水线没人认领，最后变成某个倒霉蛋用私人脚本维持。可落地的分法是划三条线：数据到特征由数据团队负责，训练到模型注册由算法团队负责，部署到监控由工程团队负责，流水线本身作为三方共用的产品，明确一个 owner。这个 owner 不对任何单一模型负责，对整条流水线的 SLA 负责——任何作业失败，第一个被叫醒的是他。没有这个角色，前面所有工具都会在三个月内退化成私人脚本的集合，而回归分析会告诉大家：问题出在第零天。

---

最后泼一盆冷水：MLOps 不是工具链比赛，堆十种工具而流程空转的团队遍地都是。判断标准很简单——**任意一次线上异常，能否在半小时内定位到"哪条数据、哪个版本、哪次变更"**。答得上，工具才算用对了地方。
