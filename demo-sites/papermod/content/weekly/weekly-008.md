"这是技术债务"大概是代码评审里最万能的挡箭牌：烂命名是债务、没测试是债务、甚至需求没做完也能叫债务。这个词被用滥之后，反而失去了它原本的锋利。这周做一期清算：债务隐喻的原意是什么、哪些指标真的能当代理、DORA 四指标和债务的关系，以及怎么把偿还变成制度而不是口号。四个条目，都来自和"永远还不完的债"搏斗过的现场。

## 条目一：债务隐喻的误用

Ward Cunningham 提出技术债务时，说的是一个很具体的东西：为了赶进度，先写不够完善的代码，但心里清楚欠在哪、迟早要还，利息是后续开发在这个区域的额外耗时。注意这个定义的两个要件：第一，举债是清醒的权衡，不是无意识的偷懒；第二，债有明确的偿还计划。按这个标准回头看，大部分自称债务的代码只是烂：没有权衡记录、没有偿还意图、也没有人知道它烂在哪。把烂代码叫债务，唯一的效果是让真正的债务也显得无可厚非。

> 看不见的债务不可管理，看得见的指标才能进入对话。度量的第一步不是选工具，是让"债在哪里"有第一个可指的位置。

### 区分烂代码和真债务

- 真债务：当时有取舍，记录在案，利息可观测
  - 例：为了赶发布用了轮询，注释里写了"上限一万连接后改长连接"
- 伪债务：当时没想清楚，现在没人敢动
  - 例：一个没人说得清功能的模块，改哪里都怕，只能绕
- 意外债务：外部世界变了，当初的合理设计不再成立
  - 例：协议升级让旧的兼容层从资产变负债

这个区分不是文字游戏，它决定了处理方式：真债务排期还，伪债务先补测试和文档再动手，意外债务要做的是整体替换而不是修补。一锅端地"重构"是最常见的浪费，把三种债务混在一起还，还到一半就说不清自己改对了没有。

把债务分类之后还有一步关键动作：标利息。同一个"烂"字背后的成本可以差两个数量级：每天被读的核心模块里一个坏函数，利息是每个读它的人多花五分钟；一个半年没人碰的边角工具烂着，利息接近于零。还债顺序应该按利息排，不按恶心程度排。这个排序做不出来，通常说明缺了 churn 数据，而不是缺审美。

## 条目二：可以度量的代理指标

债务看不见摸不着，但它的利息会渗进工程指标里。挑代理指标的标准是：数据现成、趋势稳定、和代码质量有因果关系。我常用的就三个：构建时长（结构腐化的第一现场，依赖一乱编译就慢）、变更失败率（改动引发的回滚和热修比例，直接反映代码可改性）、churn 热点（改动最频繁的文件，债务高发区）。第三个用一条 git 命令就能算出来：

```bash
# 近半年改动最频繁的十个文件：churn 热点，债务高发区
git log --since="6 months ago" --name-only --pretty=format: \
  | sort | uniq -c | sort -rn | head -10
```

| 指标 | 怎么算 | 上升说明什么 |
| --- | --- | --- |
| 构建时长 | CI 全量构建耗时 | 依赖和结构在腐化 |
| 变更失败率 | 回滚加热修占发布比 | 改动风险在累积 |
| churn 热点 | 文件改动频次排序 | 热点区域该还债了 |
| 缺陷重开率 | 关闭后重新打开的缺陷 | 修复质量在下滑 |

指标要成对看：churn 高加缺陷重开率高，基本可以锁定热点区域还债；构建时长涨但发布频率稳，多半是依赖问题而不是架构问题。单指标上升就大惊小怪，多半会还错地方。所有这些数字的意义是定位对话的起点，不是给人排名的依据[^1]。

参考：[代码 churn 与热点分析](https://example.com/code-churn-hotspots)

## 条目三：DORA 视角，体温计不是成绩单

DORA 四指标（部署频率、变更前置时间、服务恢复时间、变更失败率）常被拿来考核团队，这是误用。它们和债务的关系更像体温计：债务累积时，前置时间变长、失败率抬头、恢复变慢，指标先于人的体感变化。反过来，拿指标当目标会催生刷分：部署频率不够就拆更小的提交，失败率太高就把回滚不记为失败，数字好看了，病人还在。度量的正确姿势是趋势加对照：自己的上月比这月，团队和团队比结构不比分差。

```yaml
# 把构建时长记进流水线摘要：最便宜的债务监测
name: build-metrics
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 计时构建并写入摘要
        run: |
          start=$SECONDS
          make -j"$(nproc)"
          echo "构建耗时 $((SECONDS - start)) 秒" >> "$GITHUB_STEP_SUMMARY"
```

上面这段流水线的价值不在精确，在连续：同一个口径记半年，斜率会自己说话。构建时长从四分钟爬到十二分钟的那个拐点，通常对应着一次没人评审过的大依赖引入。把这种拐点和 git log 对齐着看，比任何架构评审都更能定位债务的源头。数据不撒谎，但数据不会自己开口，开口的是看着数据的人。

指标被当目标之后必然失真，例子就在身边：部署频率被考核，于是有人把一次改动拆成五个提交，频率上去了，变更前置时间反而涨了；变更失败率被考核，于是回滚不再记失败，数字漂亮了，事故复盘里才看见真相。对策是两条：指标只看趋势不看绝对值，考核至少绑两个相互制衡的指标，让刷一项的成本高于收益。

参考：[DORA 指标正确用法](https://example.com/dora-metrics-usage)

## 条目四：把偿还变成制度

还债最大的敌人不是难度，是优先级：永远有比还债更紧急的事。有效的方法都带一点制度性：固定比例的时间配额（每周期两成给偿还，写进排期，不靠自觉）、童子军规则（改动过的代码要比来时干净，小额高频胜过一次性重构）、绞杀者模式（新旧并行，逐步切换，避免大爆炸式重写）。三种方法可以叠加，核心思想是把还债从"项目"变成"流程"，因为项目会结束，流程不会。

- 配额制
  - 每周期固定比例，雷打不动，防止被紧急需求挤光
- 童子军规则
  - 每次改动顺带清理，范围小、风险低、评审容易过
- 绞杀者模式
  - 新旧系统并行跑，流量逐步切，旧的体面退场
- 定期盘点
  - 每季度对一次账：举债记录、偿还进度、新增利息

最后一条少有人做但最关键：举债要记账。哪个模块、为什么举债、计划怎么还、利息大概多少，四行字写进 issue。有了账本，还债才是管理；没有账本，还债是情怀。情怀撑不过一个 Q4。

最后说什么不该还：下个版本就要删的代码、churn 接近于零但读起来恶心的稳定代码、以及只有你一个人觉得丑的风格偏好。第一种还了是白干，第二种利息为零，第三种是拿团队时间为自己的审美买单。偿还的判据是 ROI：还完之后，后续改动在这个区域能省多少时间，省不出来的部分，再丑也可以先留着。

参考：[技术债务偿还制度设计](https://example.com/debt-repayment-process)
