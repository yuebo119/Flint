Agent 是过去两年被谈得最多、也被误解最深的词。本质上，它就是给大模型接上工具、目标和循环：模型不再是一次性作答，而是"观察—思考—行动—再观察"，直到任务完成或撞上停止条件。这个循环本身不神秘，[arXiv:2210.03629](https://arxiv.org/abs/2210.03629) 提出的 ReAct 模式已经勾勒出骨架。这篇文章梳理四个经过验证的设计模式，同时说清楚我对当前 Agent 热的保留意见。

## 模式一：工具调用

工具是 Agent 的手脚，让模型从"会说"变成"能做"。模式的核心是把每个工具的描述写给模型看：什么时候用、参数什么含义、返回什么结构。模型输出的不是答案，而是一次结构化的调用请求，由你的代码执行，结果回填进上下文，循环继续。

```json
{
  "name": "query_order",
  "description": "按订单号查询物流状态。当用户询问某个订单的状态时使用，参数必须是十位订单号。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "pattern": "^[0-9]{10}$" }
    },
    "required": ["order_id"]
  }
}
```

### 粒度即边界

工具设计有个常被忽视的原则：**工具的粒度就是模型的认知边界**。工具太粗，一个接口二十个参数，模型选不对填不对；太细，模型要在十几个工具里挑花眼。按"人类专家会怎么分解这个任务"来划分工具，通常错不了。另外，每个工具都要有一句话的错误语义——失败时返回什么，模型能不能读懂这个失败并换条路走。

## 模式二：规划

复杂任务不能指望模型一步到位，规划模式把任务拆成步骤序列。两种主流路线：

- **边想边做（ReAct 式）**：每一步先思考再行动，根据观察结果动态调整下一步，灵活但可能绕远路；
- **先计划后执行（Plan-and-Execute）**：先产出完整计划，再逐条执行，过程可控、可审计，但计划本身错了会一条道走到黑。

实践中两者是混合的：先出粗计划，执行中允许局部改写，超出计划范围的改动要显式记录。规划能力还有一个隐形前提——**模型对自己的能力边界有没有数**。会规划的 Agent 和会瞎撞的 Agent，差别往往就在于第一步之前有没有一次"这个任务需要哪些信息，我现在有没有"的自检。

## 模式三：记忆

没有记忆的 Agent 每次都是初次见面。### 三层记忆，各管一段

记忆分三层，各管一段：

1. **短期记忆**：当前会话的上下文，最直接，但受窗口长度限制，长对话后期早期的指令会被"挤忘"；
   - 常见对策是滚动摘要：把前面的对话压缩成一段事实摘要，替代原始记录；
2. **长期记忆**：跨会话的用户偏好、历史结论，存外部存储，按相关性检索注入；
   - 写入要有标准：什么值得记（稳定偏好、明确结论）、什么不值得记（一次性的情绪吐槽）；
3. **情节记忆**：过去完成任务的完整轨迹，遇到相似任务时检索"当时是怎么做的"，相当于 Agent 的经验库。

记忆是双刃剑。存错了比不存更糟：一条过时的偏好能让 Agent 在几个月里持续犯同一个错。所以长期记忆必须带时间戳和失效机制，检索时优先用新的，冲突时要能说清"哪条为准、为什么"。

## 模式四：反思与多体协作

反思模式让 Agent 对自己的产出做一次批判性检查："这个方案有什么漏洞？"然后修订。对高风险任务（写合同、出诊断建议）值得付这份双倍成本，对低风险任务纯属浪费。

多体协作则是把一个大 Agent 拆成多个专职 Agent：一个管检索、一个管计算、一个管汇总，靠消息传递协作。它的吸引力在于职责清晰、可分别测试，但代价是系统复杂度陡增——Agent 之间的通信协议、错误传播、循环调用，都是新的故障面。

## 我的保留意见

说了这么多模式，说观点。我对当下几种流行叙事明确不买账：

1. **"全自动 Agent 即将取代一切流程"**：在容错率高的任务里（头脑风暴、资料整理）它已经可用；在容错率低的流程里（支付、删数据、对外承诺），一个会犯错的自主循环就是事故流水线。**自主程度应该按任务的容错率分级，不是越自主越先进。**
2. **"框架选型决定成败"**：Agent 系统九成的工程量在工具封装、上下文管理和错误处理上，框架只是胶水。把精力花在选框架而不是把工具描述写清楚，是本末倒置。
3. **"上下文越长越好"：** 把整个知识库、全部对话历史无脑塞进上下文，既贵又笨——无关信息稀释注意力，模型在噪声里找信号。检索、摘要、分层记忆，这些"老办法"依然是主旋律。

一个务实的落地路径是这样的：从单 Agent 加少量工具起步，把每个工具的错误路径走通；观察真实失败案例，再决定要不要加规划、记忆、多体。绝大多数业务场景，走到第二步就够用了。

## 从演示到生产：三道坎

Demo 里的 Agent 和生产里的 Agent 之间隔着三道坎，每道都足以让演示翻车。第一道是**工具可靠性**：演示环境里工具永远返回 200，生产环境里接口会超时、会限流、会返回半个 JSON。Agent 对工具失败的消化能力，决定了它在生产里是助手还是累赘——好的实现会把工具错误当成观察喂回给模型，让它换个参数重试或换条路走，而不是把异常直接抛给用户。第二道是**上下文膨胀**：多轮循环下来，思考记录、工具返回、错误堆栈把窗口塞满，模型开始"忘记"最初的目标，表现为越跑越偏、重复调用同一个工具。工程上要设上下文预算，每轮结束后主动裁剪过期观察，只保留决策必需的摘要，而不是任其无限堆积。第三道是**评估困难**：传统软件测试断言输入输出，Agent 的中间路径千变万化，只能评估最终结果加过程合规。现实做法是建一个任务集，跑一百次看成功率分布，把失败案例归类成工具错误、规划错误、上下文溢出三类，按占比排序逐个修。三道坎的典型症状和对策汇总如下：

| 坎 | 典型症状 | 对策 |
|----|----------|------|
| 工具可靠性 | 生产接口超时、限流、返回半个 JSON，Agent 直接抛异常 | 工具错误作为观察回填给模型，配重试与降级路径 |
| 上下文膨胀 | 越跑越偏，重复调用同一个工具，忘记初始目标 | 设上下文预算，每轮主动裁剪过期观察 |
| 评估困难 | 只会说"结果不对"，定位不到具体环节 | 任务集跑成功率分布，失败案例分类归因 |

还有一道隐性门槛是成本。一次 Agent 任务动辄几十轮模型调用，单次成本是一次问答的几十倍，遇到循环失控还会烧穿预算。上线前把单任务成本的分布测出来，按业务价值决定哪些任务值得 Agent 化，哪些用普通工作流更划算——这个决策不该由"Agent 很热"来驱动，该由账单和成功率来驱动。

## 护栏清单

不管架构多优雅，上线前这些护栏一条都不能少：

- [ ] **权限最小化**：Agent 能调的每个接口都按角色授权，危险操作（删除、支付、外发）必须人工确认，不能只靠提示词约束
- [ ] **步数与预算上限**：最大循环次数、最大 token 消耗硬编码，防止 Agent 在死循环里烧穿账单
- [ ] **全链路可观测**：每一步的思考、调用、结果落日志，出问题能逐帧回放，而不是对着一句"系统错误"发呆
- [ ] **人在回路的升级通道**：置信度低或连续失败时，优雅地把对话转交人工，而不是继续瞎试

> 判断一个 Agent 系统成熟与否，别看演示视频里它多聪明，看事故复盘里它错得有多难看、恢复得有多快。
