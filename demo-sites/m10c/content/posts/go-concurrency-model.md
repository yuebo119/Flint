Go 的并发 API 少得惊人：一个 `go` 关键字、一个 channel 类型、一个 `select` 语句，加上 `sync` 包里的一把锁。新手照着教程半小时就能写出并发版 Hello World，然后自信满满地提交进生产代码，接着在半夜被叫起来查数据竞争。这篇文章想把那层"简单"的外壳拆开：goroutine 到底是什么，调度器怎么摆布它，channel 又在工程里解决什么问题。读完再回头审自己的代码，很多"应该没问题"的地方会开始冒冷汗。

## goroutine 不是线程

第一次写 `go f()` 的人，多半以为背后创建了一个线程。事实要便宜得多。goroutine 是 runtime 在用户态管理的执行体，初始栈只有 2KB 上下，按需增长和收缩；操作系统线程默认栈 8MB，创建一次要走系统调用，成本在微秒量级。一台普通服务器跑十万个 goroutine 很轻松，跑十万个线程会先把内存和调度器一起拖死。

| 维度 | goroutine | 操作系统线程 |
|------|-----------|--------------|
| 初始栈 | 约 2KB，可伸缩 | 通常 8MB，固定 |
| 创建成本 | 用户态分配，百纳秒级 | 系统调用，微秒级 |
| 调度方 | Go runtime | 操作系统内核 |
| 上下文切换 | 保存少量寄存器 | 陷入内核，刷新缓存 |
| 十万级并发的可行性 | 常规操作 | 基本不可行 |

需要强调的是，goroutine 最终仍然要落在线程上执行，区别在于这层映射由 runtime 在用户态完成，不涉及内核态切换。这才是 Go 敢把并发当成默认写法的底气：并发没有变简单，只是成本从"每次创建"挪到了"runtime 常驻"。

这个区别落在工程习惯上，是一个很具体的判断：一个任务该不该起 goroutine？答案是看它阻塞时会不会拖累别人。网络请求、等锁、等定时器，阻塞期间 goroutine 把自己挂起，底层线程腾出来跑别的任务，这种阻塞起一个 goroutine 毫无压力。纯计算的长任务起一万个也白搭，它们抢的是同一批线程，最后还是排队。带 CPU 密集任务的工作池要另配 `GOMAXPROCS` 的思路控制并发度，无脑起 goroutine 只会把调度器累死。

## GMP：三个角色一台戏

Go 调度器的核心是三个结构，名字毫无想象力，分别叫 G、M、P：

- **G（goroutine）**：待执行的任务，自带栈和状态机。
- **M（machine）**：操作系统线程，真正干活的工人。
- **P（processor）**：逻辑处理器，持有本地运行队列，负责连接 G 和 M。

调度循环大致是这样：每个 M 先绑上一个 P，从 P 的本地队列取出一个 G 执行；本地队列空了，就去全局队列拿，再去别的 P 的队列里偷一半过来，这就是 work stealing；一个 G 执行超过 10 毫秒，或者遇到 channel 阻塞、发起系统调用，调度器就把它换下来，让排队的 G 上。基于协作信号的抢占在 Go 1.14 之后才真正可靠，在那之前，一个不主动让出的长循环能把 P 卡到天荒地老。

这套设计要解决的是一个很具体的问题：如果只有一把全局队列，所有 M 抢同一把锁，核数一多锁就成了瓶颈；如果每个 P 只守着自己的队列不管别人，又会出现有 M 闲死、有 G 排队饿死。work stealing 是这两者之间的折中，平时各扫门前雪，忙闲不均时互相救济。

### 网络 IO 为什么不占线程

高并发下最能体现这套设计价值的是网络请求。按传统线程模型的想象，一万个并发连接就该配一万个线程，每个线程 sleep 在 read 上等数据。Go 不是这么干的：goroutine 发起网络读写后，runtime 通过 netpoller（底层是 epoll、kqueue 这类机制）统一登记所有等待中的 IO，然后把这个 goroutine 挂起，线程腾出来去跑队列里的其他任务。哪个连接的数据就绪了，netpoller 再把对应 goroutine 唤醒放回运行队列。等 IO 的一个 goroutine 几乎不占用线程时间片，这才是"单机十万连接"在 Go 里不稀奇的真正原因。

想亲眼看到调度器干活，可以打开 schedtrace，每隔一段时间打印一次队列深度和偷取次数：

```bash
GODEBUG=schedtrace=1000 go run main.go
```

输出里 `runqueue=0`、`gc N` 这样的字段，是调度器和垃圾回收器在同一页日志里呼吸的证据。排查"CPU 打满但吞吐不涨"的时候，这行输出比直觉靠谱。

## channel 与 CSP 的工程含义

channel 不是"线程安全队列"的语法糖，它更接近一种所有权转移的约定。Go 官方那句话很多人会背：不要通过共享内存来通信，而要通过通信来共享内存。翻译成工程语言很具体：谁持有数据、谁负责关闭、谁有权改写，都由 channel 的类型和收发方向规定，而不是靠注释和自觉。

- 无缓冲 channel：收发双方必须同时就位，常用于同步。
- 带缓冲 channel：解耦生产与消费的节奏，但缓冲不是万能药。
- `close` 是发送方的责任；接收方 `range` 到关闭自动退出。

`select` 是 channel 的另一个半边：同时等多个 channel，谁先就绪走谁，全都没就绪就走 `default` 或者继续阻塞。非阻塞发送、超时控制、优雅退出这三个高频场景，全靠 select 支撑。

《Effective Go》里专门有一节讲 channel 的惯用法，值得整段读完，地址在 <https://go.dev/doc/effective_go>。我的经验是：一个 channel 如果在代码评审里说不清"谁发、谁收、谁关"，它八成会成为日后的 bug 温床。

```go
func fetch(ctx context.Context, url string) (string, error) {
	result := make(chan string, 1)
	go func() {
		result <- httpGet(url)
	}()
	select {
	case body := <-result:
		return body, nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}
```

注意 `result` 的缓冲是 1：即使调用方超时走掉，发送方也能把结果丢进缓冲区然后退出，不会永久悬挂。少写这一个 1，就多一条泄漏的 goroutine。

## 那些坑过我的陷阱

### 会泄漏的 goroutine

goroutine 泄漏是 Go 项目里最常见的事故，没有之一。往一个没有接收方、也没有缓冲的 channel 发数据，发送方会永久阻塞；这个 goroutine 连栈带上下文悬在原地，直到进程退出才被回收。防御办法很朴素：每个后台 goroutine 都必须有一条明确的退出路径，context 取消、done channel，或者可预期的 close。说不清退出路径的 goroutine，就是在给凌晨三点的告警攒素材。

判断有没有泄漏也不难：压测跑一夜，对比进程的 goroutine 数量曲线，只涨不落的就是在漏。`runtime.NumGoroutine()` 加上定时打点，三十行代码就能有一个粗糙但好用的探针。

### 循环变量捕获

Go 1.22 之前，`for` 循环变量是整个循环共享的一个，闭包捕获的是它的地址：

```go
for _, u := range urls {
	go func() { fetch(u) }() // 1.22 之前大概率全部请求同一个 URL
}
```

Go 1.22 起改成每轮迭代一个变量，这个坑自动消失，当年满屏的 `u := u` workaround 也顺势退休。但维护老项目时仍会撞见它，版本行为差异记在这里，方便对照[^1]。

### close 用反了会直接 panic

channel 的关闭规则比想象中硬：向已关闭的 channel 发送数据会 panic，重复 close 同样 panic。所以 close 只出现在发送方，且只出现一次；接收方如果也要表达"我结束了"，另开一个 done channel，别借用数据 channel。把这几条写成团队约定，能省掉一整类线上事故。

[^1]: Go 1.22 的循环变量语义变更写在发行说明里，升级依赖时值得翻一遍，尤其是那些捕获循环变量的后台 goroutine。

> 经验法则：goroutine 的启动一行字说得清，退出路径也必须一行字说得清。两条都说不清的，评审时就应该打回。

还有一个调试技巧值得放进肌肉记忆：程序卡死时按 <kbd>Ctrl</kbd>+<kbd>\</kbd> 会向进程发送 SIGQUIT，Go runtime 会 dump 所有 goroutine 的调用栈再退出。这份栈 dump 是定位"谁把谁阻塞了"的第一现场，比加日志更快，也比 core dump 更易读。

## 小结

Go 的并发模型可以压缩成三句话：goroutine 让"启动一个执行体"便宜到不值得犹豫；GMP 调度器加 netpoller 让这些执行体在多核上被公平摆布，IO 等待还不占线程；channel 给它们定下收发与关闭的规矩。简单的是 API，不简单的是规矩。把规矩当回事，Go 的并发才好用；把 API 的简单当成本身的熟练，事故只是时间问题。
