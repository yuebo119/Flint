上周五下午五点二十，订单库的告警响了：磁盘只读，业务开始报错。值班同学定位到原因后在公司群里发了四个字：表被删了。这篇文章记录这次故障从定位到恢复的完整时间线，以及事后我们怎么把这次事故变成一场全员演练。

## 故障现场

还原一下经过。一位工程师在排查一个线上数据问题时，连错了环境，把本该在测试库执行的清理脚本跑到了生产库。脚本内容是一段没有 WHERE 条件的 DROP TABLE，目标是订单归档表。发现时是五点二十，脚本执行完成于五点十一分，中间隔了九分钟。

万幸有三点：第一，脚本执行前有人值班在线，五点十三分监控就发现了连接数异常；第二，当晚两点的全量备份完好；第三，binlog 完整，且二进制日志的保留策略是七天。这三点决定了 RPO 和 RTO 的上限。

## 恢复三板斧：全量、增量、日志

MySQL 的恢复体系由三层组成，理解它们的分工才能算出丢多少数据：

- 全量备份：某一时刻的完整快照，通常 mysqldump 或 XtraBackup 产出
  - 恢复的基线，决定你能回到多早
  - 频率决定兜底能力，日备是常见底线
- 增量备份：基于某个全量点的差异，节省空间和窗口
  - XtraBackup 的增量模式，或文件系统的快照差量
  - 恢复时要按链条依次应用
- binlog 日志：全量点之后的每一笔变更
  - 精确恢复到任意秒级位置，是 RPO 的决定因素
  - 按时间点或按位置解析回放

三者的关系可以这样理解：全量备份决定能回到哪一天，增量备份缩短恢复窗口，binlog 决定最后几笔的精度。缺了任何一层，恢复都是粗粒度的。

## 恢复步骤实录

按事前准备好的 runbook，操作分六步：

```bash
# 1. 应用置为维护页，切断写入，防止恢复期间数据继续变化
kubectl scale deploy order-api --replicas=0

# 2. 恢复当晚两点的全量备份到临时实例
xtrabackup --prepare --target-dir=/backup/full/20260115
xtrabackup --copy-back --target-dir=/backup/full/20260115

# 3. 从 binlog 中定位误操作的位置，确认起点在五点十一分
mysqlbinlog --start-datetime="2026-01-15 00:00:00" \
  --stop-datetime="2026-01-15 17:11:00" binlog.000123 > replay.sql

# 4. 回放日志到误操作前一秒，跳过 DROP 语句
mysql order_db < replay.sql

# 5. 行数与校验和比对，与五点钟的统计快照核对
mysql -e "SELECT COUNT(*), CHECKSUM TABLE orders"

# 6. 校验通过，重新打开写入，业务恢复
kubectl scale deploy order-api --replicas=3
```

从置维护页到业务恢复，全程二十六分钟。五点二十发现，五点五十六分完成恢复，RTO 控制在半小时内。数据丢失为零，因为恢复点取在误操作前一秒，binlog 里之后的部分被主动跳过。

恢复期间有三件事要同步做，不然恢复了也要二次返工。盯临时实例的磁盘写入速度，全量拷贝阶段的 IO 打满会拖长整体窗口；盯回放进度，binlog 回放是单线程，几百万条语句要几分钟，期间任何报错都要立刻停，定位是数据问题还是环境问题；盯业务侧的维护页倒计时，超时要主动通知运营，别让用户对着白页面猜。恢复不是纯技术操作，是技术加沟通的联合动作。

## 🛠️ 恢复检查清单

事后复盘，我们把 checklist 贴在值班室墙上：

- [x] 备份产出后每日校验可恢复性，未验证的备份等于没有备份
- [x] binlog 保留期从三天延长到七天，覆盖周末与节假日
- [x] 生产库的清理脚本统一走工单，双人复核 WHERE 条件
- [x] 每个核心表配置 DDL 变更审计，DROP 与 ALTER 实时告警
- [ ] 每季度做一次无预告恢复演练，随机抽一张表限时恢复

## 备份排期：三层备份的时间表

恢复能力是设计出来的，不是事故时现抓的。我们的排期表经过三次演练调整，最后定成这样：

- 全量备份：每天凌晨两点执行，保留三十天
  - 选在低峰期，用 XtraBackup 做物理热备，不阻塞业务
  - 备份文件异机存放，同机房的三份备份扛不住机房级故障
- 增量备份：每六小时一次，保留七天
  - 增量链最长不超过四段，链条太长恢复时逐段应用的耗时不可控
- binlog：实时归档到对象存储，保留三十天
  - 按天分文件，恢复时按时间窗口精确切片

### 排期表全貌

| 层 | 频率 | 保留 | 作用 |
| --- | --- | --- | --- |
| 全量备份 | 每天一次 | 三十天 | 恢复基线 |
| 增量备份 | 每六小时 | 七天 | 缩短窗口 |
| binlog 归档 | 实时 | 三十天 | 秒级精度 |

排期背后是两道数学题。RPO 等于备份间隔加日志归档延迟的上限，日备加实时 binlog 的组合，理论上能恢复到任意秒，前提是 binlog 没丢。RTO 等于备份传输时间加恢复时间加校验时间，八亿行的表全量恢复要四十分钟以上，这就是我们要把演练目标定在半小时内的原因：超时的部分必须靠预案（如从库切换）兜住。

## 三个容易忽略的细节

第一，备份集要定期真恢复一次。备份文件损坏、权限不对、路径变更，这些问题只有恢复时才会暴露。我们把"备份产出后二十四小时内自动恢复校验"写进了脚本，临时实例上恢复完跑一遍 `CHECKSUM TABLE`，通过才算备份成功。

第二，恢复目标环境要隔离。在生产的从库上做恢复演练，一个误操作连坐整库。演练统一在隔离的临时实例上做，网络策略上和生产完全隔开。

第三，权限与密钥要跟着备份走。备份文件本身要加密，解密密钥单独存放；恢复脚本依赖的账号密码在演练时能不能拿到，也要提前验证。我们吃过一次亏：备份完好，密钥在已离职同学的本地，最后找厂商兜底才解开。

## 演练怎么练

> 没有验证过的备份，只是一堆占磁盘的字节。

备份能不能用，只有练过才算数。我们的演练规则很简单：每季度随机抽一张表，不预告时间，值班同学按 runbook 恢复到两小时前的状态，限时一小时完成。第一次演练时大家才发现，runbook 里的备份路径早变了，文档和现实脱节。练过三次之后，同样的恢复从五十分钟压到二十分钟。

监控上给两个指标定了红线：RPO 超过一小时或 RTO 超过四小时，触发架构评审而不是简单加机器。备份相关的细节可以参考维基百科的 MySQL 词条（https://zh.wikipedia.org/wiki/MySQL）中的备份章节。

## 演练之后：流程改动

事故和演练的价值最终要落到流程上，否则下次照犯。这次之后我们改了五条。

其一，生产数据库的清理脚本统一收敛到工单系统，任何 DDL 和批量更新必须双人复核 WHERE 条件，复核人对着测试环境预演一遍。其二，连接串按环境物理隔离，生产的连接配置只存在于生产环境的密钥管理系统里，开发机根本拿不到，从根上消灭连错库的可能。其三，核心表的 DDL 审计接入实时告警，DROP TABLE 和 TRUNCATE 级别的事件直接打电话，不等邮件。其四，备份校验从每周一次改成每日自动，校验结果进周报。其五，每个新入职的 DBA 和值班同学，第一个月必须完整参与一次恢复演练，不看录像，亲手操作。

这些改动没有一条是"更先进的架构"，全是流程和权限的笨办法。可事故复盘的经验恰恰是：多数严重故障不是技术难题，是流程缺口。把缺口堵上，比引入任何新工具都实在。事故过去一个月，团队做了一次匿名投票，问"如果再出一次类似故障，你有信心半小时恢复吗"，八成的人投了有信心。这个数字比任何指标都让我觉得这次学费交得值。
